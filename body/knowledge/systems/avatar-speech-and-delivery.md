# Avatar speech, lip-sync and deliveries

This file describes your own machinery for the 3D avatar (the GLB model you appear as in the Avatar Studio page and in Discord voice), how your speech becomes mouth movement, how pictures, music and files you make reach Discord and the dashboard, and how your slash commands are loaded and deployed. Everything here was read from the code in `C:\Bots\new champ` (Node.js, ESM). Where the code does not show something, this file says "not verified".

Key data locations: `DATA_DIR` is `process.env.CHAMP_DATA_DIR` or `<project>\data` (`src/config.js`). The test runner sets `CHAMP_DATA_DIR` to a throwaway folder, which is why tests never touch the live data. The original avatar file is `config.avatar.path`, which is `process.env.AVATAR_PATH` or `DATA_DIR\avatar.glb` (the `avatar` block in `src/config.js`).

Map of the files this guide covers, so you can name them when asked:
- `src/avatar-library.js`: the list of GLB models, which one is selected, GLB checks, downloads, player reports and the automatic rollback.
- `src/avatar-outfits.js`: the wardrobe (fitted outfits), outfit colours, your designs collection, and the wardrobe lines in your prompt.
- `src/avatar-state.js`: the colour names and `colorValue()` used by outfit colours (and by hair, eyes and make-up, which are covered elsewhere).
- `src/discord-avatar.js`: turning a Discord voice clip into a mouth-movement packet, and the start and stop events.
- `src/speech-phonemes.js`: text to phonemes to visemes.
- `src/dashboard/public/speech-articulation.js`: the shared solver that lines phonemes up with the audio and samples mouth shapes.
- `src/dashboard/public/avatar.js`: the Avatar Studio page (player, lip sync, watch-only viewer, library sync).
- `src/cloud-publisher.js`: the relay to the hosted watch-only viewer.
- `src/generation-jobs.js`, `src/generation-deliveries.js`, `src/dashboard/public/generation-delivery-ui.js`: background picture, music and look jobs, the durable delivery store, and the bubbles that show them.
- `src/tools.js`: the tools (`avatar_models`, `avatar_outfit`, `generate_image`, `generate_self_image`, `generate_music`, `look`, `send_file`, `files send`) and the dispatcher that queues generation.
- `src/commands/*.js`, `src/loadCommands.js`, `src/deploy-commands.js`, and the interaction handler in `src/bot.js`: slash commands.

## avatar model library / avatar library / avatar models / glb / avatar selection

The avatar model library lives in `src/avatar-library.js`. It keeps a list of GLB models for your avatar that you can download, test and switch between. The original avatar is never overwritten by any of this. Downloaded and registered models are kept as separate files next to it, and the library only changes which file is selected.

Storage works like this. The library directory is `DATA_DIR\avatars` and the manifest is `DATA_DIR\avatars\library.json`. A brand-new install starts with the state `{ active: 'original', models: [], revision: 0 }`. Every save writes the full JSON to `library.json.tmp` and then renames it over `library.json`, so a crash in the middle of a save should not leave a half-written manifest. Each downloaded or registered model is stored as `DATA_DIR\avatars\<uuid>.glb`, where the uuid is a random id created when the model is added.

The model list always starts with a built-in entry, `{ id: 'original', name: 'Original avatar' }`, which stands for the file at `config.avatar.path`. That entry is added each time the list is read; it is never stored in `library.json`. Every other entry in `models` has a random UUID as its id. The function `avatarLibrary()` returns the saved state, the models list with the original placed first, and the current `report`, which is the player's result for the current revision if one has arrived (otherwise `null`). The `active` field holds either the word `'original'` or the id of one model. The function `activeAvatarPath()` returns `config.avatar.path` when `active` is `'original'`, and otherwise returns the `.glb` file for that id inside `DATA_DIR\avatars`. The Avatar Studio page loads the selected model through `GET /api/avatar/model/main` in `src/dashboard/server.js`. That route reads the file with `activeAvatarPath()` for the main character and serves it with the content type `model/gltf-binary` and `Cache-Control: no-cache`. Non-main characters are served from their own stored model path instead. An unknown character id gives HTTP 404 `{ error: 'No such character' }`.

The shape of `library.json` is `{ active, models: [...], revision, lastFailure? }`. What each field means:
- `active`: `'original'` or the UUID of the selected model.
- `revision`: a counter that goes up by one on every selection, including restoring the original. Pages use it to notice a change. It is saved, so it survives restarts.
- `models`: one record per added model. A downloaded model is `{ id, name, url, bytes, meshes }`. A model registered from disk is `{ ...metadata, id, name, sha256, bytes }`, where the metadata depends on who registered it: the outfit install scripts add `outfit` (for example `dress`) and `baseSha256`; the seamstress adds `sewn` and `version` for the clothes you sew.
- `lastFailure`: only present after an automatic rollback (see the player report section).

The player reports are not saved to the file. They live in memory in a map keyed by revision, so after a restart `report` is `null` until an open page loads the model again and reports. Nothing ever deletes a model from the list or its `.glb` file; there is no remove action.

What feeds this library and what reads it: models come in from the `avatar_models` tool's `download` action, from the outfit install scripts, and from the seamstress (clothes you sew come back as whole avatar GLBs registered here). Selections come from `avatar_models load` and `restore`, from `avatar_outfit wear`, from the Studio's outfit menu (`PUT /api/avatar/outfits`), and from the seamstress `wear` and `take_off` actions. Every open Avatar Studio page, the video-reply recorder page and the watch-only viewer read the selection. Your avatar-appearance prompt (`avatarState.prompt` in `src/avatar-state.js`) also uses `activeAvatarPath()` to look up the described traits of whichever model is selected, and those descriptions only apply to the exact file they were made from.

## glb checks / avatar download rules / avatar download errors / why was the avatar rejected / validateGlb

There is a size limit of 100 MB (`MAX_BYTES = 100 * 1024 * 1024` in `avatar-library.js`). Every candidate file is checked by `validateGlb(bytes)` before it can be saved, and the checks run in this order. Each failure throws with the message shown. First, the file must be at least 20 bytes, begin with the magic `glTF`, declare version 2, and have a header length that equals the actual file length; otherwise the error is `Not a complete GLB version 2 file. Download the actual .glb, not its web page.` Second, every chunk must fit inside the file; a chunk that runs past the end gives `Truncated GLB chunk.` Third, each chunk's length must be a multiple of four and must fit, otherwise `Invalid GLB chunk length.` Fourth, the first chunk must be the JSON chunk, otherwise `GLB is missing its JSON chunk.` Fifth, the JSON must contain at least one mesh and at least one scene, otherwise `GLB contains no avatar scene or meshes.` Sixth, no buffer or image may point to an external file; anything with a `uri` that does not start with `data:` fails with `Use a self-contained GLB with embedded textures and buffers.` Only the JSON chunk is parsed; later chunks are only checked for length.

Downloading is done by `downloadAvatar(url, name)`, which the `avatar_models` tool calls with the `download` action. Only `https:` addresses are accepted; anything else fails with `Use an HTTPS direct GLB download URL.` The request is made with a 120-second timeout. A non-OK HTTP status fails with `Avatar download failed: HTTP <status>`. If the final address after redirects is not HTTPS, the download fails with `Download redirected away from HTTPS.` A `content-length` header over 100 MB, or a streamed body that grows past 100 MB, fails with `Avatar exceeds the 100 MB limit.` Only after the bytes are complete are they checked with `validateGlb`. If that check throws, nothing is written and nothing is added to the list. On success the file is saved as `<uuid>.glb`, and a record `{ id, name, url, bytes, meshes }` is added to `models`. The name is cut to 100 characters and defaults to `Downloaded avatar` if none was given. The tool then returns that record with the message `Downloaded and checked GLB structure. Use load with this ID to test it in the player.` Downloads are not de-duplicated, so the same file downloaded twice becomes two entries. `registerLocalAvatar(source, name, metadata)` is different: it reads a file that is already on disk, validates it, and returns the existing entry if a model with the same SHA-256 is already in the list. It is used by the install scripts in the `scripts` folder (`install-avatar-outfits.mjs` and `install-bikini.mjs`) to add outfit models, and by the seamstress to add sewn outfits. It is not called by the `avatar_models` tool. When the hash is new, it copies the bytes to `<uuid>.glb` and stores `{ ...metadata, id, name, sha256, bytes }`. Unlike downloads, the name is not cut to 100 characters.

Order of the download steps, in short: parse the address (a malformed address throws the standard URL error before anything else), refuse non-HTTPS, fetch with a 120000 ms timeout, refuse a non-OK status, refuse a redirect to HTTP, refuse a declared size over 100 MB, stream the body counting bytes and stop past 100 MB, validate the GLB, then write the file and the manifest. A timeout surfaces as the fetch library's abort error rather than a message of this module's own. Nothing is written to disk until every check passes, so a failed download never leaves a half file in `DATA_DIR\avatars`.

The test `avatar-library.test.js` ("rejects HTML, truncated GLBs, external dependencies and failed downloads") checks that a web page, a cut-off GLB, a GLB with an external texture and a failed HTTP request are all refused, and that the original avatar file is never overwritten.

## avatar_models tool / download an avatar / load an avatar / restore original avatar / switch avatar model

The `avatar_models` tool has five actions: `list`, `status`, `download`, `load` and `restore`. `list` and `status` do exactly the same thing: both return the full library as JSON (`active`, `models` with the original first, `revision`, `lastFailure` if any, and `report`). `download` needs `url` and optionally `name`. `load` needs `id`. `restore` takes no parameters. Any other action fails with `Use list, status, download, load or restore.` The tool's code is `avatarTool` in `src/avatar-library.js`, and its entry is `avatar_models` in `src/tools.js`.

Who can use it: only the owner (`ctx.perms.owner`), and only when `ctx.character?.main !== false`, so other cast characters never get it. Everyone else does not see the tool at all, and a call anyway comes back as `[avatar_models: error not_available] avatar_models isn't available to you this turn`. Every result of this tool, like every tool, starts with one status line: `[avatar_models: ok]` before the JSON, or `[avatar_models: error <code>] <message>` followed by a `hint:` line when something threw (for example a GLB check failing). The thrown messages are the ones listed in the GLB checks section.

The tool's description tells you how to use it: research candidates with `web_search`, download with a direct HTTPS GLB link (not a web page), load to test, read `status` for the player report, never claim visual success without one, and try another download when one is incompatible. Failed loads restore the original by themselves.

Typical sequence when Owner asks you to try a new avatar:
1. `download` with the direct `.glb` link. The result has the new `id`, the byte count and the number of meshes.
2. `load` with that id. This only selects it.
3. `status` a few seconds later (an open Studio page checks every 2.5 seconds). `report.ok: true` means it rendered; read `details` for `visemes` and `blink shapes`.
4. If `report` is still `null`, no player page is open. Say so rather than claiming it worked.
5. `restore` whenever he wants the original back.

Selecting is done by `selectAvatar(id)`, which the `load` action calls. An id that is neither `'original'` nor present in `models` throws `Unknown avatar ID. Use list first.` A valid id sets `active`, increments `revision`, clears every stored player report, saves the file, and returns the library with the message `Selected for loading. Check status for a player report; selection alone does not confirm rendering.` Selection alone does not prove that the avatar rendered. The change only counts as working once an open player reports back, as described below. Selecting `original` is also what the `restore` action does, and `restore` is the normal way to go back to your own file. Selecting the model that is already active still bumps the revision and clears the report, so every open player reloads it and reports again. That makes `load` with the same id a way to force a fresh test.

The library's dashboard routes, all in `src/dashboard/server.js`:
- `GET /api/avatar/library`: the same JSON as `avatar_models status` (`avatarLibrary()`).
- `POST /api/avatar/library/report`: a page's report `{ revision, ok, error, details }`; answers `{ ok: true }` or `{ ignored: true }` for an old revision.
- `GET /api/avatar/model/main` (or `/api/avatar/model/<character id>`): the GLB bytes. The page adds `?revision=<n>` so the browser never reuses an old copy.
There is no dashboard route that downloads a model or changes the selection directly; that goes through the tools, or through the outfit menu for outfits.

## avatar player report / avatar rollback / lastFailure / did the avatar load / avatar went back to original

The player reports back through `reportAvatar({ revision, ok, error, details })`. The Avatar Studio page (`src/dashboard/public/avatar.js`, function `syncAvatarLibrary`) reads `GET /api/avatar/library` once when the cast loads and then every 2500 ms. Only one sync runs at a time, and it does nothing until the main character is in the cast. On every tick it also works out which outfit is showing (`suit` for the original, the model's `outfit` field for an installed outfit, or `custom` for anything else) and sets the Studio's outfit menu to it, redrawing the colour inputs when the outfit changed. When the revision in that response differs from the last one it handled, the page calls `loadModel` on `/api/avatar/model/main?revision=<rev>`. If the load succeeds, it reports `{ ok: true, details: "Loaded in player. Skeleton: N bones; visemes: <bool>; blink shapes: <bool>." }`. If the load fails, it reports `{ ok: false, error }`. The report is posted to `POST /api/avatar/library/report`. The page only remembers that revision as handled when the report request succeeds, so a failed post is retried on a later tick. A report for an old revision is ignored and the server replies `{ ignored: true }`. Both `error` and `details` are cut to 500 characters. A watch-only page does not post reports; it only remembers the revision locally. The hidden recorder page (the one that makes video replies) is not watch-only, so it does post reports. If several pages are open, the first report for a revision that arrives is stored, and a later report for the same revision replaces it. A failure is logged in the page's browser console as `Avatar selection:` followed by the error when the library itself could not be read (`Could not read avatar selection`).

The report fields, as stored: `ok` (true only when the page sent exactly `true`), `error` (text, up to 500 characters, empty on success), `details` (text, up to 500 characters). The success details tell you three things about the model: how many bones its skeleton has, whether it has `viseme_*` mouth shapes (`visemes: true/false`), and whether it has ARKit blink shapes (`blink shapes: true/false`, checked by the `eyeBlinkLeft` shape).

When a failed report arrives while a model other than the original is active, the server rolls back automatically. It calls `selectAvatar('original')`, which bumps the revision, and it stores `state.lastFailure = { ok, error, details, rejected: <the failed id>, fallback: 'original' }`. The same failure record is also stored as the report for the new revision. The rollback is covered by `avatar-library.test.js`, which checks that `report.fallback === 'original'`. A failed report while the original is active does not roll anything back; it is simply stored as the report. Because outfits are library models, a failed outfit (an installed dress, or a sewn outfit) rolls back to the original suit the same way. The `lastFailure` record stays in `library.json` until the next rollback replaces it; a later successful load does not clear it, so always compare its `rejected` id with what you just loaded before blaming it.

So the three states you can read from `status`: `report: null` means no page has loaded this revision yet (or none is open, or the bot restarted); `report.ok: true` means a page really rendered it; `report.ok: false` with `fallback: 'original'` means it failed and you are back on the original.

The `avatar_models` tool's facts are in its own section, "avatar_models tool".

Some edge cases are worth knowing. If the model file for the active id is missing from disk, the model route returns HTTP 404 with the JSON body `{ error: 'No model for <name> at <path>' }`, where the path is the character's stored model path. The page then fails to load it and shows the toast `Couldn't load <name>: <error>` (from `loadModel` in `avatar.js`), and the failed report triggers the automatic rollback to the original. The library itself does not check that the selected file exists, so this depends on the route's 404 path. If a model loads but has no `viseme_*` face shapes, the page still reports success, but the report says `visemes: false`, and lip sync is built from ARKit jaw and lip controls instead (see the lip sync section). The tool's own description and the capabilities text both warn that a model can load and still be unable to lip sync because of missing face shapes. Two environment variables affect this area: `AVATAR_PATH` sets the file used as the original avatar, and `CHAMP_DATA_DIR` moves the whole data folder, including `avatars`.

## avatar outfits / outfits / wardrobe / clothes / suit / dress / swimsuit

Outfits are fitted clothing on the actual 3D avatar. You change them with the `avatar_outfit` tool or on the Studio page. They are separate from the generated selfie outfits made by the `look` tool. A look produces pictures and does not change the GLB, while an outfit replaces the model the avatar wears. The code for this is in `src/avatar-outfits.js`.

Your wardrobe comes from three places, listed in this order:
1. The built-in `suit` (`Original suit`), which is simply the original avatar file. It is always first and always there.
2. Installed outfits from `DATA_DIR\outfits\wardrobe.json`, written by the install scripts. On this computer that file lists five: `dress` (Teal textured A-line dress), `dress-pleated` (Midnight satin pleated midi dress), `dress-wrap` (Burgundy wrap-style dress), `swimsuit` (Navy one-piece swimsuit) and `bikini` (Coral bandeau bikini). Their GLBs and front and back preview pictures sit in the same folder.
3. Clothes you sewed yourself with the seamstress tool (`wardrobeEntries()` in `src/seamstress.js`). Each finished sewn outfit appears with the id `sewn:<outfit id>`, the name `<name> (sewn)`, the model id of its latest finished version, and `sewn: true`. These are not tied to the base hash check. How sewing works is in the seamstress guide file.

The files involved live under `DATA_DIR\outfits`. The wardrobe is `wardrobe.json` and has the shape `{ baseSha256, outfits: [{ id, name, modelId }] }`. Each outfit points at a model in the avatar library through `modelId`. The colour file is `colors.json` and has the shape `{ baseSha256, palettes: { <outfitId>: { fabric, sheen } } }`; it only exists once a colour has been saved (there is none on this computer yet). The designs file is `designs.json` (see "outfit designs"). The wardrobe file is written only by the install scripts (see "installing outfits"), never by `avatar-outfits.js`.

Both files are tied to the SHA-256 of the original avatar file at `config.avatar.path`. Every time the list is built or colours are read, the code hashes that file. If the original file has changed since the wardrobe was written, the wardrobe is ignored and only the original suit is listed, and saved colours are ignored too, because `outfitColors()` returns an empty object when the stored hash does not match. The test `avatar-outfits.test.js` confirms both behaviours. This is why a changed base file makes outfits seem to vanish. Rebuilding the wardrobe for a new base is not something the code does by itself; the install scripts write the wardrobe with the hash of whatever base file is there when they run. The test ("wardrobe switches fitted models, restores suit and rejects outfits for a different base") is the owner's reason: an outfit fitted to one body must never be put on a different base model. If the original avatar file is missing altogether, `outfitList()` throws the file-read error (the outfit routes and tool fail), and the wardrobe line in your prompt is left out.

The outfit list (`outfitList()`) always starts with the entry `{ id: 'suit', name: 'Original suit', modelId: 'original' }`. Wardrobe outfits are only added when the wardrobe's `baseSha256` matches the current original file. Sewn outfits are added after them. Each outfit gets a `colors` value from its saved palette, or `{ fabric: null, sheen: null }` when nothing is saved. The `active` field is the id of the outfit whose `modelId` equals the library's active model, or `null` when the active model is not in the wardrobe. The function returns `{ outfits, active, report, palettes }`, where `report` is the library's current player report.

Choosing an outfit is done with `wearOutfit(id)`. An id that is not in the list throws `Unknown outfit. List available outfits first.` Otherwise the function calls `selectAvatar(outfit.modelId)`, which is the same as the `load` action in the library, and returns `{ outfit, revision, message }`. As with any selection, the change only counts once the player reports back. The `suit` outfit maps back to the `original` model, so choosing it restores the original GLB. Wearing a sewn outfit works the same way through its `sewn:<id>`. If the active library model is not in the wardrobe at all (for example a downloaded avatar), `active` is `null` and your prompt says the selected outfit is `custom avatar`.

## outfit colours / outfit colors / fabric colour / sheen colour / recolor outfit / colors.json

Colours are set with `setOutfitColors(id, { fabric, sheen })`. If `id` is missing, the currently active outfit is used. An id that is not installed throws `Choose an installed outfit before setting its colors.` Each supplied value is passed through `colorValue()` from `src/avatar-state.js`. That function accepts the names black, white, red, blue, green, brown, blonde, blond, pink, purple, silver, grey, gray, hazel, auburn, ginger, rose, nude, coral, gold and orange, and it accepts a six-digit hex value such as `#25878c` or a three-digit one such as `#abc`. The words `none`, `default` and `reset` clear a colour back to `null`, which means the model's own colour is used. An unrecognised value throws `Use a known color name or #RRGGBB; use none to restore the model default.` and the colours file is left untouched when that happens. An empty or missing value is skipped and keeps the old colour. The new palette is saved with the current base hash, and the bus event `avatar-outfit-colors` is emitted so connected pages update. Colours change only the fabric colour and the sheen colour. The fabric's maps, weave, roughness and sheen strength stay as they are in the GLB. The player applies `fabric` to the material colour and `sheen` to the sheen colour in `applyAvatarAppearance` in `src/dashboard/public/avatar-appearance.js`. Those overrides are reversible: the page clones the material and never rewrites the GLB or its textures. Only materials the page recognises as clothing are recoloured: a mesh or material whose name contains `wardrobe_fabric`, `wardrobe_dress`, `wardrobe_swimsuit` or `avaturn_look_` (`appearancePart`). The sheen colour only applies when the material has a sheen layer. A garment whose material names do not match is left in its own colours, even though the colour is saved.

When nothing is saved, the Studio page's colour inputs show the defaults written in `src/dashboard/public/avatar.html`: fabric `#25878c` and sheen `#889999`. Those are only input defaults; they are not written to the file. Each input has an `Original` button next to it, which saves `null` for that colour. The colour inputs and both buttons are greyed out while the outfit menu shows `Custom avatar`, which is what the page shows for a downloaded avatar and for any model that has no `outfit` tag (sewn outfits included). A save failure shows a toast with the server's error, or `Could not save outfit color`.

How a colour change reaches the screen: `setOutfitColors` writes `colors.json` (through a `.tmp` file and a rename), emits `avatar-outfit-colors` on the bus, `/api/avatar/live` forwards it to every open page as an `outfit-colors` message with all palettes, and each page re-applies the colours to the main character. A page that connects later gets the current palettes as its first `outfit-colors` message. Colours are kept per outfit id, so the dress and the swimsuit each remember their own.

The owner's test for this ("outfit recoloring keeps fabric maps and finish and restores the original palette") checks that a recolour keeps the fabric's texture maps and finish, and that `none` brings the original back.

## avatar_outfit tool / wear an outfit / change clothes / outfit routes / wardrobe prompt

The `avatar_outfit` tool has five actions: `list`, `wear`, `color`, `design` and `collection`. Any other action fails with `Use list, wear, color, design or collection.` Its entry is `avatar_outfit` in `src/tools.js`.
- `list` returns the outfit list as JSON: every outfit with its saved colours, the `active` outfit id, the player `report` and all `palettes`.
- `wear` takes an `id`. If the id looks like `design-<number>`, or matches one of your design names (ignoring case), it wears that design (base outfit plus its colours). Otherwise it is an outfit id such as `suit`, `dress`, `swimsuit` or `sewn:<id>`, and it calls `wearOutfit`. The result includes the new `revision` and the reminder that selection alone does not confirm rendering.
- `color` takes an `id` (optional, defaulting to the active outfit), a `color` value for the fabric, and a `sheen_color` value for the sheen. It returns `{ id, colors }`.
- `design` and `collection` are covered in "outfit designs".

Who can use it: only the owner, and only when `ctx.character?.main !== false`. Because the tool's `list` result includes the report, check it before telling your owner that an outfit is showing. The tool's description also says you cannot create new garment meshes with it; new garments are made with the `seamstress` tool.

The dashboard routes are in `src/dashboard/server.js`. As on every dashboard route, a thrown error comes back as JSON `{ error: <message> }` with HTTP 500 (or the error's own status), and the Studio shows that message in a toast.
- `GET /api/avatar/outfits` returns the outfit list (the same JSON as `list`).
- `PUT /api/avatar/outfits` takes a body with `id` and calls `wearOutfit`. The Studio's outfit menu uses it, then syncs the library at once instead of waiting for the next 2.5-second tick.
- `GET /api/avatar/outfit-colors` returns the saved palettes (an empty object when none, or when the base hash no longer matches).
- `PUT /api/avatar/outfit-colors` takes a body with `id`, `fabric` and `sheen` and calls `setOutfitColors`. The Studio's colour pickers use it.

The Studio's outfit menu lists every outfit by name, plus a disabled `Custom avatar` entry that is selected when the active model is not an outfit.

Your own system prompt includes a `3D avatar wardrobe:` section built by `outfitPrompt()`. It lists every outfit as `<id>: <name>, saved colors {...}`, says which outfit is selected (or `custom avatar`), and reminds you that the names describe the original style while saved colours override it, that `avatar_outfit` is separate from generated selfie looks, and that a selection needs player feedback to confirm it rendered. It then lists your design collection (`nothing designed yet` when empty) and says new garments are made with the seamstress and show as `(sewn)` once finished. This section is added in `src/companion.js`, and only for the main character. If anything fails while building it, for example because the base file is missing, the function returns an empty string and the section is simply left out.

## outfit designs / my collection / designs.json / save a design / avatar_outfit design

A design is your own named colourway of an installed outfit: a base outfit, a fabric colour and/or a sheen colour, a name and your notes. It does not make a new garment. The code is `saveDesign`, `listDesigns` and `wearDesign` in `src/avatar-outfits.js`.

Data: `DATA_DIR\outfits\designs.json`, shape `{ designs: [...], next }`. `next` starts at 1 and gives each design the id `design-<n>`. Each design is `{ id, name, base, colors: { fabric, sheen }, notes, at }`, where `at` is the time saved in milliseconds. A missing or unreadable file is treated as empty. The code comment says this file survives a memory wipe, because it is your own work. Writes go through a `.tmp` file and a rename, and each save emits `avatar-outfit-designs` on the bus. There is no delete or rename action.

Saving (`avatar_outfit` with `action: design`): `name` is required, `id` is the base outfit (default: the one you are wearing), `color` is the fabric and `sheen_color` the sheen, `notes` is optional. Rules and their errors:
- The base must be in the outfit list, or it fails with `Unknown base outfit "<base>". Installed: <ids>.`
- The name is trimmed and cut to 60 characters; under 2 characters fails with `Give the design a name.`
- Colours go through `colorValue()` (names, `#RRGGBB`, `#RGB`). At least one of fabric or sheen must be set, or it fails with `A design needs at least a fabric or a sheen colour of its own; otherwise it is just the base outfit.`
- Notes are cut to 300 characters.
On success it replies `Saved design design-<n> "<name>": <base> in fabric <colour or original>, sheen <colour or original>. It is in your collection; wear it with id design-<n>. Saving does not put it on.`

`collection` returns your designs as JSON, or `Your collection is empty: nothing designed yet. Use design with a name, a base outfit and colours.`

Wearing a design (`wear` with `design-<n>` or its name): it finds the design by id or name (ignoring case), wears the base outfit, then saves the design's colours as that base outfit's colours (a colour the design left empty is reset to the model's own). The reply adds `Colours applied for "<name>".` An unknown design fails with `No design "<id>" in your collection. Your designs: <list or none yet>.` Because wearing a design overwrites the base outfit's saved colours, wearing the plain outfit afterwards keeps the design's colours until you change them.

## installing outfits / install-avatar-outfits / install-bikini / wardrobe.json / add a new outfit

Installed outfits are added by hand with two scripts in the `scripts` folder. No tool runs them; the owner runs them with node. Both import the live data folder, so they change the real library.

`scripts/install-avatar-outfits.mjs`:
1. Hashes the original avatar file (`baseSha256`).
2. Reads `DATA_DIR\avatar-state.json` and takes the description saved for that base hash (`_models[baseSha256]`), if any.
3. Registers four GLBs from `DATA_DIR\outfits`: `dress` (Teal textured A-line dress), `dress-pleated` (Midnight satin pleated midi dress), `dress-wrap` (Burgundy wrap-style dress) and `swimsuit` (Navy one-piece swimsuit), each with `{ outfit: id, baseSha256 }` as metadata. A GLB already in the library (same SHA-256) is reused, not copied again.
4. Copies the base model's appearance description onto each outfit file (`avatarState.describeModel`), so your prompt can still describe you when one is selected.
5. Rewrites `wardrobe.json` with exactly those four outfits and the base hash.
6. If you were wearing one of those outfits, selects the matching (possibly new) model so you stay dressed the same.
7. Prints `Installed outfits: <names>`.
Note that step 5 replaces the whole wardrobe list, so running it after the bikini script drops the bikini from `wardrobe.json` until the bikini script runs again.

`scripts/install-bikini.mjs` registers `DATA_DIR\outfits\bikini.glb` as `bikini` (Coral bandeau bikini), records an empty description for it, adds or replaces the `bikini` entry in the existing `wardrobe.json` (it needs the file to exist already), writes the current base hash, and then selects the bikini straight away. It prints JSON with the installed model id, the active outfit, the wardrobe list, the report and the active model.

Both scripts stamp the wardrobe with the current base hash, so running them again after the original avatar changed is how the wardrobe is matched to a new base, provided the outfit GLBs still fit that base. The owner's tests check that the generated outfits keep the original face shapes and skeleton ("generated real outfits retain the original facial morphs and skeleton") and that the dress styles have different silhouettes while keeping their fabric maps and sheen.

## discord avatar / avatar in discord / discord lip sync / discord speech packets

The Discord avatar is how your voice replies in a Discord voice channel are shown on the avatar page. Your voice is played in Discord by the bot itself, and the local Avatar Studio page does not play that audio. Instead, the bot sends timing packets that describe each sentence, and the page moves the mouth from them while the sentence is heard in Discord. The only page that plays the clip is the hosted watch-only viewer, which gets the audio through the cloud relay described below. The code for the packets lives in `src/discord-avatar.js`, and the speech pump that calls it lives in `src/voice/session.js`.

Each spoken sentence goes through the same steps, in the speech pump of the voice session. A sentence that belongs to an older turn (you were interrupted) is dropped before anything is done with it. First, the speech service's clip for the sentence is fetched. It has to be Ogg Opus at 48 kHz (or it fails with `Fish Audio returned audio in an unexpected format`). The check `isOggOpus48k` in `session.js` looks for the `OggS` header and the `OpusHead` block, and accepts one or two channels at the 48 kHz rate, which covers the mono clips Fish sends. Second, `prepareDiscordSpeech(clip, text, conversation, character)` decodes the clip and builds the `start` packet. `character` is the cast member speaking the sentence (`main` for you, or a guest's own id), so the Studio moves that character's mouth and, in the face view, turns the camera to them. If this fails, the bot logs the error as activity `discord avatar envelope`, sets the packet to `null`, and still plays the audio. The only effect of the failure is that there is no mouth movement on the Studio page for that sentence. Between the second and third steps the session waits for the microphone lease (another bot in the same call may be talking), for the clip's estimated length plus 15 seconds; if the lease is not granted, or the turn changed meanwhile, the sentence is skipped. Then the session subscribes the call to its own player, which pauses any music while you talk. Third, the packet is held until the sentence actually starts playing in Discord. A listener on the voice player's `Playing` event calls `startDiscordSpeech(packet, clip)`, but only if the sentence still belongs to the current turn. If the turn has changed, for example because someone interrupted you, the packet is never sent. Fourth, `startDiscordSpeech` records the packet as active for its conversation, stamps it with `at`, emits `discord-avatar` on the event bus, and, when audio is passed, emits `discord-reply-audio` with the clip. The cloud relay (`src/cloud-publisher.js`) sends that clip on to the live viewer as base64 with mime `audio/ogg`. Fifth, when playback ends, or when it is interrupted, `stopDiscordSpeech(conversation, id)` emits a `stop` packet. The stop has `reason: 'ended'` when an id is given and `'interrupted'` when none is given. Nothing is emitted if there is no active packet for that conversation or if the id does not match the active one. When the whole speech queue ends (the reply is finished, or the pump stops), the session calls `stopDiscordSpeech(conversation)` with no id, which closes anything still active with `reason: 'interrupted'`. The same happens when the session is torn down.

## discord speech packet / start packet / stop packet / speech packet fields / prepareDiscordSpeech

`prepareDiscordSpeech` checks that the clip is a buffer starting with the bytes `OggS`, or it throws `Expected an Ogg Opus speech clip.` It then decodes the clip with `prism-media`, using the Ogg demuxer and an Opus decoder at 48000 Hz, two channels and a frame size of 960, into 16-bit PCM. Decoded audio longer than 180 seconds (`48000*2*2*180` bytes) is rejected with `Speech envelope exceeds three minutes`. A clip with no decodable audio fails with `Speech clip contained no decodable audio.` The stereo PCM is averaged to mono Float32 samples at 48000 Hz, using `(left + right) / 65536`. In parallel with the decode, the phonemes for the sentence are requested from `speechPhones(text)`. A phoneme failure is caught and becomes an empty list, so it never makes the whole sentence fail. The samples and phonemes go to `compileArticulation` (see the speech articulation section), which gives per-frame values and timed mouth cues. Each frame is written as `open`, `wide`, `round` and `bright`, rounded to three decimals. The finished packet is `{ type: 'start', id: <uuid>, character, conversation, text, frames, frameMs, durationMs, articulation: { version: 2, cues, timing } }`. `character` is the speaking cast member (default `main`). The `frameMs` value is 20, and `timing` is the fixed string `'audio-guided estimate'`.

What each start field means:
- `id`: a random UUID for this one sentence. The matching stop carries the same id.
- `conversation`: the voice conversation the sentence belongs to (one active packet is kept per conversation).
- `text`: the sentence, used for captions and for the letter-based fallback.
- `frames`: one entry per 20 ms of audio, each `{ open, wide, round, bright }` between 0 and 1, rounded to three decimals.
- `durationMs`: the decoded audio length in milliseconds.
- `articulation.cues`: the timed mouth shapes, `[{ start, end, viseme }]` in milliseconds from the start of the clip.
- `at`: added by `startDiscordSpeech` when the sentence really starts playing; the page measures the mouth's time from it.
The stop packet is `{ type: 'stop', id, conversation, character, at, reason }`, with `reason` `ended` or `interrupted`.

The function `pcmEnvelope` in the same file is an older, simpler envelope with 40 ms frames and only `open`, `wide` and `round`, computed from loudness and zero crossings. Nothing in the bot calls it; only tests do.

Peer bots (another companion bot on the same computer) can post their own speech packets to `POST /api/avatar/peer`; those go out on the same live stream with `peer: true` and never carry audio. That is covered in the peer avatars guide.

## avatar live stream / api/avatar/live / server-sent events / studio live connection

The packets for the current conversation are kept in memory. `activeDiscordSpeech()` returns all of them. The live route `GET /api/avatar/live` in `src/dashboard/server.js` is a server-sent events stream for the Studio page. Each message is one `data:` line of JSON with a `type`. When a page connects, the server first sends the current state: `power` (whether you are online), `sleep`, `background`, `view`, `bubble-style`, `outfit-colors` (all saved palettes), `performance`, `expression`, one `appearance` per cast member, the active speech packets as `discord-speech` (yours, then any peer bot mid-sentence) so a page opened mid-sentence catches up, peer expressions, `dance`, and `mood`. After that it streams changes as they happen: `discord-speech` (from the bus event `discord-avatar`), `appearance`, `expression`, `background`, `view`, `beat`, `outfit-colors`, `performance`, `cue`, `tool`, `play`, `dance`, `fidgets`, `bubble-style`, `power` and `sleep`. Every 15 seconds it resends `expression` and `mood`, and every 20 seconds it writes a `: ping` comment line to keep the connection open. Connecting counts as an avatar viewer joining, and closing counts as leaving. All bus listeners are removed when the page disconnects. The page keeps the newest packet for each character in `pendingAvatarSpeech`. On a `start`, it sets the character's `lips.discord` to that packet, which makes the mouth follow the packet's timeline. On a `stop` whose id matches the current packet, it clears `lips.discord` and removes the caption if nothing else is playing. A stop with a different id is ignored. On every page, including the watch-only one, a `start` turns the close-up camera to the speaker when the view frame is `face` or `eyes`. A packet for a character the page does not have is ignored.

## watch-only viewer / cloud viewer / cloud relay / hosted viewer / enable audio

The watch-only page (`WATCH` in `avatar.js`, which is set when the page is loaded as the watch-only viewer) handles speech differently. It does not drive the mouth from the bot's own packets. It only plays `start` packets that carry an `audio` field, and in practice those come through the cloud relay, which attaches the clip. It decodes that audio in its own audio context, builds the mouth timeline from the packet's articulation (or compiles one from its phonemes), and queues the sentence. The button says `Loading avatar…` and is disabled until the cast has loaded, then becomes `Start watching · Enable audio`. Before a click on it, the page keeps only the newest packet that arrived (each new one replaces the last) and plays that one after the click, because browsers will not start audio without a user gesture. After the click, packets are decoded one after another in order. It drops any packet whose `at` is more than 30000 ms old when its turn to decode comes. A clip that cannot be decoded shows the toast `Could not play reply: <error>`. A `stop` with `reason: 'interrupted'` stops the speech on that page; an `ended` stop is ignored there, because the page plays the clip to its own end. Peer bot lines never carry audio, so on the watch page they only move the peer's mouth.

The cloud relay (`src/cloud-publisher.js`, started by `startCloudPublisher()` in `src/index.js`) only runs when `DATA_DIR\cloud-viewer.json` exists and holds both a `url` and a `publisherKey`. The url must be HTTPS, or startup throws `Cloud viewer requires HTTPS.` Every request carries the key as a bearer token and has a 30-second timeout; a non-OK answer is the error `Viewer relay HTTP <status>`. The relay keeps the hosted copy in sync: every 5 seconds, and before every event, it uploads any watch asset it has not sent yet (`PUT /publisher/assets/<hash>`) and then the snapshot (`POST /publisher/snapshot`). If a sync fails, it forgets which assets were uploaded so the next sync sends them all again.

It forwards these events to `POST /publisher/event`, one at a time in order:
- Voice speech: on `discord-reply-audio`, a `discord-speech` event with the start packet, the clip in base64 and mime `audio/ogg`.
- Stop packets, and peer bot packets, as they are (from `discord-avatar`). Your own start packets are not sent from here, because they go with their audio above.
- Text replies with a video clip: `src/avatarVideo.js` (`requestClip`) emits `discord-text-reply` when a Discord server reply asks for a relay and the relay is listening, even if video replies are off. Each line goes out as a `discord-speech` start with a new id, `character: 'main'`, mime `audio/mpeg` and phonemes the relay looks up itself (an empty list if that fails).
- Expressions: `avatar-expression` goes out as an `expression` event with the character and feelings.
Relay failures are logged at most once a minute as an `error` activity with `where: 'cloud viewer'`; failures in between are dropped silently.

The route `POST /api/avatar/phones` in `src/dashboard/server.js` takes a `text` field and returns `{ phones }`, using the same `speechPhones` function as the Discord path. The Studio page uses it for the recorder, which makes video replies. The streamed reply route `POST /api/avatar/chat` (the Studio's own chat) also computes phonemes for each sentence and sends them with the sentence text and audio.

## discord avatar failures / discord avatar envelope / muted sentence / voice playback skipped

If the Discord packet cannot be built, for example because the clip is not Ogg Opus or has no decodable audio, no packet is sent at all. The Studio then has nothing to move the mouth with for that sentence, and the Discord audio still plays normally. If a sentence's clip could not be fetched, failed the Ogg Opus format check, or could not be queued for the microphone, the voice session logs the error as `text-to-speech` and posts the sentence in the text channel prefixed with a muted-speaker icon (`🔇 <sentence>`), so nothing she said is lost from the record. It also sends a stop for that sentence's packet, so a half-started mouth does not keep moving. A sentence whose clip does not finish playing within the time limit described in the lip sync section is skipped with the activity `voice playback`, and its player is stopped.

Activity events this area writes, all as `activity('error', { where, message })`:
- `discord avatar envelope`: the mouth packet could not be built for a sentence (audio still plays).
- `text-to-speech`: the clip could not be fetched, was the wrong format, or could not be queued; the sentence is posted as `🔇` text.
- `voice playback`: a clip did not finish in time (`A <seconds>s clip didn't finish playing (player <state>, connection <state>); skipped it.`), or the audio player itself raised an error.
- `cloud viewer`: the relay to the hosted viewer failed (at most once a minute).

## lip sync / lipsync / phonemes / mouth / visemes

Lip sync is the mapping from speech to mouth shapes on the avatar. The bot does not analyse the audio in real time on the server. For each clip it builds a timed list of mouth cues once, when the speech is compiled. The page then samples that list every frame. The shapes are the 15 morph names listed in the speech articulation section, and the page moves them with a spring so the mouth does not snap.

The phoneme step is in `src/speech-phonemes.js`. `speechPhones(text)` trims the text and caps it at 4000 characters. Empty text returns an empty list straight away. Results are cached by the exact text, up to 128 entries, and when the cache grows past that the oldest entry is removed. Requests for phonemes run one at a time through a queue, so two sentences never phonemize at once, and one failure does not block the next request. For text that is not cached, the function runs the npm package `phonemizer` with the `en-us` voice, joins the IPA output with ` | `, and passes the result to `ipaPhones`. How the package itself gets its phonemes is not verified. A failed request is removed from the cache so it can be tried again later. The language is always US English; there is no setting for another language, so other languages get English phonemes.

Who calls it: the Discord voice path (`prepareDiscordSpeech`), the Studio chat route (`POST /api/avatar/chat`), the phonemes route (`POST /api/avatar/phones`) and the cloud relay for text-reply clips. Every caller catches a failure and carries on with an empty list, so a phonemizer problem only costs mouth accuracy, never the speech.

The owner's test "pronunciation distinguishes lip-bite, tongue, and lip closure sounds, rather than letter names" in `speech-articulation.test.js` is the reason this step exists: the mouth should show the sounds actually spoken (lips biting for f, tongue for th, lips closing for p, b, m), not the letters written.

`ipaPhones(ipa)` turns IPA symbols into visemes, which are the mouth groups the page uses. The mapping groups sounds this way. `PP` covers p, b and m. `FF` covers f and v. `TH` covers the two th sounds. `DD` covers t, d and the flap. `kk` covers k, g, the g symbol and ng. `CH` covers sh, zh and the two affricates. `SS` covers s and z. `nn` covers n and l. `RR` covers the r sounds and the schwa-like r. `aa` covers the open vowels and the schwa and h. `E` covers the e sounds. `I` covers the i sounds and y-like j. `O` covers the o sounds. `U` covers the u sounds and w. Unknown symbols are skipped. Two-character symbols such as the affricates are matched before single characters.

Each phone also gets a weight, which decides how much of the timeline it takes up. Vowels (`aa`, `E`, `I`, `O`, `U` and `RR`) weigh 1.5. The fricatives and affricates `SS`, `FF`, `TH` and `CH` weigh 1.0. Everything else weighs 0.65. A vowel that comes after a stress mark (ˈ or ˌ) is multiplied by 1.25, and the stress carries forward until the next vowel. A length mark (ː) multiplies the phone before it by 1.25. The schwa and h sounds are multiplied by 0.7. Punctuation marks and the `|` separator become a silence phone called `sil` with weight 0.9. The whole list is capped at 1024 phones.

## lip sync priority / what drives the mouth / letter track / mouth flapping / analyser lip sync

The page decides what drives the mouth with this priority order, which is in `updateLips` in `src/dashboard/public/avatar.js`, run every rendered frame for each character. The first source that applies wins. First, a Discord packet that carries articulation version 2 is sampled against its own clock, which is the time since the packet's `at`. Second, a clip playing locally in the Studio that has articulation is sampled against the audio clock. Third, a Discord packet that has frames but no articulation uses a letter-based track, built by `visemeTrack` from the sentence's text and scaled by the frame loudness. Fourth, when audio is playing locally with no articulation, the page measures it with its analyser. If a letter track is running, the analyser picks the vowel shape from that track and uses the audio for loudness and hiss. If not, it uses the spectrum to choose O, U, aa, E or I, with loudness opening the jaw. Fifth, when there is no audio at all, such as when voice is off, no voice is set, or the speech service failed, the page flaps the mouth. The flap amplitude is `0.35 + 0.35 sin(17t) + 0.2 sin(7.3t + 1)`, clamped between 0 and 1, and it runs for `max(900 ms, characters × 62 ms)`; the next sentence starts 150 ms after that. The flap uses `aa` at half the amplitude, `O` at a fifth of it in short bursts, and the jaw at 0.15 of it.

The letter-based track (`visemeTrack`) is the old fallback, kept for speech without phoneme data. It reads the sentence's letters (digits are spelled out as words first) and gives each one a shape and a length weight: vowels hold 2.4, the hissing letters s, z, f, v, j, c and x hold 1.6, other consonants 1.0, and spaces and punctuation 0.35 (a brief neutral). Its letter mapping is coarser than the phoneme one: p, b, m close the lips; s, z, f and v all use the `SS` shape; c, j, g, x and h use `CH`; and k, d, t, n, l, r and q just open the mouth as `aa`. For a Discord packet without articulation, the track's length is the number of frames times `frameMs` (40 ms assumed when it is missing), and the shapes are scaled by the frame's loudness, with some of the frame's own hiss added to `SS` so s sounds stay clear.

The live analyser (the fourth source) measures loudness from the waveform (`(rms − 0.012) × 7`) and splits the spectrum into low (150 to 900 Hz), mid (900 to 2400 Hz) and high (3200 to 8000 Hz) bands. A strong high band counts as hiss and drives `SS` and `CH`; the balance of mid against low picks rounded (O, U) versus spread (E, I) vowels.

Two things are added on top of whichever source wins. Brows flick up briefly when loudness jumps by more than 0.22 (at most every 700 ms, with a 60 percent chance), the way people's brows move on stressed syllables. And every shape is moved toward its target by the `smoothSpeech` spring, faster while the lips are sealed (see speech articulation). The Studio's `Lip sync strength` slider (`opts.lips`, default 1, range 0.3 to 2 in steps of 0.1) scales every mouth target, so a weak or exaggerated mouth can be a setting rather than a fault.

The Studio's own chat audio gets articulation only when the message has phonemes (the code only builds it when `msg.phones` has at least one entry). Without phonemes it falls back to the letter track. The other two paths differ. The recorder (video replies) asks `POST /api/avatar/phones` for each line and compiles articulation from the answer; if that request fails, the line has no articulation. The watch-only page uses the packet's own articulation when it has one (voice packets do) and otherwise compiles one from the packet's `phones`, even when that list is empty. If the speech has no cues at all, the mouth does not move for that sentence. That situation happens when the phoneme list is empty and a packet has no articulation of its own, which on the watch page means a text-reply clip whose phoneme lookup failed. The test file `speech-articulation.test.js` checks that silence produces no cues and no mouth shapes.

## avatars without visemes / arkit mouth shapes / visemes false / no viseme shapes

Some models have no `viseme_*` face shapes. The page checks for `viseme_aa` when it loads a model and sets `hasVisemes` from that. Without visemes, each mouth shape is built from ARKit jaw and lip controls using the `VISEME_ARKIT` table in `avatar.js` (`addViseme` does the conversion; `jawOpen` is always used directly). The full table, as weights per ARKit shape:
- `aa`: jawOpen 0.55, mouthLowerDown 0.25 on both sides.
- `O`: jawOpen 0.3, mouthFunnel 0.6.
- `U`: jawOpen 0.12, mouthPucker 0.7.
- `E`: jawOpen 0.3, mouthStretch 0.35 on both sides.
- `I`: jawOpen 0.15, mouthStretch 0.3 and mouthSmile 0.1 on both sides.
- `SS`: jawOpen 0.05, mouthStretch 0.25 on both sides.
- `CH`: jawOpen 0.1, mouthFunnel 0.35, mouthPucker 0.2.
- `PP`: mouthPress 0.5 on both sides.
- `FF`: jawOpen 0.08, mouthRollLower 0.35, mouthUpperUp 0.25 on both sides.
- `TH`: jawOpen 0.15, tongueOut 0.12.
- `DD`: jawOpen 0.12. `kk`: jawOpen 0.18. `nn`: jawOpen 0.1. `RR`: jawOpen 0.16, mouthPucker 0.22.
A model that has neither kind of shape cannot move its mouth at all, whatever the speech data. The page warns in a toast when a model has neither ARKit blink shapes nor viseme shapes: `<name>'s model has no ARKit or viseme face shapes, so they can't blink or lip sync.` A model that loads with no viseme shapes can still work through ARKit controls, but the report shows `visemes: false`, and that is the first thing to look at when lip sync looks wrong.

Timing has a few rules. The Discord path always gives a timing string of `audio-guided estimate` for the packet. If the speech service's clip does not finish within the time the bot allows for it, the bot skips to the next sentence and logs `voice playback`. The voice session waits for a clip to finish for `clip.length / 6000 × 1000` milliseconds doubled, plus 8000 milliseconds, which is based on the rough rate of Fish's Opus output at about 6 KB a second. Before playback it also waits for the microphone lease for `clip.length / 6000 × 1000 + 15000` milliseconds, which is renewed for each sentence. In the Studio, a sentence starts 25 ms after the audio context's current time, and the mouth follows the clip from that moment.

## speech articulation / articulation / cues / timing / speech solver

This is the shared solver in `src/dashboard/public/speech-articulation.js`. It has no dependencies, so the server (`src/discord-avatar.js`) and the browser page (`avatar.js`) both use exactly the same code, and the server can compile a Discord packet that the page then renders. It runs once per clip. Rendering each frame after that is a search over the cue list, so no audio analysis happens while the mouth is moving.

The file exports five things. `SPEECH_SHAPES` is the list of 15 shape names: viseme PP, FF, TH, DD, kk, CH, SS, nn, RR, aa, E, I, O and U, followed by `jawOpen`. `audioFeatures(samples, rate, frameMs = 20)` analyses the audio and returns `{ frames, frameMs, durationMs }`, where each frame holds `rms`, `bright`, `round`, `open` and `wide`. The audio is first decimated to about 16 kHz by taking every `floor(rate / 16000)`th sample, and the frames are 20 ms long by default. `alignPhones(phones, frames, frameMs)` lines the phones up with the frames and returns the cue list `[{ start, end, viseme }]` in milliseconds. `compileArticulation(samples, rate, phones)` runs the first two and returns `{ version: 2, frames, frameMs, durationMs, cues, timing: 'audio-guided estimate' }`. `sampleArticulation(track, time)` returns `{ mouth, level, closure, active }` for one moment in time, and `smoothSpeech(current, target, velocity, dt, speed)` moves one shape one step toward its target.

The analysis of each frame works like this. The frame's loudness is its root mean square. A brightness value comes from the energy in four bands, centred at 400, 1000, 2200 and 4000 Hz, which are measured with the Goertzel method (a single-frequency filter). Brightness is weighted toward the upper two bands and also rises with how quickly the signal changes from sample to sample, relative to its energy. A `round` value is the share of energy in the two lowest bands. The `open` value is the loudness scaled against the 95th-percentile loudness of the whole clip, with a floor so quiet noise does not open the mouth. The 95th-percentile reference is never below 0.012, and the result is capped at 0.85 so loud frames do not fully open the mouth. In the packet, `wide` is `open × bright`, and `round` is multiplied by `open`, so it is the low-band share scaled by how open the mouth is. `bright` is also included.

Alignment finds the first and last frames where `open` is above 0.025, which are the speech edges. Inside that region it runs a dynamic-programming pass that gives each phone a run of consecutive frames, in the same order as the phones. Each frame has a cost for each possible phone. A silence phone is expensive when the mouth is open. A `PP` phone (not `m`) is cheap when the mouth is closed and expensive when it is open. Sibilants and the fricatives `FF`, `TH`, `SS` and `CH` prefer a brightness near 0.65 and need some sound. Everything else prefers low brightness and needs some sound too. On top of that there is a timing term that pulls each phone toward its expected position in the clip, based on its share of the total weight. The lowest-cost path becomes the cue list. If there are fewer frames than phones, or if frames times phones is above 3,000,000, the solver does not run the dynamic programme. It spreads the phones across the speech region in proportion to their weights instead. Silence phones are kept in the cue list, and because they have no pose in the solver, they close the mouth.

Rendering uses `sampleArticulation(track, time)`. It returns nothing for times before zero or after the clip's duration plus 60 ms, with `active: false`. For times inside the clip it finds the cue that contains the time by a binary search, and it blends into the neighbouring cue near each boundary. The blend window is 45 ms for most visemes and 14 ms for `PP`, and it is never longer than 35% of either cue's length. Each shape's pose is a weight and a jaw-opening amount. The poses are PP at `[0.92, 0]`, FF at `[0.78, 0.045]`, TH at `[0.68, 0.08]`, DD at `[0.62, 0.09]`, kk at `[0.55, 0.12]`, CH at `[0.72, 0.08]`, SS at `[0.67, 0.035]`, nn at `[0.55, 0.07]`, RR at `[0.62, 0.12]`, aa at `[0.76, 0.22]`, E at `[0.72, 0.13]`, I at `[0.67, 0.09]`, O at `[0.72, 0.15]` and U at `[0.68, 0.09]`. Every shape that is not `PP` is scaled by a gate on the frame's openness. The gate is a smooth step between openness 0.012 and 0.075, multiplied by `0.38 + 0.62 × level`, so quiet moments close the vowels. `PP` is not gated, so the lips still close in silence. The whole output fades out smoothly from 35 ms before the end of the clip to 25 ms after it. The `closure` value that is returned is the total weight of the `PP` cues at that moment, and the page uses it to suppress smiles while the lips are sealed.

Smoothing is done by `smoothSpeech`, which is a critically damped spring for each shape. Its stiffness is 40 while a shape is opening and 48 while it is closing, multiplied by a speed factor. The page uses a speed of 2 whenever `closure` is above 0.4, which makes consonant seals snap shut, and 1 otherwise. Each time step is capped at 0.1 seconds so a long frame does not make the spring explode.

The debugging numbers worth knowing are these. The frame size is 20 ms, and the packet's `frameMs` is 20. The threshold for finding speech edges is an openness of 0.025. The gate runs from 0.012 to 0.075. The blend windows are 45 ms and 14 ms, capped at 35% of the cue length. The fade runs from the clip's end minus 35 ms to its end plus 25 ms. The solver falls back to the proportional method when frames are fewer than phones or when frames times phones is above 3,000,000.

## speech articulation details / articulation tests / closure and smiles / how lip sync is tested

More exact behaviour of the solver, for when you are asked how precise it is:
- Decimation: for 48 kHz audio the step is 3 (every third sample, an effective 16 kHz); for 16 kHz audio every sample is used. A 20 ms frame at 48 kHz covers 960 samples, of which 320 are analysed.
- Brightness is `0.6 × (2200 Hz + 4000 Hz band energy) / total band energy + 0.2 × (sample-to-sample change) / energy`, clamped to 0..1.
- Openness: the reference peak is the 95th-percentile loudness, never below 0.012; the floor is the smaller of 0.006 and 6 percent of that peak; `open = (rms − floor) / (peak − floor) × 0.85`, clamped to 0..1.
- Alignment cost per frame: a silence phone costs `open × 1.2`; `p` and `b` cost `open × 0.35` (`m` is treated like any other sound, because the mouth can hum while closed); `FF`, `TH`, `SS` and `CH` cost `|bright − 0.65| × 0.4`, plus 0.3 when the frame is nearly silent (open under 0.02); everything else costs `bright × 0.25`, plus 0.55 when nearly silent. The timing term is `((position in clip − phone's expected centre) × 3)²`.
- A cue's `start` and `end` are whole multiples of 20 ms, because cues are built from frames.
- Before 0 ms or from `durationMs + 60` ms on, sampling returns `active: false` and no shapes. Inside the clip but outside every cue (leading and trailing silence), it returns `active: true` with no shapes, so the mouth rests.
- The blend toward a neighbouring cue reaches at most half (weight 0.5) right at the boundary.

How the page uses `closure`: while the lips are sealed for `PP`, the page reduces `mouthSmile`, `mouthFrown` (both sides) and `mouthPucker` by 80 percent of the closure, so a smiling face still closes its lips for p, b and m. Cheeks and eyes keep their smile. Explicit mouth commands from a face performance (such as a `mouth_closed` pose) still win.

The owner's tests in `src/speech-articulation.test.js` say what must stay true:
- "pronunciation distinguishes lip-bite, tongue, and lip closure sounds, rather than letter names": `Five blue things.` must produce `FF`, `PP`, `TH` and `U`; `see` must start with `SS` and contain `I`; a repeated request returns the cached result.
- "audio-guided cues exclude leading/trailing silence and a silent clip stays still": speech from 0.25 s to 1.7 s gives more than 10 cues, the first starting at 240 ms or later and the last ending by 1720 ms; the mouth is empty at 80 ms and 1950 ms; every shape value stays between 0 and 1; a silent clip gives no cues and no mouth shapes.
- "coarticulation blends vowel boundaries while preserving bilabial closure": near an `aa` to `U` boundary both shapes are present, with no jump across it; during `PP` the jaw is shut (0), `viseme_PP` is above 0.8 and `closure` is 1.
- "speech springs behave consistently at different render frame rates": the spring gives the same result at 60 and 120 frames a second (within 0.001) and reaches over 0.79 of a 0.8 target in a quarter second.
- "smile poses yield at speech closures, while explicit mouth commands still win": described above.

## generation deliveries / deliveries / generated pictures / generated music / files to discord / send_file

A generation delivery is a durable record of a picture, a song or a file that you made. It is saved to disk so that the result can be shown in the dashboard or sent to Discord even if the chat that asked for it has moved on. The store is in `src/generation-deliveries.js`, the background jobs are in `src/generation-jobs.js`, and the tool side that delivers each kind of result is in `src/tools.js`.

The store is the folder `DATA_DIR\task-deliveries`, which is created when the module loads. Each delivery is a `<id>.json` metadata file and, when there is binary data, a `<id>.bin` file with the bytes. The ids come from a counter that starts at the larger of the current time in milliseconds and the highest id already on disk, and then goes up by one for each save. That means the ids are large numbers close to a timestamp. A saved record holds the metadata without the base64 data, plus the new `id`, the `conversation`, the `kind`, the `time` saved in milliseconds and the `characterName`. When binary data was saved, the record also gets a `url` in the form `/api/generation-deliveries/<id>/media`. The four kinds are `image`, `audio`, `file` and `notice`. A `notice` is only a text message with no file. Nothing in this module removes old delivery files, so they accumulate; on this computer the folder is currently empty.

Record shapes by kind:
- `image`: `{ mime, name, characterName, id, conversation, kind: 'image', time, url }`. `name` is the file name in `DATA_DIR\images`.
- `audio`: `{ mime: 'audio/mpeg', name, characterName, id, conversation, kind: 'audio', time, url }`.
- `file`: `{ name, characterName, id, conversation, kind: 'file', time, url }` (no `mime`, so it downloads as `application/octet-stream`).
- `notice`: `{ message, characterName, id, conversation, kind: 'notice', time }`, no `url` and no `.bin` file.

Only the dashboard chat and the Avatar Studio chat use this store. Discord and voice calls deliver straight into Discord instead (see "where generated things arrive").

The functions are straightforward. `saveGenerationDelivery(conversation, kind, data, storageDir)` writes the bytes (decoded from the base64 in `data`) and then the JSON record. `generationDeliveries(conversation, after, storageDir)` returns the records with an id greater than `after`, in ascending id order, only for the given conversation, and returns at most 50 of them on each call. Because the first 50 in order are returned, a conversation that falls far behind catches up in batches. The owner's test "delivery pagination does not skip earlier results when many jobs complete offline" checks exactly this: 55 results give 50, then the remaining 5, oldest first, with none skipped. Every call reads every JSON file in the folder, so the store gets slower as it grows. `generationDeliveryMedia(id)` rejects any id that is not all digits with `Invalid delivery ID` (the test tries `../settings` to make sure no path can be smuggled in), and otherwise returns the metadata and the bytes. If the files are missing, the filesystem error is not handled in this module. `generationDestination(conversation, characterName)` builds the destination object that the tools receive. Its `showImage(data)` saves an `image` record, `showAudio(data)` saves an `audio` record, `sendBackground(file)` saves a `file` record with the bytes taken from `file.attachment`, and `notify(message)` saves a `notice` with only the message text.

Two routes serve these records, both in `src/dashboard/server.js`. `GET /api/generation-deliveries?conversation=<c>&after=<id>` returns the list described above. `GET /api/generation-deliveries/<id>/media` serves the bytes. The content type is kept only for `image/png`, `image/jpeg`, `image/webp`, `image/gif` and `audio/mpeg`. Anything else is sent as `application/octet-stream`, and every response carries `Content-Length` and `X-Content-Type-Options: nosniff`, so the browser never guesses a type and runs something. The dashboard's own chat uses the conversation `dashboard` (the `POST /api/chat` route, with your bot name as the character name), and the Studio's chat uses `avatar` (the `POST /api/avatar/chat` route, with the speaking character's name). Both routes spread `generationDestination(...)` into the reply's context, so `showImage`, `showAudio`, `sendBackground` and `notify` all save here. Each route then replaces `sendHere` with its own: the dashboard chat collects ordinary files into the reply's `files` list, and the Studio streams them as a `file` message. Discord does not use this store at all.

## generation sub-agents / generation jobs / queued receipt / background generation / generation queue

Generated pictures, music and appearance work all run as background jobs. The tools `generate_image`, `generate_self_image`, `generate_music`, and `look` when its action is `setup` or `new` are all queued as generation sub-agents. `isGenerationTool` in `generation-jobs.js` decides which calls are queued. When one of these tools is called from a normal reply, `runTool` returns the marker `[<name>: queued]` followed by a receipt that says `Queued generation sub-agent #<id>. It is still working; no artifact is ready yet. Keep talking with the user. The result or failure will be delivered here separately. Do not call the tool again to wait or claim it is finished.` The same call made again in the same turn returns the same receipt and does not start a second job. Generation tasks are created with `startTask` and titled `Image generation`, `Music generation` or `Appearance generation`. There are two limits. At most 12 jobs can be outstanding, meaning queued or running. A thirteenth call fails with `Generation queue is full. Wait for an existing job to finish before starting another.` At most two jobs run at the same time, and the rest wait in order.

The rule, in plain words: image generation (general pictures and pictures of yourself), music generation, and appearance work (`look` setup and new look) always run in a background sub-agent. This is enforced in the tool dispatcher (`runTool` in `src/tools.js`), whether turn classification is on or off, so you cannot make one of them run inline. Ordinary calls such as `look` with `list`, `wear`, `send` or `reference` stay immediate. A generation sub-agent is not a language model: it runs the exact tool call you made, with your exact arguments, and nothing reinterprets or expands the brief (`startTask` with `execute`, model name `generation-worker`).

What you should do with a receipt: acknowledge the handoff in your own words and keep talking. A queued receipt is not a finished picture or song, and the conversation history records it as queued: the tools note saved with your reply (built in `src/companion.js`) lists the call as `<tool> <target>: queued`, not `ok`. Queued tools are also not carried forward into the "sticky" tools kept on hand for the next turns (`updateSticky` in `src/companion.js`). When the job ends, a separate success or failure record is added. Never call the tool again just to wait or to claim the result; a repeat of the identical call in the same turn returns the same receipt anyway (the dispatcher keeps up to 500 remembered receipts).

Steps when a generation call arrives, in order:
1. The tool must be enabled for this person and place (its `enabled` check), or it fails as not available.
2. For `generate_image`, `generate_self_image` and `look`, the picture routing check runs (`imageRouteError` in `src/image-pipeline.js`; see "generated pictures").
3. Energy is paid for the act (`pressure.actionCost`), for the main character only. Short of energy, it fails before anything is queued.
4. An empty prompt (without a `song_id`, and not for `look`) fails with `Empty generation prompt`; music without `clip` or `full` fails with `Music needs length clip or full`. In both cases the energy is refunded.
5. The job is queued and the receipt returned as `[<tool>: queued]`. A picture or song is also held open for the person's reaction (the creations system).
6. When the job runs, the tool is called again with a copy of the context marked `generationJob: true`. That second call checks permissions and routing again, but it is not charged energy and is not queued again.
The copy of the context is taken at the moment of queueing, including a copy of the permissions and the character, so a change later in the conversation does not change what the job is allowed to do.

Where the record lives: each job is a task in `src/agents.js`. Its report is saved to `DATA_DIR\tasks\<date>-<time>-task-<id>.md` when it finishes (status, steps, model `generation-worker`, the result and the actions). Tasks only live in memory while they run, so a restart stops every job in progress and nothing resumes it automatically. A code change needs the usual manual restart; nothing restarts the bot by itself. The `background_task` tool's own helper limit does not count generation jobs; they have their own queue.

The owner's tests: `generation-jobs.test.js` checks that the policy covers exactly both image pipelines, music and appearance generation; that the handoff returns at once, snapshots permissions and de-duplicates same-turn calls; that delivery goes to a durable destination, not to a finished reply's attachment list; that failures reach the task state and cancelling prevents late delivery; that at most two run at once with a bounded queue; and that the conversation is updated before the original destination is notified. `generation-integration.test.js` checks that permissions and image routing reject a request before any sub-agent is started, and that cancelling stops the job before any paid request.

## generation task cancel / cancel a picture / cancel a song / generation task status / generation failed

Each job's delivery goes through a wrapper that checks the task's cancel flag first. If the flag is set, the wrapper throws `Generation task cancelled before delivery`, so nothing is delivered. Cancellation is done through the task system: the owner uses the `background_task` tool with `action: cancel` and the job's id (the number in the receipt), which calls `cancelTask` in `src/agents.js` and sets the flag. It replies `Cancelling task #<id>.`, or `Error: no running task #<id>.` when the id is unknown or already finished. `background_task` with `action: status` lists tasks, generation jobs included, and with an `id` reads one task's whole report. A job that is cancelled before it starts fails with `Generation task cancelled`. The picture and music code also checks the flag right after the provider answers, so a job cancelled mid-request throws `Generation task cancelled` before saving or delivering anything. What cancelling cannot do: a request already sent to the image or music provider may still finish on their side and cost its normal price; only the delivery is suppressed. A cancelled task gets the status `cancelled`, and no completion notice is sent to the chat for it.

A tool result that begins with `[<name>: error` makes the whole task fail, and the error text becomes the task's record. When a job finishes, its result is added to the conversation as an assistant message with the text `Generation task #<id> <status>: <result>`, the result cut to 1500 characters and tagged with the tool name and `ok` (status `done`) or `failed` (any other status). For a cast character other than you, the message carries that character's name. That message is added by the dispatcher's `completed` callback in `src/tools.js`, before anything is said in the chat, so your history already knows the outcome when you speak about it. After that, the notify function runs with `Background task #<id> "<title>" <status>:` followed by the result, and the result is passed back to the chat that asked for it, which in Discord means the channel where the request was made. The task system logs `activity('task', { id, title, status: 'started', model })` when a job starts and `activity('task', { id, title, status, steps })` when it ends; a job that finished has `steps: 1` and its tool name in `actions`.

The statuses a generation task can end with: `done` (the tool returned normally, which includes a polite non-error message such as a song too big to attach), `failed` (the tool threw, or returned an `[<name>: error` line; the message is the result), and `cancelled`.

## generated pictures / generate_image / generate_self_image / image routing / picture delivery

Pictures are delivered by `deliverGeneratedImage` in `src/tools.js`. The picture is first saved to `DATA_DIR\images` under a name made of an optional `self-` prefix, the current ISO time with colons and dots replaced by hyphens, and the file extension. Then, if the destination has `showImage` (which the dashboard and the Studio have), the picture goes there with its mime type, base64 and name. If not, the picture is attached to a Discord message with `sendHere`. The result text then tells you that the picture is showing in the chat: `The image was generated and is now showing in the chat. Say something short about it; do not describe it in detail or include links.` If you had no reference picture of yourself, the picture was drawn from the request alone and saved as your new reference, and the result says so: later pictures of you keep that face. Pictures are not checked against Discord's upload size limit. Each delivery logs `activity('file', { filename, pipeline: 'self' or 'general', bytes, to: 'avatar studio' or 'here', ms })`.

The two picture pipelines are kept apart on purpose (`src/image-pipeline.js`): ordinary pictures never receive your identity assets. `generate_image` sends only the prompt. `generate_self_image` sends your saved identity reference sheet first, as the authority for your face, hair, skin tone and body, and your current saved look second as supporting identity and clothing context (unless the request names different clothing). An empty prompt fails with `Empty image prompt` or `Empty self-image prompt` inside the pipelines.

The routing check (`imageRouteError`) steers each picture to the right tool before anything is queued. It looks at the person's message and at the prompt for wording that asks for a picture of you (for example "picture of you", "draw yourself", "your selfie", "you wearing"), and at the turn's image intent. Its errors:
- `This request is for a general image. Call generate_image; do not use or change the companion identity assets.` (you called `generate_self_image` for an ordinary picture)
- `The user requested a general image. Remove the companion from the prompt and use generate_image for the requested subject only.`
- `This is a picture of the companion. Call generate_self_image instead; generate_image never uses her identity assets.`
The code comment records an owner decision: the check never refuses changing or replacing your look, because that is the owner's call, and a wording check there once blocked it nine times in a row.

Who can make pictures: `generate_image` needs the image model to be ready (`canMakeImages()`), a place to send the result, and the `files` permission. `generate_self_image` and `look` additionally need owner status and the main character. Pictures are kept forever in `DATA_DIR\images` (self pictures start with `self-`).

## generated music delivery / generate_music delivery / song too big to attach / music to discord

Music is delivered by `makeMusic` in `src/tools.js`. If a `song_id` is given, the song must be in your songbook, otherwise the tool returns `Error: no song #<id> in your songbook`. An empty prompt with no song returns `Error: empty music prompt`. The track is saved to the music library with `addSong`, using the song's title if there is one, or the title you gave, or the first few words of the prompt. If the song came from your songbook, its status becomes `recorded` and the file name is stored with it. Then, if the destination has `showAudio`, the track goes there with mime `audio/mpeg`. If not, it is attached on Discord with `sendHere`. On Discord, tracks bigger than `MAX_FILE_BYTES` (8 MB, `8 * 1024 * 1024` bytes, defined at the top of `src/tools.js` as Discord's upload limit for bots in most servers) are not attached. The dashboard and Studio have no such limit, because they show the track from the delivery store. The tool returns `The song is saved in the music library, but it's too big to attach on Discord (<size> MB). Offer to play it in voice instead.` The song is still in the library in that case. Otherwise the tool returns that the song is done and playing in the chat, and it includes the lyrics, up to 1500 characters, unless the song is instrumental.

The exact music result on success is `The song is done and now playing in the chat.` (or `The 30-second clip is done...` for a clip), followed by `Its lyrics: <up to 1500 characters>` or `It is instrumental.`, and the instruction to say something short and not read out all the lyrics. The title used for the library is the songbook title, else the `title` you gave, else the first six words of the prompt up to the first comma, full stop, semicolon or colon. The library's `about` note is the songbook style plus `written by her, songbook #<id>`, or the prompt, cut to 300 characters. With a `song_id`, the prompt you give is added as `Production notes:`. Each delivery logs `activity('file', { filename, bytes, to, ms })`. The track stays in the music library (`DATA_DIR\music`), so it can be played in voice or playlisted later even when it could not be attached.

## send_file details / send a text file / files send / attach a file / send_file errors

Files you write are sent by `send_file`. The tool writes new text files from content you provide, and it only works where there is a chat to send to (`ctx.sendHere`) and the asker has the `files` permission. Its description says it is only for new text files you write (text, markdown, code, CSV, JSON, HTML), never for a file that already exists on the computer. It refuses names ending in `.zip`, `.7z`, `.rar`, `.tar`, `.gz`, `.png`, `.jpg`, `.jpeg`, `.gif`, `.webp`, `.mp3`, `.wav`, `.ogg`, `.flac`, `.mp4`, `.mov`, `.pdf`, `.exe`, `.db`, `.sqlite`, `.docx`, `.xlsx` or `.pptx` with `Error: send_file only writes new text files, so nothing was sent. <name> is a real file: send it with files (action send) and its path...`. The code comment gives the reason: you once "sent" a `.zip` that held only one sentence of yours instead of the real file. Empty content fails with `Error: the file has no content`. The file name is cleaned (`safeFilename`) before use. The file must be no larger than 8 MB, or it fails with `Error: <name> is too big to send (<size> MB)`. The file is also kept in `DATA_DIR\files`, overwriting any earlier file of the same name. Parameters: `filename` and `content` (both required), `recipient` and `message` (optional; `message` is a note up to 2000 characters that goes with a file sent elsewhere). With no `recipient`, or with `here`, `this chat` or `me`, the file is attached to your reply. A `recipient` can name a channel such as `#general` or a person who has DMed you. Sending to another channel or person needs the `sendElsewhere` permission (friends only), and the Discord client must be online. The tool replies `Sent <name> here. It's attached to your reply, so don't paste its contents again.`, `Sent <name> to #<channel>.` or `Sent <name> to <person> by DM.` The errors when sending elsewhere: `Error: only friends can have you send files to other channels or people. Tell them you can only send it here.`, `Error: the Discord bot is offline, so you can't send it anywhere else right now. Give it to them here instead.`, and `Error: no channel called "<name>" and nobody by that name has DMed you, so you can't send it to them.` A send logs `activity('file', { filename, bytes, to })`, with `to` being `here`, `#channel` or the person's name. Files sent elsewhere never ping anyone.

The `files` tool's `send` action is the different route for real files on the computer. It reads the file at the path, refuses files over 8 MB with `Error: <name> is <size> MB, over Discord's 8 MB limit.`, returns `Error: there is no chat here to send a file into.` when there is no chat, and otherwise attaches it here and replies `Sent <name> here.` It can only send to the current chat. For several files, `send_project` bundles them into one `.zip` (8 MB limit as well) and needs an owner-confirmed project first.

For long writing, research or project building, the `background_task` tool hands a complete brief to a helper that can prepare and deliver files with `send_file` and `send_project` while you keep talking. Its files go out through `sendBackground` when there is one, so in Discord they arrive as their own messages. Short text replies and small files you already have need no helper.

## generation tool availability / who can make pictures / generation parameters

Tool availability depends on what is set up. `generate_image` needs the image model to be ready (`canMakeImages()`), a place to send the result (`sendHere` or `showImage`), and the `files` permission. `generate_self_image` needs the same, and also needs owner status and `ctx.character.main`, which means it is only for your main character and your owner. `generate_music` needs an OpenRouter API key (`config.openrouter.apiKey`), a place to send the result (`sendHere` or `showAudio`), and the `files` permission. `look` needs the OpenRouter key, owner status, `ctx.character.main`, the `files` permission, and a place to send. `send_file` needs `sendHere` and the `files` permission. For `generate_music`, the parameters are `length` (required, either `clip` for about 30 seconds or `full` for a full song; anything else fails with `Music needs length clip or full`), `prompt` (required without a `song_id`), `song_id` (a number from your songbook), and `title`. For `generate_image` and `generate_self_image` the parameter is `prompt`. `generate_image` is for ordinary subjects and never uses your saved appearance. `generate_self_image` is for pictures of you and uses your saved identity reference. Both need a non-empty prompt, which fails with `Empty generation prompt`.

## where generated things arrive / discord delivery / voice delivery / sendBackground

The Discord side is in `src/bot.js`. When a normal reply has files, `sendHere` pushes each file into a local list for that reply. When the reply is sent, the files are attached to the reply itself if it fits in one message, or to the last message if the reply is split into several. So an ordinary chat picture appears under your text. Background results use `sendBackground` instead. That posts the file as its own message in the same channel (`message.channel.send({ files: [file] })`), and it happens later than the reply. Generation jobs use `sendBackground` whenever it exists, because `generation-jobs.js` maps the `sendHere` destination to `ctx.sendBackground || ctx.sendHere`. So a finished picture or song in Discord arrives as a separate message after the text reply. Background helper reports work the same way. The `notify` function given to a text reply in `bot.js` posts lines that start with `Doctor visit ` exactly as they are. Any other report is first passed back through your reply pipeline (an empty turn with the report as evidence) so you can say it in your own words, and the raw text is posted if that fails (logged as `task report reply`). Long text is split into 2000-character Discord messages. Progress lines from long helpers are posted as `⏳ <text>`. Scheduled activity and calendar messages (set up when the bot comes online in `bot.js`) go to the owner by DM, with `sendHere`, `sendBackground` and `notify` all going to the DM, and calendar text is also added to the DM conversation history.

In a voice call (`src/voice/session.js`), the reply's `sendHere` posts the file straight into the call's text channel as its own message; there is no `sendBackground`, so generation jobs use that. The completion report goes to the session's `reportTask`: a doctor's report is posted in text and summarised out loud; anything else you talk through yourself, out loud, as a new reply (and it is also posted as `🔊 <reply>` when voice transcripts are on). So in a call, a finished picture lands in the text channel and you also say it is done. If the call has no text channel, there is no `sendHere`, so picture and music tools are not available there (they need a place to send).

Summary of where each result goes:
- Discord text channel or DM: the file arrives as its own message in the same channel, after your reply, and you then mention it in your own words.
- Discord voice call: the file goes into the call's text channel, and you say it is done out loud.
- Dashboard chat: a delivery record in `DATA_DIR\task-deliveries` with conversation `dashboard`, shown as a bubble by polling.
- Avatar Studio chat: the same with conversation `avatar`.
- In every case the picture also stays in `DATA_DIR\images` and the song in the music library, and the job's report is in `DATA_DIR\tasks`.
Because dashboard and Studio results are stored, not streamed, a closed reply stream or a later conversation cannot lose them.

Failures and edge cases. A cancelled task reports `Generation task cancelled` for pictures and music, or `Generation task cancelled before delivery` if the cancel happened while the result was being sent, and nothing is delivered in either case. A tool error that starts with `[<name>: error` fails the task, and the error text goes into its record. A Discord send failure inside `sendBackground` is not caught in `bot.js`; the promise is returned to the tool, so the tool throws, and the generation task ends as `failed` with Discord's error as its result. The dashboard's polling of these deliveries is covered in the next section. A corrupt delivery JSON file makes the read throw. The dashboard server turns any thrown error into an HTTP 500 answer with `{ error: <message> }`, and the polling page ignores non-OK answers. Because the list function parses every JSON file in the folder before it filters by conversation, one corrupt record would stop new deliveries from showing on both the dashboard and the Studio until that file is fixed or removed by hand. A missing `.bin` file makes the media route answer 500 the same way, so that one picture's image is broken while the rest keep working.

## generation delivery ui / delivery bubbles / dashboard delivery / watchGeneration

`src/dashboard/public/generation-delivery-ui.js` shows deliveries as chat bubbles in the browser. It is kept separate from the reply stream on purpose, so a background result can arrive while another reply is still running, and so it does not depend on the reply's connection.

The function `watchGeneration(conversation, makeBubble)` starts a poll straight away and then polls every 3000 ms with `setInterval`. Each poll asks `GET /api/generation-deliveries?conversation=<c>&after=<last id>`, where `last id` is the id of the newest record already shown in this page. A poll is skipped when `document.hidden` is true, which means the tab is in the background, and also when a previous poll is still running. For each record the page makes a bubble. The bubble's text is the record's `message` if it has one. Otherwise it is `Your image is ready.` for images, `Your music is ready.` for audio, and `Your file is ready.` for anything else. The bubble is labelled with `record.characterName`. If the record has a `url`, an `image` record adds an `<img class="gen">` with the record's name as its alt text, an `audio` record adds an `<audio controls>` player, and every record with a URL also gets a download link (`<a class="file">`). The link's download name is the record's name, or `download` if there is none. A `notice` record has no URL, so it only shows its text. After each record is handled, the page remembers its id, so the next poll starts after it. A failed request, including a non-OK response, is ignored, and the next tick tries again. The function returns a stop function that clears the timer.

The watch is started in two places. The Studio page starts it in `avatar.js`, for the `avatar` conversation, and only when the page is neither the recorder nor the watch-only page. Its bubbles are assistant bubbles labelled with the character's name. The dashboard starts it in `src/dashboard/public/index.html`, for the `dashboard` conversation, loading the script on demand and drawing the bubbles in the chat panel.

Important detail about the starting point: each page starts with `after = 0`, so when a page is opened or reloaded it shows every stored delivery for its conversation again, oldest first, 50 per poll. Reloading the dashboard therefore replays old pictures and notices; that is not a duplicate job. A finished job on these pages usually makes two bubbles: one for the picture or song (`Your image is ready.` or `Your music is ready.` with the media), and one notice with the completion text the task system sends, `Background task #<id> "<title>" <status>:` followed by the tool's result. The images are shown with the CSS class `gen`, the download link with class `file`, and the link text is the record's name or `Download`. Because the polling is only done while the page is visible, a picture made while the tab was hidden will appear when the tab is shown again, within about three seconds. If a bubble does not appear, check that the page is visible and not blocked by a failed fetch, and reload the page to restart the poll.

## slash commands / commands / deploy commands / deploy / loadCommands

Slash commands are the `/` commands in Discord. Their code is in `src/commands`, and each file there is one command. There are four command files right now, which were checked with a file search: `ping.js`, `join.js`, `leave.js` and `memories.js`. No other command files exist in that folder.

Loading is done by `loadCommands()` in `src/loadCommands.js`. It reads every `.js` file in the `commands` folder next to it, and it skips anything else. Each file must export `data`, which is a `SlashCommandBuilder`, and `execute`, which is the function that runs the command. A file missing either one is skipped with the warning `Skipping <file>: missing "data" or "execute" export`. The command is stored under the name in `data.name`. `src/bot.js` calls `loadCommands()` once when the module loads, before the Discord client is created, so adding or changing a command file needs a restart of the bot as well as a deploy. On every chat-input interaction (the `Events.InteractionCreate` handler in `bot.js`), the bot looks up the command by name and runs its `execute`. Other interaction kinds (buttons, menus, autocomplete) are ignored. An unknown name is ignored. If `execute` throws, the bot logs the error as activity `/<name>` and replies ephemerally with `Something went wrong running that command.`, or sends that as a follow-up if the command had already replied or deferred. A failure in `loadCommands` itself, such as a file that does not import, is not caught in this file, so it would stop the import step; since `bot.js` awaits it at load time, a broken command file stops the bot from starting. The error is written as `activity('error', { where: '/<name>', message })`, and the follow-up or reply failure is swallowed so a dead interaction cannot crash the bot. Two files with the same `data.name` would leave only the later one (in folder order) in the map.

How to add a command: put a new `.js` file in `src/commands` that exports `data` (a `SlashCommandBuilder` with a name and description) and an async `execute(interaction)`, restart the bot so it is loaded, and run `npm run deploy` so Discord shows it. Slash commands are code changes, so the owner (or the doctor) makes them; you have no tool that creates one.

## deploying slash commands / npm run deploy / deploy-commands / register commands / guild commands

Deployment is separate and manual. `src/deploy-commands.js` is run with `npm run deploy`, which runs `node src/deploy-commands.js` as set in `package.json`. The script loads `.env` through dotenv. If `DISCORD_TOKEN` or `CLIENT_ID` is missing, it prints `Missing DISCORD_TOKEN or CLIENT_ID in .env` and exits with code 1 without contacting Discord. If `GUILD_ID` is set, it registers the commands to that one server with `Routes.applicationGuildCommands`, and they take effect at once. If `GUILD_ID` is not set, it registers them globally with `Routes.applicationCommands`, and Discord can take up to an hour to show them. It sends the full set of commands with `rest.put`, which replaces every command on that route, so any command removed from the folder also disappears on the next deploy. It logs `Registered <n> command(s) to guild <id>` or `Registered <n> command(s) globally`. Nothing in `bot.js` calls the deploy script on startup, so a new or changed command does not show up until the owner runs the deploy.

What the deploy sends: each command's `data.toJSON()`, the same definitions the bot loads, so the names, descriptions, options and the "not in DMs" flags come from the command files. The three environment keys: `DISCORD_TOKEN` (the bot's token, also used by the bot itself), `CLIENT_ID` (the application id) and `GUILD_ID` (optional, one server's id). Their values live in `.env` and are never copied into this guide. A Discord refusal (a wrong token, a wrong id) is thrown by `rest.put` and the script ends with that error; nothing is half-registered, because the put replaces the set in one request. The guild route and the global route are two different lists; a deploy only replaces the list on the route it used.

## /ping / ping command / latency

`/ping` takes no options, has no owner check, and works anywhere. It first replies `Pinging...`, then edits that reply to `Pong! Round trip: <ms>ms · WebSocket: <ms>ms`. The round trip is the time from the interaction's creation to the reply message's creation; the WebSocket figure is the gateway heartbeat ping of the Discord client.
## /join and /leave / join command / leave command / bring her into voice

The commands are `src/commands/join.js` and `src/commands/leave.js`. `/join` works only in a server (it is blocked in direct messages) and joins the voice channel that the person who runs it is in. It replies `Join a voice channel first, then run /join.` if they are not in voice. If `config.voice.channelIds` is set (from the `VOICE_CHANNEL_IDS` environment variable), it only joins channels on that list, and otherwise replies `I'm only allowed in: <channels>`. If the speech service is not ready, it replies with the XTTS reason when the provider is XTTS, or with `Fish Audio needs its API key. You can also select a configured local speech provider.` Otherwise it defers the reply and calls `joinChannel` from `src/voice/session.js`. On success it edits the reply to `Hopped into **<channel>**. Just talk, I'm listening.` On failure it edits the reply to `Couldn't join: <error>`. There is no owner check in this command, so any member who can see the command and is in a voice channel on the allowed list can bring you in, and the allowlist is the only gate. `/leave` also works only in a server, and it leaves the voice channel for that server. It replies `Later! 👋` when it left, or an ephemeral `I'm not in a voice channel.` when she was not in one. It has no owner check either.

More detail on `/join`:
- The checks run in this order: is the person in voice, is the channel allowed, is speech ready. The first three replies are ephemeral (only the person sees them); the success and `Couldn't join` messages are public.
- "Speech ready" (`ttsReady` in `src/voice/provider.js`) means: for XTTS, the local XTTS server is available; for `kokoro` or `gtts`, always ready; for Fish (the default when `TTS_PROVIDER` is not set), a Fish API key is set. With XTTS selected, the reply is XTTS's own reason for not being ready.
- If you are already in that same channel, `joinChannel` returns the existing session and nothing restarts. If you are in another channel in the same server, that session is closed first and you move.
- The connection must be ready within 20 seconds, or the reply is `Couldn't join: Could not connect to the voice channel within 20s`.
- `VOICE_CHANNEL_IDS` is a comma-separated list of channel ids; it can also be changed from the dashboard settings (`voiceChannelIds`). Empty means any channel.
- The text channel where `/join` was typed becomes the call's text channel (transcripts, `🔇` lines and delivered files go there).
- What a voice session does once joined is in the voice calls guide.

`/leave` closes the whole session for that server (`leaveChannel` calls the session's `destroy`), the same as when everyone else leaves the channel. It does not check who asked.

## /memories / memories command / forget me / memories notes / wipe notes

`/memories` has three subcommands, and it works in direct messages too. `list` shows what she remembers about the person who runs it. The reply is ephemeral, so only that person sees it. It lists each memory as `#<id> <text>` and stops adding lines when the text would pass about 1950 characters, adding `…and more (see the dashboard)` at the end. If there are no memories, it says `I don't remember anything about you yet.` `forget` takes an optional whole-number `id`. With an id, it forgets that one memory, but only if it belongs to the person who runs the command, and replies `Forgot #<id>.` or `No memory #<id>.`. With no id, it forgets every memory that person has, and it also clears that person's profile record, replying `Forgot <n> memories.`. `notes` is for the owner only. Anyone else gets `Only the owner can look at my working notes.` With no options it shows the working notes for this channel (scratchpad `text:<channel id>`) and, when run in a server, the server's voice call scratchpad (`voice:<server id>`), each line as `#<id> [<kind>] <text>` or `(empty)`, plus every active thread as `#<id> **<label>**: <state>` or `(none)`. The reply is ephemeral and is cut to 1990 characters. The optional `wipe` choice clears either `scratchpad` (the channel and voice notes), `threads` (all active threads, which are shared by every conversation) or `all` of them, and replies `Wiped <n> note(s) and <m> thread(s).` with singular or plural words. The owner check comes from `isOwner` in `src/contacts.js`, which accepts the ids in `OWNER_IDS` (and the dashboard).

More detail on `/memories`:
- The subcommand descriptions in Discord are: `list` "Show what I remember about you", `forget` "Forget one memory, or everything" (its `id` option: "Memory # from /memories list (leave empty to forget all)"), and `notes` "Owner: see or wipe her working notes...". The command itself is described as "See or erase what the bot remembers about you".
- `list` starts with `**What I remember about you:**` and shows each memory as `#<id> <text>`.
- Every reply of `/memories` is ephemeral; nobody else in the channel sees it.
- `forget` with no id runs `forget(userId)` in `src/memory.js`, which deletes all that person's memory rows and clears their profile (`profiles.clear`). With an id it deletes that row only if it belongs to the person. The reply is `Forgot <n> memory` or `Forgot <n> memories`.
- Anyone can list and forget their own memories; only `notes` is owner-only.
- Known display bug: the threads header reads `Active threads (<n>/undefined)`, because the command prints `scratch.MAX_THREADS` and `src/scratchpad.js` no longer exports that constant. The list itself is complete.

## what she should tell owner when this breaks

Use this to explain symptoms to Owner and to say what they most likely mean. Check the code paths named above before saying anything is fixed, and say plainly when something has not been checked.

If Owner says the avatar did not change after you loaded a model, explain that `load` only selects the model. Nothing has been rendered until an open Avatar Studio page loads it and reports back. Check `status` for the report. If the report says `ok: false`, the library has already rolled back to the original, and `lastFailure` in `GET /api/avatar/library` says why. If there is no report at all, no Avatar Studio page is open, because the player must be open to report.

If the avatar went back to the original by itself, that is the automatic rollback in `reportAvatar` in `src/avatar-library.js`. It happens when a downloaded or outfit model fails in the player. Read `lastFailure.error` from `GET /api/avatar/library` to see the reason.

If a model download was rejected, the message says why. `Use an HTTPS direct GLB download URL.` means a web page or an insecure link was given. `Not a complete GLB ...` means a web page or a cut-off file was given. `Use a self-contained GLB ...` means the model points at external textures or buffers. `Avatar exceeds the 100 MB limit.` means the file is too large. `Avatar download failed: HTTP <status>` means the server refused the request.

If the mouth does not move on one sentence but the voice plays, that sentence most likely had no phoneme data, so it had no cues (see the lip sync section). Check whether phonemizer failed, using `/api/avatar/phones` or the logs. Also check whether the model has `viseme_*` shapes, which the player report shows as `visemes: false` when it does not.

If the mouth moves without matching the words, the page is probably using the letter-based track or the live audio analysis. That is expected when no phoneme data arrives, and it is the designed fallback, not a fault.

If the mouth does not move at all and there is no sound in the Studio, the page may be the watch-only page, which does nothing until its `Start watching · Enable audio` button is clicked. Browsers will not start audio without a click. Also check that the cast has loaded. If voice is off in the Studio, the mouth flaps by design.

If there is no avatar speech in the Studio for Discord voice, check the activity `discord avatar envelope`. A packet that could not be built means the clip was not Ogg Opus or had no decodable audio, and then no packet is sent. Also check that the page is connected to `/api/avatar/live`, since the page reconnects by itself when it drops.

If the message is `Fish Audio returned audio in an unexpected format`, the speech service returned something other than 48 kHz Ogg Opus. That is a voice provider problem, not an avatar problem.

If a voice clip was cut off, the player stopped waiting too soon. The session logs `voice playback` with the message `didn't finish playing`. Compare the clip length with the rough estimate of 6 KB per second, because a clip much longer than that rate suggests the wait was too short for it.

If a picture or song is missing from Discord, first check whether the generation task was cancelled, which shows as `Generation task cancelled`. Then check the task list for `[<name>: error`. A song bigger than 8 MB is saved to the music library but not attached, and the tool says so with `too big to attach on Discord`. Pictures have no size check; if Discord refuses the upload, the job ends as `failed` with Discord's error in its record, and the picture is still in `DATA_DIR\images`.

If a picture showed up in the Studio but not in Discord, that is expected. The Studio gets the picture through the delivery store, and Discord gets it as a message of its own after the reply, through `sendBackground`.

If a picture is showing in the dashboard but the page did not update, the dashboard only polls while the page is visible, and only every three seconds. Reload the page to restart the poll, and check the browser console for failed fetches.

If a download link for a file in the dashboard does not open as expected, note that files are served as `application/octet-stream`. Only images and MP3 audio keep their real type, so that is normal.

If you see `Generation queue is full`, there are already twelve outstanding generation jobs. Wait for one to finish and try again.

If outfits disappeared, the original avatar file has probably changed, so the wardrobe and colours no longer match its SHA-256, and only the original suit (plus any sewn outfits) is listed. Running the install scripts again stamps the wardrobe with the new base's hash (see "installing outfits"), but only does any good if the outfit GLBs were made for that new base. If only the colours went back to the originals, the same cause applies, because a changed base file hides saved colours.

If a slash command says it is not a command or does nothing, the command file is probably missing `data` or `execute`, so `loadCommands` skipped it and printed a warning. Otherwise the command may never have been deployed, so run `npm run deploy`, which needs `DISCORD_TOKEN` and `CLIENT_ID` in `.env`. Server-only deploys show up at once, and global ones can take up to an hour.

If the deploy prints `Missing DISCORD_TOKEN or CLIENT_ID in .env`, fix `.env`. The script exits without contacting Discord until both values are present.

If `/join` says `Fish Audio needs its API key`, the speech provider is Fish and no Fish key is set. (Kokoro and gTTS are always counted as ready, and XTTS gives its own reason instead.) Either add the key or pick a configured local provider in Settings.

If `/join` says `I'm only allowed in ...`, the voice channel is not on the `VOICE_CHANNEL_IDS` list, so the owner needs to add it or join a listed channel.

If a command replies `Something went wrong running that command.`, an exception was thrown inside that command's `execute`. The details are in the activity feed under `/<name>`.

## avatar and delivery troubleshooting / more symptoms / outfit did not change / picture never arrived / receipt but nothing came

More symptoms, what they mean and what to check. Check the code paths named in this guide before saying anything is fixed, and say plainly when something has not been checked.

If you said an outfit is on but Owner cannot see it: `avatar_outfit wear` only selects. Run `avatar_outfit list` and read `report`. `null` means no Studio page has loaded it yet; `ok: false` means it failed and you are back in the original suit; `ok: true` means a page really showed it.

If an outfit's colour does not change on screen: check that a colour was actually saved (`list` shows it under that outfit's `colors`), that you coloured the outfit you are wearing (with no `id`, `color` goes to the active one), and that the garment's materials are ones the page recognises as clothing (names containing `wardrobe_fabric`, `wardrobe_dress`, `wardrobe_swimsuit` or `avaturn_look_`). Sheen only shows on materials that have a sheen layer. If the Studio's colour pickers are greyed out, the page thinks you are wearing a `Custom avatar` (a downloaded model, or a model with no `outfit` tag, which includes sewn outfits); the tool can still save colours for any outfit in the list.

If a design will not save: the errors say why. A name under 2 characters, a base outfit that is not installed, or no colour of its own (a design must change the fabric or the sheen). Saving a design never puts it on; use `wear` with its `design-<n>` id.

If a generation tool returned `[<tool>: queued]` and nothing came yet: that is normal, the job runs in the background. Do not call the tool again. Use `background_task` with `action: status` to see the job, and its id to read the report. Two jobs run at once and the rest wait, so a third picture waits for one of the first two.

If a job is missing after a restart: generation jobs live in memory and do not resume. Its report file in `DATA_DIR\tasks` shows how far it got only if it finished before the restart. Start the request again.

If Owner cancelled a picture and was still charged: cancelling stops delivery, not a request already sent to the provider.

If the dashboard shows old pictures again after a reload: each page starts reading the delivery store from the beginning for its conversation, so stored results are shown again. Nothing was regenerated.

If a delivery bubble appears with no picture, only `Your file is ready.` and a link: the record was a `file` kind, sent through `sendBackground` by a helper, not an image. Files download as `application/octet-stream` by design.

If a picture of you came back as a general picture, or the tool refused: the routing check in `src/image-pipeline.js` decided the request was for a picture of you (use `generate_self_image`) or for a general picture (use `generate_image`). Follow the error's instruction; it names the right tool.

If `generate_self_image` says it saved a new reference: you had no identity reference, so this picture became your face for later pictures. Tell Owner so he can replace it with the `look` tool if he does not like it.

If a song is in the library but not in Discord: it was over 8 MB. Offer to play it in voice.

If `send_file` refused a file name: it only writes new text files. For a picture, song, zip, PDF or other real file on disk, use `files` with `action: send` and its path.

If a voice-call picture did not appear: in a call, files go to the call's text channel. If the call was started without a text channel, picture and music tools were not available there at all.

If the hosted watch-only viewer stopped updating: check that `DATA_DIR\cloud-viewer.json` still has an HTTPS `url` and a `publisherKey`, and look for `cloud viewer` errors (only one is logged per minute). A viewer that never clicked `Start watching · Enable audio` stays silent.

If a slash command change does not show: two steps are needed, a bot restart (the command files are loaded once at startup) and `npm run deploy` (Discord's copy of the definitions). A guild deploy shows at once; a global one can take up to an hour.

If `/memories notes` shows `/undefined` in the threads header: that is a known display bug in `src/commands/memories.js` (it reads a constant `scratchpad.js` no longer exports), not missing data.
