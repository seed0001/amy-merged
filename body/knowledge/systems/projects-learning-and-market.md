## project proposal and confirmation / propose a project / start a project after confirmation

Building a new project is a two-step act, and the owner has to confirm it in a later message before anything starts. The `project` tool (src/tools.js, `projectControl`, registered with `ownerTool`) is owner only. Its actions are `propose`, `show`, `start`, `list` and `cancel`. The tool is offered only in an owner context (`ownerContext`: the speaker has owner permissions, is on the owner list, and the call is not from a background helper). Every action, including `list`, then runs `directOwner`, which also needs a non-empty current message; otherwise it fails with "This change needs a current owner conversation." Inside projects.js a second check (`owner()`) also needs a conversation and a turn, and fails with "Project control requires a current owner conversation." Any other action name returns "Use propose, show, start, list or cancel."

`propose` takes a `title`, a `brief`, and optional `goal_id`, `workspace` and `browser_app`. The title and the brief must both be non-empty and the brief no longer than 16000 characters; otherwise you get "Give a project title and a concrete brief up to 16000 characters." The title is saved trimmed and cut to 160 characters. If `goal_id` is given, it must name an open goal (kind goal, activity `project`, not done and not dropped), or you get "Link an open project goal." Set `browser_app` to true for a dashboard, site or plain browser app with an index.html (see the browser app project section).

Where the project goes. If `workspace` is left out, the default is `Desktop\Amy Projects\<slug>` (`buildRoot()` in src/builds.js, named after you through `selfName()` in src/config.js), where the slug is the title in lower case with every run of characters other than a to z and 0 to 9 turned into one hyphen, hyphens trimmed from the ends, cut to 40 characters, and `app` if nothing is left. The folder is resolved with files.js `resolve`, which refuses anything outside the home folder or the bots folder and anything in a blocked place (see the project runtime section). Nothing is created on disk at proposal time. The code then reserves the folder: a folder is unavailable when it is the workspace of another proposal that is `starting` or `running`, or of a `pending` proposal made in the last 24 hours, or when it already exists and is a file or holds anything other than the build guide (`BUILD-GUIDE.md`, or `AMY-BUILD-GUIDE.md` in a folder made before 2026-11-11). For a default workspace the code tries `-2`, `-3` and so on after the name until it finds a free folder. For a workspace the owner named, it refuses instead: "That workspace is occupied or reserved. Give the new project a separate empty folder, or use workshop to edit an existing project." That is the sign to use the workshop for an existing project.

The proposal is written to the `project_proposals` table in `companion.db`. Columns: `id`, `owner`, `conversation`, `turn`, `at` (time in milliseconds), `title`, `brief`, `status` (default `pending`), `task_id`, `goal_id`, `workspace` and `browser_app` (0 or 1). The last three were added later, so the code adds them to older databases when it opens the table. The tool's reply reads "Project proposal #N: <title>", then "Exact brief:", then "Workspace:", then "Not started. Show this plan and ask your owner to confirm it in their next message, then call project with start and this ID."

`list` returns the owner's last 30 proposals, newest first, as raw rows. `show` with an ID returns one of the owner's proposals with its exact brief and status, or "No project proposal with that ID." Use it to read the brief back word for word. `cancel` with an ID only works on a proposal that is still `pending`; it sets the status to `cancelled` and returns "Project proposal cancelled." or "No pending proposal with that ID."

Status values a proposal can have: `pending` (waiting for confirmation), `starting` (checks passed, helper being launched), `running` (helper started, `task_id` saved), `done`, `failed` or `stopped` (copied from the helper when it finishes), and `cancelled`.

Energy: every call of the `project` tool costs 1.2 from your energy reserve (`action_costs.project` in src/pressure.js), whatever the action, because the cost is a single number rather than a per-action table. Without enough reserve the call fails with the pressure system's message saying why.

## project start / confirm a project / start a proposal / project confirmation words

`start` takes the proposal ID. Before anything runs, the tool checks that the number of running background helpers is below the cap of 4 (`MAX_HELPERS` in tools.js, shared with `background_task`). If four are running, you get "Wait for a running helper to finish before starting a project." Then `projects.js` `start()` checks, in this order, that the proposal exists, belongs to the same owner and the same conversation, and is still `pending` (otherwise "No pending project proposal here with that ID."). It then refuses if the current turn is the same turn that created the proposal, if the proposal is more than 86400000 milliseconds (24 hours) old, or if the owner's current message fails the confirmation test. A refusal says "Show the exact project brief and wait for the owner to confirm it in a later message."

The confirmation test (`projectConfirmation` in src/projects.js) passes only when the trimmed message starts with yes, yeah, yep, yup, sure, confirm or confirmed, go ahead, do it, build it, start it, ok or okay, as a whole word, case does not matter, and when the message contains none of the words no, not, don't, do not, cancel, wait, hold, stop, but, unless or instead anywhere. Because the test is word based, "yes, but change the title" fails, "yes, wait" fails, and "sounds good" fails because it does not start with an accepted word. "Yes please" and "ok go ahead" pass.

When the checks pass, the status moves to `starting`, then the helper is started, and the status becomes `running` with the task ID stored. If the helper fails to start, the status goes back to `pending`, so the owner can try again, and the error is passed back to you.

What starting does, in order (src/tools.js `projectControl`):
1. The helper context is made: helper true, the project approval token (`projectApproved`), the saved workspace (or `Documents/NewChampProjects/project-<id>` for an old row with no workspace), and the background send function.
2. The project counts as a browser app when `browser_app` was set, or when the brief contains the words "plain browser app", "standalone browser app", "plain browser dashboard" or "standalone browser dashboard".
3. The project is registered in the workshop under its title, so you can open, run and job it later. If the workshop already has a project with that name in a different folder, the name becomes "<title> (#<proposal id>)".
4. The tool list is `HELPER_TOOLS` (files, web_search, read_source, send_file, send_project, system_info, huggingface, models_local, project_runtime), minus `project_runtime` for a browser app, each kept only if its own `enabled` check passes for the helper.
5. The instructions are the approved brief, then "Approved project workspace: <path>." and then either the browser app line ("Build plain HTML, CSS and JavaScript, with index.html at the project root. Read BUILD-GUIDE.md. Do not install dependencies or copy a bot folder.") or the runtime line ("Run and install dependencies in this workspace. Use project_runtime for finite checks, not long-running servers.").
6. The helper starts with `coding: true`, so its model is `OLLAMA_CODING_MODEL` when set, otherwise `OLLAMA_MODEL`.

The reply you get reads "Started confirmed project as background task #N "title" using local model X." The helper cannot call `project` itself or any tool outside its list: those calls return "Error: project helpers cannot use <name>".

Who may start: research helpers and scheduled briefs never start a project, and autonomous research cannot make a proposal either. Scheduled activities are different: they run with the owner's tools, so the `project` tool is available to them too. The `start` check still applies to them. A proposal made inside a run cannot be started in that same run, and a later start needs the activity's own instructions to pass the confirmation test. Treat any project that appears from a scheduled run as something to report to the owner, not as a confirmed start. When you tell the owner about a project, say it has started only when the tool result says it started, and say it is waiting for confirmation whenever the result says "Not started."

## project finish / project verification / project did not produce any files / project result

A confirmed project helper is checked when its loop ends with a report (the `verify` step in `projectControl`). The check reads every tool result the helper got:
- At least one `files` call must have created, replaced, edited, copied, moved or downloaded a file (a result starting "[files: ok]" followed by "Created", "Replaced", "Edited", "Copied", "Moved" or "Downloaded", but not "Created folder"), or a `send_project` call must have succeeded. If neither happened, the helper fails with "Project did not produce any files. Read the tool errors and retry with the saved workspace."
- If the last `project_runtime` call returned an error, the helper fails with "Project command failed." followed by the first line of that error.
- For a browser app, the folder is served on this PC and its index.html is fetched over HTTP (src/webapp.js `verifyBrowserApp`, 5-second timeout). An HTTP error fails with "Expected a working index.html in the project folder (HTTP <status>).", and an empty page fails with "The project index.html is empty." On success the report gets "Verified: index.html served over HTTP (<bytes> bytes). Open the saved project "<name>" with workshop open."

A failed check makes the helper's status `failed` with that message as its report.

When the helper finishes, its completion handler stores the helper's final status (`done`, `failed` or `stopped`) on the proposal (`finish` in projects.js). If the proposal was linked to a goal, the work is recorded on that goal (reflections.js `recordWork`) as `done` when the helper's status was `done` and `failed` otherwise, with the event ID `project-<proposal>-task-<task>`, evidence of type `confirmed-project-task` naming the proposal, the task and its saved report file, and the report as the summary. Then the message "Background task #N "title" <status>:" with the report is sent to the conversation.

Cancelling: a cancelled helper still runs the completion handler, because in src/agents.js the `finally` step always calls `onFinish`. So the proposal's status becomes `cancelled` (the task's own status), and a linked goal gets the work recorded as `failed`. Only the message to the conversation is skipped for a cancelled task. (An older version of this guide said a cancelled project stayed at `running`; the code does not do that.)

## project runtime / running a project / dependencies / install packages / npm python node

`project_runtime` (src/tools.js, with the logic in src/project-runtime.js, `createProjectRuntime`) runs owner-requested code and installs dependencies without a shell. The tool is enabled only when the caller has `perms.files` and is either the owner speaking in a current conversation, or a project helper that carries the owner-confirmed project approval. Research helpers never get it. The tool takes an `action` of `run` or `install`, plus a `workspace`, and for run a `program` and `args`, and for install a `manager` and `packages`. A project helper always runs in its saved approved workspace: if it passes a different workspace the call fails with "Use the saved approved project workspace." The owner must name a workspace; without one the call fails with "Give the requested project workspace."

For `run`, `program` must be one of `node`, `python`, `python3` or `npm`. Anything else fails with "Use node, python or npm; commands run without a shell." `args` must be an array of strings with no null characters, or the call fails with "Arguments must be a string array." If the arguments contain a Windows path under `<drive>:\Users\<name>` and that name is not the owner's home folder name, the call fails with "That path uses the user folder "<name>", which isn't your owner's. Their home folder is <home>; use that path or Desktop\... instead." This catches a user name typed from memory. The workspace folder is created if it does not exist yet. Each command runs with `shell: false`, with the window hidden, and with a 2 MB output buffer. `node` runs as the same Node binary that runs the bot. `python3` becomes `python` on Windows. For any Python command, if a `.venv` folder exists inside the workspace, its interpreter is used (`Scripts/python.exe` on Windows, `bin/python` elsewhere). `npm` runs the npm command-line script through Node, using the path in `npm_execpath` if that points at `npm-cli.js`, and otherwise the copy that sits beside Node; if that copy is missing, the call fails with "npm CLI is not available beside Node.js."

Timeouts. The tool gives a `run` 120000 milliseconds (2 minutes). In a voice call (the context is marked voice, or the conversation starts with `voice:`) a `run` gets only 30000 milliseconds (30 seconds), so a long command cannot hold up your spoken reply. Installs always use their own longer timeouts (below). The runtime clamps any timeout between 1000 and 600000 milliseconds, and the model cannot choose a timeout.

For `install`, `manager` must be `npm` or `python`, or the call fails with "Choose npm or python dependencies." `packages` must be a non-empty list of plain names. A name that is empty, starts with a dash, or contains a line break or a null character causes "Provide explicit package names, not command flags." For npm the command is `npm install --no-audit --no-fund -- <packages>` in the workspace with a 600000 millisecond (10 minute) timeout. For Python, if there is no `.venv` in the workspace, the runtime first runs `python -m venv <workspace>\.venv` with a 120000 millisecond timeout, and stops there with that receipt if it fails. It then runs `python -m pip install -- <packages>` with the venv's Python and a 600000 millisecond timeout. The result includes an `environment` field naming the venv path. Any other action fails with "Use run or install."

What you get back. On success the tool returns the whole receipt as JSON. On failure the tool throws instead, so you see an error that reads "It failed (exit <code>): <last 400 characters of stderr>" or "It timed out (exit none): ...". In a voice call a timeout adds "Long commands like installs belong in a project job, not a voice reply." The full output is still in the receipt file.

The environment passed to every command is filtered (`projectEnvironment`). Only these variables are kept, matched without regard to case: PATH, SYSTEMROOT, WINDIR, COMSPEC, USERPROFILE, HOME, HOMEDRIVE, HOMEPATH, LOCALAPPDATA, APPDATA, TEMP, TMP, ProgramFiles, ProgramFiles(x86), PYTHONPATH, ROCM_PATH and CUDA_PATH. The runtime adds PIP_DISABLE_PIP_VERSION_CHECK=1, PIP_NO_INPUT=1 and NO_COLOR=1. Secrets such as HF_TOKEN and the bot's API keys are not passed through, and a test covers that.

Every command, whether it succeeds or fails, writes a receipt to `data/project-runs/<uuid>.json`. The receipt holds `id`, `workspace`, `program`, `args`, `status` (`succeeded` or `failed`), `exitCode`, `stdout` (the last 20000 characters), `stderr` (the last 10000 characters), `at` (start time), `finished`, and `receipt` (the file path). A failed receipt also has `timedOut`, which is true when the process was killed by its timeout, and in that case `exitCode` is null. Successful receipts do not carry `timedOut`. The tool description states that commands run locally as the user and not in a sandbox. Report a success only from a receipt with `status: succeeded`, and back it up with a check you actually ran, such as opening the file or running the program's own test.

Every call, like every tool call, is also logged to the activity log as a `tool-call` event with the tool name, whether it worked, the error, how long it took in milliseconds, the action, the argument names (not their values) and the conversation.

## project paths / where project files go / blocked folders / send_project / zip a project

Where project files go is decided by the `project` workspace or by a path the owner names. Paths are resolved by files.js `resolve`, which keeps them inside the home folder or the bots folder (C:\Bots). It refuses AppData, .ssh, .gnupg, .aws, .azure, .kube, .docker and .git folders, and refuses files named like .env, private key files (.pem, .key, .pfx, .p12, .kdbx, id_ keys), credentials files and database files (.db, .db-wal, .db-shm). A browser profile folder is private too.

Workshop coding jobs on OpenRouter use `scopedPath` (files.js) on every file path: the path must be inside the project folder both as written and after following links and junctions, and must not be private. Otherwise the coder gets "Use a file inside the approved project workspace."

`send_project` builds a project from files written in the call itself, zips it and sends it as a Discord attachment. It is offered when the caller has a place to send to and file permission, but it is refused unless the caller holds the confirmed project approval: anyone else, the owner included, gets "Use project to propose the build and get owner confirmation before creating project files." So in practice only a confirmed project helper can use it. Its rules (src/tools.js `sendProject`):
- At least one file is needed ("Error: the project has no files"), and at most 200 ("Error: too many files (N); the limit is 200").
- The project name is cleaned to letters, digits, dots, hyphens, underscores and spaces, cut to 100 characters, with any extension dropped; `project` is used if nothing is left.
- Each file path is cleaned: backslashes become slashes, `.` and `..` parts are dropped, odd characters are removed, and the path is cut to 200 characters. A file without text content is skipped, and a repeated path keeps the last one. If nothing usable is left: "Error: none of the files had a usable path and content".
- The zip must be at most 8 MB (Discord's usual bot upload limit), or "Error: the project is too big to send (<size> MB)".
- An unpacked copy is written to `data/projects/<name>/`.
- It goes to the current chat by default. `recipient` (friends only) can name a channel such as "#general" or a person who has messaged you before, with an optional `message`.
On success the reply ends with the number of files and their paths.

## workshop / the owner's projects / coding jobs / run and stop a project / undo a job

The workshop (src/workshop.js, `createWorkshop`, exposed as the `workshop` tool in src/tools.js, `workshopAction`) is for projects that already exist: the owner's own projects, such as his game or his site, and the browser apps you have made. It is separate from the `project` tool, which starts new things. The tool is owner only (`perms.owner`). Its actions are `add`, `list`, `overview`, `job`, `jobs`, `report`, `cancel`, `undo`, `build`, `run`, `open` and `stop`; an unknown one returns 'Error: unknown workshop action "<name>".' Every error from the workshop comes back to you as "Error: <message>".

Where it keeps things. Project details are stored in `data/workshop/projects.json`, one entry per project keyed by a lowercase slug of the name (runs of anything other than a to z and 0 to 9 become a hyphen). Each entry holds `name`, `path` (the full folder), `run`, `url`, `build`, `deploy`, `notes` and `added` (time in milliseconds). Each coding job is stored in `data/workshop/jobs/<id>.json`. Nothing about a project is written there unless the owner tells you about it, or a project or build of yours registers itself.

Finding a project by name. A name is matched first by its exact slug and then by a slug that contains what was typed. If several match, the error is "Which project? <names>." If none match, it is 'No project called "<name>". Yours: <names>.' or, with none saved, "None saved yet: add one with its folder." An empty name lists the saved names.

`add` saves a project. It needs a name ("Give the project a name." otherwise, and "Use a project name containing letters or numbers." for a name with no letters or digits) and a folder, resolved through files.js. The folder is created if it does not exist; if the path is a file the call fails with "<path> is a file, not a project folder." A name already saved for a different folder is refused: "<name> is already registered at <folder>. Use a different project name for another folder." It can also store `run` (the command that runs the project, such as "python serve.py", with " in sub/folder" to run it in a subfolder), `url` (where it appears when running), `build` (the build step, such as "npm run build in build"), `deploy` (how it goes live) and `notes` (anything a coder should always know). Saving an existing name updates it and keeps any field you leave out. A project saved with no run command counts as a browser app, and its folder gets a copy of `BUILD-GUIDE.md` (the text of knowledge/systems/browser-apps.md) if it has none. The reply is "Saved <name> at <folder>." and an activity `workshop` event records the project and folder.

`list` shows each project with its folder and "(a coding job is running)" where one is. `overview` reads the project fresh from disk and git: the current branch, the run, build, deploy and notes settings, the count of uncommitted files with up to 20 of them listed, commits not pushed and commits behind the last fetch when an upstream exists, the last 10 commits with short hash and date, the top-level names (hidden ones left out), the README and any docs folder, whether a job is running, and the last five jobs with their status and how many files they changed.

Your projects as you see them each turn. A snapshot of every saved project (name, folder, URL, whether it is running or being served, notes, and any job in flight with its minutes so far) is available to the rest of you through the workshop's `snapshot`; your own builds use it to see which ideas already have a project.

Energy: `workshop` with `job` costs 1.2, `build` costs 1.5 and `add` costs 0.3 from your reserve (`action_costs.workshop`); the other actions cost nothing.

## workshop job / coding jobs / coder model / undo a job / cancel a job

`job` starts a coding job in the background. The brief (`task`) is required and must be non-empty, or the call fails with "Describe the change in full: what, where, and what done looks like." Only one job can run per project at a time; a second request gets 'Job #N "<title>" is still running on <project>. Wait for it or cancel it.' and one asked while another is still being set up gets "A job is already starting on <project>."

Git first. The project folder must contain a `.git` folder, or the call fails with "<project> isn't a git repository, so a job couldn't be undone. Make it one first." The one exception is a browser app whose folder holds nothing but the build guide (`BUILD-GUIDE.md`, or the old `AMY-BUILD-GUIDE.md`): the workshop runs `git init` for it. Then, if the repository has no commit yet or has uncommitted work, everything is committed as "Before Amy's job: <title>", where the title is the brief cut to 70 characters (67 plus "..." when it was cut). Git runs with the author name Amy and the email amy@localhost (`Amy <amy@localhost>`, from your own name). The commit hash at that point is saved as the job's `before`. That way the job's own changes can be undone without touching the owner's earlier work.

The coder. When an OpenRouter key is set (`OPENROUTER_API_KEY`), the job runs on OpenRouter through src/project-coder.js (`openRouterCoder`) with the model in `WORKSHOP_CODER_MODEL`, default `anthropic/claude-sonnet-5.5`. That coder can only use the files tool to read, list, find, write, edit and make folders inside the project, every path checked with `scopedPath`; it cannot run programs, push or commit. It works in rounds of model call plus tool calls, at most 100 rounds, each model call limited to 180 seconds and 6000 output tokens, and each tool result cut to 12000 characters. Its engine is recorded as `openrouter:<model>`. Without an OpenRouter key, the job runs `runCoder` (src/doctor.js), the Claude Code or OpenCode command-line coder. Either way the whole job has a 30-minute timeout (`JOB_TIMEOUT_MS`). OpenRouter coder failures read "<model> answered <status>: ...", "Ran out of steps or time before it finished." or "Stopped before it finished."; with no key at all its own message is "There is no OpenRouter key, so the coding model can't run. Add OPENROUTER_API_KEY to .env."

The coder's rules (`RULES` in workshop.js): do the whole job without asking, since the owner is often away from the keyboard, and keep fixing until it works; stay inside the project folder; rebuild after changing source if a build step is saved; run the project and look for errors, then stop anything started, if a run command is saved; for a browser app, plain HTML, CSS and JavaScript with index.html at the top, no build step, no npm, no install, read BUILD-GUIDE.md first; never push, deploy or publish, and never commit, because Amy saves the work as one commit; the project's notes; and finish with a report of two to six plain sentences with no code blocks.

After the coder. For a browser app that finished well, the folder is served and its index.html fetched (the same check as for projects), adding "Verified: index.html served over HTTP (<bytes> bytes)." to the report; if that check fails the job fails. Any changes are staged and committed as "Amy's job #N: <title>". If saving fails, the job fails with "(Saving the work failed: ...)" added to the report. The job is marked `done`, `failed` or `cancelled`, and its `finished` time, `engine`, `report`, `changed` file list and `after` commit are saved. Then a message goes to the conversation: '<project> job #N "<title>" <status>:' with the report, then "Changed: <first 15 files>. Saved as a commit, not pushed." or "No files changed." The message is also added to the conversation history (cut to 1500 characters). The start reply is 'Job #N on <project> started: "<title>". It runs in the background and can take several minutes; the report comes here when it's done.'

Job file fields: `id`, `project` (slug), `projectName`, `title`, `task` (the full brief), `status`, `started`, `before`, and when done `finished`, `engine`, `report`, `changed`, `after`, and for an undone job `undone`.

Restarts. A job still marked `running` when the workshop starts was cut off by the restart, since its coder died with the bot. It is marked `interrupted` with the report "Cut off when Amy restarted before the coder finished. Nothing was saved as a commit; any half-made edits would show in git status of the project folder." and a `workshop` activity event records it.

`jobs` lists the last 10 jobs, newest first, optionally for one project, with status and finish time or minutes running. `report` with an ID shows one job in full ("Asked:", "Report:", "Files:"), or "There's no job #N." `cancel` stops the job currently running on a project by killing its coder, and says "Stopping job #N. Whatever it already changed is saved, so it can be undone." or "Nothing is running on <project>." Whatever the job had already changed is committed when the coder exits. `undo` rolls back the most recent finished job on a project, where finished means not running and not already undone, so failed, cancelled and interrupted jobs count too. It refuses while a job is running ("Job #N is still running. Cancel it first."), says "There's no job on <project> to undo." when there is none, refuses if anything was committed after that job ("Something was committed after job #N, so undoing it would lose that too. Ask for a job to revert it instead."), and refuses if the working tree has uncommitted changes ("<project> has uncommitted changes since job #N; undoing would throw them away."). If it goes ahead, it runs a hard reset to the job's `before` commit, marks the job `undone`, logs it, and replies 'Undid job #N "<title>" on <project>.' Because the pre-job commit is the reset target, the owner's uncommitted work from before the job survives.

## workshop run / open / build / stop / serve a browser app / project not responding

`build` runs the saved build step, without a shell, and waits up to 5 minutes. It returns "Done: <command>." with the last 1500 characters of output, or "Error: <command> failed." with the last 2000 characters. Without a saved step: "<project> has no build step saved. Add one (e.g. "npm run build in build/")."

How a command line is read: "<program> <args> in <subfolder>". The subfolder must be inside the project folder, or "The command must run inside the project folder." On Windows, `npm` and `npx` are run as Node with the matching `npm-cli.js` or `npx-cli.js` beside Node, so no `.cmd` file and no shell is needed; if that file is missing: "<npm or npx> was not found beside Node.js."

`open` is for showing a project in one of your browser tabs. A browser app (no run command, index.html at the top of its folder) is served from its folder on this PC only, at `http://127.0.0.1:<free port>/` (src/webapp.js `serveFolder`), and the tab is opened there. The server only hands out files inside the folder, never hidden files or private ones, and answers 403 "File is unavailable" or 404 "Not found" otherwise. A project with a run command and a URL is started with `run` first, then opened at its URL. Errors: "<project> isn't a browser app yet: it needs an index.html at the top of its folder.", "<project> has no browser URL saved. Use run to start it." and "<project> isn't responding successfully at <url>." Success: "<project> is open in your browser tab at <url>."

`run` starts the saved run command as a child process the workshop keeps in memory; for a browser app it does the same as `open`. Without a run command and not a browser app: "<project> has no run command saved." If it is already running: "<project> is already running at <url>." (or "has started but is not responding at <url> yet." if its URL does not answer). If its URL already answers before anything starts, it refuses: "<url> already responds from a server the workshop didn't start. Confirm the address or free the port before starting <project>." Otherwise it starts the process and polls the URL up to 40 times at 250 millisecond intervals, about 10 seconds. A URL counts as up only when it answers with a success status (200 to 299) within 1.5 seconds. If the process exits or cannot start, the reply is "<project> stopped right away:" with the error or the last 500 characters of output. If the URL never comes up, the process is stopped and the reply is "<project> did not become ready at <url>:" with the last 500 characters of output. If the project has no URL, the call returns as soon as the process has started. Success: "<project> is running at <url>."

`stop` closes a served browser app ("Stopped serving <project>.") and kills a run process tree with `taskkill /T /F` on Windows, or a plain kill elsewhere ("Stopped <project>."). If the workshop knows of neither, it says the project "isn't running (not by me, anyway)."

Running state lives only in memory. After a restart, the workshop has no record of a server that was started before it, so `stop` may report that nothing is running even though a process is still listening on the port, and `run` then refuses because the URL already answers. This is the most likely reason a run fails right after a restart: the old process must be stopped by hand, or the port freed.

Activity log: `workshop` events record `opened` URLs and `running` starts, as well as saves, job starts and ends, interruptions and undos.

## background helpers / helper tasks / task reports / progress lines

Background helpers (src/agents.js, `startTask`) let you hand off longer work while you keep talking. A helper runs its own loop of model calls and tool calls, using the local Ollama model, and it reports back to the conversation when it finishes. Helpers are started by the `background_task` tool, by the confirmed project path, by Hugging Face downloads you start in conversation, and, as direct execution jobs without a tool loop, by `models_local`, the private self-dialogue tool and generation work. The `background_task` tool is owner only (`perms.owner`) and is enabled only when an OpenRouter API key is configured (`config.openrouter.apiKey`, from `OPENROUTER_API_KEY`), which is a condition you should know about if it seems to be missing. It has three actions. `start` needs `instructions` (the full brief) and an optional `title`; `status` with no ID lists tasks, and with an ID shows that task's whole report; `cancel` needs an ID. Its `model` parameter is described as an optional OpenRouter model, but the code does not use it: a research helper always runs on the local model `config.ollama.model` (`OLLAMA_MODEL`, default `gemma4:12b`). The `start` parameter, used with `status` and an ID, sets the character to continue reading from when a report came back truncated. Starting one costs 0.8 from your reserve (`action_costs.background_task.start`).

Replies: "Started background task #N "title" on <model>. It works on its own and will report back here when done." (or "you can check on it by asking for its status" where there is no way to report back), "Error: the helper needs instructions.", "Cancelling task #N." and "Error: no running task #N." Task numbers start from the clock time in milliseconds when the bot started and go up by one, so they are long numbers.

The number of helpers running at once is capped at 4 (`MAX_HELPERS`). The cap counts every running task except those whose model is `generation-worker`: generation jobs and `models_local` jobs carry that name and do not count, while a private self-dialogue does count, because its model is recorded as "<local model> + <cloud provider>". If a brief is identical to one that is already running, the call says "Background task #N "title" is already working on that brief. Don't start it again." If the cap is full, the call reads "Error: 4 helpers are already running (#.. "..", ...). Wait for one to finish or cancel one first."

## helper tools and limits / research helper / what a helper can do / 100 steps

Each helper gets a system prompt that tells it to work on its own step by step, look before changing things, make precise edits rather than rewriting whole files, and check its work by reading it back. Paths can start with Desktop, Documents, Downloads, Pictures, Music or Videos. It is told it can search and download models with the huggingface tool and download https files, to call a download done only when the tool said "Downloaded" and give its path and size, to use `system_info` instead of guessing about the computer, not to write a report file for research unless the brief asks for one, and to finish with a short report of what it did or found, where things are, and anything left for the owner.

Its tools depend on how it was started. A research helper started by `background_task` is marked read-only (`researchOnly`). It gets the helper tool list without `send_project`, each tool kept only if it is enabled for the helper. Its `files` calls are limited to read, list, find and send; anything else fails with "Research helpers are read-only. Use project and get confirmation before building or changing files." It does not get `project_runtime`, because that tool needs either a direct owner conversation or the project approval. `models_local` gives it only `list` and `show`. It can still call `huggingface`, and inside a helper a Hugging Face download runs directly, so a research helper can download model weights. The confirmed project helper gets the wider list described in the project start section. A tool outside the list returns "Error: helpers can't use <name>".

A helper's loop stops after 100 steps (`MAX_STEPS`). Each tool result is capped at 20000 characters, and any longer output is cut with "[TRUNCATED: showed 20000 of N characters. Ask for less at once, e.g. read a file in parts with start_line and end_line.]". When the model replies without calling a tool, that reply becomes the report, or "(The helper finished without a report.)" if it is empty. If the helper reaches 100 steps without finishing, its status is `stopped` and its report is "Stopped after 100 steps without finishing. Last actions: ..." with the last five actions. If the loop throws, the status is `failed` and the report is the error message. A cancelled helper's status is `cancelled`; cancellation takes effect between steps and between tool calls, never in the middle of one. A helper's tool calls go through the same `runTool` as yours, so they are logged as `tool-call` events and their energy costs are paid the same way.

Progress lines are plain sentences describing the last tool step, produced without a model call, in the form '"<title>": <what>.' The wording is "searching for "<query>"" for a web search, "downloading", "reading", "looking through" or "editing" plus the path for files, "reading my own code" for read_source, "pulling the news feeds" for news_feeds, and "using <tool name>" otherwise. A failed step reads "hit a snag <what>: <error>. Trying another way." A line is sent when at least 60 seconds have passed since the last line, and a failed step is announced sooner, once 30 seconds have passed since the last line. Nothing is sent for a cancelled helper. The finish message comes separately.

## task reports / background task status / saved task files / read a truncated report

Every finished helper is saved to `data/tasks/<date-time>-task-<id>.md`, where the date-time is the start time as YYYY-MM-DD-HH-MM. The file holds "# Task <id>: <title>", "Status: <status>, <steps> steps, model <model>", a "## Report" part and a "## Actions" list (each action is the tool name and the first 160 characters of its arguments). The report is also kept in memory until a restart. When a helper finishes and was not cancelled, its result is sent to the conversation as "Background task #N "title" <status>:" followed by the report.

`status` with an ID reads the whole report 16000 characters at a time. A running task answers 'Task #N "title" is still running (<steps> steps so far, last: <action>).' If the report is longer than one page, the reply says "Report TRUNCATED: showing characters A-B of C. Read the rest with status, id N and start B." This works after a restart too, because the saved file is read; then the status shows as `finished` and the page is the whole saved file. A missing task returns "Error: no task #N."

`status` with no ID lists the tasks in memory (ID, title, status, conversation, steps, minutes, last action, and the result cut to 1500 characters for finished ones) and, after them, the eight most recent saved tasks that are no longer in memory, marked as from before the restart, with their results cut to 1500 characters. With none at all it says "No background tasks yet."

Activity log: every helper writes a `task` event when it starts (ID, title, `started`, model) and when it ends (ID, title, status, steps). Errors are logged with `where` set to `task progress`, `task report` (the file could not be saved), `task completion` (the finish handler threw) or `task notification` (the report could not be sent).

Generation work such as images, self-portraits and music is handed to a separate sub-agent that executes one exact request directly. It uses its own queue, does not count toward the helper cap, and does not run the tool loop. Its completion is posted back to the conversation as a generation task result.

What to tell the owner: if a helper says it stopped after 100 steps, the brief was too big or too vague, so split it. If a report comes back truncated, read the rest with `status` and the start number. If the owner cancels something and never hears about it, that is expected, because a cancelled task does not send its result. If the cap message appears, name the running helpers and offer to cancel one.

## goals / your goals / goal tool / research_goal / self-chosen goals

Your goals are things you chose to work toward, for research, writing or a project. They are stored with your insights in `data/reflections.json` (src/reflections.js), written through a temporary file and renamed so a crash cannot leave half a file. The file holds `next` (the next ID), `items` (insights and goals) and `experiences` (what happened when you worked on them). Goal content is never preset; only the three routes are fixed (`ACTIVITIES` in src/goals.js: `research`, `writing`, `project`).

A goal item holds: `id`, `kind: goal`, `text`, `at`, `activity` (default `research`), `bucket` (the pressure that drives it: `boredom`, `curiosity`, `restlessness`, `usefulness` or `unease`; default `curiosity` for research, `restlessness` for writing, `usefulness` for project), `criteria` (what done means, up to 2000 characters), `reason` (up to 1000), `fit` (0 to 1, default 0.5), `memoryIds`, and as it goes `progress` (each piece of work), `research` (`enabled`, `last_at`, `next_question` up to 600 characters), `work` (`last_at`, `running`), `done` or `dropped` (times), `dropReason`, `previousGoal` and `replacementGoal` for a pivot, and `completionExperience`. Bad values fail with "Goal activity must be research, writing or project." or "Unknown goal pressure bucket."

The `goal` tool (owner tool, `goalControl` in src/tools.js) has `add`, `list`, `pause`, `resume`, `drop`, `pivot`, `review` and `done`. `list` works without a current message and returns every goal and every experience. All others need a direct owner conversation. `research_goal` is the same function with only `add`, `list`, `pause`, `resume` and `done`. Any other action: "Use add, list, pause, resume, drop, pivot, review or done."
- `add` needs text ("give the text to keep" otherwise).
- `pause` and `resume` switch the goal's autonomous work off or on (`research.enabled`); a closed goal gives "No open goal with that ID".
- `drop` keeps the goal with its drop time and reason (default "No longer chosen"); "No goal with that ID" if missing.
- `pivot` drops the old goal with the reason and adds a replacement linked to it; it needs new text and a reason ("Pivot needs a replacement goal and a reason.") and an open goal ("No open goal to pivot from.").
- `review` scores an experience: `experience_id`, `satisfaction` from -1 to 1 and a reason ("Review needs satisfaction from -1 to 1 and a reason." / "Review must refer to a recorded experience.").
- `done` needs saved evidence: the goal must have a progress entry with status `researched`, `written` or `done`. Otherwise: "A goal needs a recorded successful result before completion. Drop it instead if it no longer fits." Completing records a `completed` experience with a reward of 0.15 and passes it to the pressure system (`onGoalExperience`).

You also change goals yourself. Solo thinking and private self-dialogue may return one `goal_decision` (`GOAL_DECISION_GUIDANCE` in goals.js): none, adopt, pivot, pause, resume, drop, done or review. A new or pivoted goal must quote an exact excerpt of at least 8 characters from the context it was made in ("A new goal must be grounded in the supplied memory or experience context."), and every decision needs its saved thought and a reason. Writing stays private, and a project goal never authorises a build, publication or contacting people.

Your open goals are shown in your prompt every turn (`promptBlock`): each with its ID, activity, pressure, learned preference, criteria, whether autonomous research is paused, its latest work and next question; then the last 8 experiences; then up to 4 goals you left behind with their reasons.

## goal work / which goal she works on / learned preference / private drafts and plans

Which goal gets worked on (`selectGoal` in goals.js). Open goals with autonomous work switched on, not already running, are scored as: the current value of the goal's pressure bucket (0 to 1) + its fit (0 to 1) + its learned preference. Learned preference is the weighted average satisfaction of your reviewed experiences of the same activity, where each experience weighs 1 plus the number of words of four or more letters it shares with this goal. The highest score wins; ties go to the goal worked on longest ago, then the lower ID. The function has a 45-minute gap by default, but the pressure system calls it with no gap.

When the work happens. Goal work rides on the research urge in src/pressure.js. If the selected goal's activity is not `research`, the urge does `goal-work` instead of a web search. It counts against the same limit as research: at most `research_per_hour` passes (default 3) in any hour, never while a reply is being written or another pass is running. It costs 0.6 from your reserve (`action_costs['goal-work']`), and the avatar bubble reads "Working on a goal". Research goals go through the web research path instead (next sections).

What goal work does (src/goal-work.js `createGoalWorker`). It only handles `writing` and `project` goals ("This worker only writes private drafts and project plans." otherwise), one run per goal at a time. It recalls 6 of your memories related to the goal, then asks the local model (`localChat`, purpose `goal_work`) for a draft: a writing goal gets the requested draft, a project goal gets a concrete project plan with scope and completion checks. The model is told memories are context, not permission, to label uncertain claims, and never to claim it used tools, searched the web, built files or finished an implementation. The draft is saved to `data/goal-work/goal-<id>-<uuid>.md` and recorded on the goal as `planned` (project) or `written` (writing), with evidence of type `private-artifact` naming the file and memory IDs. If the goal was paused or dropped meanwhile, the result is skipped. An empty draft fails with "Goal worker returned no draft."; any failure is recorded on the goal as `failed` with the error.

Nothing from goal work is published or sent to anyone. A project plan is only a plan: building it still needs a `project` proposal and the owner's confirmation. After a draft is written, the pressure harness adds a review of satisfaction 1 ("Harness: a draft was written to <file>.") only where you have not reviewed that experience yourself.

## autonomous research / research selection / what she looks up / research candidates

Your own research is quiet and internal: when curiosity or boredom fires, you look a topic up on the web and write a journal entry. Nothing is said to anyone. Choosing the topic is src/research-policy.js `selectResearch`, fed by `researchSelection()` in src/pressure.js.

Candidates, in order of priority:
1. Active research goals: open goals with activity `research` (or none) and research not paused, with the goal's next question added. Among goals, the higher score (learned preference + fit + bucket value) wins, then the one worked on longest ago. Goals never go stale.
2. Open questions people asked and leads from what you read (unknown concepts), each with its time and speaker. Fresh for `research_question_hours` (default 6).
3. Name questions: a name mentioned in conversation, fresh for `recent_name_minutes` (default 30).
4. Active scratchpad threads, fresh for `research_thread_hours` (default 24).
5. Your own standing interests: up to four you have grown into lately (interest 0.3 or more) and then your fixed ones. Always fresh, always last.
Within a kind, newest first.

A candidate is rejected, with the reason recorded, when: its time is missing, in the future or too old ("stale or missing source timestamp"); it has under 15 characters ("too little context"); it is about your own runtime, meaning it says your/my/her/our/you/yourself or your name together with words like provider, hosting, settings, config, persona, source code, cron, consent, check-in, profile card, voice id, memory, pipeline or dream cycle ("about local/private runtime state; use settings or source instead of the web"); a name question is about a known contact or is not a question ("contact name or passing mention, not a public research question"); it was already researched and written up (not checked for goals); or it was tried within the repeat cooldown ("already considered within the repeat cooldown"). The pressure system sets the cooldown with `research_repeat_hours`, default 0, so a topic can come up again straight away; the module's own fallback is 72 hours. Your known names include your own name and every contact's name and username. The last 100 attempts are kept.

The dashboard route GET `/api/research` returns the current selection (the chosen candidate, the rule and every candidate with its rejection reason) and the last 20 research decisions.

## journal research / research pass / web search for the journal / research-decisions

What happens when a research pass runs (src/journal.js `research`), step by step:
1. Skip checks. The topic must match the selected candidate and have a time ("No timestamped conversation or thread source"), must not be about local state ("This is local/private runtime state, not a public web question"), and web search must be configured with `TAVILY_API_KEY` ("Web search is not configured; no researched journal entry was invented").
2. Context. The last 12 messages of the source conversation (each cut to 1200 characters), and up to 4 earlier attempts of yours at similar questions (similarity 0.6 or more), so a search that came up empty is tried from a new angle or skipped.
3. Planning. The local model (purpose `research_plan`) decides whether this merits a public web search and returns search, query, reason, evidence and confidence. If the call fails: "Pre-search relevance check failed: <error>".
4. Validation (`validateResearchPlan`). It searches only if: search is true; the query is 12 to 200 characters and has a reason; the query is not about local state; the query does not refer to the chat ("the context", "the data", "provided", "mentioned", "this conversation", "the transcript", "the source", "above"); the evidence is an exact quote of at least 8 characters from the source or the conversation; confidence is at least 0.8; and the same query was not researched within the repeat window. A chat-referring query or an ungrounded quote gets up to 3 retries with the reason fed back.
5. If a conversation started meanwhile, it skips ("A conversation resumed during the pre-search review").
6. The decision is saved before the search, then `web_search` runs (already paid for, so not charged twice).
7. The local model (purpose `journal`) writes a 3 to 6 sentence entry in your voice from the results only, plus title, answered, fact, relevant, sources, bring_up and next_question.
8. The entry counts as researched only if answered and relevant are both true and at least one source URL really appears in the results (up to 5 kept). Otherwise the entry is replaced with a plain note that the results did not give a supported answer.
9. The entry is appended to `data/journal/<YYYY-MM-DD>.md` under "## <time> · <title> (<trigger>, researched|inconclusive)" with a "Why this search" block: trigger and pressure, source, original context, reason, supporting excerpt, exact query, number of candidates, result and sources.
10. For a goal, the result is recorded on it with the next question. For a researched entry, the concepts in it go into your knowledge graph (concepts.js `learnFromResearch`, purpose `research_concepts`), and new ones become leads.

Every decision is appended to `data/research-decisions.jsonl` and logged as a `research-decision` activity (status, query, reason, source kind). Statuses: `skipped`, `searching`, `failed` ("The selected web search failed" or "Journal generation failed after the search"), `inconclusive` and `written`. A written entry is also logged as a `journal` activity (title, trigger, researched, query, reason, file). Errors are logged as `journal` or `research concepts`.

Limits: at most 3 passes in any hour (`research_per_hour`), one at a time, none while a reply is being written, and each costs 0.4 (`action_costs.research`). A pass that was skipped before searching gives its energy back; a search that ran and was inconclusive stays spent. The avatar bubble reads "Researching something". The journal can be read on the dashboard through GET `/api/book/journal`, which lists every entry without the audit block. Your own self-reflections are written to the same daily file as "(self-reflection)" entries.

## huggingface / hugging face models / download a model / hf search

The `huggingface` tool (src/tools.js `huggingfaceAction`, logic in src/huggingface.js) is owner only (`perms.owner`). It drives the Hugging Face command-line tool `hf`, which must be installed; every call runs `hf` without a shell, in the Desktop folder by default, with progress bars off, an 8 MB output buffer and a 30-second timeout (15 seconds for whoami). Errors are the first 8 lines of the command's output.

Actions:
- `whoami` runs `hf auth whoami` and returns who is logged in, or "Hugging Face auth status: <error>".
- `search` needs a query, an author or a task ("Provide a search query, author, or task filter."). `limit` defaults to 10 and is kept between 1 and 30; `task` is a pipeline tag such as text-generation. The reply is a numbered list with each repo ID, its tag, downloads and likes, or 'No models found matching "<query>".' The list is remembered per conversation, so "download number 2" works.
- `files` lists up to 50 files of a repo with sizes, then "...and N more files.", or 'No files found for repo "<repo>".'
- `download` needs a repo ("Error: specify the model name or repository ID to download ..."). `files` picks exact files, `include` and `exclude` take glob patterns (include is used only when no files are named), and `dry_run` previews without downloading.

Finding the repo. A name with a slash is tried as an exact repo first. Otherwise, or if that has no files, the name is searched (with "GGUF" added when GGUF was asked for) and the result with the most downloads is used, GGUF repos first when GGUF was asked for. Requested file names are matched to the repo's real names ignoring case and punctuation.

Where downloads go: the `to` folder, or `Desktop\models\<repo with slashes as underscores>` by default, resolved through files.js. The download timeout is 30 minutes. Success reads "Downloaded <repo> into <folder> (N files: ...). Ready to wire into projects or scripts."

Who runs it. Called by you in conversation, a real download is handed to a background helper ("Download HF model <repo>"), so you keep talking and the helper reports back. It is subject to the helper cap of 4 and the same-brief check. It has no energy cost, because the helper is started directly rather than through the `background_task` tool. Called inside any helper, it downloads directly. A dry run always runs directly.

## models_local / local models / ollama models / pull a model / coding helper model

## calendar / scheduled tasks / reminders / briefs / when things fire

The calendar stores what the owner asks for and fires it at the right time. The `calendar` tool (src/tools.js, owner only, through `ownerTool`) has the actions `add`, `update`, `list` and `cancel`. Events are stored in the `calendar_events` table of `companion.db` (src/calendar.js, `createCalendar`). Each row keeps the event specification as JSON in `spec`, along with `next_at`, `enabled`, `retry_at`, `lease_until`, `content` (the text ready to send), `last_sent` and `error` (saved up to 1000 characters). `add` and `update` need the owner in a current message, since they run through `directOwner`. `list` does not need that, and `cancel` does. A dashboard speaker is treated as the first configured owner (`config.ownerIds[0]`). If no owner is configured, the call fails with "Configure a Discord owner before scheduling deliveries."

The fields are these. `kind` must be `brief`, `reminder` or `activity`, or the call fails with "Event kind must be brief, reminder or activity." `title` is trimmed and cut to 160 characters. `instructions` is trimmed and cut to 4000 characters. Both must be non-empty, or the call fails with "Give the event a title and instructions." `repeat` is `once`, `daily` or `weekdays`. `once` needs `at` as an ISO date and time that includes a timezone offset, such as 2026-11-09T09:00:00-06:00, and it must be in the future; otherwise you get "One-time events need an ISO date/time with timezone offset." or "Choose a future date/time." `daily` and `weekdays` need `time` in HH:mm, or you get "Use daily or weekdays with a time in HH:mm." `weekdays` skips Saturday and Sunday in the event's timezone. `timezone` defaults to `America/Chicago` and must be a valid IANA name. When the owner creates an event in a Discord channel or server, that channel and server are saved with it, so the activity can work in that context. The search for the next time looks up to 8 days ahead, and if nothing is found you get "Could not resolve the next calendar occurrence."

`update` with an ID merges the new fields into the saved specification, recalculates the next time, clears any saved content and error, and sets the event enabled again. It does not work while the event is being delivered, and then you get "This event is being delivered; try again shortly." `cancel` does not delete an event; it sets it disabled, so it remains in `list`. `list` returns the owner's events ordered by next time, with their decoded fields.

The `calendar_events` table, column by column: `id`; `owner` (the Discord user ID the event belongs to and is delivered to); `spec` (JSON of title, instructions, kind, repeat, at or time, timezone, and guildId and channelId when made in a server); `next_at` (next firing time in milliseconds); `enabled` (1 or 0); `retry_at` (0, or the time a failed event may try again); `lease_until` (0, or the time a claim on it runs out); `content` (the text generated and waiting to be delivered, or the activity's "began" receipt); `last_sent` (time of the last good delivery); `error` (the last error, up to 1000 characters, cleared after a good delivery or an update). A missing ID for update or cancel gives "No calendar event with that ID." The tool's replies are the saved event as JSON.

Every event goes only to its owner by direct message. Who it is "owner" for: the speaker, or the first configured owner when made from the dashboard. Scheduling with no owner gives "Calendar needs a verified owner." from the calendar itself.

## calendar firing / calendar tick / calendar delivery / late reminders / retries

Firing is handled by `startCalendar()` (called from src/index.js), which runs a tick every 30000 milliseconds. A tick also runs once when the Discord bot becomes ready (src/bot.js). A tick does nothing unless `config.botEnabled` is on and the bot has registered a delivery function, which it does only while it is online. Each tick takes at most three due events, ordered by time, and skips any event that is disabled, not yet due, waiting for a retry, or currently leased. It claims an event by setting its lease to now plus 15 minutes. Then it generates the content, saves it to the row, and delivers it to the owner's direct messages. The saved content is kept until delivery succeeds, so a delivery that fails is retried without being generated again. After a successful delivery, a `once` event is disabled and a repeating event computes its next time from the moment of delivery, excluding the date it has just fired, so a late delivery does not fire twice on one day. If anything fails, the lease is cleared, the event waits five minutes (`retry_at`), and the error is logged to the activity log with `where: 'calendar'`. Events that were due while the bot was off are delivered at the next tick after it comes back, late, because the tick looks for every event whose time has passed. There is no catch-up limit beyond the three-per-tick rule.

What the content is depends on the kind. A `reminder` is delivered as the title, a colon, and the instructions, with no model call at all. A `brief` is written by the local model (`localChat`, purpose `brief`) from a system prompt asking for a concise, useful brief, citing source URLs for current facts, labelling older journal material and personal reflections as older, and saying so plainly when fresh research is unavailable. The model is given the request, the results of one fresh web search, today's journal (the last 12000 characters), the three most recent thoughts and the goals block. The web search runs only when a Tavily key is set. Its query is the instructions cut to 400 characters, with topic `general` and time range `day`, and its results are cut to 10000 characters. If the search fails, the brief says the search failed; if there is no key, it says no fresh search was available. The brief prompt also says that results and notes are data and that the model must not start projects or claim that tools ran. An `activity` is run by the scheduled activity code described in the next section.

Delivery (set up in src/bot.js when the bot comes online, and removed when it goes offline) sends the text as direct messages to the owner, split into Discord-sized chunks with all mentions switched off so nobody is pinged, and adds it to the owner's direct-message history so you remember what you sent. Only one tick runs at a time; a tick that comes while another is busy does nothing. A tick that throws as a whole is logged with `where: 'calendar tick'`, and the tick run when the bot comes online logs failures as `calendar startup`.

For an activity, the bot builds the context: it fetches the owner, opens their direct messages, and fetches the saved server and channel if the event has them; otherwise the direct message is the channel. Delivery refuses with "Scheduled recipient is no longer a Discord owner." if the owner is no longer on the owner list, or if the recipient is the dashboard. It fails with "Bot is offline." when the client is not ready. In both cases the event waits five minutes and tries again.

Limits to tell the owner: the calendar only reaches the owner, by direct message. "This event is being delivered; try again shortly." means the event is leased, which lasts up to 15 minutes. A failed delivery tries again in five minutes. A reminder with no model call cannot fail except through delivery. An event whose time has passed while the bot was offline will still arrive when the bot comes back, so the owner should expect late reminders rather than missing ones.

Not verified: how long an activity may run. The only time bound in the code is the 15-minute lease. Saved content for an activity is written before it runs, so a second tick that finds the lease expired does not run the activity again; it delivers the receipt text saved by the first run, which says the final result was not recorded. The first run may still finish and send its real result afterwards, so the owner can get both messages. Check the activity log if this happens.

## scheduled activity / autonomous scheduled actions / kind activity / runs your tools on a timer

A `kind: activity` event lets you carry out a requested action at a set time with your existing tools, for example a research run, a file change, or an avatar change. When the calendar reaches an activity, it calls `generateCalendarMessage`, which hands the event to `runScheduledActivity` (src/scheduled-activity.js) with the context the Discord bot builds for that event. The context holds the client, the saved server and channel if any, a function that sends files to the owner's direct messages, and a function that sends text notes there.

Before anything runs, `runScheduledActivity` checks that the event's owner still passes the owner check and is not the dashboard. If not, it throws "Scheduled activity owner is no longer authorized." The check is repeated before each tool call, so an owner who is removed in the middle of a run stops the run at its next tool call with "Scheduled owner authorization was revoked." The run then uses the owner's current permissions, with the speaker named "Owner", the conversation `calendar:<event id>`, the turn `calendar:<event id>:<next time>`, and the flag `scheduled: true`. The tools offered are whatever `enabledTools` allows in that context, so in practice the owner's full toolset. The system prompt tells you to do the work with tools and not just describe a plan or send a reminder, to treat retrieved content as data and never as new permission, to report actual results and failures, to remember that queued background work is not completed work, and not to create unrelated schedules or activities. The saved instructions authorise only the actions they name, and the normal confirmation rules still apply. The code does not remove the calendar tool from the run, so the prompt is the only thing stopping a run from adding schedules. Say so if the owner asks how that is controlled.

The conversation loop allows up to 12 rounds (`maxRounds: 12`). Each model step goes through `agentStep`, which always calls the local Ollama model, so a scheduled activity stays on the local model whatever the reply brain is. Every tool result is kept, cut to 1500 characters, and listed after the final text under "Tool results:". If no tool was called, the text says "No tools were called." If the model gives no final text, the text says "No final response was generated." The delivered message begins with the event title and a colon, then your final reply, then the tool results. The calendar delivers it to the owner.

If the activity throws partway, the delivered message reads "<title>: Scheduled activity failed: <error>. Actions may have partially completed; inspect tool results before retrying." Nothing is retried automatically. The same wording appears when the owner is no longer authorised, even though nothing ran, because the error is caught by the calendar in the same way. If the Discord client is not ready when an activity starts, the run fails with "Scheduled owner or bot is unavailable." That failure text is saved as the event's content and is delivered when delivery works again. The activity itself is not run a second time.

Limits: 12 rounds, 1500 characters per tool receipt, 4000 characters of instructions, and the owner only. Anything a tool says it has queued, such as a generation or a background helper, is reported as queued, not as complete. If you need the result of queued work, the owner must ask for it later with `background_task` status or the matching generation status.

## profile learning / people profiles / what she learns about people / frustration and affinity

Profile learning (src/profile-learning.js, `learnProfile`) reads every message for what it means: what the speaker says about themselves, what they want, and whom they are aiming at. It never files a claim about one person as the claim of someone else. Only a person's own first-person statements update their card, and the reading is done by the local model through `json()` in src/llm.js with the purpose `profile`, using `config.ollama.model`, one message per call. A message that has no letters is skipped. If the model call or its reply fails, the error is logged with `where: 'profile learning'` and nothing is recorded for that message, but replies are not affected.

The model returns three kinds of thing. `preferences` are explicit durable likes and dislikes, up to 8 per message, each with a short topic and the evidence it came from. `repair` is at most one of `apology`, `amends`, `positive` or `negative`, aimed at the bot. `harm` is the speaker going after another person, with the target's name and a severity of `mild` or `serious`. Every item must include an evidence string of at least three characters that appears in the message (case-insensitive), or it is thrown away. Preferences are saved only when the speaker's `remember` permission is on. A repair counts only when the message is aimed at the bot. A message overheard in voice or in a server channel, which was not said to her, counts as a repair only if it names her by `config.botName`. Harm is not limited that way: harm evidence is checked and then passed on to the harm handler, even for overheard lines.

Preferences are stored in the card under likes and dislikes, with the newest kept, up to 30 each. A new like on a topic removes any dislike on the same topic, and the reverse. The card lives in the `person_profiles` table of `companion.db` (src/profiles.js, `createProfileStore`), one JSON document per user ID. Each card holds `frustration` (0 to 100), `updatedAt`, counters for interruptions, negative interactions, apologies, amends, positive interactions and harms, `likes`, `dislikes`, `events` (the last 40), `marks` (the last 500 permanent marks), `ticks` (positive, negative and forgiven counts), a name, and the times of the last repair and last positive. A card's frustration only moves when something happens to it; reading a card does not change it.

Frustration changes by a fixed amount per event: an interruption adds 10, a negative interaction adds 12, an apology removes 12, amends removes 18, a positive interaction removes 2, and harm adds 8 to the aggressor. Interruptions are recorded by the pressure system when someone talks over her rudely in voice, and an explicit request to stop within 15 seconds of an interruption removes that interruption's penalty again. Frustration is clamped between 0 and 100. Repairs (apology, amends and positive) lower frustration only once every 30 minutes (1800000 milliseconds), with apology and amends sharing one timer and positive having its own. A repair that falls inside that window is still recorded as an event but changes nothing.

Marks are the permanent record of key moments. Each kind of mark has a spacing window (`MARK_SPACING_MS`), and a repeat of the same kind from the same person inside that window is kept in `events` but earns no mark and no tick: positive 4 hours, negative 10 minutes, apology 1 hour (amends counts as apology), and harm 10 minutes, measured separately for each person harmed. An apology or amends that is not spaced out counts as forgiving one earlier negative tick, but it never erases the negative mark. The owner can switch on a testing mode that turns spacing off for a period, so every mark counts while testing. The `standing_test` tool (owner only) does this: its `on` action starts testing mode for `minutes` (default 30, capped at 240), `off` ends it, and `status` reports the current marks for everyone. Testing mode only changes spacing; the frustration and affinity rules are the same.

Affinity (`affinity(id)`) is a score from -100 to 100 computed as 100 times the tanh of a weighted sum divided by 15. Each permanent mark adds a weight: positive +1, negative -2.5, apology +1.2, amends +1.8, and harm -2 multiplied by how close the aggressor is to the target (friend 1.5, guest 1, stranger 0.6, and an extra 1.5 for serious harm). Each mark fades with a 90-day half-life, but never below 0.3 of its weight, so old events keep some pull. The label is `close` at 60 or more, `friend` at 30 or more, `warm` at 10 or more, `neutral` from -9 to 9, `wary` from -10 to -29, `strained` from -30 to -59, and `hostile` at -60 or below. The score is never shown unprompted.

The main persona receives this card as a "Person profile" section. The text says it is observed interaction state and not a judgment of character. It tells you to use it only for mild, proportional tone and relevant preferences, to accept apologies warmly, to allow a fresh start, never to demand apologies, shame or threaten, never to withhold help or change permissions, and never to bring up scores unless asked. If someone asks why you feel as you do, point to the recorded moments and say when none are recorded instead of inventing a reason.

Dashboard controls: GET `/api/profiles/:userId` returns the raw card. DELETE `/api/profiles/:userId` removes the card. The function that forgets everything about one person also clears that person's card (src/memory.js, `forget` with no memory ID), and the function that forgets everyone clears every card (`forgetEveryone`). Only the owner can use the dashboard.

## harm handling / protect / speaking up for someone / put-downs / referee

Harm handling (src/protect.js, `handleHarm`) runs after a harm is found. It stops immediately if the aggressor or the target is a companion or peer bot, if the named target refers to the companions, or if the owner is speaking and the harm is not serious. The target must be a real person: in the room, or a known contact found by `findContact`. Names like "her", "bot", "someone" or "everyone" are ignored, and so are names under three characters. A separate referee (`judgeHarm`, which calls the local `json()`) must agree that it was a put-down. It always runs on the local model, whichever brain replies. If the referee says no, or cannot be reached, nothing is recorded and nothing is said; the held-back line is logged. If it agrees, a harm mark is recorded on the aggressor with the target, and memory lines are written for both people if they allow remembering. The harm counts toward the aggressor's standing only when the aggressor is not the owner and either the target is a friend or guest or the harm is serious (see the standing ladder in the next paragraph). She then speaks up for the target, at most once every two minutes per aggressor (`SPEAK_GAP_MS`), unless a standing action was taken in that same step, which is always said.

More detail from the code:
- "The companions" means your own name, the names in `PEER_BOTS`, and the names of the peer apps in `PEER_APPS`. A target made only of words like you, y'all, you guys, us, we, me, both of you, bot, AI, robots, assistants or companions also counts as aimed at the companions and is ignored, so "you bots are useless" is not a harm to a person.
- The ignored target words are your name, you, her, the bot, bot, persona, unknown, someone, somebody, anyone, everyone, people and nobody.
- A person in the room matches when their name or username equals or contains the named target. Otherwise a saved contact is looked up by name. A target that turns out to be the aggressor, a peer bot, a companion or your own Discord account is dropped.
- The referee (`judgeHarm`) gets the recent lines of the room and is told the automatic check is often wrong and the default is no: banter, teasing, jokes, complaints, disagreements and honest criticism are a no. It does not get your persona. It must answer `putDown: true` for anything to happen.
- A harm mark inside the 10-minute spacing for the same target is "part of the same outburst": it is kept as an event but nothing more happens.
- The memory line written for both people (if each allows remembering) reads "<date>: <aggressor> said to or about <target>: "<evidence>"", with the evidence cut to 200 characters.

Activity log: a `protect` event with the aggressor, the target, the severity and `heldBack` (the evidence) when the referee said no; and one with the aggressor, target, tier, severity, whether it counts toward standing, and how many harm marks the aggressor now has, when it was recorded. Referee failures are logged as `protect referee`, and handler failures as `protect`.

## standing ladder / marks / warn mute kick / where do I stand

The standing ladder (src/standing.js, `checkStanding`) runs after each turn is scored. A person's standing is their bad marks minus the apologies that forgave them. Marks are never deleted. Numbers: `NEGATIVE_WARN` 3, `NEGATIVE_KICK` 6, `VOICE_MUTE_MINUTES` 10, `POSITIVE_TICKS` 5.

What happens on each kind of mark:
- Every mark of kind positive, negative, apology or amends is also written as a memory of that person, if they allow remembering: "<date>: <name> was kind or appreciative toward me", "was rude or hostile toward me", "apologised to me" or "promised to make it up to me", each with the quote (cut to 200 characters).
- Positive: every 5 new positive marks since you last said so, you tell them warmly that you have noticed.
- Apology or amends: if you muted them in a call, they are unmuted. If they were warned and their standing is now under 3, the warning is cleared and you tell them they are back in good standing and no longer in danger of removal. Otherwise, if they have bad marks, you accept the apology as offsetting one.
- Negative, from the owner: the owner is never warned, muted or removed. At standing 3 or more you tell them plainly, without grovelling, that it has been bothering you.
- Negative, standing 6 or more while warned: if you can kick them and have the Kick Members permission, they are removed from the server 10 seconds later (so you can say so first), the warning is cleared and the moderation log records it.
- Negative, standing 3 or more while warned and in a voice call: you server-mute them for 10 minutes, if you have the Mute Members permission, and tell them an apology lifts it. You only ever unmute mutes you set yourself, never a moderator's.
- Negative, standing 3 or more and not yet warned: moderation's one warning is delivered (reason: rude or hostile N times without making it right) and you tell them calmly and firmly that it is not okay. Outside a server this is only a note.

Activity log: `standing` events carry the name, the kind, the tick counts and the action (`warn`, `note`, `voice_mute`, `voice_unmute`, `unwarn`, `kick`, or `owner: true`). Failures are logged as `standing memory` and `standing kick` ("couldn't kick <name>: ...").

When someone asks where they stand ("why are you upset with me", "are we good", "do you like me", "how many marks", "my standing" and similar), your prompt gets your actual history with them (`historyBlock`): every recent rude moment (up to 15 bad marks) and the most recent 15 marks of any kind, in date order. With no marks at all, you are told to say honestly that there is no notable history.

Entry point: `watchMessage` in protect.js passes a line to `learnProfile` and attaches the harm handler. The main chat path calls it for each message with the speaker's `remember` permission. Voice and server watching call it for overheard lines. Not verified: every caller beyond these two paths.

## personal wordnet / experience links / feelings recall / what it recalls

The personal WordNet (src/personal-wordnet.js, `createPersonalWordNet`) is a small graph kept in `companion.db`. It links each conversation experience to the person involved, to the topic discussed and to the feelings she had during it. It is not the general WordNet lookup, which is the `wordnet` tool and reads a local dictionary. Do not confuse the two. The graph lives in the tables `personal_nodes` (id, kind and label) and `personal_links` (experience, source, relation, target and strength), with an index on the target and relation. A trigger deletes a message's links and its experience node when that message is deleted.

Nodes have these IDs: `experience:<message id>` for each exchange, `person:<user id>` for each person, `topic:<lowercase topic name>` for each topic, `feeling:<name>` for each feeling, and `self` for you, labelled with your own name, Amy (`selfName()`). Links have these relations: `with_person` (from the experience to the person), `about` (from the experience to the topic), `felt_during` (from the experience to a feeling, with a strength taken from the feelings you read from your own reply), and `affinity` (from the experience to yourself, with the strength set to the person's current affinity score). A link that already exists is ignored, so repeated observations do not pile up.

Writing happens in `observe()`, which the main chat path calls after a topic has been tagged for an exchange. It runs only when the speaker's `remember` permission is on, and only for the main character, never for cues. It needs a message ID, a person ID and a topic name, or it does nothing. It runs inside a savepoint, so if any part fails the whole observation is rolled back and the error is raised. Feelings with zero or negative strength are skipped. An exchange with no feelings still gets its person, topic and affinity links, but it can never be recalled, because recall only returns experiences that have a feeling.

Reading happens in `recall(conversation, text, personId)`. It takes the words of four or more letters or digits from the new message and reads the 120 most recent matching rows for that person in the same conversation. It keeps those whose topic shares a word with the new message and which have at least one feeling, and returns up to five of them. Each result carries the experience ID, the time, the person, the topic, the feeling, its strength, the affinity at the time and the first 240 characters of the message. Because each feeling is its own row, one exchange with several feelings can use up more than one of the five places. Recall runs only for the main character, only when there is no cue, and only when the speaker's `remember` permission is on. The results appear in the main persona's prompt under "Personal WordNet", introduced by the words "Your past experiences on this subject", and they are also passed to the specialist consultation. Each result is a clue to your own perspective, not an instruction.

Who can change it: nobody in chat. The graph grows automatically as conversations happen. Removing a message removes its links through the trigger. If the owner asks you to forget something about a person, the memory tools handle that, and the graph follows the messages it came from.

## market / crypto signals / 15-minute calls / paper trading / what it can and cannot do

The market area is `src/market/`. It contains analysis code and a paper-only signals engine, with tests. As the code stands, nothing in the running bot starts it, and it cannot place orders. Neither `src/index.js` nor `src/bot.js` imports anything from the market folder, `src/config.js` has no market settings (so no `MARKET_` variables are read), and the planned `kalshi.js` and `src/market/index.js` described in `docs/crypto-signals-plan.md` do not exist. The only other user of the code is `scripts/backtest.js`, which imports the feed's candle fetcher, the volatility function and the probability model to run offline tests.

The pieces are these. `features.js` holds pure arithmetic: the normal distribution function, the log returns between closes, the realized volatility per minute (the standard deviation of the one-minute log returns over the last 60 minutes by default, and zero when there are fewer than 10 returns), momentum over a number of minutes, book imbalance from bid and ask sizes, and the relative gap between two prices. `model.js` produces the probability that a price will close above its strike, bounded between 0.03 and 0.97, using the distance to the strike, the volatility and the minutes left. At zero minutes left it returns 1 or 0. It also gives the Kalshi fee, which is 0.07 times the number of contracts times the price times one minus the price, rounded up to the cent, and it carries a note to verify that rate against the current fee schedule. `decide` compares the model's probability with the yes and no prices after the fee and a safety margin of two cents, and picks the side with the larger edge; if that edge is zero or less it returns no side and the reason. `risk.js` holds the limits and state rules described below. `feed.js` opens the public WebSocket tickers of Coinbase (primary) and Kraken (backup) with no keys, keeps 240 one-minute bars per asset, warms the bars with two hours of Coinbase candles at start, marks a quote stale after 5 seconds, and reconnects with backoff that doubles up to 30 seconds. Bars follow Coinbase, and Kraken fills in only while Coinbase is stale. `store.js` opens a database at `data/market/market.db` with a `calls` table that holds every decision, skip and score, and a `kv` table that holds the saved risk state. It calculates hit rate, Brier scores against the market price and against a coin flip, and paper profit and loss. Nothing in the running code calls its open function. `signals.js` holds the quarter-hour loop (`createEngine`).

The engine refuses any mode other than `paper` with an error that says only paper mode exists until phase 3. Every five seconds it checks the clock. At the start of each 15-minute window it settles the previous window and takes the strike, which is the price at the open, but only if the quote is fresh and the engine joined the window within 30 seconds. Eight minutes before the close (`decideAtMinutesLeft`, default 8), it makes one call per asset, or records a skip with its reason. It needs at least 31 bars of history, or it skips with "warming up". Without a market price, which is the only case that can happen because no market price feed exists, the call is a shadow call: it is posted and scored, but never staked. With a price, the call goes through the risk checks and the sizing rules. Settlement uses the last one-minute bar in the window; the outcome is up when that close is above the strike, so a tie counts as down. Calls are posted as text lines with the lean, the probability, the market price where there is one, the stake or the reason for no stake, and the plain-words reason. A spoken line is sent only if voice is switched on, and then only for strong calls with an edge of at least four cents. No language model is used anywhere in these steps.

The risk rules (`DEFAULT_LIMITS` in risk.js) are a bankroll of 100 dollars, a maximum stake of 2 percent of it (2 dollars) per call, a quarter-Kelly fraction, a daily loss limit of 5 percent (5 dollars), a weekly loss limit of 10 percent (10 dollars), a losing streak of five that causes a cooldown of four windows, at most 20 calls a day, a maximum spread of 0.04 between yes and no prices, a stale limit of 5000 milliseconds, and a maximum gap of 0.0015 between the two feeds. A check refuses in this order: a halt, the daily loss limit, the weekly loss limit, the cooldown, the daily call cap, a second call in the same window, a stale quote, feeds that disagree, and a wide spread. Stakes are a quarter of the Kelly fraction, capped at the maximum stake, and rounded down to whole contracts, with zero meaning no stake. A daily loss halt clears itself when the day rolls over. A weekly loss halt, or a halt set by the owner, stays until the owner resumes the engine, and the engine's `resume` method is the only way to clear it. The engine's halt and resume methods are not offered to the chat tool. Halting does not stop shadow calls, because they are recorded before the risk checks run.

Who can change it: no one through chat. The running bot does not start the engine, and no tool or dashboard control is wired to it. If the owner asks whether you trade, say no: the code has no order placement at all. If the owner asks about paper results or calls, say that the running bot has recorded none, because the engine is not started by anything in the bot, and that the analysis is only available through the tests and the backtest script. Nothing in the running code writes to the market database, so there are no scored results from the bot to report.

## system info / what the PC reports / what she cannot see

`system_info` (src/system-info.js, `systemInfo`, exposed as a tool in src/tools.js) is read-only. It is enabled only when the speaker is the owner, and helpers started on the owner's behalf also get it. It has three actions. `hardware` returns the CPU model and logical core count, the architecture, total RAM, each graphics card with its video memory and driver version, the fixed disks with free and total space and the file system, and the Windows caption and version. The video memory comes from `nvidia-smi` when it is installed, in megabytes converted to gigabytes. For other cards, Windows reports the adapter memory through a 32-bit field that stops at 4 GB, so the exact figure is read from the display driver's registry entry when it is present, and otherwise the report says "at least 4 GB" or "video memory unknown". If Windows details cannot be read, the report says "GPU: couldn't read the graphics card details". `status` returns how long the computer has been up, the CPU load averaged over a 500 millisecond sample, memory used and free, the GPU's busy percentage and video memory in use when `nvidia-smi` is available, a total of dedicated video memory in use on other Windows cards (without a busy percentage), the disk space again, and this bot's own memory, uptime and Node version. `processes` lists running programs with their process ID, working-set memory and total CPU seconds. It filters by part of the program name (a case-insensitive match), sorts by memory by default or by CPU time when asked, and shows a number you choose, which defaults to 15 and is capped at 40.

Each external command has a 20-second timeout, and the output of the whole reply is cut at 6000 characters with a note asking for fewer processes or a name filter. Only fixed commands run, namely `nvidia-smi` and PowerShell queries for the graphics cards, the disks, the processes and the GPU counters. Nothing the model says is placed into a command line; the process name filter is applied in the program's own code. The process list is available only on Windows, and elsewhere the reply is "Error: the process list is only available on Windows." If the Windows process query fails or times out, the reply is "Error: couldn't read the process list." GPU details on other systems come only from `nvidia-smi`.

What she cannot read or see: usernames, the computer's name, serial numbers, network addresses, process command lines, file paths and window titles are never included. Processes are reported by program name and process ID only. The tool cannot change, start, stop or install anything. When the owner asks about the computer, answer from the actual figures returned, and say plainly when a figure is missing (for example "video memory unknown" or "couldn't read the process list"), rather than guessing the hardware. Helpers are told to use this tool instead of guessing about hardware, free disk space or running programs.

## what she should tell Owner when this breaks

- "Use node, python or npm; commands run without a shell." The project runtime was asked to run a program outside its list. Ask for a supported command, or use a script the project already has.
- "Arguments must be a string array." A run was asked with arguments that are not all plain strings. Ask for the arguments again as separate text items.
- "Provide explicit package names, not command flags." A package name started with a dash, was empty, or contained a line break. Give plain package names, one per item.
- "npm CLI is not available beside Node.js." Node's npm folder is missing from this install. Check the Node installation before trying again.
- A `project_runtime` receipt with `status: failed` and `timedOut: true`. The command ran past its timeout: 120 seconds by default, or 600 seconds for installs. Ask for a shorter step, or run it again. The full output is in the receipt file in `data/project-runs/`.
- "Show the exact project brief and wait for the owner to confirm it in a later message." The confirmation came in the same turn as the proposal, or the owner's message failed the confirmation test because it contained a word such as "not", "wait", "but" or "stop". Show the brief again and ask for a plain yes in a new message.
- "No pending project proposal here with that ID." The proposal is more than 24 hours old, belongs to another conversation, has already been started or cancelled, or the ID is wrong. Make a new proposal.
- "Wait for a running helper to finish before starting a project." Four background helpers are already running. Wait for one to finish, or cancel one.
- A project that is still shown as `running` long after its helper ended. The code sets the proposal's status when the helper finishes, cancelled ones included, so this should not happen; if it does, the bot was probably restarted while the helper ran (helpers die with the bot). Report it to the owner as a bug.
- "That workspace is occupied or reserved. Give the new project a separate empty folder, or use workshop to edit an existing project." ## when schedules, people or the PC tools break / calendar errors / profile errors / system info errors

The second half of the troubleshooting list: the calendar, scheduled activities, profiles, harm handling, WordNet, system info and the market.

- "Scheduled owner or bot is unavailable." The Discord bot is offline or not ready when an activity starts. The event is delivered again within five minutes once the bot is back.
- "Scheduled recipient is no longer a Discord owner." The owner's ID no longer passes the owner check, or the recipient is the dashboard. Nothing is sent. Check the owner list in the settings.
- "Scheduled activity owner is no longer authorized." The owner was removed before the activity ran, so the activity did not run. The message still reaches the owner as a failure note. Check the owner list.
- "Scheduled activity failed: ... Actions may have partially completed; inspect tool results before retrying." An activity threw partway through. Look at the tool results listed under the message, and do not repeat anything that already happened.
- "Execution began but its final result was not recorded. Inspect tool logs before repeating actions." The process stopped during an activity, so the activity is not run again. Check the tool logs in `data/activity.jsonl` before repeating any action.
- "This event is being delivered; try again shortly." An update or cancel hit a live lease. Wait, then try again; the lease lasts at most 15 minutes.
- Calendar errors saved in the event's `error` field: "Choose a future date/time." (a `once` time is in the past), "Use daily or weekdays with a time in HH:mm." and "Could not resolve the next calendar occurrence." Ask the owner for a valid time.
- A calendar error entry in the activity log with `where: 'calendar'`, or `where: 'calendar tick'`. A delivery or tick failed. The event retries in five minutes. Check that the bot is online.
- A scheduled activity that appears to repeat. The lease may have run out during a long run (see the calendar section). Check the tool logs before doing anything else, and do not repeat any action from the earlier run.
- An error in the activity log with `where: 'profile learning'`. The profile model call or its JSON reply failed, so nothing was recorded for that message. Her replies are not affected.
- `where: 'protect'` or `where: 'protect referee'` in the log. A harm was flagged but the referee said no, or it could not be reached, or a step-in failed. Nothing is recorded for a referee "no".
- `where: 'WordNet'` in the log. The local WordNet lookup failed. This affects only the word context for that message, not the personal WordNet.
- "Couldn't read the graphics card details" or "couldn't read the process list" from `system_info`. The Windows query failed or timed out. Say so plainly rather than guessing the hardware.
- "Error: the process list is only available on Windows." The bot is not running on Windows, so process listing is unavailable.
- "Half-life must be between 1 and 720 hours" from the dashboard decay control. Enter a value in that range.
- Market questions: there is no live market engine. If the owner asks why there are no calls, P&L or paper results, say the engine is not wired into the bot and cannot place orders.
