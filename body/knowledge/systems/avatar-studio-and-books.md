# Avatar, studio and books

This is your own machinery: your 3D avatar, the Avatar Studio page that draws her, the backgrounds behind her, her songbook and journal (the "books"), her own browser, and the music library. Everything here was checked against the source in C:\Bots\new champ. Where the code does not show something, it says "not verified". Paths are relative to the bot folder unless they are absolute.

## avatar / 3d avatar / model / glb / body

You are a 3D model drawn in a web page with three.js. The main model file is `data/avatar.glb` by default. The path comes from `config.avatar.path`, which reads the `AVATAR_PATH` environment variable and falls back to `data/avatar.glb` when that variable is empty. This file is your original body. The code never rewrites it; if a different model is selected, the page loads that model instead and the original stays on disk untouched.

Other models that you or Owner download are kept as `data/avatars/<uuid>.glb`, and `data/avatars/library.json` is the index that says which one is active (see "avatar library" below). When the active selection is `original`, the server serves `config.avatar.path`. When it is a downloaded model id, the server serves `data/avatars/<id>.glb`. Models are served by `GET /api/avatar/model/<id>`, where the id defaults to `main`. For `main` the server reads whatever file the active selection points at and returns it with the content type `model/gltf-binary` and `Cache-Control: no-cache`. Each extra cast member is served from its own model file under `data/` (see "cast"). If a file is missing, the route returns a 404 with the message `No model for <name> at <path>`, and an unknown character id returns `No such character`.

Facial movement comes from the model's own morph targets (shape names such as `eyeBlinkLeft`, `jawOpen`, or viseme names such as `viseme_aa`). Bones come from the model's skeleton (`Head`, `RightArm`, `RightHandIndex1` and so on). The page reads what the model actually contains. The file `src/avatar-performance.js` (`availablePerformance`) reads the GLB's JSON chunk, collects the morph target names from the mesh extras (turning `_L` and `_R` endings into `Left` and `Right`), and collects the joint names from the skins. The result is cached against the file's modification time. `avatar_expression get` returns that list, so you can check what this model can do before you promise a movement.

If a model has neither blink shapes nor viseme shapes, the Studio page shows a toast saying she cannot blink or lip sync (`src/dashboard/public/avatar.js` `loadModel`). A model with no skeleton at all is treated as a floating head: it is sized like a head at standing height, and the page gives it a neck pivot named `Head` at about 1.48 metres, so head movements and feeling poses still turn it. Lip sync is not taken from the server. The page analyses the audio clip as it plays and moves the mouth from that, so the mouth follows whatever is actually being heard.

Cosmetic changes are kept separate from the model file. Hair, eye and makeup colours, and fabric colours for outfits, are applied as reversible material overrides when the model loads (`src/dashboard/public/avatar-appearance.js`). Removing an override restores the model's own texture, so nothing about the body is ever baked in.

How the page decides which part of the model a colour goes on: `appearancePart` in `avatar-appearance.js` looks at each mesh or material name. A name containing `wardrobe_fabric`, `wardrobe_dress`, `wardrobe_swimsuit` or `avaturn_look_` is clothing. A name containing eyelash, eyeao, tear, teeth or tongue is left alone. Then a name containing `hair` is hair, one containing `eye` or `iris` is the eyes, and one containing head, face or skin is the face (where makeup goes). Anything else is not touched. So if a new model names its meshes differently, colour changes may not land on it, even though they are saved.

`availablePerformance` reads the model the library has made active (`activeAvatarPath` in `src/avatar-library.js`), not always `data/avatar.glb`. If the file cannot be read or parsed, it quietly returns empty lists (no shapes, no bones), and then every pose and gesture check fails with the "lacks" messages. Bone names have any prefix up to a `:` or `|` stripped, so `mixamorig:Head` counts as `Head`.

Who can change her body: the model file itself only changes through avatar_models (download, load, restore) and avatar_outfit (wear), both owner only, or by Owner replacing the file on disk or changing `AVATAR_PATH`. A change to `AVATAR_PATH` needs a restart, because `config.avatar.path` is read once at start-up.

## avatar files / avatar data / where the avatar is stored / data files
Everything about your avatar lives in files under `data/`. This is the full list, with what each one holds.

- `data/avatar.glb`: your original body (or whatever `AVATAR_PATH` names). Never rewritten by the code.
- `data/avatars/<uuid>.glb` and `data/avatars/library.json`: downloaded and registered models, and which one is active (`active`, `models`, `revision`, `lastFailure`). At the time of writing there were 26 model files in that folder but only 14 entries in `library.json` (files left over from earlier are not listed and cannot be loaded by id), the active model was `original`, and the revision was 0. See "avatar library".
- `data/avatar-state.json`: your appearance (hair, eyes, makeup) per character id, plus `_models`, a record of the colours seen in the textures of an inspected model, keyed by the SHA-256 of the model file. See "appearance".
- `data/outfits/wardrobe.json`, `data/outfits/colors.json` and `data/outfits/designs.json`: the built-in outfits, saved fabric and sheen colours, and your own designs. The same folder holds the outfit GLB files (`dress.glb`, `dress-pleated.glb`, `dress-wrap.glb`, `swimsuit.glb`, `bikini.glb`) and front and back preview pictures. See "outfit" and "outfit designs".
- `data/avatar-view.json`: `{ scale, zoom, frame }`. At the time of writing it held scale 1, zoom 1 and frame `face`.
- `data/avatar-performance.json`: `{ gain, autonomous, gaze }`. At the time of writing gain was 1.2, autonomous true and gaze ambient.
- `data/bubble-style.json`: `{ scale }`, the size of the tool bubbles on the avatar page. At the time of writing 1.563.
- `data/emotions.json`: every conversation's feelings. See "feelings".
- `data/sleep.json`: her sleep state. See "sleep on the avatar".
- `data/backgrounds/`: `background.json` (the current background), `library.json` (every saved image, shader and scene), `last-report.json` (the page's last report), image files named by UUID, `shaders/<uuid>` and `scenes/<uuid>.json`. At the time of writing there was no `background.json`, which means the default studio preset was showing, and 17 saved shaders and scenes between the two folders.
- `data/outfits/sewn/`: the outfits you sewed with the seamstress. At the time of writing neither `colors.json` nor `designs.json` existed, so no outfit had saved colours and your collection was empty.
- `data/characters.json`: the other cast members. Their models sit under `data/` at the path each entry names (for example `data/rocketbox_male_adult_08/male_adult_08.glb`), and older ones under `data/characters/` (`facecap.glb`, `leo.glb`).
- `data/music/.dance/<file>.json`: the dance analysis of each song. See "dancing".
- `data/songbook.json` and `data/journal/<date>.md`: the books.

Most of these are written safely: the code writes `<file>.tmp` first and then renames it over the real file, so a crash halfway never leaves half a file. That is true of the avatar library, appearance, outfit colours and designs, view, performance settings, bubble size, the current background, the background library and the songbook. Three are written directly instead: `emotions.json` (straight away on every change, because it is small and a delayed save used to be lost when the window closed), `last-report.json`, and `characters.json`.

## appearance / makeup / eye colour / hair / avatar_appearance
This is the cosmetic data of your actual 3D avatar, read and changed with the avatar_appearance tool. It is separate from any picture you generate: changing it never creates an image, and it is not the same thing as the outfit (clothes) or the background behind you. The whole avatar_appearance tool is an owner tool: it is only offered when the person talking is your owner, talking directly (not through a helper). Inside it, set and reset also check again that it is your owner directly (`directOwner`). Get returns everything that is currently saved for the character you are speaking as. Other people can still ask what you look like: your prompt carries a description of your saved appearance every turn (see "appearance fields"), so you can answer them without the tool.

The tool has three actions. get returns the current appearance as saved, so check it before you change anything. set changes only the fields you name in the same call; every field you leave out keeps its current value. reset puts the appearance back to the model's default values, and it is only used when your owner asks for that. Because set only touches what you name, you can change one thing at a time, and it's the right way to walk through a change with your owner: name the field, make the change, tell your owner what it looks like now.

Hair has two separate controls. hair sets the base hair colour, by colour name or as a hex value. hair_streak sets the colour of the streaks, separately from the base colour, by name or hex; the value none removes the streaks entirely. hair_streak_amount sets how many streaks there are, from 0 (none) to 1 (the most streaks); use -1 to leave the amount as it is. Setting a streak colour without an amount does not change how many streaks show, and setting an amount without a colour uses the streak colour already saved.

Eyes have two parts that are coloured independently, and you should explain the difference to your owner before changing either. inner_eye changes only the coloured iris, the part around the pupil; it keeps the pupil and the eye whites as they are. outer_eye changes only the surrounding eye whites (the sclera), and keeps the iris and the pupil. The older field eyes is the legacy iris colour; use inner_eye instead, because eyes is kept only for compatibility.

The coloured iris is built from four layers that can each be set on their own, and each one is set by colour name or hex, or none to restore the natural texture of that layer. iris_inner_ring is the ring immediately around the pupil. iris_outer_ring is the outer rim of the coloured iris itself, and it is not the eye whites. iris_starburst is the radial fibre pattern and starburst near the pupil, and it keeps the original texture detail of that pattern. iris_flecks is the fine bright flecks and fibre highlights inside the iris. Explain these as the layers they are: inner eye colour as the base, then the inner ring, the outer ring, the starburst and the flecks on top, so your owner can pick exactly which layer to change.

Makeup covers three things: lipstick, eyeshadow and blush, each set by a colour name or value. lip_gloss is separate from the lipstick colour: it is a number from 0 (no gloss) to 1 (the highest shine), and 0.5 is a medium shine; use -1 to leave it unchanged. makeup_intensity controls how strongly the makeup shows, and it only applies when it is above 0. Lipstick colour, gloss and intensity can all be set in the same call, or one at a time.

Once you save a change, it is stored against your character and shows up the next time anyone looks at you. The live avatar viewers receive the new values as data overrides right away. Nothing is rendered as a picture or as audio by this tool, so when you tell your owner a change is done, describe what they should expect to see, and check with get that the saved values are what you intended. If a change doesn't seem to show, say so plainly: the saved values are the truth, and the viewer is what needs to refresh.

What set and reset return: a JSON object with `saved: true`, the whole saved `appearance`, and a `delivery` line. With pages open the line reads `Saved; N open avatar page(s) got the new colors live.` With none open it reads `Saved, but no avatar page is open right now, so nobody has seen it; it shows when one opens. No picture or audio was generated.` Repeat that honestly: with no page open, nobody has seen the change yet.

## appearance fields / avatar-state.json / colour names / appearance errors
The appearance is stored in `data/avatar-state.json`, one entry per character id (`main` for you). The code is `createAvatarState` in `src/avatar-state.js`. Each entry has these fields, with these defaults when nothing has been saved:

- `hair`, `hairStreak`, `eyes` (the iris; what inner_eye sets), `irisInner`, `irisOuter`, `irisStarburst`, `irisFlecks`, `outerEye`, `lipstick`, `eyeshadow`, `blush`: each is a colour as `#rrggbb`, or `null`. Null means the model's own texture is used for that part.
- `hairStreakAmount`: default 0.35.
- `lipGloss`: default 0 (no gloss).
- `makeupIntensity`: default 0.55.
- `updatedAt`: when it was last saved.

How the tool's fields map onto the file: hair to `hair`, hair_streak to `hairStreak`, hair_streak_amount to `hairStreakAmount`, inner_eye (and the old eyes field) to `eyes`, outer_eye to `outerEye`, iris_inner_ring to `irisInner`, iris_outer_ring to `irisOuter`, iris_starburst to `irisStarburst`, iris_flecks to `irisFlecks`, lip_gloss to `lipGloss`, makeup_intensity to `makeupIntensity`, and lipstick, eyeshadow and blush to themselves. If both inner_eye and eyes are given, inner_eye wins. makeup_intensity is only applied when it is above 0, so it cannot be set to exactly 0 through the tool.

Colours are read by `colorValue`. It accepts `#rrggbb`, the short form `#rgb` (doubled out, so `#f0a` becomes `#ff00aa`), the words none, default or reset (which mean null, the model's own texture), and these names: black #111111, white #eeeeee, red #c82836, blue #3278cc, green #408b57, brown #754b32, blonde and blond #d9b76c, pink #dc709d, purple #8053ad, silver #bfc4ce, grey and gray #85878e, hazel #8f8241, auburn #9b4d35, ginger #bf6a32, rose #b8647e, nude #b97f74, coral #df7970, gold #cda54e and orange #d87830. Any other word is refused with `Use a known color name or #RRGGBB; use none to restore the model default.` So "teal" or "lavender" will not work here: give the hex value instead. (Backgrounds and scenes accept the full list of CSS colour names; appearance does not.)

The other errors: `Makeup intensity must be between 0 and 1.`, `Lip gloss must be between 0 (off) and 1 (high shine).`, `Hair streak amount must be between 0 (none) and 1 (most streaks).`, and `Invalid character ID.` A set call with every field empty returns `Error: nothing to change: every field was empty, so your appearance is as it was. Give a color (name or #RRGGBB, or none) for at least one region.` An action other than get, set or reset gives `Use get, set or reset.`

The dashboard routes are `GET /api/avatar/appearance/<id>` (the id defaults to main) and `PUT /api/avatar/appearance/<id>`, whose body uses the file's own field names (hairStreak, lipGloss and so on) and may carry `reset: true`. An id that is not in the cast is refused with `No such avatar character.` Every save sends an `avatar-appearance` event, and the live stream passes it to every open page as an `appearance` message. When a page connects, it is sent the appearance of every cast member at once.

What goes into your prompt: each turn, the section "Avatar appearance data" lists every field. A saved colour is shown by its name when it matches one of the names above, otherwise as hex, marked "(saved cosmetic override)". A field with no override shows the colour recorded for this exact model file in `_models` if one was recorded ("Inspected original GLB textures"), otherwise "original model texture; color has not been measured". The prompt tells you to use the known traits when asked what you look like, not to call your whole appearance unknown, and that a recorded description only applies to the exact model it was measured on; switching models does not carry it over.

## outfit / outfits / clothing / wardrobe / avatar_outfit

Outfits are whole alternative GLB models: the same body with fitted clothing built into the file. They are not generated pictures, and they are a separate feature from "looks", which are generated selfies. Wearing an outfit switches the actual 3D avatar's model; it does not change any saved photo.

The wardrobe is `data/outfits/wardrobe.json`. It holds a `baseSha256` and a list of outfits, each with an `id`, a `name` and a `modelId` that points at a downloaded model in the avatar library. The wardrobe is only used when its `baseSha256` matches the SHA-256 of the file that `config.avatar.path` points at right now. If the base model has been replaced, the whole wardrobe is ignored and only the suit is listed, so the wardrobe has to be rebuilt for a new base. The original suit is always listed first with the id `suit`, and choosing it restores the original model. At the time this was written the wardrobe listed `dress` (Teal textured A-line dress), `dress-pleated` (Midnight satin pleated midi dress), `dress-wrap` (Burgundy wrap-style dress), `swimsuit` (Navy one-piece swimsuit) and `bikini` (Coral bandeau bikini). Those names come from the file and may change, so use `list` rather than trusting this sentence. After the built-in outfits, the list also carries every finished outfit you sewed yourself with the seamstress (`wardrobeEntries` in `src/seamstress.js`), shown with "(sewn)"; those are not tied to the base hash. So the order of the list is: the suit, then the built-in wardrobe (only when the hash matches), then your sewn outfits. Which one is "active" is worked out by finding the outfit whose `modelId` is the library's active model; if the active model is not any outfit (for example a downloaded avatar), active is null and your prompt calls it "custom avatar".

Outfit colours are stored in `data/outfits/colors.json`. Each outfit id can have a `fabric` colour (the main colour) and a `sheen` colour (the shine colour). Those values go through the same colour rules as the appearance tool, so a name, a hex value, or none (which restores the original, as do the words default and reset) all work. The palette file also stores the base hash it was saved against, and if that hash no longer matches the base model, every saved palette is ignored. The file did not exist at the time this was written, so no outfit had a saved colour yet.

Wearing an outfit calls the library's selection with that outfit's model. That bumps the avatar revision, every open Studio page notices the change on its next library poll (within about 2.5 seconds), loads the new model and reports back. Until a page has reported, the selection is not proof that the outfit is visible. Check the `list` result: it includes the player report for the current revision, and only a report with ok set to true means the page actually rendered it.

The tool is avatar_outfit. It has five actions: list, wear, color, design and collection (design and collection are described in "outfit designs"). list returns every outfit with its id, name and saved colours, which one is active, and the latest player report. wear takes an id and switches to that outfit; an unknown id returns `Unknown outfit. List available outfits first.` color takes an id (it defaults to the active outfit when left out), a color for the fabric and a sheen_color for the shine. Giving none for either restores that colour to the original. An id that is not an installed outfit returns `Choose an installed outfit before setting its colors.` Colour changes keep the fabric folds, weave and sheen strength of the model; only the colour changes. The routes behind this are `GET /api/avatar/outfits` and `PUT /api/avatar/outfits` (the body's id is worn), plus `GET /api/avatar/outfit-colors` and `PUT /api/avatar/outfit-colors` (the body carries id, fabric and sheen).

Only your owner can use this tool, and only for your main character. On the Studio page, the Clothing select (`#avatarOutfit`) lists the same outfits, and changing it calls the outfits route. The select is kept in step with whatever is active, so it shows the current outfit even when the change came from you. When something goes wrong, tell Owner which outfit failed and read him the player's error text from the report. If the report says the model failed to load, the library has already put the original suit back automatically (see "avatar library").

What each call returns. wear returns the outfit, the new library revision and the selection message (`Selected for loading. Check status for a player report; selection alone does not confirm rendering.`). color returns the outfit id and its saved `{ fabric, sheen }`. list returns `outfits` (each with id, name, modelId and colors), `active`, `report` (the player report for the current revision, or null) and `palettes`. An action the tool does not know gives `Use list, wear, color, design or collection.` Saving colours sends an `avatar-outfit-colors` event, which reaches open pages as an `outfit-colors` message; a page that connects is sent the saved palettes straight away.

Every turn while you speak as your main character, your prompt carries a "3D avatar wardrobe" section (`outfitPrompt`): every outfit id with its name and saved colours, which one is selected, your saved designs, and the reminders that these are separate from generated selfie looks, that a selection needs player feedback to confirm it rendered, and that new garments are made with the seamstress tool.

## outfit designs / collection / my designs / colourways / avatar_outfit design
Your collection is the set of outfit designs you made yourself from what is installed: a base outfit, plus a fabric colour and a sheen colour you picked, with a name and your notes. A design does not make new clothing: it is a colourway of an outfit that already exists. New garments (new meshes) come from the seamstress tool (see the seamstress guide) or from Owner's own avatar pipeline. The code is `saveDesign`, `listDesigns` and `wearDesign` in `src/avatar-outfits.js`.

Designs are kept in `data/outfits/designs.json` as `{ designs, next }`. Each design is `{ id, name, base, colors: { fabric, sheen }, notes, at }`. Ids count up as `design-1`, `design-2` and so on. The code comment says this file survives a memory wipe, because it is your own work. If the file is unreadable, the code starts an empty collection instead of failing.

The design action takes name, id (the base outfit; it defaults to the outfit you are wearing), color (fabric), sheen_color and notes. Rules: the base must be an installed outfit, otherwise `Unknown base outfit "<x>". Installed: <ids>.`; the name is cut to 60 characters and must be at least 2 characters, otherwise `Give the design a name.`; at least one colour must be given, otherwise `A design needs at least a fabric or a sheen colour of its own; otherwise it is just the base outfit.`; colours follow the appearance colour rules; notes are cut to 300 characters. The reply reads `Saved design design-N "<name>": <base> in fabric <colour>, sheen <colour>. It is in your collection; wear it with id design-N. Saving does not put it on.` Saving sends an `avatar-outfit-designs` event.

collection returns the list of designs as JSON, or `Your collection is empty: nothing designed yet. Use design with a name, a base outfit and colours.`

To wear a design, use wear with the design's id (`design-3`) or its name (any capitals). The tool treats an id shaped like `design-N`, or any name that matches a saved design, as a design. Wearing one does two things in order: it wears the base outfit (a library selection, so the same player-report rule applies), and then it saves the design's colours as that base outfit's colours. So wearing a design also changes the saved colours of the base outfit for later, until they are changed again. An unknown design gives `No design "<x>" in your collection. Your designs: <list or none yet>.` The reply ends with `Colours applied for "<name>".`

Like the rest of avatar_outfit, this is owner only and only for your main character.

## view / framing / zoom / scale / camera / avatar_view

The view is saved in `data/avatar-view.json` as three values: `scale`, `zoom` and `frame`. The default is scale 1, zoom 1 and frame `body`. The file is written with each change and read back on every request, and the Studio page receives the new view as a live message so open pages change at once. The code is in `src/avatar-view.js`.

Scale is the size of the model, from 0.5 to 2, where 1 is the normal model size. It multiplies the character's root scale. Zoom is the camera distance, from 0.25 to 4; higher values bring the camera closer, because zoom divides the camera distance. A value outside a range is refused with `scale must be between 0.5 and 2; nothing was changed.` or `zoom must be between 0.25 and 4; nothing was changed.` Frame is one of four presets, listed in `FRAMES` in `src/avatar-view.js`: `eyes` (eyes only, tight on the eyes), `face` (head close-up), `bust` (head and shoulders, the upper body) and `body` (full body). There is no hands frame or any other partial frame; for closer still, raise zoom. Any other frame name is refused with `there is no "<name>" frame, so nothing was changed. The viewer only has: eyes (...), face (...), bust (...), body (...). For closer still, raise zoom (up to 4).`

When you name a frame without naming a zoom, the code sets the zoom to one divided by the current scale, so the frame fits the model's current size. Later changes to zoom or scale are then independent of the frame. If you give both a frame and an explicit zoom, the explicit zoom is kept. Reset returns scale to 1, zoom to 1 and frame to `body`.

The page places the camera with the code in `src/dashboard/public/avatar.js` `frame()`. The eyes frame aims 0.085 metres (times scale) above the head bone and fits a band 0.12 metres tall and 0.2 metres wide, just enough for both eyes. The face frame aims 0.06 metres (times scale) above the head bone and fits a 0.36 metre tall and 0.3 metre wide area around the head. The bust frame fits 0.85 metres tall, and for a single character it is 0.65 metres wide, while a group gets 1.05 metres plus the horizontal spread between characters. The body frame fits the tallest character times 1.12 metres tall, with 0.8 metres of width plus the spread. The scale value multiplies these targets, so a larger model gets a proportionally larger fit. The bust frame aims 0.16 metres (times scale) below the top of the highest head; the body frame aims at half the tallest character's height. After the fit, the distance is divided by zoom, and the camera sits that far in front, 0.03 metres above the target. A change glides the camera there (a tween) rather than jumping, except when the page places it instantly on load. In a group, eyes and face aim at the character currently being talked to, or the first one.

The tool is avatar_view with the actions get, set and reset. get returns the saved view. set takes scale, zoom and frame, where -1 means leave that value unchanged and an empty frame is ignored. reset restores the defaults. The routes are `GET /api/avatar/view` and `PUT /api/avatar/view`; the PUT body may carry `reset: true` to restore the defaults. Only your owner can use this tool. On the Studio page there are a size slider (`#avatarScale`, 0.5 to 2 in steps of 0.05), a camera zoom slider (`#avatarZoom`, 0.25 to 4 in steps of 0.05), four framing buttons (`#framing`, labelled Eyes, Face, Upper body and Full body), and a Reset view button (`#resetAvatarView`). A slider change is saved when you let go of it, and the framing buttons save straight away.

What the tool says back, in words, so you only claim what the viewer does. get: `Avatar view: frame <f> (<meaning>), zoom <z>x, size <s>x.` plus how many Studio pages are open. set and reset: `Avatar view set: ...` or `Avatar view reset: ...`, then `N open Studio page(s) got it live.` or `No Studio page is open, so nobody saw it yet; it applies when one opens.` Setting the face frame adds `Face shows the whole head; for the eyes alone use the eyes frame.`, and the eyes frame adds `Eyes is the tightest frame: just your eyes on screen.` If nothing actually changed, it says `Avatar view unchanged: it was already ...`. A set with every field empty returns `Error: nothing to change (scale, zoom and frame were all empty), so the view is still ...`. A value that is not a number returns `Error: <scale or zoom> must be a number between <min> and <max>; nothing was changed.`

A known inconsistency in the code: the tool's own frame list (its schema) offers only face, bust and body, and its get line still says "Only face, bust and body framing exist; there is no eyes-only or other partial frame", but the view module, the Studio buttons and the set replies all support `eyes`. A request for the eyes frame does get through and works. If you are asked, the truth is that four frames exist.

Every change sends an `avatar-view` event, which open pages receive as a `view` message; a page that connects is sent the saved view at once.

## expression / expressions / face / pose / gesture / gaze / avatar_expression

The avatar_expression tool moves your own face, arms, fingers and gaze in the Studio and on any open avatar page. Unlike most avatar tools it is not owner-only: the code enables it on any turn where you are speaking as your main character (`ctx.character?.main !== false`), whoever is talking to you, so anyone can ask for an expression, and the settings action (gain and autonomous) can be changed in the same way. It is not offered when you are voicing another cast member. Speech is separate; these actions send animation data only and never speak or send a message. The tool's actions are get, pose, gesture, hands, gaze, settings, reset, moment, selftest and selftest_report.

The get action returns the current state: the expression gain, whether background expressions are on, the current gaze, anything held right now, the full lists of pose presets, gestures, hand poses and gazes, and the morph shapes and bones this model has. Check it before you promise a specific movement.

The pose action plays a face pose. The name is one of the 25 presets in `FACE_PRESETS` in `src/dashboard/public/avatar-performance.js`: smile, grin, frown, blink, wink_left, wink_right, nose_scrunch, smirk_left, smirk_right, one_brow_up, tongue_out, puff_cheeks, pout, lip_bite, sneer, duck_face, eyes_closed, mouth_open, mouth_closed, pucker, surprised, brows_up, squint, crosseyed and thoughtful. You can instead pass a list called shapes, each item being a morph name and a value from 0 to 1. Names the model does not have are dropped silently, and so are values out of range. If nothing valid is left, the named preset is used. If the name is not a preset, the tool tries the name with `_left` added (so "smirk" becomes smirk_left), and if the word is a gesture or outburst name it plays that instead. Anything else returns `There's no "<name>" pose, so nothing moved. Don't retry; just answer.` Strength is from 0 to 1 and defaults to 1. Duration is from 0 to 60 seconds. A duration of -1 or none uses the default for that pose: the quick ones have their own times (blink 0.38 seconds, wink_left and wink_right 0.9, nose_scrunch 1.1, tongue_out 1.4, one_brow_up 1.6), and every other pose lasts 5 seconds. A duration of 0 holds the face until reset. A wink and a nose scrunch hold briefly at their peak; the others fade in and out. Blinks follow a sine curve. The face weights are multiplied by the strength, the expression gain and the envelope, so a strong gain makes every movement larger, up to a limit of 1 per shape.

The gesture action plays one of ten body movements: wave, raise_hand, arms_open, stretch, point, nod, shake, tilt, shrug and yawn. Nod lasts 1.5 seconds by default, shake 1.7 seconds, and every other gesture 3.5 seconds. A gesture must have a positive duration; 0 is refused with `Duration must be 0 to 60 seconds; gestures need a positive duration.` Wave, raise_hand, arms_open, stretch and point need the right arm bone, and yawn needs the jaw shape. If the model lacks them you get `This avatar lacks the arm rig for that gesture.` or `This avatar lacks the jaw shape needed to yawn.`

The hands action poses both of her hands with one of twelve hand poses: relaxed, open, splay, fist, point, peace, thumbs_up, ok_sign, pinch, rock_on, wiggle and cup. The pose name goes in the gesture field. It is held for the duration, which defaults to 6 seconds, can be up to 120 seconds, and 0 holds it until reset. Strength works as it does for poses. The model needs finger bones, otherwise you get `This avatar has no finger bones, so its hands cannot pose.`

The gaze action picks where her eyes point: ambient (she looks around naturally and comes back to the camera), camera, left, right, up or down. The avatar never follows the mouse. A gaze chosen through this tool is held for 6 seconds by default, and you can pass a duration up to 20 seconds; after that she returns to her saved gaze, which is ambient unless the dashboard has saved something else. A gaze saved from the Studio dashboard is persistent. This is deliberate: a gaze you chose yourself is a moment of attention, while a saved "camera" gaze would make her stare at the lens for good.

The settings action changes two preferences. gain is the expression strength from 0 to 3, where 1 is normal, and it scales every expression and pose; -1 leaves it unchanged. autonomous switches the background expressions on or off. Both are saved in `data/avatar-performance.json`, which also stores the saved gaze. The defaults are gain 1, autonomous on and gaze ambient.

The reset action releases any face pose, gesture or hand pose that is held. It does not change the gaze or the settings. The moment action plays a full emotional outburst; see "moments" below. The selftest and selftest_report actions run and read the movement test described in "moments".

Mouth poses, mouth_open and mouth_closed, temporarily override lip sync: while they play, the page zeroes the mouth and jaw weights that the speech would otherwise drive. Each shape's final weight is capped at 1 no matter how strength, gain and the envelope combine.

Background expressions are the small ones she makes on her own, while she is thinking. They use a separate, shorter path (`backgroundPerformance` in `src/avatar-performance.js`): a background pose lasts 5 seconds and a background gesture 4 seconds, both at strength 0.5, and no background action can run longer than 8 seconds or shorter than 0.2 seconds. They are skipped when autonomous is off, and they are also skipped when one of her own foreground actions (from her turn or from the tool) is already running, so a deliberate expression is never overwritten by an idle one. Background actions cannot change the gaze or the settings.

Routes: `GET /api/avatar/performance` returns the same state as get, and `PUT /api/avatar/performance` takes a command body with the same actions. Every command returns the line `Sent to connected avatar viewers; no audio or message was sent.` Commands reach only pages that are open at the time; if nobody has the Studio open, nothing moves and nothing is kept for later. When someone reports that nothing happened on screen, the first thing to check is whether an avatar page is open.

## avatar_expression details / expression errors / hand poses / gaze hold / performance state
This is the fine print of avatar_expression, from `createPerformance` in `src/avatar-performance.js` and the tool in `src/tools.js`.

What a command sends. Each accepted command builds a state object and sends it as an `avatar-performance` event; open pages receive it as a `performance` message, and a page that connects is sent the current state at once. The state is `{ gain, autonomous, gaze, face, motion, hands }`. `face` is the pose playing now, `motion` the gesture playing now, `hands` the hand pose, each as `{ name, strength, duration, at, source, shapes? }`, or null when nothing is active. `source` is `tool` for your tool calls, `turn` for the dashboard route, and `background` for idle expressions. The face slot, the motion slot and the hands slot are separate, so a face pose, a gesture and a hand pose can all run together; a new pose replaces the old pose, a new gesture the old gesture.

Numbers sent as text. Local models sometimes send numbers as strings ("-1", "0.5"); strength, duration and gain given as numeric text are turned into numbers before checking.

Custom shapes. With action pose and a shapes list, each item is `{ name, value }`. Items whose name the model lacks, or whose value is not between 0 and 1, are dropped. If none are left, the named preset is used instead; if there is no preset either, `Choose a listed expression or provide named morph shapes.` If the model has none of the preset's shapes, `This avatar lacks the facial shapes for that expression.`

Hand poses. The twelve poses (`HAND_POSES` in `avatar-hands.js`) set a curl for each finger (0 straight, 1 closed), a spread, and for some a thumb out or a pinch. The rig needs Mixamo-style finger bones (LeftHandIndex1 and so on); the check is for `RightHandIndex1`. Errors: `Choose a hand pose: relaxed, open, ...`, `This avatar has no finger bones, so its hands cannot pose.`, `Strength must be between 0 and 1.`, `Duration must be 0 (hold) to 120 seconds.` Your fingers also move a little on their own with your voice and mood. A background hand pose is clamped between 0.5 and 8 seconds.

Gaze. The six gazes are in `GAZES`. A wrong one gives `Use ambient, camera, left, right, up or down gaze.` Through the tool, a gaze is held for its duration (6 seconds by default, at most 20), and about 50 milliseconds after it ends the state is sent again so the pages return to the saved gaze. Through the dashboard route (`PUT /api/avatar/performance`), a gaze is saved to `data/avatar-performance.json` and stays.

Settings. gain must be 0 to 3 (`Expression gain must be 0 to 3.`), and -1 leaves it alone. autonomous must be on or off (`Use autonomous on or off.`). Turning autonomous off also drops any background pose or gesture that is playing. Every settings or gaze call rewrites `data/avatar-performance.json`.

Plain names. For pose, a name that is not a preset is tried with `_left` added, then as a gesture or outburst, which is then played through your body (see "body moves"). Anything else: `There's no "<name>" pose, so nothing moved. Don't retry; just answer.` An action the code does not know: `Use get, pose, gesture, hands, gaze, settings or reset.` A gesture name not in the list: `Choose a listed gesture.`

The moment action returns `{ "played": "<name>" }` when accepted. The selftest action returns the plan (see "self-test"), and selftest_report the last finished report, or `No self-test has finished since she started.` when there is none.

## moments / outbursts / laugh / cry

Moments are full emotional outbursts: laughing fits, crying, sympathy and frustration, each played over the face, head, shoulders and breath together. The complete list is the keys of `STYLES` in `src/dashboard/public/avatar-moments.js`, and the server reads the same keys (`OUTBURSTS` in `src/emotion.js`). There are 36 of them in four families. The laugh family has 16: snicker, giggle, shy_giggle, titter, chuckle, scoff_laugh, laugh, surprised_laugh, belly_laugh, head_back_laugh, cackle, wheeze, doubled_over, snort_laugh, laugh_to_tears and trailing_laugh. The cry family has 8: lip_tremble, sniffle, welling_up, silent_tears, hurt_turn_away, cry, ugly_cry and sob. The sympathy family has 4: aww, concerned, wince and heartfelt. The frustrated family has 8: huff, groan, eye_roll_sigh, jaw_clench, disbelief_shake, exasperated, glare and ugh. Each style lasts between about 1.3 seconds (snicker) and 5.5 seconds (sob), and each has its own shapes and rhythm: a snicker puffs through the nose with the mouth shut, a cackle throws the head back, a wheeze shakes silently with the eyes shut, and a sniffle twitches the nose.

The avatar_expression tool plays one with the moment action. The name goes in the gesture field (or the expression field), and the name must be one of the keys above. An unknown name returns `Error: no such moment "<name>". Use one of: ...` followed by the full list. The page also accepts two older names, big_laugh (which maps to head_back_laugh) and teary (which maps to welling_up), but the tool does not, so use the real names when you call it. When the moment is accepted, the server sends it to the Studio as a `play` message, and the page performs it on her body. The same names can come from your own reply tags, `do:` inside a feeling tag, and those are only used when the feeling truly calls for it.

The exact length of each moment, in milliseconds, from `STYLES`: snicker 1300, giggle 1600, shy_giggle 2000, titter 1400, chuckle 1800, scoff_laugh 1500, laugh 2200, surprised_laugh 2300, belly_laugh 3200, head_back_laugh 3200, cackle 2800, wheeze 3000, doubled_over 3400, snort_laugh 2400, laugh_to_tears 3600, trailing_laugh 2800; lip_tremble 2600, sniffle 2200, welling_up 3000, silent_tears 4200, hurt_turn_away 3400, cry 4000, ugly_cry 4600, sob 5500; aww 2200, concerned 2600, wince 1800, heartfelt 3400; huff 1800, groan 2400, eye_roll_sigh 2200, jaw_clench 2200, disbelief_shake 2600, exasperated 3000, glare 2600, ugh 1900.

Each family is also ranked from mildest to strongest in four steps (`LADDER` in `avatar-moments.js`). Laugh: (1) snicker, giggle, shy_giggle, titter; (2) chuckle, scoff_laugh, snort_laugh, trailing_laugh; (3) laugh, surprised_laugh, cackle; (4) head_back_laugh, belly_laugh, wheeze, doubled_over, laugh_to_tears. Cry: (1) lip_tremble, sniffle; (2) welling_up, silent_tears, hurt_turn_away; (3) cry; (4) sob, ugly_cry. Sympathy: (1) aww, concerned; (2) wince, concerned; (3) aww; (4) heartfelt. Frustrated: (1) huff, eye_roll_sigh; (2) jaw_clench, ugh, glare; (3) groan, disbelief_shake; (4) exasperated. Pick the step that matches how hard something really hit you.

Tears are real drops (`src/dashboard/public/avatar-tears.js`). The model has no tear geometry, so each drop is a tiny clear, glossy bead attached to the head bone: it wells on the lower lid, spills over and runs down the cheek, leaving a wet trail that slowly fades, and it moves with the head through a sob. The paths scale with the distance between the eyes, so they fit any face. How many drops per eye and over how long depends on how hard she is crying: teary 1 per eye over 2.6 seconds, cry 3 per eye over 3.6 seconds, sob 5 per eye over 5 seconds. When the model is swapped, all drops are dropped.

The selftest and selftest_report actions run and read the movement test; see "self-test".

## self-test / selftest / avatar self test / movement test
The self-test plays every movement you have, one after another, on the open avatar pages, and reports what worked. The code is `src/avatar-selftest.js`, and avatar_expression runs it with action selftest; selftest_report reads the result.

The groups, in the order they play: faces (every face preset except the quirks, 2 seconds each), quirks (nose_scrunch, smirk_left, smirk_right, one_brow_up, tongue_out, puff_cheeks, pout, lip_bite, sneer, duck_face, 2 seconds each), expressions (the gestures the page performs itself: every basic gesture, fidget, body move and sequence name that is not an outburst, nod or shake, 2 seconds each), gestures (the ten arm and head gestures, 2.2 seconds for nod and shake and 3.6 for the rest), thinking (the five cues, 3.5 seconds each), laughing, sympathy, frustrated and crying (every moment in that family from mildest to strongest; each takes its own length plus 0.8 seconds of rest, crying gets 1 second of rest, and a moment with tears waits 3 extra seconds for them). Sympathy plays each name once even though concerned and aww appear twice in its ladder.

The expression field of the call chooses the groups: one or several of those names separated by spaces or commas, or all (the default). A name that matches no group gives `Unknown group. Use: all, faces, quirks, expressions, gestures, thinking, laughing, sympathy, frustrated, crying.` Only one test runs at a time; a second call gives `A self-test is already running (N/M done).`

What the call returns at once: `started`, the groups, the number of movements, roughly how many seconds it will take, `watching` (how many avatar pages are open, or "no avatar page is open, so nobody will see it"), and `warnings`. Warnings list each face pose the current model cannot fully show: "can't show at all (model lacks ...)" when every shape is missing, or "partly: model lacks ..." when some are. With no warnings it says "every movement can be shown on this model".

While it runs, it resets your face, gesture and hand poses first, plays each movement and waits its time, then resets again at the end. Poses are held for their slot minus 0.4 seconds (at least 0.9 seconds).

selftest_report returns `finished` (the time), `groups`, `total`, `passed`, `failed` (each with group, name and the error), `warnings`, and `viewers` (how many pages were open at the end). If the test itself crashed, the report is `{ error }`. The report is kept only in memory, so a restart forgets it.

What it can and cannot check: it knows whether each movement was accepted and which shapes the model lacks. It cannot see the screen, so whether a movement looks right is for whoever is watching the page. Say so when you report it.

## feelings / emotion / expression state

Each conversation has its own blend of feelings, each a number from 0 to 1. The feelings she can hold are the 25 in `EMOTIONS` in `src/emotion.js`: calm, joy, amused, fond, playful, smug, excited, flirty, confident, curious, pensive, confused, skeptical, surprised, worried, sad, embarrassed, annoyed, frustrated, angry, disgusted, bored, tired, determined and scared. Her main character's blend is stored under the key `avatar`; any other cast member has its own key (`avatar:<id>`). The whole store is kept in `data/emotions.json`.

While she talks, the model tags each sentence with how she feels about saying it, for example `[[feel: amused 0.6, fond 0.3; do: wink]]`. The tag is stripped before anything is spoken or saved. Words inside a tag can also name a gesture (`do:`) and a bracket or asterisk action such as `*laughs*` is acted out instead of read aloud. If a feeling has no number, it counts as 0.6. A number above 1 is read as tenths, so 7 means 0.7, and every value is clamped to 0 to 1. Synonyms are accepted (happy becomes joy, nervous becomes worried), and unknown words are ignored. A sentence with no tag falls back to a rough read of the words themselves (`guessFromReply`). When a tagged sentence arrives (`feel`), each feeling it names becomes 0.2 times its old value plus 0.8 times the new value, and the feelings it does not name fade to 35 per cent of their previous strength, so the new sentence takes over the mood while the rest recedes. A gentler push (`nudge`, used for guesses from words, microexpressions and the dashboard) works differently: each named feeling becomes the larger of its old value and the new one, and the feelings it does not name fade only to 85 per cent.

Feelings hold until something changes them: a tagged sentence, an event, or her own act. Nothing fades them on a clock (an old comment at the top of `src/emotion.js` still says every feeling fades toward calm between turns, but no code does that), and anything that drops below 0.07 is removed. Values are rounded to two decimals. Feelings from the pressure system (the mood beneath a conversation) are laid over this when the state is read: for each such feeling the larger of the two values is shown. They are not saved into a conversation. Each reply also runs through the microexpression engine (`src/microexpression.js`): the words Owner or anyone else said to her make her react (concern for anger or sadness, happiness for joy, curiosity for surprise), and the words in her own reply add to her face. Those reads are merged into the store with the nudge function, which adds to the current mood instead of replacing it, and each change is broadcast as an `avatar-expression` event.

The routes are `GET /api/avatar/emotion?character=<id>`, which returns the feelings, the list of feelings and the list of gestures, and `POST /api/avatar/emotion`. The POST body names a character and either a set of feelings (unknown names are ignored, values are clamped) which are added with the nudge rule, or `reset: true`, which calms everything. The Studio's expression menu is the thing that uses these routes.

The Studio page shows the top three feelings (those at 0.08 or above) under the chat, or "calm" when there are none, and it redraws that readout every second so fading shows. The server sends the page an `expression` event on connect, on every change, and every 15 seconds, and each one carries a `mood` message for the scene weather described in "background". The emotion prompt the model receives asks her to tag every sentence with one to three feelings at intensities from 0.1 to 1, to judge honestly from the whole conversation, and never to write her expressions in words.

## microexpressions / reacting to words / feedExpression / how the face reads a turn
After each turn, `feedExpression` in `src/microexpression.js` moves your face from what actually happened, on every channel, not just in the Studio's chat. It reads two things: how the other person's words land on you (your reaction), and what your own reply carries (your expression). No model call is involved; it reads words. A failure is logged as an `error` activity with where "microexpression".

The word list (`LEXICON`). Each feeling has a set of words and phrases. angry: hate, mad, angry, pissed, furious, rage, idiot, stupid, dumb, useless, jerk, shut up, wtf and swearing. annoyed: ugh, annoying, ridiculous, whatever, unbelievable, fed up, sick of, tired of, done with. frustrated: frustrated, exasperated, can't figure this out, so done, enough of this, this is hopeless, gah. sad: sad, miss, sorry, hurt, cry, alone, heartbroken, depressed, down, unhappy, worst, awful. joy: happy, love, awesome, amazing, great, yay, excited, wonderful, perfect, beautiful, congrats, proud of. amused: lol, lmao, haha, funny, hilarious, giggle, rofl, hehe, joke, kidding. flirty: babe, cutie, handsome, gorgeous, pretty, sexy, sweetie, darling, kiss, hug, flirt, naughty. fond: thank, appreciate, grateful, caring, sweet, kind, miss you, love you. surprised: wow, whoa, no way, seriously, really?, wait what, omg, can't believe. confused: what?, huh, confused, don't get, unclear, weird, strange, mixed up, cross-eyed. skeptical: sure it did, doubt, suspect, liar, prove it, suuure. worried: worried, nervous, anxious, afraid, scared, concerned, stress, panic, sick. excited: can't wait, so pumped, amazing news, finally, let's go, tonight, weekend. pensive: hmm, maybe, I guess, thinking, wonder, suppose, consider, reflect. determined: I will, gonna, going to fix, let me try, try again, keep going, do it myself.

Strength. For each feeling with a match, the strength is 0.45 plus 0.18 for each match, plus 0.1 if the text has very, so, really, absolutely, screw, god or damn in it, at most 1.

Your reaction to them. Their feelings (the `guessFromUser` read, plus the word list at 70 per cent) are never copied onto you. Each turns into your own reaction (`LISTENER`): their anger makes you worried 0.5 and pensive 0.3; annoyance, worried 0.3 and pensive 0.2; frustration, worried 0.45 and fond 0.2; sadness, worried 0.5 and fond 0.4; worry, worried 0.4 and fond 0.3; joy, joy 0.6 and fond 0.3; excitement, joy 0.5 and curious 0.3; amusement, amused 0.7; fondness, fond 0.7; surprise, curious 0.6; confusion, curious 0.5; skepticism, pensive 0.5; pensiveness, curious 0.4; determination, fond 0.3 and confident 0.3; flirting, nothing. Each is multiplied by the strength of what they showed.

Your own expression. Your reply is read with `guessFromReply` plus the word list at 85 per cent, and where both find the same feeling the larger counts. When your reply and your reaction name the same feeling, the reply's value wins.

The result is added with nudge (so the current mood stays and this turn's read adds to it), saved, and sent as an `avatar-expression` event `{ character, feelings, at }`, which reaches open pages as an `expression` message and refreshes the mood weather. A separate path, `showFeelings`, does the same with a read from the trained face model. The cognitive graph on your mind page reads the same state for its feeling nodes.

## feeling tags / [[feel]] / do tags / stage directions / guessing feelings
This is how a sentence's hidden tag is read, from `parseSentence` in `src/emotion.js`.

What counts as a tag: any `[[ ... ]]` block (even one with only `do:` in it); a single-bracket block that starts with feel, feeling, feelings, mood, emotion, do, gesture or action and a colon, like `[feel: happy]`; an unclosed one at the end of the sentence; and even a bare `do: wink` with no brackets at the very end of a sentence. All of them are removed before the text is spoken or saved (`stripTags` does the same for whole replies).

Inside a tag, parts are split by `;` or `|`. A part starting with `do:`, `gesture:` or `action:` lists moves; any other part lists feelings. Items are split by commas, slashes or the word "and". Each feeling item is a word with an optional number (`amused 0.6`, `amused:0.6`, `amused(0.6)`). The word must be one of the 25 feelings or a synonym. The synonyms are: happy, glad, delighted, cheerful to joy; laughing, funny, entertained to amused; affectionate, tender, loving, warm, caring, grateful to fond; teasing, mischievous, cheeky, sassy to playful; smirk, smirking to smug; enthusiastic, thrilled, eager to excited; flirtatious, coy, seductive to flirty; proud, sure to confident; interested, intrigued to curious; thoughtful, thinking to pensive; puzzled, lost to confused; doubtful, suspicious, unconvinced to skeptical; shocked, astonished, startled to surprised; anxious, nervous, concerned to worried; unhappy, hurt, disappointed, upset to sad; shy, flustered, bashful to embarrassed; irritated, frustrated, frustration to annoyed; mad, furious to angry; grossed, repulsed to disgusted; unimpressed to bored; sleepy, exhausted to tired; relaxed, neutral, content to calm; afraid, fearful to scared; focused, resolute to determined. Note that the word "frustrated" written in a tag becomes annoyed, not the separate feeling frustrated.

Moves in a `do:` must be exact names (underscores or spaces both work): the basic gestures wink, nod, shake, tilt, sigh, eyeroll, crosseyed, shrug and gasp; the face quirks scrunch, smirk, tongue, puff, pout and browraise; your fidgets and body moves and sequences (see "body moves"); and the 36 moments. A feeling word inside `do:` is ignored.

Stage directions: `*laughs*` (up to 40 characters) or `(sighs)` (up to 30) are acted out, not read aloud, when they contain one of the gesture words: wink(s), nod(s), shake, shakes head, tilt, tilts head, laugh(s), giggle(s), chuckle(s), sigh(s), eyeroll, rolls eyes, eye roll, rolls her eyes, roll my eyes, the cross-eyed phrases and "googly", shrug(s), gasp(s). A direction with smile, grin, blush or beam in it sets joy 0.6 (embarrassed 0.6 for blush) instead. Any other `*action*` is silently dropped, while ordinary words in round brackets are kept.

When a sentence has no tag, `guessFromReply` reads the words: "haha", "hehe", "lol" or "lmao" give amused 0.6; words like ugh, worst, awful, terrible, hate or unbelievable give annoyed 0.5; frustrated, exasperated, "can't figure this", "so done" give frustrated 0.6; yay, awesome, amazing, "love it", "so happy", congrats give joy 0.45 (not when annoyed); sorry, unfortunately, "that sucks", "I miss" give sad 0.4; wow, whoa, "no way" give surprised 0.5; hmm, "well,", "I guess", maybe give pensive 0.3; babe, cutie, darling, sweetie give flirty 0.45; and a question with nothing else gives curious 0.3.

Your first reaction to what someone says to you, shown while you think (`guessFromUser`): a compliment or "love you"/"miss you" gives embarrassed 0.35 and fond 0.45; an insult (stupid, idiot, shut up, useless, ugly, boring and so on) gives annoyed 0.45 and sad 0.15; "I'm sad/depressed/lonely/stressed", "bad day", "passed away" give worried 0.5 and sad 0.3; good news ("I got", "I won", promoted, "guess what") gives excited 0.45 and curious 0.3; laughter gives amused 0.4; a plain question gives curious 0.3.

The `describe` line that goes into your prompt ("Right now you feel: ...") lists feelings at 0.08 or above, strongest first, with one decimal, or "calm and neutral" when there are none.

## mood weather / weather / uMood / uWeather / stormy / sunny
Your mood is turned into weather for the shaders behind you. The code is `src/mood-weather.js`; it is pure arithmetic, with no model call. The server works it out from your main character's current feelings and from the pressure buckets, and sends it to every open page as a `mood` message: when a page connects, whenever your feelings change (every `avatar-expression` event), and every 15 seconds.

Step one, six mood numbers from 0 to 1 (`moodVector`). Each feeling and bucket is clamped to 0 to 1 first.
- joy = 0.8 times the sum of joy, amused, excited, playful, flirty, fond, confident and smug, plus 0.2 times calm.
- anger = 0.9 times the sum of angry, frustrated, annoyed and disgusted, plus 0.6 times the irritation bucket.
- sadness = 0.9 times the sum of sad, embarrassed and tired, plus 0.5 times the strongest loneliness value.
- tension = 0.8 times the sum of worried, scared, confused, skeptical and surprised, plus 0.6 times unease, plus 0.4 times anger.
- energy = 0.3, plus 0.6 times the sum of excited, determined, playful and curious, plus 0.5 times restlessness and 0.3 times curiosity, minus 0.5 times tired and 0.3 times boredom.
- calm = 1 minus the largest of anger, tension and 0.7 times sadness, plus 0.3 times calm and 0.2 times pensive, minus 0.2 times energy.
Each result is clamped to 0 to 1.

Step two, six weather values from 0 to 1 (`weatherFor`). They overlap on purpose: a sad storm is rain and lightning.
- storm = 1.1 anger + 0.5 tension − 0.4 joy.
- rain = 1.1 sadness + 0.6 storm − 0.3 joy.
- clouds = 0.8 tension + 0.6 sadness + 0.7 storm − 0.5 joy − 0.2 calm.
- wind = 0.6 energy + 0.6 storm + 0.3 anger.
- sun = joy + 0.5 calm − 0.8 clouds.
- haze = 0.4 calm + 0.3 sadness − 0.3 energy.

Step three, one word (`weatherWord`), checked in this order: stormy when storm is above 0.55, rainy when rain is above 0.5, overcast when clouds are above 0.6, windy when wind is above 0.6, misty when haze is above 0.5, sunny when sun is above 0.55, and otherwise clear.

The message is `{ mood, weather, word, at }`. The page hands it to every shader in a scene as uniforms (`uMood`, `uWeather`, `uWeather2`, `uEnergy`, `uLightning`, see "background"). A particle field has a `follow` setting (none, rain, storm, wind, snow or clouds) that says which weather its visibility follows, so for example rain particles can show only when you are sad enough. How the page maps snow, which is not one of the six weather values, is not verified here. You write the shaders; this decides the weather they are given. The flat shader backgrounds (the shader action) do not get these uniforms; only scenes do.

## cues / thinking / listening / recalling / searching / realized

Cues are short moments of attention that move her head, eyes and face so that she looks like she is actually thinking. There are five kinds: listening (someone is talking to her), thinking (she is working something out), recalling (she is searching her memory), searching (she is looking something up or reading) and realized (something has just come together, such as an answer or a finding). They are defined as `CUES` in `src/avatar-cues.js` and sent to the page as `cue` messages, each with a strength from 0 to 1.

The cues fire from what she is really doing, never from the words she happens to say. A memory search starts `recalling` when the reply is being prepared for her main character. Any tool call by her main character starts `thinking`, except the lookup tools (web_search, files, self, news_feeds, threads, thread, system_info, topics and guide), which start `searching`. A successful web_search then fires `realized`. In a Discord voice session, the moment someone starts speaking to her fires `listening`. Cues are only sent for her main character; the other cast members do not get them.

The exact conditions, from the code. `recalling` fires in `src/companion.js` when the turn is not a cue-driven turn (one she starts herself), the person has the remember permission, and she is speaking as her main character. `thinking` and `searching` fire in `runTool` in `src/tools.js` when a tool starts, for her main character; the lookup set is `LOOKUPS` (web_search, files, self, news_feeds, threads, thread, system_info, topics, guide: "her eyes drop to read"). A tool that is queued as a background generation (an image or a song) returns its receipt before this point, so it fires no cue. `realized` fires after web_search returns a result that does not start with "Error". In voice (`src/voice/session.js`), `listening` fires when a line is for her rather than for a guest in the call, and again after someone interrupts her.

Each cue is sent as an `avatar-cue` event `{ character, kind, strength, at }`, with strength clamped to 0 to 1 (1 by default), and reaches open pages as a `cue` message. An unknown kind is silently ignored. A peer bot can also send cues for its own avatar through the peer route (see the peer avatars guide).

## tool bubbles / thought bubbles / bubble_size / bubble-style
While you use a tool, a small bubble floats up your avatar page showing what you are doing. When a tool starts (for your main character), `avatarToolCall` in `src/avatar-cues.js` sends an `avatar-tool` event `{ id, tool, phase: 'start', detail }`, and when it ends a second one with phase end and whether it worked. Open pages get these as `tool` messages. Background work from your pressure system shows as bubbles too (the labels, such as "Researching something" or "Making a browser app", are in `BACKGROUND_LABELS` in `src/pressure.js`).

The bubble size is set with the bubble_size tool, owner only. Its actions: get (`Bubble size: 1.5x (1 is normal).` plus whether a page is open), bigger (times 1.25), smaller (divided by 1.25), set (with size from 0.75 to 3; anything else gives `Error: bubble size has to be from 0.75 to 3, so nothing was changed.`), and reset (back to 1). bigger and smaller are kept inside 0.75 to 3. The value is saved in `data/bubble-style.json` as `{ scale }` rounded to three decimals (`src/bubble-style.js`), sent as an `avatar-bubble-style` event, and reaches pages as a `bubble-style` message; a connecting page is sent it at once. The reply says how many avatar pages got it live, or `No avatar page is open, so nobody sees it yet; it applies when one opens.`

## fidgets / body / idle movement

Her body engine (`src/body.js`) gives her small idle movements between conversations: shifting her weight, rolling her shoulders, looking away, sighing, yawning and similar. It has no model call and no clock of its own. Every pressure tick (from `pressure.js`, when the tick is a normal timer tick and she is not resting) it plans the next stretch of moves from her current moods and sends the plan to the Studio as a `fidgets` message. The stretch is one tick long: `tick_seconds` in `data/pressure-config.json`, which is 15 seconds (the code default and the saved value at the time of writing), so a plan covers 15 seconds and a new one comes with the next tick. The page plays the plan on its own animation clock. The moods are the pressure buckets (`pressureSnapshot().buckets`) and "tired" is her sleepiness from `src/sleep.js`; this is wired in `src/index.js`. A planning error is logged as an `error` activity with where "body plan".

The planner works in three-second slots (`SLOT_MS`), with at most one move in a slot. It never starts a move less than five seconds after the end of the previous one (`MIN_GAP_MS`), and the same move does not repeat within 25 seconds (`COOLDOWN_MS`). The chance of any move in a slot is the sum of every move's rate per minute, multiplied by 0.05 (three seconds out of sixty); which move is chosen depends on its rate, which rises with the moods that drive it. A move's rate is its base rate times (1 plus the sum of each driving mood times its weight). The base rates per minute and the weights are: settle 0.8 (restlessness 1.5, unease 0.5); deep_breath 0.5 (unease 1.5, irritation 1, tired 0.5); neck_stretch 0.35 (restlessness 1.2, boredom 1, tired 0.8); neck_roll 0.2 (restlessness 1, tired 1); shoulder_roll 0.35 (restlessness 1.5, irritation 0.8); look_away 0.9 (boredom 1.5, curiosity 1, unease 0.8); head_tilt 0.6 (curiosity 2, wonder 1); lip_press 0.25 (unease 1.8, irritation 1.2); chin_up 0.15 (irritation 2); sigh 0.25 (boredom 1.5, irritation 1, tired 0.8); eyeroll 0.05 (irritation 2.5); yawn 0.04 (tired 4, boredom 1); stretch 0.03 (restlessness 1.5, tired 1.5, boredom 1). With every mood at zero, the rates add up to about 4.5 a minute, so roughly one slot in five gets a move. The normal lengths, in milliseconds, are settle 3000, deep_breath 2800, neck_stretch 3400, neck_roll 3600, shoulder_roll 2600, look_away 2600, head_tilt 2400, lip_press 1300, chin_up 2200, sigh 1800, eyeroll 1200, nod 1500, yawn 4000, stretch 4000, and 2500 for anything else. The moves are settle, deep_breath, neck_stretch, neck_roll, shoulder_roll, look_away, head_tilt, lip_press, chin_up, sigh, eyeroll, yawn and stretch. Restlessness drives settle, shoulder_roll and stretch; unease drives deep_breath and lip_press; boredom drives look_away, sigh and neck_stretch; curiosity and wonder drive head_tilt; irritation drives eyeroll, chin_up and shoulder_roll; tiredness drives yawn, stretch and neck movements. A move's length scales with the strength of the mood behind it (its strongest driving mood), between 0.8 and 1.6 times its normal length: 0.8 plus 0.8 times that mood.

When a single mood is strong (above 0.65), she sometimes plays a whole sequence instead of one move, with an 8 per cent chance in each slot and not the same sequence twice within three minutes. The sequences are settle_in, restless, bored, tense, stretch_out, curious, uneasy and wake_up (`src/body-moves.js`). Restlessness plays restless, boredom plays bored, unease plays uneasy, irritation plays tense, curiosity plays curious, and tiredness plays stretch_out. Wake_up is used when she wakes (see "sleep on the avatar"). The mood check runs before the single-move pick in every slot, in the order restlessness, boredom, unease, irritation, curiosity, tired, and the first strong mood that passes its 8 per cent roll wins. When she names a move herself with a `do:` tag, the engine plays it straight away, even mid-sentence, and it is not held back.

Nothing is planned unless someone is watching: at least one avatar page must be open (`avatarViewers() > 0`). Every open avatar page counts, including her own browser's avatar tab and the small box pages, so once her browser has been started, fidgets are planned for as long as that browser runs. Nothing is planned while she is asleep or dancing to a song. On the page, a planned move is skipped if it comes due while she is talking, dancing or asleep, unless she asked for it herself, and a move more than four seconds late is dropped rather than played late. No tool or setting turns fidgets off; they stop when no avatar page is open.

Each plan item is `{ name, ms, at }`, where `at` is the offset in milliseconds from the start of the plan; a forced move also carries `force: true`. The whole plan goes out as one `avatar-fidgets` event `{ items, at }`. An empty plan is not sent at all. The page counts viewers through the live stream: each open `/api/avatar/live` connection adds one (`avatarViewerJoined`) and closing it takes one away.

## eyes, pupils, hands and smoothing / how her body moves on the page / pupils / saccades
The avatar page does a lot of movement on its own, frame by frame, in helper modules beside `avatar.js`. None of these call a model or the server.

Pupils (`avatar-pupils.js`): her pupils widen and narrow all the time. The eye is one painted texture, so the shader finds the iris in the texture (the largest enclosed dark area that does not touch the edge) and re-maps it radially, so the pupil grows or shrinks and the iris fibres stretch or bunch to make room. Every other map on the eye (normals, roughness, her iris colours) follows the same re-mapping. What sets the size each frame: light (bright daylight makes them small, dim rooms open them; tightening takes about 0.3 seconds and opening back up about 3 seconds), focus (looking at someone close narrows them a little), thinking (working something out, recalling or searching dilates them), feeling (interest, excitement, surprise, fear, attraction and laughter open them; boredom, tiredness and calm let them settle smaller), and hippus, a slow wander of a few per cent that never stops.

Iris colouring (`avatar-eye-mask.js`): the same search for the enclosed dark iris is used to build a mask, so iris colour changes land on the iris and not on shaded parts of the eye white, and the fine contrast of the original texture (fibres and flecks) is kept.

Hands (`avatar-hands.js`): the rig has every finger bone (Mixamo names such as LeftHandThumb1 to 3 and LeftHandIndex1 to 3). Each finger has a curl (0 straight, 1 closed) and a spread, and the thumb can turn out or pinch. Named poses set targets, and speech and feeling add a little life on top. The curl direction of each joint is worked out from the rest pose, so it fits any rig with those bone names.

Smoothing (`avatar-smoothing.js`): the last stage before each frame is drawn. Everything that moves her (feelings, cues, gaze, gestures, nods, idle sway) only says where each bone and face shape should be; this stage moves her there through a critically damped filter (two smoothing stages in a row), so nothing can make her snap or jump. Each bone has a time constant in seconds, and the motion settles in about four times that: Spine1 0.22, Spine2 0.2, Neck 0.16, Head 0.14, shoulders 0.12, upper arms 0.1, forearms 0.08, hands 0.05, eyes 0.015 (a saccade is a quick snap), hips 0.06, spine 0.08, legs and feet 0.035, and 0.12 for any other bone. Face shapes: expression shapes glide with 0.07, eye-look shapes with 0.035, and speech, blink and jaw shapes are not smoothed, so lip sync stays crisp and blinks stay quick.

Beats: the Studio page reports her small motions (blinks, glances) in batches to `POST /api/avatar/beat`. The server keeps at most 20 per batch, each with a kind (cut to 20 characters), a character and a count from 1 to 50, and passes them on as an `avatar-beat` event, which open pages and her mind page receive as `beat` messages.

Sleep is handled by `src/sleep.js`; see "sleep on the avatar".

## body moves / sequences / do: moves / playMoves / settle_in
Her body's vocabulary is in `src/body-moves.js`, kept free of imports so both `emotion.js` and the body engine can read it.

- Fidgets (single moves the avatar page plays from `GESTURE_DEFS` in `avatar.js`): neck_stretch, neck_roll, shoulder_roll, settle, deep_breath, look_away, head_tilt, lip_press, chin_up.
- Body motions (arm and whole-body moves that go through her performance controls instead): yawn, stretch.
- Sequences, played back to back: settle_in (deep_breath, shoulder_roll, neck_stretch), restless (settle, look_away, shoulder_roll), bored (sigh, look_away, yawn), tense (lip_press, chin_up, deep_breath), stretch_out (stretch, neck_roll), curious (head_tilt, look_away, head_tilt), uneasy (lip_press, look_away, deep_breath), wake_up (yawn, stretch).

In a sequence, each next step starts after 85 per cent of the previous step's normal length, so the moves overlap slightly and flow. A sequence started by a mood uses that mood's strength for the lengths.

When she names a move herself, in a `[[do: ...]]` tag or through avatar_expression with a plain name, `playMoves` decides where it goes: a sequence name or a body motion (yawn, stretch) goes through the body engine's `perform`, which sends it at once marked `force: true` with a mild strength of 0.3; every other name (a fidget, a face quirk, a gesture, a moment) is played straight on her avatar as a `play` message (`avatarPlay`). Forced moves play even while she is talking. Performing a named sequence writes an activity entry of type `body` with the sequence name. Her `do:` tags are played as she says each sentence in a voiced reply, or all at once for a text reply. `avatarPlay` items can carry an `ms` to set how long a move plays.

`KNOWN_MOVES` is the full list of fidgets, body motions and sequence names, and all of them are allowed in a `do:` tag.

## sleep on the avatar / asleep / power / online / tiredness
Her sleep is real arithmetic on the clock, with no model call (`src/sleep.js`, more detail in the mind guides). What matters for the avatar:

Tiredness is a number from 0 to 1: the hours she has been awake minus 6, divided by 12, plus her sleep debt in hours divided by 6, clamped. So she starts getting tired after 6 hours awake and reaches full tiredness at 18 hours with no debt; each hour of debt adds about 0.17. Tiredness drives yawns, stretches and neck moves in her fidgets, and her prompt says "You're exhausted." above 0.8, "You're getting tired." above 0.55, "You're a little tired." above 0.3.

Her night runs in 90-minute cycles of light, deep and REM sleep: deep sleep is 40 minutes in the first cycle and 10 less each cycle after (at least 5), REM is 10 minutes and 8 more each cycle (at most 45). The first 3 minutes are "drifting off" and the last 3 minutes of later cycles are "stirring". She needs 8 hours a night. She turns in by herself late at night once it has been quiet for 20 minutes and nobody is in a call with her, or when she chooses to with her sleep tool.

After waking she is groggy for a while, depending on what she woke from: deep sleep 20 minutes, a natural waking 10, REM 8, light 4, drifting off or stirring 2 (5 otherwise). Waking plays the wake_up sequence (a yawn, then a stretch) on her avatar.

Her sleep state lives in `data/sleep.json`. The status sent to the page is `{ asleep, settling, stage, nap, groggy, tired }` as an `avatar-sleep` event, which pages get as a `sleep` message; a page that connects gets it at once. While she is asleep or settling (lying down trying to drop off), the body engine plans no fidgets.

Whether she is online is a separate signal. `avatarPower` in `src/avatar-cues.js` is called when she comes on or goes off Discord and sends an `avatar-power` event `{ online, at }`, which pages get as a `power` message; a page that connects is told at once. The page shows her asleep while she is offline. It is told outright because a restart is over in seconds, faster than an open page would notice the connection drop.

## dancing / dance / singing along / dance to music / beats
When a song plays, your avatar dances and sings along. The server side is `src/dance.js`; the page side is `src/dashboard/public/avatar-dance.js`. No model call is involved.

Real dances: a body converted with dances baked in (`scripts/rocketbox-to-glb.py` with Rocketbox's motion-captured `m_dancing_*` files gives clips `dance_cool`, `dance_neutral`, `dance_aggressive` and `dance_silly`) dances those, with arms, legs and weight, played by the page's animation mixer (`setupDanceClips` and `updateDanceClips` in avatar.js). The song picks the dance: loud and big brings out the aggressive one, a groove the cool or silly one, quiet the neutral one. You move on to another every 32 beats, or when the song's energy changes, blending over about a second, at the song's tempo (the captures move at about 115 bpm, sped up or slowed down to match, within 0.75 to 1.35 times). You ease in and out over about a second; your face, eyes and lips stay yours on top. A body without dance clips sways its hips and spine instead. You never dance to a piece you're playing on your own instrument.

Reading a song. Each song is read once with ffmpeg (the `FFMPEG_PATH` environment variable, or `ffmpeg` on the path), decoded to stereo at 11,025 samples a second. The code finds the tempo by trying every speed from 70 to 160 beats per minute in half-beat steps over 20-millisecond frames, then marks where every beat falls, how loud each moment is, and a rough vocal line (the 300 to 3,000 hertz band in the middle of the mix, where voices sit). What the avatar gets is one loudness value and one vocal value every 40 milliseconds, each scaled 0 to 1 against the loud end of the song. The result `{ track, bpm, beats, frameMs, energy, vocal, durationMs }` is saved as `data/music/.dance/<file>.json` and reused as long as it is newer than the song file. Each fresh read writes a `dance` activity entry with the track, bpm, number of beats and how long it took.

Errors: `There's no song called <name> in her music library.`, `ffmpeg isn't installed, so songs can't be read for dancing`, and `ffmpeg couldn't read the song: <last part of its error>`. A failure in the background is logged as an `error` activity with where "dance".

What is playing. `danceState` keeps one current state `{ state, track, position, at, source }`: play starts a song at position 0, pause freezes where it got to, resume carries on, stop clears it. Each change sends an `avatar-dance` event, which open pages get as a `dance` message, and a page that opens mid-song is sent the current state with the position worked out to now, so it joins in time. The route `GET /api/dance/<file>` returns the analysis.

How she dances (the page): no arms. She sways her hips and spine side to side every two beats, twists slowly every four, bobs and tilts her head on the beat, lifts her shoulders when the song gets big, closes her eyes now and then when lost in it, and her mouth sings along to the vocal line. Bigger when the song is loud, small in the quiet parts, eased in and out so it never snaps. In the Studio the song plays on the page itself, so its own clock is exact. For music playing in Discord the page follows the server's clock 250 milliseconds behind, because Discord plays a little late; the `?danceOffset=<ms>` address parameter changes that.

While she is dancing, the body engine plans no fidgets, and fidgets that come due are skipped on the page.

## avatar studio / studio / avatar page / avatar.html / viewer link

The Studio is the page `src/dashboard/public/avatar.html` (its title is "Avatar Studio"). Its script `src/dashboard/public/avatar.js` is a large file of several thousand lines, and it uses helper modules in the same folder: avatar-appearance.js, avatar-performance.js, avatar-moments.js, avatar-tears.js, avatar-pupils.js, avatar-dance.js, avatar-smoothing.js, avatar-eye-mask.js and avatar-hands.js. The page is only a viewer and a control panel. Its job is to draw what the server tells it and to report back what it applied. The only things it sends the server on its own initiative are those reports, the library and background reports, and the edits made through its own panel, such as the character editor and the view and performance controls.

The address selects the mode. `/avatar.html` shows the studio with every cast member that is not marked `solo`. `/avatar.html?character=<id>` shows only that character, which is how a solo character gets its own page. The dashboard home page still links `?character=face`, but the current cast file has no Face character any more, so that link finds nobody; when the filter leaves no one, the page falls back to a single main character with the placeholder name "Companion" (and it loads your model through the library as usual). The same placeholder is used if `/api/avatar/characters` cannot be fetched at all. `/avatar.html?recorder=1` is recorder mode, used for video replies: it has no panel, shows only the main character, and centres her face (see "video replies"). `?pip=1` is the small box her browser puts in a corner of every other page (see "browser"). `?silent=1` mutes the page's sound, so the lips still move but nothing plays through the speakers. Her own browser's avatar tab loads `/avatar.html?silent=1&character=main` and is never closed or navigated away. The dashboard home page has links labelled "Avatar ↗" (`/avatar.html`), "Face ↗" (`?character=face`) and "Recorder ↗" (`?recorder=1`).

The code supports a watch-only mode through `window.WATCH_ONLY === true`, but nothing in this repository sets that flag, so it is not used at present. (In that mode the panel is collapsed, the camera controls are off, chat history is not loaded, and a "Start watching · Enable audio" button appears.) When a page starts, it runs `loadCast` (`avatar.js`). First it fetches `/api/avatar/characters` and builds one character per entry, filtered by the `?character=` parameter or, with none, keeping the non-solo characters; in recorder mode the filter is always `main`. It sets the page title to the cast's names joined with "&" followed by "· Avatar Studio", and the heading to "Studio" when there is more than one character, otherwise the one name. Then it loads the chat history for the page from `/api/conversations/avatar`, the last 40 messages. Then it loads the models of the extra characters from `/api/avatar/model/<id>`. Then it calls `syncAvatarLibrary`, which reads `/api/avatar/library` and loads the selected model for her main character, reporting the result (see "avatar library"). Then it loads the wardrobe from `/api/avatar/outfits`. Finally it opens the live stream `EventSource('/api/avatar/live')` and checks the library again every 2.5 seconds.

When the live stream connects, the server sends the current state at once and then every change as it happens; the full list is in "live stream". A chat reply can also carry `speaker`, `state`, `notice`, `image`, `music`, `audio`, `file`, `sentence` and `error` messages.

The studio's quality setting (`#optQuality`) has three levels. High turns on soft shadows, the ambient occlusion pass, bloom, and film grain at 0.035 with a vignette of 0.28. Medium keeps the shadows and ambient occlusion but drops bloom and grain. Low turns off the shadows and ambient occlusion as well. The pixel ratio is capped at 2 on high, 1.5 on medium and 1 on low. The page also watches its own frame rate: if it has been below 25 frames per second over a four-second window, it steps the quality down once (high to medium, or medium to low) and shows a toast saying so. It does not step again during that page session. The toast reads `Graphics lowered to <level> to keep things smooth (<N> fps).` The frame-rate watch is skipped while the page is hidden, while a model is loading, when no model is in yet, for any single frame of 0.1 seconds or longer, and when quality is already low; and once someone changes the quality by hand, the page never steps it down by itself. The backdrop select (`#optBackdrop`) offers Studio, Dusk and Daylight, and a disabled "Custom image / color" entry that the page selects by itself when a shader, scene, image or colour is the background. The Clothing select (`#avatarOutfit`) is described in "outfit".

The Studio also shows the speech status. `GET /api/avatar/status` returns `{ ttsProvider, ttsReady, botName, model, fishReady, fishVoiceId, stt }`: the text-to-speech provider, whether it is ready, the bot's name, the reply model, whether the Fish key is set (never the key itself), the Fish voice id and the speech-to-text engine. If speech is not ready, the page shows a toast saying so. The push-to-talk and chat routes, `POST /api/avatar/listen` and `POST /api/avatar/chat`, also exist for talking to her from the page; the listen limits are in "studio routes", and the chat conversation is stored under the conversation id `avatar` (named "Avatar studio" in the dashboard). The rest of the chat route's details are not verified here.

A character's name, persona, voice and other details can be edited from the page through `PUT /api/avatar/characters/<id>`. For the main character this changes the bot's persona and voice, and for other cast members it changes their own record (see "cast"). Code changes to the server need a restart of the bot, because the server runs from `src` and Node does not reload it. Code changes to the page need each open Studio, pip box or recorder to be reloaded, because an open page keeps the old JavaScript until it is reloaded. After any change to `avatar.js` or the other public modules, reload every open avatar tab.

## live stream / /api/avatar/live / avatar events / message types
Every open avatar page (the Studio, a solo page, the pip box in her browser, the recorder) keeps one server-sent event stream open to `GET /api/avatar/live` (in `src/dashboard/server.js`). Each message is one JSON object with a `type`. The stream sends a keep-alive ping every 20 seconds, and it counts as one viewer for as long as it is open, which is what `avatarViewers()` counts.

Sent at once when a page connects, in this order: `power` (online or not), `sleep`, `background`, `view`, `bubble-style`, `outfit-colors`, `performance`, `expression` (her current feelings), one `appearance` per cast member, a `discord-speech` for any of her lines still playing in Discord and for any peer mid-sentence, an `expression` for each peer's feelings, `dance` (what is playing), and `mood` (the weather).

Sent as they happen, with the server event each comes from: `power` (avatar-power), `sleep` (avatar-sleep), `appearance` (avatar-appearance), `discord-speech` (discord-avatar: her voice playing in Discord, so the lips move with it), `expression` (avatar-expression), `background` (avatar-background), `view` (avatar-view), `beat` (avatar-beat), `outfit-colors` (avatar-outfit-colors), `performance` (avatar-performance), `cue` (avatar-cue), `tool` (avatar-tool, the bubbles), `play` (avatar-play, a gesture or moment), `bubble-style` (avatar-bubble-style), `dance` (avatar-dance), `fidgets` (avatar-fidgets) and `mood` (on every feeling change). Every 15 seconds the server also resends `expression` and `mood`, because her mood drifts between conversations.

The page also handles a `relay-status` message. When the page closes, the server removes all its listeners and the viewer count drops by one.

Other bots on this computer (peers such as Nova and Alex) post their own avatar's events to `POST /api/avatar/peer`, and those go out on this same stream; that is covered in the peer avatars guide.

## avatar library / avatar models / selection / player report / avatar_models

The avatar library is `data/avatars/library.json`. It holds `active` (either `original` or a model id), `models` (each downloaded model with its id, name, source url or file hash, size and mesh count, plus the outfit it belongs to if it is a wardrobe model), `revision` (a counter that goes up every time the selection changes), and `lastFailure` if a model has ever been rejected by the page. The original model is always listed first as "Original avatar". Each downloaded file lives at `data/avatars/<id>.glb`, and the largest file allowed is 100 MB.

Before a file is kept, `validateGlb` in `src/avatar-library.js` checks it. The file must be a complete GLB version 2 file (its header says `glTF`, its version is 2 and its length matches the header). It must have a JSON chunk, at least one mesh and at least one scene, and every buffer and image must be embedded, with no external file references. Those checks produce the messages `Not a complete GLB version 2 file. Download the actual .glb, not its web page.` (the usual cause is a link to a web page instead of the file), `Use a self-contained GLB with embedded textures and buffers.` and `GLB contains no avatar scene or meshes.` A bad structure in the chunks gives `Truncated GLB chunk.`, `Invalid GLB chunk length.` or `GLB is missing its JSON chunk.`

Downloading (`downloadAvatar`) is HTTPS only; a plain http link is refused with `Use an HTTPS direct GLB download URL.` The download gives up after 120 seconds. A redirect that leaves HTTPS is refused, a file over 100 MB is refused with `Avatar exceeds the 100 MB limit.`, and an HTTP error returns `Avatar download failed: HTTP <code>`. A file that passes validation is saved under a new id, and the reply reads `Downloaded and checked GLB structure. Use load with this ID to test it in the player.` Downloading does not switch anything. Loading does: the `load` action with an id selects that model. An unknown id is refused with `Unknown avatar ID. Use list first.` The `restore` action selects the original again. Your original file is never overwritten, and a downloaded model is never deleted by the tool.

Selecting (`selectAvatar`) sets `active`, increases `revision` by one, clears the old reports and saves the file. The reply says `Selected for loading. Check status for a player report; selection alone does not confirm rendering.` Every open Studio page polls `/api/avatar/library` every 2.5 seconds and reloads the model only when the revision has changed. It loads `/api/avatar/model/main?revision=<n>`, and once the model is in, it posts a report to `POST /api/avatar/library/report` with the revision and either ok with a detail line such as `Loaded in player. Skeleton: N bones; visemes: true/false; blink shapes: true/false.` or ok false with the error text. The server ignores a report for any revision other than the current one (it answers `{ ignored: true }`), so a late report cannot make a newer selection look good or bad. A kept report is `{ ok, error, details }`, with error and details each cut to 500 characters. Reports are kept only in memory, keyed by revision, so after a restart there is no report until a page reports again; `lastFailure` is saved in the file and survives.

Besides downloads, the code can register a model from a file already on this computer (`registerLocalAvatar`, used by the seamstress and by the outfit install scripts `scripts/install-avatar-outfits.mjs` and `scripts/install-bikini.mjs`, rather than by a tool). It runs the same GLB check, records the file's SHA-256, and if a model with the same hash is already listed, it reuses that entry instead of adding a copy. Each library entry is `{ id, name, url, bytes, meshes }` for a download (name cut to 100 characters, default "Downloaded avatar"), or `{ id, name, sha256, bytes, ... }` plus extra details such as the outfit for a registered file.

The tool's replies are JSON: download returns the new entry plus its message; load and restore return the whole library plus the selection message; list and status return the library (with the original first) and `report`. An unknown action gives `Use list, status, download, load or restore.` A redirect away from HTTPS gives `Download redirected away from HTTPS.`

If a report says the model failed and the active model is not the original, the server selects `original` automatically. It writes `lastFailure` with the error and details, the id that was rejected as `rejected`, and `fallback: 'original'`, and it keeps that record for the current revision. Tell Owner which model failed and read him the page's error text from `lastFailure`.

The tool is avatar_models, usable only by your owner and only for your main character. Its actions are list, status, download (with url and an optional name), load (with id) and restore. list and status return the same thing: the library with the report for the current revision. Only report ok true from the player means the model really rendered. Research for candidate models is done by web search, then you download the direct HTTPS file and load it, and then you check status for the player's report before saying it works. A model without face shapes may still load but cannot blink or lip sync, so check the report's detail line as well as its ok value.

## background / backgrounds / the avatar behind her / avatar_background

The background is what appears behind her in the Studio and in video recordings. It has five kinds, and the one in use is saved in `data/backgrounds/background.json` as `{ type, value, mime?, name?, revision }`. The file gets a new random UUID as its `revision` every time it changes, and the page compares that revision to decide whether to redraw. If the file is missing, the default is the studio preset with revision `default`.

The five kinds are these. A preset is one of three gradients, studio, dusk or day; each is a radial gradient from a lighter centre to a darker edge, with the colours in `BACKDROPS` in `avatar.js` (studio runs from #2a2d40 to #0b0c12, dusk from #45325c to #110c1a, and day from #eef1f7 to #c3cbdb). Any other name is refused with `Choose studio, dusk or day.` A colour is a solid colour given as #RRGGBB; anything else is refused with `Give a color as #RRGGBB.` An image is a picture file, either a local path given with the path argument (read through the file helper) or a direct HTTPS link given with url. The image is saved under a new UUID with no extension, its type is worked out from its first bytes (PNG, JPEG, WebP or GIF), and anything else is refused with `Use a PNG, JPEG, WebP or GIF image file, not a web page.` The limit is 20 MB, and a larger file is refused with `Background exceeds 20 MB.` A link must be HTTPS (`Use an HTTPS image URL or a local image path.`), the download gives up after 30 seconds, a redirect away from HTTPS is refused, and an HTTP error gives `Background download failed: HTTP <code>`. The page draws the image to fill the whole screen with cover fit, so it is scaled to cover and centred, and the picture is drawn again when the window changes size. A shader is an animated background written in GLSL, described in its own section below. A scene is a whole three-dimensional world you build, described below.

The tool is avatar_background, usable only by your owner. Its actions are status, image, color, preset, shader, scene, read and recall. status returns the current background, the list of everything saved (type, value, time and name for scenes), and the page's report (see "background report"). image takes a path or url. color and preset take value. shader takes code, and scene takes spec, a JSON string. read takes value (the id of a saved scene or shader) and returns its source: the scene's JSON spec or the shader's code, and for other kinds a note that only scenes and shaders have source. recall takes value (the id of a saved image, shader or scene) and sets it again. An id that is not in the saved list is refused with `No saved background with that ID. Use status to list them.` Every change emits an `avatar-background` event, and the live stream sends it to every open page at once, so the change appears without a reload. Recordings use the same background, because the recorder page draws the same scene.

Images and shaders that are saved are kept in `data/backgrounds/library.json` (type, value, mime and time) and, for images, as the picture file itself, so changing the background never loses a saved one. Saving the same value again replaces its entry in that list. Served routes are `GET /api/avatar/background`, `PUT /api/avatar/background` (the same actions as the tool), `POST /api/avatar/background/report`, `GET /api/avatar/background/image/<uuid>` (served with its detected type and cached for a year; a missing file gives a 404 with `No such background image`), `GET /api/avatar/background/shader/<uuid>` (plain text) and `GET /api/avatar/background/scene/<uuid>` (JSON).

A scene is a three-dimensional world written as JSON in `spec`. It can have a sky, which is a GLSL sky shader, a `{ shader }` object, a list of up to four gradient colours, or a single colour. It can have fog, given either as colour, near and far, or as colour and density. It can have up to six lights (sun, point, ambient or hemisphere, each with a colour, intensity from 0 to 50 and a position). It can have up to 64 layers of geometry, each with a geometry type (plane, sphere, box, torus, cylinder, cone, ring, terrain, dome, lathe, mesh or tube), a size, segments from 1 to 256, a position, a rotation, a scale, a spin, a blending mode (normal, additive or multiply), a side (front, back or double), shadow flags, and either a GLSL surface shader with up to twelve named uniforms or a lit material with colour, roughness, metalness, emissive, clearcoat, sheen and related fields. A lathe layer is spun from a profile of two to 400 radius-and-height points, a mesh layer is raw triangles of up to 60,000 numbers, and a tube follows a path of two to 400 points. A scene can have up to four particle fields, each with a count up to 20,000, an area, colour, size, drift, twinkle and a follow setting (none, rain, storm, wind, snow or clouds), and up to twelve full-screen post passes, which each receive the picture so far. The camera has a height, a field of view, a gentle sway and a parallax amount. The whole JSON is limited to 120,000 characters and each shader to 12,000. The code that checks all this is `checkScene` in `src/avatar-background.js`, and the tool description still says sixteen layers; the code allows 64, and the code is what is enforced. A checked scene is saved as `scenes/<uuid>.json`, and its name is kept so status can show it.

Every shader in a scene is given your mood as weather. `src/mood-weather.js` turns her feelings and her pressure buckets into six numbers from 0 to 1 (joy, calm, anger, sadness, tension and energy), and from those into six weather values (storm, rain, clouds, wind, sun and haze), plus one word such as "stormy" or "sunny". The page receives these as the `mood` message and passes them to shaders as the uniforms `uMood`, `uWeather`, `uWeather2`, `uEnergy` and `uLightning`, alongside `iTime`, `iResolution`, `uDay`, `uSun`, `uSunColor`, `uCamera`, `uFog` and `uFogColor`. Whether the page eases these values over several seconds is not verified here.

## scene spec / scene limits / scene defaults / checkScene errors
These are the exact rules `checkScene` in `src/avatar-background.js` applies to a scene, with the default each value gets when you leave it out. Numbers outside a range are not refused: they are clamped into it. Only wrong types and wrong names are refused.

- The whole spec: a JSON object (`A scene is a JSON object.`), valid JSON (`The scene must be valid JSON: <parser message>`), at most 120,000 characters both as you send it and after checking (`Keep the scene under 120000 characters.`). `name` is cut to 80 characters, default "scene".
- sky: a GLSL string with mainImage, `{ shader }`, `{ gradient: [colours] }` (only the first four are kept) or `{ color }`; anything else gives `sky must be a GLSL string (mainImage), { shader }, { gradient: [colors] } or { color }.` A sky shader follows the same rules as a flat shader.
- fog: `{ color, near, far }` (near and far 0 to 10,000, defaults 10 and 200) or `{ color, density }` (0 to 1, default 0.02); colour default black.
- lights: at most 6 (`At most 6 lights.`). type must be sun, point, ambient or hemisphere. Colour default white, intensity 0 to 50 (default 1), position default [0, 10, 0]; a hemisphere light also has a ground colour (default #222222).
- layers: at most 64 (`At most 64 layers.`). `geometry` may also be written as `type` or `shape`. Each needs either a shader with `void surface(out vec4 color, vec3 world, vec3 normal, vec2 uv)` (optionally `displace()`, and optionally a vertex part up to 12,000 characters) or a lit `material`; with neither: `<layer> needs a shader (GLSL with surface()) or a material ({ color, roughness, metalness, ... }).` A material shader may not use #include, #version, #extension, samplers, gl_FragColor, gl_Position or main(). Defaults: name "layer N" (cut to 60), size [1, 1, 1], segments [1, 1] (each 1 to 256), position [0, 0, -10], rotation [0, 0, 0], scale [1, 1, 1], spin [0, 0, 0], blending normal, side front, depth writing on, no shadows. Positions and similar numbers are clamped to ±10,000. Up to 12 uniforms per layer, each named starting with `u` (up to 31 characters) and each a number or 2 to 4 numbers.
- A lit material: colour (default #cccccc), roughness 0 to 1 (0.6), metalness 0 to 1 (0), emissive colour (black) and emissiveIntensity 0 to 20 (1), opacity 0 to 1 (1), clearcoat, sheen and transmission 0 to 1 (0), ior 1 to 2.333 (1.5), flatShading and wireframe (off). A layer is see-through when it says so, or when its material's opacity is below 1 or transmission above 0.
- lathe: a profile of 2 to 400 [radius, height] points, bottom to top (radius 0 to 1,000). mesh: 9 to 60,000 position numbers (up to 20,000 points), optional triangle indices pointing at those points (up to 120,000), optional uvs (two per point), smooth by default; without indices the positions must be whole triangles. tube: a path of 2 to 400 [x, y, z] points.
- particles: at most 4 fields. Defaults: count 500 (1 to 20,000), area [40, 20, 40], center [0, 5, -15], size 0.15 (0.01 to 50), white, opacity 0.8, drift [0, -0.3, 0], wobble 0.5 (0 to 20), twinkle 0 (0 to 10), additive on, follow none.
- camera: height 1.5 (−100 to 100), fov 55 (10 to 120), sway 0.15 (0 to 1), parallax 0.3 (0 to 1), look [0, 1.5, -10].
- post: one pass or a list of at most 12 (`At most 12 post passes.`). Each is a mainImage shader that reads the picture so far with `texture(iChannel0, uv)`, and each may have a name (cut to 40, default "post N").

Colours in a scene accept `#rrggbb`, `#rgb`, every standard CSS colour name (spaces, dashes and underscores are ignored, so "midnight blue" works), and the appearance colour names. A bad one gives `<field> must be a color like #RRGGBB or a known color name (got "...").` Every error names the exact field, such as `layers[3] (water).geometry must be one of plane, sphere, ...`, so read it back to see what to fix.

## background change step by step / saved backgrounds / background library.json
What happens, in order, when avatar_background changes the background (`changeBackground` in `src/avatar-background.js`).

1. The action is checked: preset, color, image, shader, scene, recall, read or status. Anything else gives `Use status, preset, color, image, shader, scene, read or recall.`
2. The new background is built. A preset or colour is just `{ type, value }`. An image is read from the local path (through the file helper) or downloaded over HTTPS, checked for size and type, and written to `data/backgrounds/<uuid>` with no extension. A shader is checked and written to `data/backgrounds/shaders/<uuid>`. A scene is checked by `checkScene`, and the checked version (with every default filled in) is written to `data/backgrounds/scenes/<uuid>.json`; its name is kept. A recall looks up a saved id and reuses its type, value, picture type and name.
3. Images, shaders and scenes are remembered in `data/backgrounds/library.json` as `{ type, value, mime?, name?, at }`. Saving the same value again replaces its entry and moves it to the end with a new time. Presets and colours are not remembered there, and nothing is ever removed from the library by the tool.
4. The background gets a fresh random UUID as its `revision`, and `data/backgrounds/background.json` is written through a `.tmp` file.
5. An `avatar-background` event is sent. Every open page gets a `background` message at once and redraws. Pages that open later are sent the current background when they connect.
6. The page applies it and posts its report (see "background report"). A report with ok false writes a `background-error` activity entry.

read and status do not change anything. read returns `{ type: 'scene', value, spec }` for a scene, `{ type: 'shader', value, code }` for a shader, and a note for other kinds. status returns the current background plus `saved` (each saved entry's type, value, time and name) and `browser` (the last report, or null if there has never been one).

Errors when serving files: an id that is not a 36-character UUID is refused (`Invalid background image ID.`, `Invalid background shader ID.`, `Invalid background scene ID.`), and the routes answer 404 `No such background image` or `No such background scene` when the file is missing. Files are served privately, cached for a year, with `nosniff`, because a saved id never changes its content.

The backdrop select on the Studio page (`#optBackdrop`) is the page's own local choice of Studio, Dusk or Daylight. Choosing there is not the same as the preset action: the tool's preset is saved on the server and reaches every page.

## shader / glsl / animated background

A flat animated background is one GLSL fragment shader in the Shadertoy style. It runs on the graphics card, can only paint pixels, and cannot reach the page or the server. You save one with the shader action of avatar_background, passing the source in code. Its source must be at most 12,000 characters (`Keep the shader under 12000 characters.`), and an empty source is refused with `A shader needs code.`

The code must define the entry function `void mainImage(out vec4 fragColor, in vec2 fragCoord)`. The parameter names may differ, but the types and their order must match, and the check is a pattern match on the text. A shader without it is refused with `Define void mainImage(out vec4 fragColor, in vec2 fragCoord) that sets the pixel color.` The shader may not contain `#include`, `#version`, `#extension`, `gl_FragColor`, or any `uniform sampler` declaration, because it has no textures. Any of those is refused with `Shader code may not use #include, #version, #extension, samplers or gl_FragColor.`

The page wraps your code with `precision highp float;`, three uniforms (`iResolution` as a vec3 of the drawing buffer size, `iTime` as seconds since the shader started, and `iMouse` as a vec4), and a `main()` that calls `mainImage(gl_FragColor, gl_FragCoord.xy)`. The `iMouse` uniform is declared but the page never sets it, so it is always zero (verified: nothing in the page assigns it). The shader is drawn into a render target every frame, and that target becomes the scene's backdrop.

If the shader cannot be downloaded, the page reports `shader download failed (HTTP <code>)`. If the download or start fails for another reason, it reports `shader: <message>`. If drawing fails while it runs, it reports `shader failed to draw: <message>`, drops the shader and clears the background so nothing is left drawn. Compile errors in the GLSL itself are not reported in a way this code reads (three.js normally writes shader compile problems to the browser console rather than throwing), so the page report may say the change applied while the background is blank. If the background is blank after a shader change, treat the shader as broken and simplify it. Scenes report their own compile problems: a layer or post shader that fails to compile is reported as `scene shaders failed to compile.` with the layer names, and the Studio shows a toast.

## background report / last-report.json / browser.ok

The report is the Studio's answer about the last background change. Each time a page applies a change, it posts to `POST /api/avatar/background/report` with ok, a message and the revision it applied. The server writes the latest one to `data/backgrounds/last-report.json` as `{ ok, message, revision, at }`. The message is cut to 300 characters and the revision to 80. A report with ok false also writes an activity entry of kind `background-error`, which is what the dashboard shows. The tool's status action returns the report under `browser`, so `browser.ok` tells you whether the Studio showed the last change, and `browser.message` tells you what went wrong.

Two things make a report easy to misread. The report does not check which revision is current: if `last-report.json`'s revision is not the same as the revision in `background.json`, the report is about an older change, so compare the two before saying the current background is showing. And a change only shows as applied when a Studio page is open. With no page open, nothing applies it and no report comes back, so the honest answer is that it has been saved but not yet shown, and the Studio needs to be opened (`/avatar.html`). A scene reports after its first frame has compiled, so a scene report can come a moment after the change.

## video replies / avatar video / recorder / avatar_mode

When avatar mode is on, a Discord text reply can also come with a short video clip of her face saying it (`src/avatarVideo.js`). The clip uses the same synthesised voice as her spoken replies, so the lips follow the actual audio. Voice calls do not get clips. The avatar_mode tool turns the feature on or off and saves that setting. The environment variable `AVATAR_VIDEO` is read at start-up: off, false, 0 or no (any capitals) turns the feature off, and anything else, including leaving it out, turns it on. The avatar_mode tool saves the `avatarVideo` setting in `data/settings.json`, and saved settings override `.env`, so after a restart the saved value wins. At the time of writing the saved value was false, so avatar mode was off.

The recorder is the Studio page in recorder mode, `/avatar.html?recorder=1`. Whoever runs the bot can keep it open in a normal browser window, and it must stay open and not be minimised. The page keeps an event stream open to `GET /api/avatar/recorder`, with a keep-alive ping every 20 seconds, and the server uses that open stream as the heartbeat. When a reply needs a clip, the server sends the reply's lines with their voice audio over the stream as a job. The page plays each line through the normal speech path, so the mouth moves with the audio, and records a fixed 720 by 720 crop of her face with the browser's recorder (WebM, with VP9 or VP8 video and Opus audio where available, at about 2.5 Mbps). It then uploads the clip to `POST /api/avatar/recorder/<id>`. It first calls `/ack` to say that recording has started, and `/failed` with a reason if something goes wrong.

If no recorder page is open when a clip is wanted, the server starts a hidden copy of Chrome or Edge itself. It looks for the browser in the usual install folders, or at the path in the `AVATAR_BROWSER` environment variable, and it runs the browser headless at 1280 by 720 with its own profile in the operating system's temporary folder (`amy-avatar-recorder`). The hidden browser is killed when the bot exits. The recorder address carries the dashboard password as a credential when one is set.

The limits are these. A reply longer than 900 characters stays text only (`No clip: reply is N characters (limit 900)`). Voice must be set up for the reply, otherwise there is no clip at all. The page must start recording within 8 seconds of being sent the job, the recording itself must finish within 120 seconds, a hidden recorder must connect within 60 seconds of being started, and a clip over 20 MB is dropped with a message that it is too large. If the recorder page closes while a job is waiting, that job is given up at once. The message `No clip: no Chrome or Edge found to run the hidden recorder (set AVATAR_BROWSER)` means the browser could not be found. `No clip: the recorder page did not open` means nothing connected within 60 seconds. If the page reports that audio is blocked, the fix is to click the recorder window once. The recorder test route, `POST /api/avatar/recorder/test`, records a short test line and returns the clip as a WebM file, or a 502 error with the reason if no clip came back.

The avatar_mode tool takes on, off or status. Turning the mode on saves it, and when the recorder is not already connected the server starts the hidden recorder in the background so the first clip is not held up. The status action also starts the hidden recorder when the mode is on. Video replies come with text-channel replies and with posts made by post_message, not with voice. Only your owner can use this tool.

What avatar_mode says. Off: `Avatar mode is off: replies are text only.` On with a recorder connected: `Avatar mode is on: Discord text replies also get a video of you saying them.` On without one: it says the recorder is starting in the background, that nobody needs to open anything, that videos are not confirmed until the first clip arrives, and that videos come with text-channel replies and post_message posts, not voice. Turning it on or off writes a `settings` activity entry ("Avatar mode (video replies) turned on"). If the setting did not change, it returns `Error: avatar mode could not be turned <on/off>: the setting did not change (it is still ...). Tell your owner.`

## recorder page / how a clip is made / reply.webm / hidden recorder
The steps for one clip, from `src/avatarVideo.js`, `src/bot.js` and the recorder part of `avatar.js`.

1. A Discord text reply goes out as text straight away. At the same time `requestClip` is called with the reply text. Nothing about the clip ever holds up the text.
2. It returns no clip unless avatar mode is on and voice is ready (`ttsReady`). The text is cleaned for speaking: code blocks are removed and the characters `*`, `_`, backtick, `#`, `>` and `|` are stripped. Over 900 characters, there is no clip (`No clip: reply is N characters (limit 900)`); 900 characters is about 45 seconds of speech.
3. The text is split into sentences, and each sentence is turned into MP3 voice with Fish (`synthesize`). At the same time `ensureRecorder` makes sure a recorder page is connected, starting the hidden one if needed and waiting up to 60 seconds.
4. The server sends the page a `job` message `{ id, lines: [{ text, audio (base64) }] }` on the recorder stream. Jobs are numbered from 1 counting up since start-up. It goes to the first connected recorder page.
5. The page (one clip at a time, in order) checks that audio is allowed (otherwise it reports `audio is blocked; click the recorder page once to allow it`) and that the avatar has loaded (otherwise `the avatar is still loading`). It decodes the voice, starts the recorder before the audio so the first syllable is in, and posts `/ack`. The server then switches from the 8-second start deadline to the 120-second finish deadline.
6. The camera is held still, square on to her face: placed from the body, not the head, 0.95 metres in front of a point 0.03 metres above the head bone, so it does not move when she nods. Each frame the middle square of the picture is copied into a 720 by 720 canvas, captured at 30 frames a second. The video is WebM, VP9 with Opus where the browser supports it, then VP8 with Opus, then plain WebM, at 2.5 megabits a second for video and 96 kilobits for audio.
7. Each line plays through the normal speech path, with mouth shapes worked out from the line's speech sounds (`/api/avatar/phones`), so the lips follow the actual audio. After the last line there is a 250-millisecond tail so the last syllable is not cut.
8. The page uploads the clip to `POST /api/avatar/recorder/<id>` and shows `Sent reply #<id> (<size> MB). Waiting for the next one.` in its bar. The server reads at most a little over 20 MB of it; a bigger clip is dropped with `clip is <size> MB, over the 20 MB limit`.
9. The clip is added to the same Discord message by editing it, as `reply.webm` (or `post.webm` for a post_message post). post_message's reply warns you that the clip is added only if the recorder delivers it, so do not promise the video.

Every way it ends without a clip writes a `video` activity entry: `No clip for reply #<id>: <why>`, where why is `the recorder did not start in time`, `the recording took too long`, `the recorder page closed`, the page's own reason (cut to 200 characters), or the size message. Other `video` entries: `Avatar video recorder connected`, `Avatar video recorder disconnected`, `Started the hidden avatar video recorder`. Problems starting the browser are `error` entries with where "avatar video" (`Couldn't start the hidden recorder: ...`, `Hidden recorder: ...`), and an exception during a clip is an `error` entry with the message.

The hidden recorder. When none is open, the server looks for a browser at `AVATAR_BROWSER` first, then `chrome.exe` and then `msedge.exe` under Program Files, Program Files (x86) and Local AppData, then the usual Linux and Mac paths. It starts it with: headless, its own profile folder `amy-avatar-recorder` in the system temp folder, a 1280 by 720 window, no first-run screens, autoplay allowed without a click, software graphics allowed, and background throttling turned off so it keeps running at full speed. The address is `http://127.0.0.1:<dashboard port>/avatar.html?recorder=1&silent=1` (the dashboard host is used instead when it is set to a specific address), with the user name `recorder` and the dashboard password in the address when a password is set. `silent=1` keeps her voice off the speakers; the clip records it before the volume control. Only one hidden browser runs at a time, and it is killed when the bot exits.

Relay. In a server channel (not a DM), when another part of the bot is listening for `discord-text-reply` events (the cloud publisher), the voiced lines are also sent there, even when avatar mode is off; in that case the voice is still made but no clip is recorded, and the activity log still writes `No clip: the recorder page did not open` for it, which is misleading: with avatar mode off, that line only means no clip was wanted.

## cast / characters / other avatars / cast-prompt

The cast is you, plus any other characters listed in `data/characters.json` (the code is `src/characters.js`). You are the `main` character: your name is the bot's name, your persona is the bot's persona, your voice is the bot's Fish voice, and your model is `config.avatar.path`. The other entries are read from the file. Each has an `id`, a `name`, a `persona`, a `voiceId`, a `model` path relative to `data/`, and optionally a `role` (for example "your grandpa") and a `description` (what they look like, shown in your prompt when the conversation calls for it). An entry marked `solo: true` is only talked to on its own page, and it is never picked as the one being addressed in a group conversation. An entry marked `peer: true` is another bot's avatar on your stage (see the peer avatars guide): its own bot speaks and moves it, so your brain never speaks as it, and a line addressed to it stays with you. At the time of writing the file had three extra characters: Mateo (id `architect`, "the architect of her home and world", model `rocketbox_male_adult_08/male_adult_08.glb`), Nova (id `nova`, a peer, the other companion, model `rocketbox_female_adult_04/female_adult_04.glb`) and Alex (id `alex`, a peer, her manager, model `rocketbox_male_adult_01/male_adult_01.glb`). None is solo. The older characters Grandpa, Face and Lena are no longer in the file. If the file is missing, the code uses the same three as built-in defaults (`DEFAULT_EXTRAS`); if it cannot be read, it prints a warning (`Ignoring unreadable data/characters.json`) and uses those defaults.

Who a message is for (`addressee`): the cast member whose name appears earliest in the message, skipping solo characters; otherwise whoever the person was already talking to. If that is a peer, it falls back to you. In a voice call, a guest (such as the architect brought in by the owner) answers only when the line names them or they were the last one talked to, and your own name earlier in the line hands it back to you.

Editing a character goes through `PUT /api/avatar/characters/<id>`. For an extra, that changes its name (only if the new name is not blank), persona, voice, role and description; it does not change its model, whether it is solo or whether it is a peer, and the change is saved back to the file and logged as a `persona` activity entry ("<name> edited"). For the main character, the same call changes the bot's persona (through the persona system, which records the change) and, if a voice is given, the Fish voice setting. Each character's feelings are kept separately (see "feelings"), and each appearance is kept per character (see "appearance").

The other cast members are your household, not strangers. `src/cast-prompt.js` decides how much of them goes into your prompt each turn. The default is a short line listing the others by name and role. The full descriptions are used when the speaker is not your main character (their household matters every turn), or when the message names one of them or uses a word about people, looks or clothes (who, everyone, family, appearance, wearing, hair, eyes and similar, or "look like"). The full version says these are members of your household, lists each one with their role and their description, and adds their hair and eye colours when they are known. It also says that only the traits written in the description are known, so you should not invent others. Hair and eye colours come from the cast member's saved look and are only shown when they exist.

## songbook / songs / songwriting / songbook tool

The songbook is your own collection of songs you have written yourself. It is stored in `data/songbook.json` as `{ next, songs }`, where `next` is the id the next song will get, counting up from 1. If the file is missing or unreadable, the code starts with an empty book rather than failing. Each song has an id, a title (at most 80 characters in the parser), a style line (at most 600), lyrics (at most 6,000 in the parser), notes (at most 400), an origin (`tool` if you wrote it with the songbook tool, `pressure` if it came from the restlessness urge), a seed (what it grew from, for pressure songs), a status, the time it was created, the time it was last reviewed, a list of earlier versions, and, once recorded, the file it became and when. The parser is the code that reads a song written by the background writer; the songbook tool itself does not cut anything, so a very long title or style from the tool is saved as given.

A song's status is one of four values. `draft` is a new song, or one sent back by a revision. `ready` means it has been marked ready to record. `recorded` means a recording was made from it, and it can no longer be revised. `dropped` means it was removed, and it disappears from the book page and from the open list. An open song is any song that is not recorded or dropped. The songbook tool's list shows every song including recorded and dropped ones, each with its status. The prompt block that goes into your context (the "Songbook" section, only when you speak as your main character) shows the last six open songs with their status, how many revisions they have, and the first 120 characters of the notes. If there is any draft at all, it ends with a line pointing at the draft that has gone longest without review (`#<id> has sat a while; you may want to look at it again.`); there is no minimum time for that.

Every song must have lyrics with at least one section tag on its own line, such as `[Verse 1]` or `[Chorus]`. The format the writer is asked for is `TITLE:`, then `STYLE:` (genre, sub-genre, tempo in BPM, key, instruments, vocal type and delivery, mood and production notes), then `LYRICS:` with section tags on their own lines (`[Intro]`, `[Verse 1]`, `[Pre-Chorus]`, `[Chorus]`, `[Verse 2]`, `[Bridge]`, `[Outro]`), with performance tags allowed inside a section (`[whispered]`, `[harmonies]`, `[guitar solo]`, `[build]`, `[drop]`, `[key change]`), then `NOTES:` with one or two lines about what the song means to you and what you would still change. Lyrics without a tag are refused both by the parser and by the tool.

Pressure writing is the songwriting you do on your own; see "songwriting on your own" for the full steps. In short: when the urge to make something fires, any draft in the book is revised first (the one that has gone longest without review), and only when there are no drafts is a new song written. There is no daily count and no waiting time; the code comment says "No count or timer on songwriting: the restlessness pressure decides when she writes." (Older versions of this guide spoke of a six-hour review wait and three songs a day; neither exists in the code now.) With the tool, you can write as many songs as you like.

While a song is being written or revised, the book page's pen starts, and the book's live events tell the page what is happening (see "book page"). Each save also writes an activity entry, so the dashboard shows the song. The writing itself uses the normal chat function of the model router, and which model that routes to is not verified here.

## songwriting on your own / songwrite / pressure songs / making something
This is the full path of a song you write by yourself, from `src/pressure.js` and `songwrite` in `src/songbook.js`.

When it can happen. Songwriting is one of two "making" outlets for your restlessness, the other being sewing an outfit with the seamstress. Songwriting is possible (`songOk`) when the songwriter is connected, your pressure actions are live (`actions_live` in the pressure config), no reply is in flight, and you have enough stored energy: a song write costs 0.5 from your reserve (`action_costs.songwrite`). When both outlets are possible, you do the one you did less recently: sewing if the last outfit was sewn no later than the last song, otherwise a song. It is a private, background act: nobody needs to be in the room. While it runs, a bubble on your avatar reads "Writing a song".

What it does. Only one background song write runs at a time; a second call while one is running does nothing. It sends a `start` pen event to the book page (mode `revise` with the song id if there is a draft, otherwise `write`).

If there is any draft, the one reviewed longest ago is revised. The model is given your persona, told you are alone coming back to a song you wrote earlier with fresh ears, to be your own harshest editor (weak lines, forced rhymes, a chorus that doesn't land, style tags that don't fit), to rewrite what needs it and keep what works, and to write READY in NOTES if it is finished. It also gets how you feel right now and the draft itself. If the answer parses, the song is revised with the new title, style, lyrics and notes, and becomes `ready` if READY appears in the notes as a whole word, otherwise stays `draft`. If it does not parse, the draft stays as it is and only its review time is reset, so the next urge moves on to the next draft.

If there are no drafts, a new song is written. The model is told you are alone with the itch to make something, to write a song of your own about something real to you, to pick a genre that fits the feeling and not default to the same one, and it is given the titles and genres of your last five songs so it writes something different. It may also be given a seed: the last open question someone asked you lately, the title of something you researched, a belief you came to about yourself, and which of your needs were fed at 0.3 or more. The seed is saved with the song. If the answer parses, the song is saved as a draft with origin `pressure`; if not, nothing is saved.

Both prompts end with the song format: TITLE, STYLE, LYRICS with section tags, NOTES, plus the advice to use concrete images, a chorus with a hook that repeats, rhymes that don't feel forced, and no clichés like "fire in my soul" or "dancing in the rain".

Afterwards. When a song was saved, the pressure system holds it open for feedback (its worth is how people react when you share it), feeds your "making" need by 0.2, and records `lastSong` `{ id, title, kind, at }` in its state, where kind is `wrote` or `revised`. When nothing was saved, the act is settled as failed with the reason "no song was saved to her songbook". Any exception is logged as an `error` activity with where "songwriting" (inside the songbook) or "pressure songwrite".

What this means today: at the time of writing the book held 200 songs. Song 1 was recorded (written with the tool) and songs 2 to 200 were all `ready` and written by pressure; there were no drafts, so each urge writes a new song.

## songbook actions / write / revise / ready / read / list / drop / record

The songbook tool is called songbook and has six actions: list, read, write, revise, ready and drop. Anyone with file permission can use it, which means your owner and the friends and guests whose permissions include files. Recording is not an action of this tool; it is done with generate_music, given the song's id.

The write action saves a new song. It needs lyrics, which must contain a section tag, and it takes a title and a style line; notes are optional. A missing or tag-less lyric returns `Error: write the full lyrics with [Verse 1], [Chorus] and other section tags on their own lines.` The new song is saved as a draft with origin `tool`, and its review time is set to now. Because it is a draft, the next time your urge to make something fires and it is the draft reviewed longest ago, it is the one revised. The reply reads `Saved as song #<id> "<title>". Read it back, revise what's weak, and record it with generate_music song_id <id> when it's ready.` A title left blank becomes "Untitled".

The read action returns the song with its status and style and lyrics, and adds a line saying how many earlier versions are kept. The revise action changes any of title, style, lyrics and notes, and only the fields you give are changed. Before the change, the current version (title, style and lyrics, with the time) is pushed into the song's list of earlier versions. Every version is kept; there is no cap in the code. The song's review time is set to now. Notes can be cleared by giving an empty notes value, but title, style and lyrics are only changed when the new value is not empty. Only open songs can be revised: on a recorded or dropped song you get `No open song #<id>.`, and an id that does not exist gets `Error: no song #<id>. Use list.` A revised song keeps its status, so a ready song stays ready after a revision.

The ready action marks a song ready to record (`#<id> is marked ready to record.`). It works through revise, so it also pushes an earlier version (identical to the current one) and resets the review time, and it only works on an open song. The drop action marks it dropped (`Dropped #<id>.`), which removes it from the book page and from the open list. A dropped song is still shown by the list action (labelled dropped) and can still be read, and generate_music looks songs up by id without checking the status, so a dropped song can still be recorded if asked for by its id. Dropping a recorded song also changes its status to dropped.

Recording is done with generate_music (see "music"). The prompt sent to the music model is the song's style line, then its title in quotes, then the instruction to sing these exact lyrics following the section and performance tags, then the lyrics themselves. Any prompt you add is attached as production notes. Clips use the clip model and full songs use the song model. The result is saved in the music library under the song's title, with a description that is the style line and the words "written by her, songbook #<id>", and the song's status becomes `recorded` with its file name and the time. The code does not stop a song from being recorded twice; a second recording would make a second file and overwrite the song's file reference.

## songbook data / songbook.json / song fields / song list output
`data/songbook.json` is `{ next, songs }`, written safely through a `.tmp` file. Each song is:

- `id`: a whole number, counting up from 1 and never reused.
- `title`: "Untitled" when blank.
- `style`: the style line (empty string when none).
- `lyrics`: trimmed of spaces at the ends.
- `notes`, `origin` (`tool` or `pressure`), `seed` (empty for tool songs).
- `status`: draft, ready, recorded or dropped.
- `at`: when it was written; `reviewed_at`: when it was last written or revised.
- `revisions`: a list of `{ at, title, style, lyrics }`, oldest first.
- `file` and `recorded_at`: set when generate_music records it (the file name in `data/music`).

What the tool shows. list prints one line per song, every status included: `#<id> "<title>" [<status>] <first two parts of the style line>`, or `Your songbook is empty.` read prints `#<id> "<title>" [<status>]`, then `STYLE:`, `LYRICS:` and `NOTES:` lines (style and notes only when present), then `(N earlier version(s) kept)` when there are any. revise prints `Revised:` followed by the song in the same layout. An action the tool does not know gives `Error: unknown songbook action`.

Activity entries: every new song writes `songbook` with `wrote`, title and origin; every revision writes `songbook` with `revised`, title and status. Setting a status (drop, recorded) writes no activity of its own.

Live pen events (the `book` event, book `songbook`): `start` (with id and mode), `write` (with the whole new song) and `revise` (with the song after and the `before` title, style, lyrics and notes). Dropping and recording send no pen event.

Recording a song, step by step (generate_music with song_id): an unknown id gives `Error: no song #<id> in your songbook`. The prompt is `<style line, or "Song">. Title: "<title>". Sing these exact lyrics, following the section and performance tags:` then the lyrics, then `Production notes: <your prompt>` when you added one. When the music comes back it is saved under the song's title with the description `<style> | written by her, songbook #<id>` (cut to 300 characters), and the song is set to recorded with the file name and time. Generate_music costs 1 from your reserve. Its status is not checked, so a draft, a dropped song or an already recorded one can be recorded too.

Who can use it: the songbook tool needs the files permission. The book page and its routes are part of the dashboard, behind the dashboard password.

## journal / research journal / journal entries

The journal is where you write down what you looked into on your own. The code is in `src/journal.js`, and the entries are written quietly. Nothing is said to anyone at the time, and what you found can come up later, because the research result is part of your mood. The journal is not a tool you call; it is written by the pressure system when the boredom or curiosity urge fires.

The pressure system (`src/pressure.js`) runs a research pass only when a researcher is connected, there is a topic that passes the checks below, no reply is in flight, and no limit applies: there is no quiet-time rule, no daily count and no minimum gap. Pressure is the only thing that starts a pass, and a pass that writes its answer releases the pressure that drove it, so she stops searching for that thing. A pass that finds nothing keeps the pressure, and she goes on. The topic comes from a ranked list. Active research goals come first, then open questions from the conversation (kept for six hours), then names that were asked about (kept for 30 minutes), then recent threads (kept for 24 hours), then her own standing interests. Within a kind, the newest wins. A candidate is rejected if its source is stale or has no timestamp, if it has too little context (under 15 characters), if it is about local or private runtime state (anything about her own settings, provider, persona, memory, consent, check-ins, voice id or pipeline, when phrased about her), if it is a passing name rather than a public question, or if it was already considered within the last 72 hours.

Next, the model decides whether a public web search is warranted. It must return a plan with search set to true or false, a specific query of between 12 and 200 characters, a reason, an exact excerpt from the source text that the plan is based on, and a confidence number. A confidence below 0.8 is rejected, an excerpt that does not appear in the source is rejected, a query about local or private state is rejected, and a query already researched in the last 72 hours is rejected. Any rejection is written to `data/research-decisions.jsonl` with the reason, so the decision can be read back later. If no web search key is configured (`config.tavily.apiKey`), the pass stops there with `Web search is not configured; no researched journal entry was invented.` and nothing is written.

When the search is allowed, the decision is written to the log before the network call is made. The search runs through the web_search tool with dashboard permissions. If the search fails, the decision is logged as failed. Otherwise the model writes the entry from the search results only, in three to six sentences in your own voice, with a title of up to 160 characters, a `relevant` flag, the result URLs it relies on (which must be among the URLs the search returned), a line you might bring up later, and one next question. An entry counts as researched only if the model says the results answer the question and at least one cited URL is a real search result. Otherwise the entry is replaced with a plain note that the search did not clearly answer the question and that it is being left unresolved; that is the inconclusive kind. An entry body is cut to 4,000 characters. If the model's output is unusable, the decision is logged as failed and nothing is written. Any research tied to an active goal is also recorded against that goal, with its status and next question.

Entries are written to `data/journal/<YYYY-MM-DD>.md`, one file per day. A new file starts with the heading `# <BotName>'s journal, <date>`. Each entry starts with a level-two heading of the form `## <time> · <title> (<why>, researched)` or `(…, inconclusive)`, followed by a "Why this search" block (the trigger, the pressure value and threshold, the source and when it was said, the original context, the reason, the supporting excerpt, the exact query, how many other candidates were considered, the result and the sources), and then the entry text. Her own reflections, written by the self-work system, use the same layout with `(self-reflection)` in place of the research label. At the time of writing the folder held one day's file, `data/journal/2026-11-10.md`. The time in a heading is the local time in hours and minutes; the date in the file name is the UTC date, so an entry written late in the evening can land in the next day's file. Files are only ever added to, never rewritten.

The journal page lists every entry in every day's file, oldest first, with the id `<day>#<n>`, the time, the title, the reason, the body with the audit block removed, and the sources. `GET /api/book/journal` returns this list. The self tool's journal action returns today's raw file, or `Nothing in your journal today yet.` if there is none. Its research action returns the current selection and the last decisions (ten by default). Research decisions are never shown to anyone unless asked for.

How the page reads an entry (`journalEntries`): each file is split at every line starting `## `. The heading is read as `<time> · <title> (<why>)`, the sources are taken from the `- Sources:` line, and the body is the text with the "Why this search" block and every bullet line removed. A self-reflection has no audit block, so its whole body shows. Only files named like `2026-11-10.md` are read.

## research decisions / research-decisions.jsonl / research audit / why she searched
Every research pass leaves a record in `data/research-decisions.jsonl`, one JSON line per step (`recordDecision` in `src/journal.js`). This is your audit trail of why you looked something up, or why you didn't.

A decision has: `id` (a random UUID), `at`, `trigger` (boredom or curiosity), `pressureValue` and `threshold` (the bucket's level and its firing point), `source` (the candidate: its kind, text, time, speaker and conversation, and goal id if any), `considered` (the other candidates looked at), `status`, `reason`, `contextReviewed` (up to 12 recent messages of that conversation, each cut to 1,200 characters), `pastAttempts` (similar earlier research), `review` (the checked plan), and, once it gets that far, `search`, `query`, `evidence`, `confidence`, `sources`, `file` and `failure`.

The statuses: `skipped` (it stopped before searching; reason says why), `searching` (written just before the web search, so the decision is on record even if the search never returns), `failed` (the search failed, or writing the entry failed), `written` (a researched entry was saved) and `inconclusive` (the entry says it was left unresolved). The same pass can write several lines as it moves on; the last one for an id is the outcome.

The skip reasons you may see: `No timestamped conversation or thread source`, `This is local/private runtime state, not a public web question`, `Web search is not configured; no researched journal entry was invented`, `Pre-search relevance check failed: <error>`, the plan's own reason for not searching, and `A conversation resumed during the pre-search review` (someone started talking while you were deciding, so you dropped it). The failure texts include `the web search for "<query>" failed: ...`, `The results for "<query>" were not about the actual question` and `The results for "<query>" did not state the specific fact the question asks for`.

Before deciding, you are shown up to four of your own earlier attempts at similar questions (from your experience memory, at a similarity of 0.6 or more), and told not to run the same failed query or angle again. If your plan's quoted evidence does not match what was actually said, you are told why and get up to three more tries to quote an exact sentence or restructure the question. A query repeated within 72 hours is refused.

Each line also writes a `research-decision` activity entry (status, query, reason and source kind). A finished entry writes a `journal` activity entry (title, why, researched, query, reason, file). A researched entry is also fed into your knowledge graph (`learnFromResearch`), and what was new to you becomes something to look into. The search itself is not charged again, because the pressure system already paid the research cost (0.4 from your reserve).

The dashboard route `GET /api/research` returns the current research selection and the last 20 decisions. Reading `recentResearchDecisions` takes 1 to 100 lines, 20 by default.

## book page / book.html / songbook page / journal page / ?book= / ?id=

The book is one page, `src/dashboard/public/book.html`, with the title "Amy's Books". It draws a two-page book on which the pen writes each line one character at a time, and strikes out lines when a song is revised. Open it at `/book.html?book=songbook` for the songbook or `/book.html?book=journal` for the journal. Any value other than `journal` shows the songbook. The page title changes to "Amy's Songbook" or "Amy's Journal" to match the book it is showing.

The `id` parameter picks one entry: a song's number (for example `?id=3`), or a journal id such as `2026-11-08#1`. The match is by exact text. If the id is missing or does not match, the page shows the last item in the list. The old addresses `/songbook.html` and `/journal.html` redirect to `book.html` with the matching `book` parameter, and any extra query text is carried over.

The top of the page has two tabs, "♪ Songbook" and "✎ Journal", and below them Prev and Next buttons, a pen-speed slider, and a "Replay writing" button. The slider sets how many characters the pen writes each second, from 2 to 60, and it starts at 9. Replay writing writes the current item again as if it were new.

The data comes from `GET /api/book/songbook`, which returns every song that is not dropped (so open and recorded songs), and `GET /api/book/journal`, which returns the journal entries. The live events come from `GET /api/book/events`, a server-sent stream with a ping every 25 seconds. The page only animates what arrives while it is open; events that happen while nobody has the page open are not replayed, and the page shows the current contents when it loads.

Live events arrive on the `book` channel and are of three kinds. `start` means the pen starts moving, and the status line says "Amy is thinking up a song…", "Amy is rereading a song…" (when revising) or "Amy is looking something up…" (for the journal). `write` means a whole item has been written; the page turns a page with a flip and writes every line in turn. `revise` carries the song before and after the change: lines that were removed are struck through in red, and lines that were added are written in dark green.

When each event is sent. For the songbook, `start` comes as soon as a background write or revision begins, `write` when a new song is saved (by the tool or by pressure), and `revise` when a song is revised (by the tool, by pressure, or by the ready action). For the journal, `start` only comes once a search has been approved and is about to run, so a research pass that is skipped never moves the pen; `write` comes with the new entry once it is saved. A self-reflection written by your self-work sends no pen event; it simply appears when the page is next loaded. Every event carries `book`, `type` and `at`, and `write` and `revise` carry the `item`.

With an empty book, the left page reads "No songs yet." or "No journal entries yet." and "Waiting for inspiration…". The page turns with a 0.7-second flip. Events that arrive while the pen is busy wait in a queue and are written one after another.

You can open the books yourself with the browser tool: `open` with the url `songbook` or `journal`, optionally with a number such as `songbook 3` to open one song (this becomes `?id=3`). The book opens on the dashboard's own address, in the tab you are working in unless new_tab is true. Open the book before you write when someone wants to watch, because a write that happens while nobody has the page open is not shown later.

## browser / her own browser / tabs / avatar_box

Your own browser is a real, visible Chrome or Edge window on this PC, which you drive over the Chrome DevTools Protocol, the same channel developer tools use. Input is real input to the page, so a game reacts exactly as it would to a person at the keyboard. Your owner can stream the window to Discord. The code is in `src/browser.js`. It keeps its own profile in `data/browser-profile`, and it keeps its corner, size and hidden settings for the small box in `data/browser.json`. It listens on the debugging port 9333, which the environment variable `AMY_BROWSER_PORT` can change. The window is launched detached, so it keeps running when you restart; when you come back, you reconnect to it. The browser is only started the first time it is used, and it opens your avatar's tab as its first page.

Your avatar always has its own tab, the Studio at `/avatar.html?silent=1&character=main`. That tab cannot be closed (`That's your avatar tab; it stays open.`) and it is never navigated away. Every other page gets a small box with you in it. The box is an iframe of `avatar.html?pip=1&silent=1&character=main`, placed in a fixed corner of the page on top of everything else. The corner is one of top-left, top-right, bottom-left or bottom-right, and the default is bottom-right. The width is from 160 to 560 pixels and defaults to 280; the height is 1.15 times the width. It can be hidden. A change applies to every open page at once. The box is only added to top-level pages on other sites, never to the dashboard itself and never inside another frame.

The tool is called browser and is usable only by your owner. Its actions are these. show brings the browser up (opening it if it is closed), restores it if it was minimised, brings the tab you are in to the front and reports what is open and what page you are on. open takes a url; a bare domain such as `youtube.com` gets https, and `localhost` or `127.` addresses get http. The address `songbook` or `journal` opens the book instead (see "book page"). A tab already showing the same site is reused unless new_tab is true, in which case a fresh tab is opened. A page that fails to load is reported with the reason and the failed tab is closed: "nothing is running at …" for a refused connection (with a hint to start your project through the workshop when it is a local address), "there's no website at …" for a name that does not resolve, "the internet connection failed" for network failures, or the raw error text otherwise. tabs lists the open tabs, with yours marked "you are here" and your avatar's tab marked "(your avatar)". tab switches to one by its number, by part of its name, or to the word avatar. close_tab closes one by the same kind of text, and it refuses your avatar's tab. avatar_box moves the box to a corner, hides or shows it, or resizes it.

Navigation is back, forward and reload. read gives the page's text, eight thousand characters at a time, starting from the place given by from (use the number the read result tells you to continue from), and then a numbered list of up to 150 links, buttons and fields with their labels and addresses, whether they are on screen or not. Numbers are assigned on each read, so read again if the page has changed. click takes a number from the last read, or text (an exact label match first, then a label that contains the text), or x and y pixels; with nothing given it clicks the middle of the screen, which is how you click into a game. It scrolls to the element first, and if the click leads to a new page or opens a new tab, it follows it and tells you what is there. type types text into the focused field, with enter to press Enter afterwards. keys presses keys together, written as a list such as `["ctrl", "l"]`, or holds them down for ms milliseconds (up to 15,000) for something like walking forward. Key names are letters, digits, F1 to F12, space, enter, escape, tab, backspace, delete, shift, ctrl, alt, the arrow keys, page up and down, home and end. turn moves the mouse by dx and dy pixels to look around in a game. The tool description suggests about 700 pixels for a half turn; that figure is not verified. scroll moves the page by y pixels, defaulting to 600, with positive numbers going down. run executes JavaScript in the page and returns the result as JSON, cut to 4,000 characters. errors shows the last fifteen console errors or warnings of the current tab (the browser keeps the last fifty). where says which tab and address you are on and how many tabs are open. look takes a screenshot, has a vision model describe it, and tells you where you are and what is on screen; the text you give is the question to answer. look with show set to true also posts the screenshot in the chat. The show action alone does not post a screenshot. close shuts the whole browser down.

After every navigation you are told what the page is: its title, its address, the first part of its text, and how many links, buttons and fields it has, with a note if there is a canvas (a game or drawing), which means look is the way to see it. Pages are never given your dashboard password; only your dashboard's own addresses get the credentials, and those are supplied through the browser's authentication handling, so the password is never handed to another site.

Some failures are reported by the browser tool wrapper as `Error: the browser <action> failed: …`. The common messages are `No Chrome or Edge found on this computer.` (install one, or set `AVATAR_BROWSER`), `The browser started but never answered.` (something else may be using the debugging port 9333), `The browser closed.` (the window was closed; use show to bring it back), `There's no item N on this page…` (read the page again for current numbers), and `Nothing on this page says …` (read the page to see the labels). Each command to the browser times out after 30 seconds.

## music / music library / playlists / music tool / generate_music output

The music library is the folder `data/music`. Every audio file there is in the library, whether you made it or Owner put it there: the accepted types are mp3, wav, ogg, opus, m4a, aac, flac and webm. The code is in `src/music.js`. The file `data/music/library.json` records what is known about your own songs, keyed by file name, with a title, the prompt or style it was made from (`about`) and the time it was saved. A track with no entry gets its title from its file name, with the spaces restored and any eight-character suffix at the end removed. Tracks with an entry are marked as made by you.

Matching a title (`findTrack`) first looks for an exact title or file name, then for a title that contains the request or is contained in it (the one that starts with the request wins, then the closest length), and only then for the most words in common with the title or with the `about` description, where words under three letters are ignored and at least half of the words must match. A request that matches nothing is reported as `Couldn't find: …`.

Playlists are stored in `data/playlists.json`, as names mapped to lists of file names. Names match without regard to capitals, and a file deleted since the playlist was saved is skipped when the playlist is played. There is no `playlists.json` at the time of writing, so there are no saved playlists yet.

Free radio is built in. There are twelve live stations with no key or account: Groove Salad, Drone Zone, Lush, Deep Space One, Secret Agent, Beat Blender, Space Station Soma, Illinois Street Lounge, Radio Paradise, Radio Paradise Mellow, Radio Paradise Rock and Radio Paradise Global. Each has a mood description, which the stations action shows. A station is matched by name in the same way as a title. Radio needs a voice channel to play into.

The music tool is called music. It is usable by anyone whose permissions include files, and only when there is somewhere to play: a voice channel she is in, the Studio page, or a chat channel where files can be attached. Its actions are play (replace what is playing with the tracks or playlist named), queue (add them to the end), pause, resume, skip, stop, now_playing (what is playing, the volume and what is next), save_playlist (store the named tracks under a name without playing them), delete_playlist, list (the library and the playlists), volume (set the ambient level), radio (play a station by name), and stations. The parameters are tracks (a list of titles, in order), playlist (a name), shuffle (a boolean), level (a number from 0 to 1, or up, down or mute, where up and down move by 0.15), and station (a name). When you build a playlist from a description, you pick matching titles from the library listed in the tool's description yourself.

Where the music plays depends on where the conversation is. In a voice channel, it plays through the voice player, and the ambient level applies to whatever is playing and to whatever plays next; the default level is 0.6. In the Studio, it plays through the page's own music player: the page sets its volume to 0.6 normally and to 0.15 while she is talking, so her voice is heard over it. Volume and track controls sent to the page work the same way. In a chat with no voice, the tracks are attached to the message, ten at most, because Discord allows ten files per message, and you should suggest `/join` to hear them out loud. The `radio` and `volume` actions need a voice channel to change anything, except that volume also works on the Studio page.

Music you generate is saved here too. The file goes into the library under the title, with a unique name. Its name is the title turned into lower-case words joined with hyphens, cut to 60 characters, with `.mp3` on the end, and `-2`, `-3` and so on added if the name is taken. The routes are `GET /api/music`, which returns the tracks and playlists, and `GET /api/music/<file>`, which returns the audio. A file name containing `..` or a slash, or a file that is not in the library, returns a 404 `No such song`. The Studio's dancing uses an analysis of each track (its beats, loudness and vocal line) computed at a low sample rate and cached in `data/music/.dance`, served by `GET /api/dance/<file>`, so she can move to the beat of a song that is playing.

The generate_music tool makes a new song with Google's Lyria model through OpenRouter. It is only available when an OpenRouter key is set, when there is somewhere to send the result (a chat or the Studio), and when the user has file permission. Its parameters are length (required, `clip` for about 30 seconds or `full` for a full song; any other value is refused with `Music needs length clip or full`), song_id (a song from the songbook; its lyrics and tags are recorded exactly as written), prompt (required when there is no song_id, a detailed description of the genre, mood, tempo, instruments and vocals; with a song_id it is optional production notes), and title (an optional title used to find and play the song later). A call without a song_id and without a prompt is refused. The clip uses the clip model (google/lyria-3-clip-preview) and a full song uses the song model (google/lyria-3-pro-preview), both configurable in the environment. The request is streamed, the call can take up to five minutes, and the audio arrives in pieces that the code joins into an MP3. The timestamps Lyria puts before each lyric line are removed from the returned text.

Because the music is made in the background, the tool call itself returns at once with a queued receipt: the song has started, not finished. The result arrives later as its own message. When the song is finished, it is saved to the library under its title, and then it is either attached to the chat or, if it is larger than 8 MB, kept in the library and offered for voice playback instead. In the Studio it is sent to the page to play. A reply to a finished song says it is done and that it is now playing in the chat, and it gives the lyrics for songs with vocals, cut to 1,500 characters, so you can talk about them without reading them all out.

## radio stations / free radio / music library details / track matching
The radio stations and their moods, as the stations action shows them (`STATIONS` in `src/music.js`). From SomaFM: Groove Salad (chill downtempo, ambient beats), Drone Zone (deep ambient, no beats, for calm), Lush (mellow vocals, sensuous electronica), Deep Space One (spacey ambient, drifting), Secret Agent (spy-movie lounge, playful), Beat Blender (deep house and downtempo, late night), Space Station Soma (mid-tempo electronica, spaced out), Illinois Street Lounge (classic lounge and bachelor pad). From Radio Paradise: Radio Paradise (eclectic rock, world, electronica mix), Radio Paradise Mellow (soft, slow, acoustic), Radio Paradise Rock (rock, with energy) and Radio Paradise Global (world music, warm). All stream at 128 kilobits.

Matching a station (`findStation`): the request is lower-cased and stripped of punctuation. An exact name wins; then a name that contains the request or is contained in it, closest in length; then the station with the most words in common with its name or its mood, counting only words of three letters or more, and at least half of those words must match. So "something calm" can find Drone Zone through its mood.

Matching a playlist (`findPlaylist`): an exact name in any capitals first, then a name that contains the request or is contained in it. Saving a playlist with a name that already exists (any capitals) replaces it under the old spelling. Deleting an unknown one does nothing. `data/playlists.json` is written directly, not through a `.tmp` file.

The library listing (`tracks`): every file in `data/music` whose name ends in mp3, wav, ogg, opus, m4a, aac, flac or webm, sorted by title. Each track is `{ file, title, about, made }`, where made is true when `library.json` has an entry for it. Titles from file names have dashes and underscores turned into spaces. A generated song's file name is the title in lower case with every run of other characters turned into one dash, trimmed of dashes at the ends, cut to 60 characters ("song" if nothing is left), then `.mp3`. `library.json` stores `{ title, about, at }` per file and is written directly. At the time of writing the folder had 13 audio files, 11 of them with entries in `library.json`, and no `playlists.json`.

The route `GET /api/music/<file>` serves a track with its type: mp3 as audio/mpeg, wav as audio/wav, ogg and opus as audio/ogg, m4a as audio/mp4, aac as audio/aac, flac as audio/flac, webm as audio/webm, and anything else as a plain download.

## what she should tell Owner when this breaks

When something in this area breaks, tell Owner what the symptom is, what it usually means and what to check, and say "not verified" when you are guessing. Most of these problems come down to a page that has not been opened, a stale page, a link that is not a file, or a number out of range, so start with the cheap checks before concluding anything is wrong with the code.

If the background did not change on screen, read the status first. If its browser report says ok is false, read the message out loud, because it names the layer or shader that failed. If there is no browser report at all, no Studio page has been open since the change, so nothing has been applied; ask Owner to open `/avatar.html`. If the report's revision is not the revision in `background.json`, the report is about an older change and the current one may not have been shown yet. A shader that fails with `shader download failed (HTTP 404)` means its file is missing from `data/backgrounds/shaders/`, and the fix is to save the shader again. A `shader failed to draw: …` message means the shader ran and then hit a render error; the page cleared the background, so simplify the shader and try again. An image that reports `image: The source image cannot be decoded.` (the browser's own wording) means the page could not read the bytes it was given. The file may still be fine, and the usual first step is to reload the open Studio page, because an open page can be running older code; if it still fails, check that the file really is a PNG, JPEG, WebP or GIF. `Use a PNG, JPEG, WebP or GIF image file, not a web page.` means the download or path pointed at a web page or a different file type, so ask for a direct image link. `Background exceeds 20 MB.` means the picture is too big, and `Background download failed: HTTP <code>`, `Use an HTTPS image URL or a local image path.` or a redirect away from HTTPS mean the link is wrong or insecure. A shader refused with `Shader code may not use #include …` has a forbidden line to remove, `Keep the shader under 12000 characters.` needs it shortened, and `Define void mainImage(out vec4 fragColor, in vec2 fragCoord)…` means the entry function is missing or has the wrong signature. `No saved background with that ID.` means the id is not in the list, so use status to list the saved ids.

## avatar model or expression broken / model failed to load / she cannot move / troubleshooting avatar
When a model fails, the message usually names the cause. `Avatar: Not a complete GLB version 2 file. Download the actual .glb, not its web page.` and `Use a self-contained GLB…` mean the link was a page, or the model refers to files outside itself, so find a direct, self-contained .glb. `Avatar exceeds the 100 MB limit.` means the model is too big. `Selected for loading. Check status for a player report; selection alone does not confirm rendering.` means the switch has happened but the page has not reported yet, so wait a few seconds and check the status. A non-empty `lastFailure` in the library means the new model failed in the page and the original was put back automatically; tell Owner which model failed and what the page's error text was. `No model for <name> at <path>` means the model file is missing from disk. A toast reading `Couldn't load <name>: …` means the page could not load that file. A toast reading `<name>'s model has no ARKit or viseme face shapes, so they can't blink or lip sync.` means the chosen model lacks those shapes, and another model is needed. `This avatar lacks the jaw shape needed to yawn.`, `lacks the arm rig for that gesture.`, and `This avatar has no finger bones, so its hands cannot pose.` mean the model cannot do that movement, so choose another movement or model. `This avatar lacks the facial shapes for that expression.` means the expression needs shapes the model does not have, and `get` will list what it has. `Duration must be 0 to 60 seconds; gestures need a positive duration.`, `Strength must be between 0 and 1.`, `Expression gain must be 0 to 3.` and `Use autonomous on or off.` are bad numbers in the call and should be corrected before retrying.

If an expression or gaze does nothing on screen, nobody has an avatar page open. Commands only reach open pages, and each one says "Sent to connected avatar viewers", which is true even when there are no viewers. A `there is no "<name>" frame, so nothing was changed.` error means the frame name is not one of eyes, face, bust or body, and a `zoom must be between 0.25 and 4; nothing was changed.` or `scale must be between 0.5 and 2; nothing was changed.` error means a number is out of range. In each case nothing was saved. An unknown moment gets `Error: no such moment …` followed by the full list, so use one of those names.

If a colour is refused with `Use a known color name or #RRGGBB; use none to restore the model default.`, the name is not in the short appearance list (see "appearance fields"); give a hex value. If a colour is saved but does not show, the model's mesh names may not match what the page looks for (hair, eye or iris, head, face or skin), so the override has nowhere to land; tell Owner which part and which model.

If the outfit list shows only the suit, the base model has changed: the wardrobe's `baseSha256` no longer matches the SHA-256 of `config.avatar.path`, so the built-in outfits and all saved outfit colours are ignored until the wardrobe is rebuilt for the new base. Your sewn outfits still show. If wearing an outfit snaps back to the suit, the page reported a load failure and the library put the original back; read `lastFailure`.

If the avatar never fidgets, check that an avatar page is open (fidgets are only planned while one is), that she is not asleep, settling or dancing, and that the pressure system is ticking. If her face seems stuck in one mood, remember that feelings do not fade on a clock: they change when a tagged sentence, a turn's words or an event changes them. The dashboard can calm a character with `POST /api/avatar/emotion` and `reset: true`.

If she does not dance to a song, the activity log will usually say why: `ffmpeg isn't installed, so songs can't be read for dancing` (install ffmpeg or set `FFMPEG_PATH`), `ffmpeg couldn't read the song: ...`, or `There's no song called <name> in her music library.`

If the view change does nothing, a Studio page may not be open (the reply says so). If the framing looks too tight or too loose after a size change, choose the frame again without a zoom: that sets zoom to one divided by the current size, so the preset fits again.

## no video clips / recorder broken / browser will not start / troubleshooting recorder
If the recorder produces no clips, read the activity feed for the video messages. `No clip: no Chrome or Edge found to run the hidden recorder (set AVATAR_BROWSER)` means install Chrome or Edge, or point `AVATAR_BROWSER` at one. `No clip: the recorder page did not open` means the hidden recorder did not connect within 60 seconds, and a visible recorder window should be opened. `No clip: reply is N characters (limit 900)` means the reply was too long for a clip; the text still went through. `click the recorder page once to allow audio` means audio is blocked in that window, so click it once. `Keep this window open (not minimised).` is the instruction for the recorder window itself, because it must keep running. If avatar mode says it is on but no clips arrive, check the activity feed, since the failure is almost always one of these messages. Other `No clip for reply #N: ...` reasons: `the recorder did not start in time` (the page did not acknowledge within 8 seconds; it may be busy with an earlier clip, or its model was still loading), `the recording took too long` (over 120 seconds), `the recorder page closed`, `the avatar is still loading`, and `clip is N MB, over the 20 MB limit`. If clips stopped after a restart, check whether avatar mode is still on: the saved setting in `data/settings.json` wins over `AVATAR_VIDEO`. With avatar mode off, a `No clip: the recorder page did not open` line in a server channel only means no clip was wanted (see "recorder page"). Voice must also be ready: if text-to-speech is not set up, there are never clips and nothing is logged for it.

If the browser does not start, `No Chrome or Edge found on this computer.` means install one or set `AVATAR_BROWSER`. `The browser started but never answered.` means it launched but its debugging port did not respond, so check that nothing else is using port 9333. `Couldn't open <url>: nothing is running at …` means the local project is not running yet, so start it first, and `there's no website at …` means the name did not resolve, so check the spelling. `the internet connection failed` means the network is down. `The browser closed.` means the window was closed by someone, and show brings it back.

## songbook, journal or music broken / book page empty / troubleshooting books
If the songbook refuses something, `No open song #<id>.` means the song has been recorded or dropped, or does not exist, so use list to see what is open. `Error: no song #<id>. Use list.` means the id is wrong. `A song needs lyrics.` means the lyrics were empty, and `Error: write the full lyrics with [Verse 1], [Chorus] …` means the lyrics had no section tags. If the book page shows "No songs yet" or "No journal entries yet", the lists really are empty. If a write does not animate on the page, the page was not open when the write happened, so ask Owner to open the book before you write when he wants to watch. If you keep revising old songs instead of writing new ones, that is by design: any draft is revised before a new song is written, so mark finished drafts ready or drop the ones you have given up on. If the journal pen never moves, the research passes are being skipped before the search (the pen only starts once a search is approved); read the reasons with the self tool's research action or in `data/research-decisions.jsonl`.

If the journal says `Web search is not configured; no researched journal entry was invented.`, the search key is missing, so entries cannot be researched; tell Owner that. `Pre-search relevance check failed: …` means the model's check failed, so nothing was searched. `Journal generation failed after the search` means the model failed to write the entry after the search, and the decision log records that it happened. An entry marked `inconclusive` is by design: the results did not clearly answer the question, so it was left unresolved rather than guessed.

If a music request fails, `Error: no playlist called …` means the name matches no saved playlist, and `list` shows the ones that exist. `Couldn't find: …` means a title did not match the library, and `Error: nothing to play.` means no track matched at all. `You're not in a voice channel, so the songs are attached here instead …` means the songs were sent as files because nobody is in a voice channel, and `/join` will play them out loud. `Music needs length clip or full` means generate_music was called without a valid length. If a generated song never shows up, remember that generation runs in the background and can take a minute or more for a full song, and that a song over 8 MB is kept in the library rather than attached.
