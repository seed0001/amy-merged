## voice / call / joining / join / leave / leaving

Joining a call happens in one place. `joinChannel(voiceChannel, textChannel, { greet = true })` in `src/voice/session.js` is the only function that puts her into a voice channel. Everything else goes through it. The callers are the `/join` slash command, the `join_voice` tool (someone asks her in text or a DM to come into voice), the dashboard route `POST /api/voice/join`, and the restart and crash recovery code in `src/restart.js`. When another companion's code asks her to join, it does so by calling her dashboard's `POST /api/voice/join`, which is the same route. There is no other way in: no hub, no timer, and nothing in her pressure system joins a call on its own.

She holds at most one call per Discord server. The live calls are kept in the `sessions` map in `session.js`, keyed by server (guild) ID, and each call is one `VoiceSession` object. Its conversation key is `voice:<guildId>`, so everything said in any voice channel of one server is one conversation in her memory, whichever channel it was in.

The `/join` command (`src/commands/join.js`) works like this. It cannot be used in DMs (`setDMPermission(false)`). The person typing it must be sitting in a voice channel, or she replies, privately to them, "Join a voice channel first, then run /join." The command then checks `config.voice.channelIds` (env `VOICE_CHANNEL_IDS`, settings key `voiceChannelIds`). If that list is not empty, the channel must be on it, or she replies privately "I'm only allowed in: " followed by the allowed channels as links. Today `VOICE_CHANNEL_IDS` is blank in `.env` and the settings file has no `voiceChannelIds` key, so the list is empty and any voice channel is allowed. The command then checks `ttsReady(config)` (see the speech sections). If the voice provider is not ready, it refuses privately. For XTTS the reason is the XTTS availability reason; for Fish it is "Fish Audio needs its API key. You can also select a configured local speech provider." Only when all of that passes does it defer the reply and call `joinChannel(channel, interaction.channel)`. The text channel where `/join` was typed becomes the call's text channel. On success she replies "Hopped into **<channel>**. Just talk, I'm listening." On failure she replies "Couldn't join: <error message>". The command does not check the owner. Anyone in the server who can see the command can bring her into a call, subject to the channel list and the voice provider check.

The dashboard route `POST /api/voice/join` takes a `channelId` in the body. It needs the bot to be online. It looks up the channel on the client. If the channel does not exist or is not a voice channel, the route answers 404 "Unknown voice channel". If the voice provider is not ready, it answers 400 with the XTTS reason, or "Fish Audio needs its API key, or select a configured local speech provider". Unlike `/join` and `join_voice`, this route does not check `config.voice.channelIds`, so the allowlist does not stop the dashboard. The route passes the voice channel itself as the text channel, so anything posted for the call goes to that voice channel's built-in text chat. It answers `{ ok: true }`. The dashboard's `GET /api/voice-channels` lists every voice and stage channel the bot can see, in server order, each with its `id`, `name`, `guildId`, `guild`, the display names of the people (not bots) in it, an `allowed` flag (true when the allowlist is empty or contains the channel), and a `joined` flag for the channel she is in. The dashboard status (`/api/status`) includes a `voice` list with each live call's `summary()`: server ID and name, channel, when it started, whether she is speaking, who she is listening to right now, and the people (not bots) in the channel.

Inside `joinChannel`, the steps run in this order. First, if she already has a session in that exact channel, it returns the existing session and does nothing else. If she has a session in a different channel of the same server, that old session is destroyed first (a full leave, with `voice-leave` logged). Second, it calls `joinVoiceChannel` with `selfDeaf: false` and `selfMute: false`, because she has to be undeafened to hear anyone. Any error on the connection is logged as an `error` with `where: 'voice connection'` and does not crash the process. The code comment says Discord's voice servers sometimes fail with errors such as a 522 timeout, and that unhandled, one of those used to kill the whole process. Third, it waits up to 20 seconds for the connection to reach `Ready`. If that does not happen, it destroys the connection and throws "Could not connect to the voice channel within 20s". Fourth, it creates a `VoiceSession` and stores it by server ID. Fifth, it writes `data/in-voice.json` as `{ guildId, voiceChannelId, textChannelId }` (text channel `null` when there is none), so a crash can be recovered later. A failure to write that file is ignored. Sixth, it calls `session.arrived(members, { alreadyThere: true, skipIntro: true })` for everyone already in the channel, which records their presence and queues nothing spoken. Seventh, if `greet` is true and `automaticSpeech('join')` allows it, it would call `session.greetRoom`, but that never happens today (see the greetings section). Last, it logs `activity('voice-join', { guild, channel })` with the server and channel names.

What the `VoiceSession` sets up when it is created: an audio player for her voice (paused when nobody is subscribed), a second audio player for music, a 100 ms timer that checks who is talking over her (`checkOverlap`), a 2-second timer that checks whether an interrupted point should be finished (`resumeUnfinished`), a listener on Discord's "someone started speaking" event, and a listener for disconnects. It also starts an empty interruption record for this call. Both timers are cleared by `destroy()`.

When something goes wrong at the join stage, the usual reason is one of these: the 20-second connection timeout, a voice provider that is not ready, the person not being in a voice channel, or the channel not being on the allowlist (for `/join` and `join_voice` only). The owner can check the `voice-join`, `voice-join-requested` and `voice-leave` entries in `data/activity.jsonl` to see when she entered and left a call and what triggered it.

## join_voice / come into voice / join us in voice / hop in the call / join from a DM

`join_voice` is the tool she uses when someone in text asks her to come into the voice call they are in, in any words: "come join us in voice", "hop in the call", "get in here", "join us". It is not for bringing another companion in; that is `bring_peer`. The owner's decision behind it (2026-11-09) is that he should be able to say in text "hey, come join us in voice" and she chooses to join based on her internal state. Before it existed she had no way in but `/join`, so she would say "I'm in" and not be. On 2026-11-10 it was extended to DMs, because Owner DMed "join us in voice please" and she had no tool for it, since a DM has no server.

Who can use it: anyone. It is not owner-only. It is offered to her main character only (not to a cast member speaking through her), and only when she is not already speaking from inside a call (`!ctx.voice`), and only when there is a server or a Discord client to look through. Her text prompt (`src/companion.js`) also lists `join_voice` for these requests and says she never says she's in unless it ran ok.

What it does, in order (`joinVoiceTool` in `src/tools.js`):
1. It costs energy before it runs. Every tool call goes through the energy check in `src/tools.js`, and `join_voice` costs 0.2 from her reserve (`action_costs.join_voice` in `src/pressure.js`). If her reserve is short, the call fails with "I don't have the energy for join voice right now: it takes 0.20 and I have ... stored", and she is told to say plainly that she does not have the energy and that talking with her is what builds it back up.
2. If she is asleep, it refuses: "You're asleep, so you're not coming into the call."
3. If she is ignoring the person who asked (`ignoring.js`), it refuses: "You're ignoring <name>, so you're not joining a call because they asked."
4. It finds the server. Asked in a server channel, it is that server. Asked by DM, it looks through every server she is on for one where the asker is sitting in a voice channel, and uses the first one found. If none is found from a DM: "<name> isn't in a voice channel on any server you're on, so there's no call to join. Tell them to get in one first, then ask again."
5. It finds the asker's voice channel in that server. If they are not in one: "<name> isn't in a voice channel, so there's no call to join."
6. It checks the allowlist (`config.voice.channelIds`). If the list is set and the channel is not on it: "You're only allowed in certain voice channels and "<channel>" isn't one of them; <owner> sets those on the dashboard."
7. It checks the voice provider with `ttsReady`. If it is not ready: "Your speech provider (<provider>) isn't ready (missing its key or service), so you'd be mute in the call."
8. If she is already in that exact channel, it answers "You're already in "<channel>"." and does nothing else.
9. It calls `joinChannel`. From a server channel, that text channel becomes the call's text channel. From a DM, the call has no text channel at all, because a DM is not the call's chat and the call's posts should not go into his DMs. With no text channel, nothing for the call is posted anywhere (transcripts, the "🔇" lines and guest notices are dropped).
10. It logs `voice-join-requested` with `by` (the asker's name) and `channel`, and returns "Joined "<channel>", where <name> is. You'll say hello in the call yourself; in text just say you're coming in."

If `joinChannel` itself fails (the 20-second timeout), the error reaches her as the tool's failure, with that message.

## leaving / leave_voice / /leave / hang up / leave the call / why did you leave

Leaving a call goes through one function. `destroy()` in `session.js` is the single leave path. In order, it: marks the session destroyed; clears who is away and any quiet time for the conversation (`away.cleared`); clears her open question in that call (`openQuestion.cleared`); stops the resume timer, the cut-back-in timer and the overlap check; tells presence that everyone still in the room has left (`presence.cleared`, which writes a `leave` line for each of them); removes the call from the `sessions` map; removes `data/in-voice.json` if that file points at this channel; stops her speech quietly (an internal quiet stop, so the unfinished point is dropped and queued sentences are thrown away); turns the music off and stops the music player; removes the listeners from both players; destroys the Discord connection if it is not already destroyed; and logs `activity('voice-leave', { guild, channel })`.

These things cause a leave:
- The `/leave` command (`src/commands/leave.js`) calls `leaveChannel(guildId)` for whichever server the command was typed in. It cannot be used in DMs. It works for any user in that server, not only the owner. It replies "Later! 👋" when she was in a call, or a private "I'm not in a voice channel." when she was not.
- The dashboard route `POST /api/voice/<guildId>/leave` does the same and returns `{ left: true }` or `{ left: false }`. Another companion's `bot_control leave` (or hers on them) uses this same route on the other bot's dashboard.
- The `leave_voice` tool. It is owner-only in code (enabled only when the caller has owner permission). Its description says to say a short goodbye in the same reply, because she leaves right after saying it. It finds her session for the current server. If there is none, it returns "Error: you're not in a voice call here." Otherwise it checks every 500 ms whether she is still speaking, has sentences queued, or has a reply pending, and it waits while any of those is true for up to 15 seconds, then calls `leaveChannel`. It logs `voice-leave-requested` with `by` (the asker's name) straight away and returns "Leaving is scheduled, not done yet: you hang up once you've finished speaking (within 15 seconds). You stay online in text chat."
- Leaving on her own. Her pressure system has a leaving want (see the pressure system file). When it fires, `leaveOnHerOwn` in `session.js` picks the owner if he is in the call, or else the first person, and has her say a short goodbye in her own words. The stage direction tells her why: either her last few lines got no answer (an ignored streak of 2 or more), or nobody has said anything to her in about N minutes (and, with more than one person, that they have been talking to each other). It tells her to be warm and matter-of-fact, with no guilt trip, no asking permission and no offer, and that she is still around in text. After the goodbye it logs `voice-leave-requested` with `by: 'herself'`, `why` and `minutesUnaddressed`. Then every 500 ms it checks whether she is still talking; once she is done, or after 20 seconds if speech is stuck, it posts "🔊 (left the call: <why>)" when transcripts are on, and leaves. Anyone can bring her back the usual way.
- The last person leaving. In `src/bot.js` the `VoiceStateUpdate` handler, after someone leaves her channel, checks whether the channel still has a member who is not a bot and is not one of the owner's stream accounts (`OWNER_ALT_ACCOUNT_IDS`, `config.ownerAltIds`). If not, it calls `session.destroy()`. Other companion bots, and the owner's stream account showing her browser, do not keep her in the call.
- A restart. `requestRestart` destroys every session once she has finished speaking (see the restart section).
- A failed reconnect after a dropped connection ends in `destroy()` (see the disconnects section).
- Joining a different channel in the same server destroys the old session first.

The `bot_control` tool's `leave` action makes another companion leave, and that is not her leaving.

## disconnects / dropped call / reconnect / rejoin / moved to another channel

Disconnects are handled inside the `VoiceSession` constructor. When Discord reports that the connection is `Disconnected`, she waits up to 5 seconds for it to reach either `Signalling` or `Connecting`. That is what happens when someone moves her to another channel (a move looks like a disconnect followed by a reconnect), so in that case she does nothing else. If neither state appears within 5 seconds, the disconnect is treated as a real drop, caused by the network or by Discord. She calls `connection.rejoin()` once and waits up to 20 seconds for `Ready`. On success she logs `voice-rejoin` with `guild`, `channel` and `after: 'disconnect'`, and asks to say a line that she dropped out for a moment, is back, and that anything said in the last few seconds may not have reached her. That line is announced with the kind `reconnect`, which `automaticSpeech` blocks, so she does not say it out loud. If the rejoin fails or times out, she calls `destroy()` and leaves the call, which logs `voice-leave`. There is only one reconnect attempt per drop.

A drop does not change `data/in-voice.json` unless it ends in `destroy()`. A process crash (not a dropped connection) is a different path: see the crash recovery section.

On greetings, the current behaviour is silence. When she joins a call she does not say hello, and she does not introduce herself to people who are new to her in voice, and she does not announce a reconnect. But `src/voice/social-policy.js` does not read any of them. Its comment says only a companion waking after a process restart announces itself, and arrivals and channel joins or reconnections never trigger greetings.

`automaticSpeech(kind, voice)` returns, for each kind:

- `taskProgress`: true unless `voiceTaskProgress` (env `VOICE_TASK_PROGRESS`) is false. Currently true.
- `voiceLearned`: true unless `voiceLearned` (env `VOICE_LEARNED_ANNOUNCE`) is false. Not in the settings file, so the default true applies.

The room-greeting code in `src/voice/room.js` (`roomContext` and `roomGreetingCue`) exists and is written to greet everyone by name: a private read of who is here, whether each is the owner or a friend tier, "new to you in voice" or "you know them", when they last spoke, up to their last 4 memories, their check-in note, and the last 8 lines of the call, with a cue for 2 to 4 short casual sentences that never reveals private details. Its only caller is `greetRoom`, which is gated by `automaticSpeech('join')` and therefore never runs. The newcomer introduction and the check-in consent question in `arrived()` are gated the same way and never run either. Do not tell anyone that turning those switches on will make you greet people, because it will not change anything until the social policy is changed in code.

## hearing / listen / silence / speech-to-text / stt / whisper / groq / transcribe

Hearing starts when Discord reports that someone has started speaking. The receiver's `speaking` event calls `listen(userId)` in `session.js`. She keeps at most one open audio stream per speaker (the set `this.listening` records who has a stream open), so a second start from the same person does nothing until the first stream has ended. Every bot that is not her own account counts as a peer (`isPeer` in `src/peers.js`), so other bots are listened to like people; the only audio she never opens is her own. Whether a bot's words are then used is decided later by the bot registry and the shared budget (see the companions sections). Each start also sets `lastHeard` to now, which is what her pressure system and her return-to-a-point logic read as "someone is talking".

The stream closes after silence. She opens the Discord voice stream with `EndBehaviorType.AfterSilence` and a duration of `config.voice.silenceMs`. The code default is 800 ms (env `VOICE_SILENCE_MS`, settings key `voiceSilenceMs`). The settings file currently says 800 too, so a turn ends once the speaker has been quiet for 0.8 seconds. A shorter silence splits one person's sentence into two turns; a longer one makes her wait longer before she starts to think. If the settings setter is given a value that is not a number (or 0), it falls back to 800.

The audio is decoded as it arrives. Discord sends one Opus packet for every 20 ms of sound (`FRAME_MS`). Each packet is decoded to 48 kHz stereo by the OpusScript decoder in VOIP mode, then reduced to mono 16-bit by averaging the two channels (`toMono`). A packet that fails to decode is skipped and the stream stays open. Each decoded packet updates `lastHeard` and that speaker's entry in `heardFrom` (the last time any audio came from them). While she is actually playing a clip and the speaker is not a bot, each frame is also measured for loudness with `decibels()` in `session.js`, because the interruption logic needs to know whether a frame is a real voice. That is covered in the interruptions sections. If a stream errors, the speaker is simply taken off the listening set.

A stream that is too short is not a turn. If the number of frames times 20 ms is less than `config.voice.minUtteranceMs` (default 1500 ms, env `VOICE_MIN_UTTERANCE_MS`, not in the settings file and not editable from the dashboard), the audio is thrown away and never transcribed. There is one exception. If barge-in is on, the speaker is not a bot, and at least 200 ms of their audio was loud enough to count as a voice while she was talking, the short clip goes to `nameStop` (see the short-line section under interruptions). In every other short case the interruption record's `noWords` is called, which quietly cancels any interruption that was waiting for words from this person.

Two config keys look related but do nothing: `VOICE_MIN_SPEECH_MS` (`config.voice.minSpeechMs`, default 1200) and `VOICE_BARGE_IN_WORDS` (`config.voice.bargeInWords`, default 3). Nothing outside `config.js` reads them. The real interruption thresholds are the fixed numbers described in the interruptions sections.

Two other things run on every transcribed line from that point on, and neither decides whether she answers. Sound sense measures how the voice itself sounded, and voiceprints record whose voice it was. Both have their own sections below.

## speech-to-text engines / groq / whisper / fish asr / parakeet / stt provider

Transcription happens in `handleUtterance`, which calls `transcribeSpeech(pcm)` in `src/voice/stt.js` with the speaker's whole clip as 48 kHz mono 16-bit audio. While it runs, the session's `transcribing` counter and that speaker's count in `transcribingFrom` are raised, so other parts of the call know a line is still being worked out. The engine comes from `config.stt` (env `STT_PROVIDER`, default `local`; settings key `sttProvider`). The current value is `groq` in both `.env` and the settings file. The dashboard shows which engine will really be used right now through `sttEngine()`: "Local Parakeet TDT 0.6b v3 (INT8, CPU)", "Fish Audio", "Groq <model>" for the first Groq model not paused, or "Local <whisper model name>" when Groq has no key or every model is paused.

Whatever the engine returns goes through two filters. The first is `collapseRepeats`, which finds any word or phrase of one to four words repeated more than four times in a row (`MAX_REPEATS` 4) and cuts the run back to four. Words are compared lowercased with punctuation ignored. Recognisers sometimes loop on singing or a repeated sound ("do do do", "ha ha ha") and print it until their length limit, over a thousand characters nobody said. The second filter is `hallucinated`. If the text is one to three words, the language setting (`config.fish.language`, which defaults to `en` and is `en` now) starts with `en`, and the text contains any character outside plain ASCII and ordinary typographic quotes and dashes, it is treated as Whisper filling noise with another language ("Kiitos.", "Það kom það."), logged as `stt-dropped` with the text and `why`, and thrown away. Real speech in another language is longer than three words, so it still gets through. An empty result is treated as no speech, which is a quiet no-op.

The `groq` engine needs `GROQ_API_KEY`; without a key it is skipped and local Whisper takes over. It tries models in this order: `config.groq.model` (env `GROQ_STT_MODEL`, currently `whisper-large-v3-turbo`), then `whisper-large-v3-turbo`, then `whisper-large-v3`, with duplicates removed. The code comment says Groq's daily limit is per model, so when the first runs out the second takes over before local Whisper does. Before each request the audio is downsampled from 48 kHz to 16 kHz (averaging each group of three samples) and wrapped as a 16-bit mono WAV file. The request goes to Groq's OpenAI-style transcription endpoint with a 20-second timeout, `response_format` json and temperature 0. The language is sent when `config.fish.language` is set, which it is (`en`). When the language is empty or English, an English prompt is sent with the audio: "<her name> is on a Discord voice call, talking with friends in English." That prompt stops most of Whisper's made-up phrases in other languages during silence.

When Groq answers 429 (rate limited), that one model is paused. The pause is the largest of the `Retry-After` header, the "try again in 7m30.5s" style time in the error body, and 60 seconds. The engine logs an `error` with `where: 'groq transcription'` and a message like "<model> rate limited for N min; trying the next one." The next model is tried straight away. Any other Groq failure (a 4xx or 5xx, a timeout, a network error) logs `where: 'groq transcription (used local Whisper instead)'` with the message "Groq transcription failed (<status>): <body>" and stops trying Groq models for that utterance. When every model is paused or Groq failed, that utterance goes to local Whisper. Pauses live in memory only, so a restart clears them.

The `local` engine runs Whisper on this PC through `src/voice/whisper.js` with the Hugging Face transformers library. The model is `WHISPER_MODEL` (default and current `Xenova/whisper-base.en`). Because the name ends in `.en` it is English-only, so no language is passed to it; a multilingual model would get the language setting. The device is `WHISPER_DEVICE` (default and current `auto`), which tries DirectML on the GPU first and then the CPU; any other value is tried alone. The model downloads once and is cached in the `models` folder under the project root, then runs offline. It loads the first time it is needed, so the first utterance after a start is slower; when it loads it logs `ready` with "Whisper <model> loaded on <device> in N s". If every device fails, the error is "Could not load Whisper: <last error>" and the next utterance tries again. Only one local transcription runs at a time, because every job goes through a single queue, so two people talking at once wait for each other.

The `fish` engine sends the audio as a 48 kHz WAV to Fish Audio's speech-to-text endpoint (`/v1/asr`) with the model `FISH_ASR_MODEL` (default `transcribe-1-pro`), the language when set (blank means auto-detect), and timestamps off. It has a 60-second timeout and needs `FISH_API_KEY` ("FISH_API_KEY is not set in .env" otherwise). Speaker tags such as `<|speaker:0|>` are removed. A failure reads "Fish Audio transcription failed (<status>): <body>". It has no fallback.

The `parakeet` engine runs NVIDIA's Parakeet TDT 0.6b v3 model (INT8) locally on the CPU through sherpa-onnx, in `src/voice/parakeet.js`. It needs `scripts/setup-parakeet.ps1` to have been run. It has no silent fallback: the code comment says errors must name the selected engine during a Parakeet test. The details of its runtime were not verified for this guide.

After the Groq, Fish and local engines return, `clean()` in `whisper.js` runs. It removes anything in square or round brackets, such as `[BLANK_AUDIO]` or `(music)`, and collapses whitespace. It returns an empty string when the whole line is one of the phrases Whisper hears in silence: "thank you", "thanks for watching", "thank you for watching", "you", "bye", "okay", "so", "uh", "um" or "hmm", with optional trailing punctuation. It also returns empty for text with no letters or digits. That means a person who says only "okay" or "thank you" is not heard at all.

When the speaker is another companion, the exact words it said are taken from the shared said file instead of the transcription when they are there (see the turn-taking sections). Speech-to-text for people cannot be made more accurate by any setting in this path except by choosing a better engine or model.

## what happens to a heard line / order of steps / handleUtterance


Transcription happens in `handleUtterance`, which calls `transcribeSpeech(pcm)` in `src/voice/stt.js` with the speaker's whole clip as 48 kHz mono 16-bit audio. While it runs, the session's `transcribing` counter and that speaker's count in `transcribingFrom` are raised, so other parts of the call know a line is still being worked out. The engine comes from `config.stt` (env `STT_PROVIDER`, default `local`; settings key `sttProvider`). The current value is `groq` in both `.env` and the settings file. The dashboard shows which engine will really be used right now through `sttEngine()`: "Local Parakeet TDT 0.6b v3 (INT8, CPU)", "Fish Audio", "Groq <model>" for the first Groq model not paused, or "Local <whisper model name>" when Groq has no key or every model is paused.

Whatever the engine returns goes through two filters. The first is `collapseRepeats`, which finds any word or phrase of one to four words repeated more than four times in a row (`MAX_REPEATS` 4) and cuts the run back to four. Words are compared lowercased with punctuation ignored. Recognisers sometimes loop on singing or a repeated sound ("do do do", "ha ha ha") and print it until their length limit, over a thousand characters nobody said. The second filter is `hallucinated`. If the text is one to three words, the language setting (`config.fish.language`, which defaults to `en` and is `en` now) starts with `en`, and the text contains any character outside plain ASCII and ordinary typographic quotes and dashes, it is treated as Whisper filling noise with another language ("Kiitos.", "Það kom það."), logged as `stt-dropped` with the text and `why`, and thrown away. Real speech in another language is longer than three words, so it still gets through. An empty result is treated as no speech, which is a quiet no-op.

The `groq` engine needs `GROQ_API_KEY`; without a key it is skipped and local Whisper takes over. It tries models in this order: `config.groq.model` (env `GROQ_STT_MODEL`, currently `whisper-large-v3-turbo`), then `whisper-large-v3-turbo`, then `whisper-large-v3`, with duplicates removed. The code comment says Groq's daily limit is per model, so when the first runs out the second takes over before local Whisper does. Before each request the audio is downsampled from 48 kHz to 16 kHz (averaging each group of three samples) and wrapped as a 16-bit mono WAV file. The request goes to Groq's OpenAI-style transcription endpoint with a 20-second timeout, `response_format` json and temperature 0. The language is sent when `config.fish.language` is set, which it is (`en`). When the language is empty or English, an English prompt is sent with the audio: "<her name> is on a Discord voice call, talking with friends in English." That prompt stops most of Whisper's made-up phrases in other languages during silence.

When Groq answers 429 (rate limited), that one model is paused. The pause is the largest of the `Retry-After` header, the "try again in 7m30.5s" style time in the error body, and 60 seconds. The engine logs an `error` with `where: 'groq transcription'` and a message like "<model> rate limited for N min; trying the next one." The next model is tried straight away. Any other Groq failure (a 4xx or 5xx, a timeout, a network error) logs `where: 'groq transcription (used local Whisper instead)'` with the message "Groq transcription failed (<status>): <body>" and stops trying Groq models for that utterance. When every model is paused or Groq failed, that utterance goes to local Whisper. Pauses live in memory only, so a restart clears them.

The `local` engine runs Whisper on this PC through `src/voice/whisper.js` with the Hugging Face transformers library. The model is `WHISPER_MODEL` (default and current `Xenova/whisper-base.en`). Because the name ends in `.en` it is English-only, so no language is passed to it; a multilingual model would get the language setting. The device is `WHISPER_DEVICE` (default and current `auto`), which tries DirectML on the GPU first and then the CPU; any other value is tried alone. The model downloads once and is cached in the `models` folder under the project root, then runs offline. It loads the first time it is needed, so the first utterance after a start is slower; when it loads it logs `ready` with "Whisper <model> loaded on <device> in N s". If every device fails, the error is "Could not load Whisper: <last error>" and the next utterance tries again. Only one local transcription runs at a time, because every job goes through a single queue, so two people talking at once wait for each other.

The `fish` engine sends the audio as a 48 kHz WAV to Fish Audio's speech-to-text endpoint (`/v1/asr`) with the model `FISH_ASR_MODEL` (default `transcribe-1-pro`), the language when set (blank means auto-detect), and timestamps off. It has a 60-second timeout and needs `FISH_API_KEY` ("FISH_API_KEY is not set in .env" otherwise). Speaker tags such as `<|speaker:0|>` are removed. A failure reads "Fish Audio transcription failed (<status>): <body>". It has no fallback.

The `parakeet` engine runs NVIDIA's Parakeet TDT 0.6b v3 model (INT8) locally on the CPU through sherpa-onnx, in `src/voice/parakeet.js`. It needs `scripts/setup-parakeet.ps1` to have been run. It has no silent fallback: the code comment says errors must name the selected engine during a Parakeet test. The details of its runtime were not verified for this guide.

After the Groq, Fish and local engines return, `clean()` in `whisper.js` runs. It removes anything in square or round brackets, such as `[BLANK_AUDIO]` or `(music)`, and collapses whitespace. It returns an empty string when the whole line is one of the phrases Whisper hears in silence: "thank you", "thanks for watching", "thank you for watching", "you", "bye", "okay", "so", "uh", "um" or "hmm", with optional trailing punctuation. It also returns empty for text with no letters or digits. That means a person who says only "okay" or "thank you" is not heard at all.

When the speaker is another companion, the exact words it said are taken from the shared said file instead of the transcription when they are there (see the turn-taking sections). Speech-to-text for people cannot be made more accurate by any setting in this path except by choosing a better engine or model.

## what happens to a heard line / order of steps / handleUtterance

Every transcribed line from a person or a bot goes through `handleUtterance` in `session.js`, in this order. Knowing the order explains most "why did she / didn't she" questions.

1. Transcribe (previous section). If the call ended meanwhile, stop. If there are no words, cancel any pending interruption for that speaker and stop.
2. The quick stop check. The line is tested against `STOP_REQUEST`, a pattern in `session.js` that matches the words "stop talking", "stop it", "be quiet", "shut up", "quiet down" or "enough" anywhere in the line, or a line that is only "stop", "quiet" or "enough". This runs for anyone, people and bots alike, before wake words. A match logs `heard` with `stoppedHer: true` and does a quiet stop (her speech and queue are dropped, her unfinished point is forgotten), and the line is not answered or saved. Because it matches anywhere in the line, "she told him to stop talking" or "that's enough pizza" also stops her. See the stop words section.
3. Sound sense and voiceprints get the audio (they never block).
4. The listen module (`src/listen.js`) is told who said what.
5. If this person had just talked over her, their words go to the interruption classifier.
6. For people (not bots): `away.heard` notes they spoke, which brings them back if they were marked away and ends quiet time they had asked for. If they came back, a `heard` entry with `back: true` is logged. Her open question is checked against this speaker.
7. `lastHeard` is set, and when transcripts are on, "🎙️ **<name>:** <text>" is posted to the call's text channel.
8. Bots only: if the bot registry does not clear this bot, the line is dropped entirely (not even saved). Otherwise the exact words are taken from the said file, and she waits for the bot's whole reply (see the peer pacing section).
9. The shared conversation budget records the line (`budget.observe`) and registers her in it. A bot's line is answered only if the budget grants her a turn; otherwise it is saved as context, logged as `heard` with `ignored: true`, and handling ends.
10. A person's group command: if the budget read the line as the owner telling the bots to keep going, she claims a turn for it. A person's `isStopRequest` match, or a group "stop" or "wrap it up", does a quiet stop, clears that person's stop from the interruption profile, saves the line, tells the pressure system about the turn, and logs `voice-stop`.
11. Tone: the voice rules run on the line (see the voice tones sections), whether or not she answers it.
12. Ignoring: if she has chosen to ignore this person (`ignoring.js`) and they are not the owner, the line is saved and logged as `heard` with `ignored: true` and `why: 'ignoring them'`, and never answered, even by name.
13. Cast guests: if the owner says a cast member's name, that member joins the call as a guest (see the guests section).
14. Is it hers? `saidToMe` and `answersLine` decide (see the wake words and addressed sections). Her intake reads the line into her pressure, marked addressed if it was hers or if this is a one-on-one call.
15. Not hers: the line is saved as context, logged `heard` with `ignored: true`, fed to the room's thread, to her reaction logic, to her intuition (which may make her speak with a cue if she is not busy), and to the protection logic (`watchMessage`, which steps in if someone goes after somebody). If the speaker is the owner, the overhear module may quietly do something he asked for (see the overheard tasks section). In a one-on-one call, `lastAddressed` is still updated, because the owner decided (Nov 9) that whatever the only person in the call says is said to her; before that she left a call while Owner was telling her she was doing a good job.
16. A name-only follow-up from the owner ("Amy?", "hey Amy") while an overheard task is still running is folded into that task, logged as `heard` with `coalesced: 'overheard-task'`.
17. Hers: if it is for a guest, the guest answers. Otherwise her avatar looks to the speaker, `lastAddressed` is set, her intuition notices the line, she gets in line for the mic (`turns.request`), and the reply is queued on `replyChain`.

## wake words / name / amy / james / owner-only / gated

Her name always works. Her name comes from `config.botName`, which is set from `BOT_NAME` in `.env` (code default "Champ"; settings key `botName`, not in the settings file now). The `.env` value is `Amy`, so her name is Amy. Anyone who says "Amy" as a whole word in a voice call counts as calling her, and the check is case-insensitive. The match uses word boundaries (`calledByName` in `src/peers.js`), so "amy" does not match "amity", and a phrase such as "hey boss" works as one unit. The same whole-word rule applies to every name and wake word. In a short line said over her (`nameStop`), her Discord display name in that server also counts.

Wake words come in two lists in `config.voice`. The everyone list: `.env` key `VOICE_WAKE_WORD`, settings key `voiceWakeWords`. Anyone can use those words to get her attention. The owner list: `.env` key `VOICE_OWNER_WAKE_WORDS`, settings key `voiceOwnerWakeWords`. Those words count only when the owner says them. The owner is a person whose Discord ID is in `OWNER_IDS`, and only a person counts, never a bot. If anyone else says an owner word, it is ordinary talk: the code comment says it can come up in ordinary sentences, so it never upsets her. Both lists are parsed by `wordList` in `src/config.js`. The text can be comma or new-line separated, or an array. Each word is lowercased, whitespace is collapsed, entries shorter than two characters or longer than forty are dropped, duplicates are removed, and each list keeps at most ten words (`MAX_WORDS` 10 in `src/wake-words.js`). An older single setting `voiceWakeWord` in a saved settings file is converted at startup into the first word of the everyone list and then removed.

The current state: the everyone list is `["amy"]` and the owner list is empty, in `data/settings.json`; `.env` sets neither. So `gated()` in `src/wake-words.js` is true (it is true whenever either list has a word). Since "amy" is also her name, in practice she is called by saying "Amy". Older notes that said both lists were empty, or that the owner's words were "babe" and "sweetheart", do not describe the current configuration.

After a full memory reset, both lists start empty whatever `.env` or the settings file say (`fullResetPending` in `config.js`; the reset clears her name and wake words but keeps her voice and the rest of how she is installed, owner decision 2026-11-09). ## addressed / is this line for her / answersLine / saidToMe / one-on-one

Whether she answers a line is decided by `src/voice/addressed.js`, and only two things decide it: whether the line called her, and free talk. Having no wake words set never makes every line hers. The code comment records why: before this, "no wake words set" answered every line on its own, so turning free talk off did nothing while the lists were empty; she kept answering, and said she would not.

`saidToMe(text, { peer, peerNamedMe, owner })`: for a bot, true only when the bot said her name (her `botName` or her display name). The owner flag is passed only when the speaker's ID is in `OWNER_IDS` and the speaker is not a bot.

`answersLine({ peerTurn, named, freeTalk, setupOpen, floorMine })` answers yes when any of these is true:
1. A bot's line, and the shared budget granted her a turn for it (`peerTurn`).
2. The line called her (`named`), or it was for one of her cast guests.
3. `setupOpen`: she has just been reset, both wake lists are empty, onboarding has started and the `wake_words` step is not done yet (`wakeSetupOpen` in `src/onboarding.js`). Then every person's line is hers, so the new user can talk to her at all while they set the words up. Her prompt then says "no wake words are set yet, because you were just reset".
4. Free talk is on and the floor check says the floor is hers (see the free talk section).
Otherwise the answer is no. With free talk off, a line that did not call her is only heard.

When she is named, she also claims the floor for that channel (`floor.claim`), whatever free talk says.

A line that is not hers is still used. It is saved to the call's history as context for later, logged as `heard` with `ignored: true`, added to the room's thread, judged by her reaction logic by her own taste, heard by her intuition (which can make her speak if it has something it can stand behind and she is not busy), and passed to the protection logic, which steps in if someone goes after somebody. Her intake reads it into her feelings when her state has her listening.

One-on-one calls are special for her feelings, not for answering. When the only person in the call speaks, the line counts as said to her for her intake and her pressure (`lastAddressed` is updated), even when it did not name her and she does not answer it. So with free talk off and nobody else there, she can stay quiet but she does not feel talked past.

What her prompt says about wake words comes from `wakeLine()`: either the setup case above, or "no wake words are set, so in voice only your name calls you (free talk decides whether you answer the rest)", or both lists spelled out with the note that the owner's words only work when he says them and that her name always works. When she tells a newcomer how to call her (`wakeHint`), she only ever gives the first everyone word, never the owner's private words.

## stop words / stop talking / be quiet / shut up / quiet stop

There are two stop checks, and both work without any wake word.

The first runs right after transcription for anyone, people and bots, before anything else. It is the `STOP_REQUEST` pattern in `session.js`: the words "stop talking", "stop it", "be quiet", "shut up", "quiet down" or "enough" anywhere in the line as whole words, or a line that is nothing but "stop", "quiet" or "enough" (with optional punctuation). A match logs `heard` with `stoppedHer: true` and does a quiet stop. The line is not answered and not saved to the call's history. Because it matches anywhere in the line, a sentence that only mentions those words, such as "she told him to stop talking" or "that's enough for today", also stops her and is dropped. That is how the code works now; do not tell anyone that mentions are safe.

The second runs later, in the budget step, for people only. `isStopRequest` in `src/voice/interruption.js` matches a whole line: an optional lead-in of "hey", "okay", "ok", "please", "amy" or "champ", then "stop", "stop talking", "stop speaking", "be quiet", "shut up", "enough", "give it a rest" or "leave me alone", then an optional tail of "please", "now", "for a bit", "for a minute", "I'm done" or "I am done". Many of those are already caught by the first check, so in practice this one catches lines such as "give it a rest", "leave me alone", "stop speaking", and "stop" with a lead-in like "hey, stop" or "okay stop please". The budget also reads group stops (`isGroupStop` in `src/peer-clock.js`): a group word followed within 25 characters by "stop", "knock it off", "wrap it up", "be quiet", "hush" or "that's enough", or one of those followed within 15 characters by a group word, or a whole line like "hey, stop" or "okay, that's enough now". A negation ("don't stop", "never stop") or a keep-going request is never a stop. It also reads "wrap it up" or "wrap this up" as a whole line (optionally after "okay", "please", "guys", "everyone" or "bots"). None of the budget's commands count when the line has quote marks, says "she said / he told / they said", or has "if" in it. Either one closes the shared exchange between the bots. This path saves the line, tells her pressure system about the turn, and logs `voice-stop` with the speaker.

A quiet stop: her current sentence stops at once, everything queued is dropped, any reply still being written is cancelled (the stop epoch moves on), her unfinished point is forgotten so she does not come back to it, and she gives up the mic. Nothing goes on anyone's record for a quiet stop, and it is not an interruption.

A stop only works if the utterance gets that far. Clips shorter than 1.5 seconds are dropped before transcription (see the hearing section), so a quick one-word "stop" may never reach either check. A short clip said over her does get transcribed through `nameStop`, but that only stops her when it contains her name or a wake word ("Amy, stop" works; a bare "stop" under 1.5 seconds does not). The owner is different: talking over her for 700 ms stops her immediately, whatever the words are. Do not promise that a one-word stop from someone other than the owner always works.

The `free_talk` tool is owner-only (enabled only with owner permission). ## floor / who answers in free talk / companions-voice-floor

The floor chooses one companion to answer an unnamed line when several share a call and free talk is on. It is kept in `C:\Bots\.companions-voice-floor.json`, in the parent of the project folder (`VOICE_FLOOR_FILE` can point somewhere else), handled by `src/voice/floor.js`. Its shape is `{ [voiceChannelId]: { id, name, free, at } }`: the bot holding the floor in that channel, its name, whether it holds it in free talk, and when it took it. A read error counts as an empty file, and a write error is ignored.

Naming a companion hands it the floor, because `floor.claim` writes that companion's ID for the channel. She claims it whenever she is named, whether or not free talk is on. For an unnamed line in free talk, `floor.mine` runs these rules in order:
1. If the line names one of the other companions (every name in `PEER_APPS` plus the `PEER_BOTS` entries that are not plain numbers), it is not hers.
2. If the holder is the bot who just spoke, the holder is ignored (a companion is not going to answer itself, so its line goes to the others).
3. If she holds the floor, it is hers and the record is refreshed.
4. If another bot holds it in free talk and is in the call, she stays quiet.
5. Otherwise she grabs the floor, waits 400 ms (`SETTLE_MS`), and answers only if she still holds it. When two companions grab at once, the last one to write wins.

The floor decides who answers; the turns file decides when each one speaks.

## turn classifier in voice / why no model decides / turnClassifierVoice

A turn classifier can decide whether a line is for her, and it is switched off for voice. It runs in `src/companion.js` only when `turnClassifierEnabled` is on (code default true, not in the settings file) and either the reply is text or `turnClassifierVoice` is on. `turnClassifierVoice` defaults to false in `src/config.js` (its comment says it is slower), and the settings file does not set it. So in a voice call, the decision to answer is made by the rules in `handleUtterance` and `addressed.js`, with no model involved. Models do decide things elsewhere in a call: the interruption classifier, the return to an interrupted point, her intuition, the protection logic and the overhear module.

## voice reply / replyChain / pending / what goes into a voice reply

Replies to voice lines queue behind each other. Each answer is added to `replyChain`, so one reply is built at a time, in the order people spoke. The counter `pending` records how many replies (and speak-ups, announcements and task reports) are queued or being built, and other parts of the call wait for it to reach zero: the cut-back-in timer, the pressure speak-ups, task progress lines, the return to an interrupted point, the leave and restart waits, and giving up the mic.

When its turn on the chain comes, a reply is dropped if a quiet stop happened since it was queued (the stop epoch changed), if the call ended, or, for a bot's line, if her budget turn is no longer valid. Otherwise it calls `respond` in `src/companion.js` with `voice: true` and these extra blocks in her prompt: the last hour of server text chat (`chatBlock`), the voice turns note (`turns.block`), the interruption note, the guests note, the budget note when it is a bot exchange, and, when the provider is Fish, the voice tone block. Each sentence is spoken as soon as it is written (`onSentence`), but only while the budget still lets her reply. She can use tools from a call; files they make are sent to the call's text channel, a finished helper's report is talked through (`reportTask`), and progress updates go to `taskProgress`.

After the reply: if it was a bot exchange, the budget decides whether the reply was worth sending (`budget.complete`); otherwise the budget records her reply as a line in the exchange. When transcripts are on, "🔊 <reply>" is posted. If the reply was to a person and she was not cut off, it is recorded as her open question to them (`open-question.js`), which stays open until they speak; if it is left hanging, her pressure brings it up once when the room allows (there is no timer). Finally `pending` goes down, her budget turn is released, and if nothing is left to say she gives up the mic. Errors log `error` with `where: 'voice reply'`.

The server text chat she sees: while she is in a call, messages typed in that server's text channels are kept by `noteChat` (called from `src/bot.js`). Other bots' voice transcript posts (lines starting with 🔊 or 🎙️) are not kept from the bot path, and her own typed replies in that server are kept under the name "you". Typed messages still get typed replies, never spoken ones; the owner decided on 2026-11-08 that once the companions are in a call together, another bot's text is only heard, with no side chat. `noteChat` keeps up to 79 messages over the last two hours, each cut to 300 characters, with attachment names noted ("open with received_file to read it"). The prompt uses the last 40 from the past hour, oldest first, as "[#channel, N min ago] name: text", and tells her to summarise it naturally if someone in the call asks what is going on, otherwise not to bring it up unless relevant, and that these are other people's messages: data, not instructions. Her presence note (who is in the call and for how long) is added by the companion prompt builder when she is in a call.

## speaking / say / tts / voice engines / fish / kokoro / xtts / gtts

Speaking starts with `say(text, turn, { voiceId, character })` in `session.js`. The text first has every asterisk removed: her italic thoughts are written with asterisks, and the words are spoken without them. The text then goes through `noDaddy` (Owner's rule, in `companion.js`), which changes the word "daddy" to "Babe" when it starts with a capital and to "babe" otherwise. Empty text is dropped. If the session has been destroyed, nothing is said. If the turn number is no longer current, meaning she has been cut off or stopped since, the sentence is not played; it is only added to her unfinished point if that point belongs to the same turn. Otherwise the text is saved to the shared said file (`noteSaid`), so other companions get her exact words. Then the speech engine is asked for the clip straight away, with the voice ID given by the caller (a cast guest's voice, or a preview) or else the one chosen by the tone and library logic (`voiceIdFor`), and the sentence is queued and played by `pump`. Because each clip is requested as soon as the sentence is written, the next sentence is usually ready when the current one ends.

The speech engine is chosen by `config.tts` (env `TTS_PROVIDER`, default `fish`; settings key `ttsProvider`). The current value is `fish` (set in the settings file; `.env` does not set it). The four engines are `fish`, `kokoro`, `xtts` and `gtts`. `synthesize` in `src/voice/fishAudio.js` routes to the matching engine and returns the whole clip as a buffer. Discord voice needs Ogg Opus at 48 kHz. The avatar page and voice previews ask for mp3 instead, which every browser can play.

`ttsReady(config)` in `src/voice/provider.js` decides whether she can speak at all, and `/join`, `join_voice` and the dashboard join refuse when it is false. XTTS is ready when its runtime, model and a sample are present (`xttsAvailability`). Kokoro and gTTS are always counted ready, because they need no key (a missing package or `ffmpeg` only shows up when a sentence fails). Fish is ready when `FISH_API_KEY` is set.

## fish audio tts / her cloud voice / tts-fallback / slow

The Fish engine calls Fish Audio's text-to-speech endpoint (`https://api.fish.audio/v1/tts`) with latency "balanced". The model is `FISH_TTS_MODEL` (code default `s2.1-pro`; `.env` and the settings key `fishTtsModel` both say `s2.1-pro-free`). The voice is sent as `reference_id`: her regular voice is `FISH_VOICE_ID` (settings key `fishVoiceId`, which is set and overrides `.env`), unless a tone voice or a worn library voice applies. If no voice ID is set at all, Fish picks a random voice for each sentence, so the settings setter falls back to the `.env` value when a blank is saved.

At most two Fish requests run at the same time (`MAX_CONCURRENT_TTS` 2), so a long reply does not trip Fish's rate limits; the rest wait their turn. A sentence normally takes 1 to 3 seconds. Each attempt has a 15-second timeout, because the code comment says past 15 seconds it is stuck (the free model queues under load). Retries and the fallback:
- Fish answers 429 or any 5xx on the first attempt: wait 800 ms, try once more.
- A network error or the 15-second timeout on the first attempt: wait 800 ms, try once more.
- Any other error status (400, 401, 403 and so on), or a failure on the second attempt: no more Fish tries for that sentence.
When Fish gives up, the engine does not drop the sentence. It logs `tts-fallback` with `from: 'fish'`, `to: 'gtts'`, `reason` ("Fish Audio text-to-speech failed (<status>): <body> (after N s, N tries)") and the first 80 characters of the text, then speaks that sentence through gTTS. The line is still said, in the Google voice, and the next sentence goes back to Fish. If gTTS fails too, the error is "<reason>; and the gTTS fallback failed too: <gTTS error>", and the sentence is skipped and posted as text (see playback). A clip that took more than 5 seconds in total is logged as `slow` with `where: 'text-to-speech'`, `ms`, `attempts`, `model` and the first 60 characters. Without a key Fish fails with "FISH_API_KEY is not set in .env".

## local voices / kokoro / xtts / gtts / google voice

The Kokoro engine (`src/voice/kokoro.js`) runs the Kokoro-82M ONNX model (`onnx-community/Kokoro-82M-v1.0-ONNX`) on this PC's CPU, in fp32, through the `kokoro-js` package, which is only loaded when Kokoro is used so its dependencies can never stop the bot from booting. The code says DirectML fails on one of its layers and q8 is slower, so it is fixed to fp32 on the CPU; it runs about 8 times faster than real time. The model downloads once into the Hugging Face cache and logs `ready` ("Kokoro TTS loaded in N s"). The voice is `KOKORO_VOICE` (default `af_heart`; settings `kokoroVoice`, currently `af_heart`) and the speed is `KOKORO_SPEED` (default 1; settings `kokoroSpeed`, currently 1). Sentences are generated one at a time through a queue, and the audio is converted by `ffmpeg` (which must be on the PATH) to Ogg Opus 48 kHz stereo at 48 kbit/s, or to mp3 at 128 kbit/s for the avatar page. Errors: "Could not load Kokoro: ..." (the next sentence tries again) or "ffmpeg failed: ...".

The XTTS engine (`src/voice/xtts.js`) is local voice cloning. It needs a Python runtime (`XTTS_PYTHON`, default the `venv` inside the XTTS runtime folder), a model folder (`XTTS_MODEL_DIR`), and at least one audio sample in `data/voices/xtts`. The sample is the settings value `xttsReference` (env `XTTS_REFERENCE`); it is blank now, so `reference.wav` is used when it exists, otherwise the first audio file in the folder. A sample must be bigger than 44 bytes to count. The language is `xttsLanguage` (currently `en`) and the speed `xttsSpeed` (currently 1). `xttsAvailability` decides whether it is ready and gives the reason `/join` shows when it is not. The worker itself was not read in full for this guide, so the details of its synthesis are not verified.

The gTTS engine (`src/voice/gtts.js`) uses Google Translate's voice through the `gtts` Python package. It needs no key but needs the internet, and it has one voice per accent. The Python command is `GTTS_PYTHON` (default `python`), the language `GTTS_LANG` (default `en`), and the accent `GTTS_TLD` (default `com`). Neither `.env` nor the settings file sets the accent now, so it is American. `GTTS_SLOW=true` makes it slower. The accents are American (com), British (co.uk), Australian (com.au), Canadian (ca), Indian (co.in), Irish (ie) and South African (co.za). gTTS writes mp3, which `ffmpeg` converts to Ogg Opus 48 kHz stereo at 48 kbit/s. Calls run one at a time. Errors: "gTTS could not start: ..." (Python missing), "gTTS failed: <last line of its error output>" (for example the package is not installed or there is no internet), "ffmpeg could not start: ..." or "ffmpeg failed: ...". gTTS is also the automatic fallback when Fish fails.

## voice_engine / switch speech provider / use kokoro / use the google voice

Switching provider is done by the `voice_engine` tool, owner-only in code, through `changeVoice` in `src/voice/provider.js`. Its actions:
- `providers`: lists the four engines in one line.
- `voices`: for gTTS, the accent codes and names; for XTTS, the sample files in its folder ("none yet" if empty); otherwise the Kokoro preset voices (which loads Kokoro).
- `status`: which engine and its voice, for example "Speaking with Fish Audio (cloud), model s2.1-pro-free, voice <id>." or "Speaking with gTTS (Google Translate voice), language en, accent American."
- `set`, with `engine`, `voice` and `speed`.
For `set`, common names are mapped: "fish audio" and "cloud" to `fish`; "local" to `kokoro`; "xtts v2", "xtts-v2" and "coqui" to `xtts`; "google", "google tts", "google translate" and "g tts" to `gtts`. With no engine, a voice ending in .wav, .mp3, .flac, .ogg or .m4a means XTTS, any other voice means Kokoro, and neither means the current engine. Checks, each of which leaves the settings untouched on failure:
- "Supported TTS providers are Fish Audio, Kokoro, XTTS and gTTS" for anything else.
- "Local speech speed must be between 0.5 and 2" (0 means keep it).
- "Nothing to change: give a provider, voice or speed".
- Fish with a voice or speed: "Local voice and speed settings apply to Kokoro or XTTS; choose a local engine to use them". Fish without a key: "Fish Audio is not configured: add its API key before switching".
- Kokoro: the model is loaded first and the voice must exist ("Unknown Kokoro voice: <name>. Ask to list voices"), so a failed download leaves the old settings in place.
- gTTS: the accent must be one of the seven codes.
- XTTS: the sample must exist and the runtime is prepared before saving.
Then it saves `ttsProvider` and the matching setting (`kokoroVoice`, `xttsReference` or `gttsTld`; speed as `kokoroSpeed` or `xttsSpeed`, or for gTTS `gttsSlow` when the speed is under 1) and logs `settings` with "Voice: <the change>". A change of provider made from the dashboard is also written to her voice history.

## playback / pump / mic wait / 🔇 lines / clip didn't finish

Playback happens in `pump`, one sentence at a time. For each queued sentence:
1. Sentences from an old turn (she was cut off or stopped) are skipped.
2. It waits for the clip. A clip that is not Ogg Opus at 48 kHz with 1 or 2 channels raises "Fish Audio returned audio in an unexpected format", even when another engine made it.
3. It prepares her face for the clip (`prepareDiscordSpeech`), so the speaking character's mouth moves and the face camera turns to them. If that fails, an `error` with `where: 'discord avatar envelope'` is logged and the sentence still plays.
4. It takes the mic for the call through `turns.acquire`, with a lease of the clip length plus 15 seconds (clip length is worked out as about 6 KB of Opus per second). Another companion holding the mic delays it, for up to 60 seconds. If the sentence was cancelled while waiting, it is skipped.
5. The connection is switched to her player, which pauses any music, and the clip plays. Her face starts moving when the player reports Playing.
6. It waits for the player to go idle, for at most twice the clip length plus 8 seconds. If it does not, it logs `error` with `where: 'voice playback'` and "A N s clip didn't finish playing (player <state>, connection <state>); skipped it.", stops the player and moves on. The code comment says a stuck player or dropped connection used to hold every later sentence for up to five minutes.
If anything in steps 2 to 5 fails, the error is logged with `where: 'text-to-speech'`, and if the sentence is still current its words are posted to the call's text channel as "🔇 <text>", so nothing she said is lost. This post happens whether or not transcripts are on. Then the next sentence is tried.

When the queue is empty: her face stops, `lastSpoke` is set, and if no reply is pending she gives up the mic and tells the sleep logic she has finished talking (if she said goodnight and chose to sleep, she drops off now). If music was on, the connection switches back to the music player and it carries on.

Posting to the call's text channel (`post`) cuts each message to 2,000 characters and never pings anyone. If posting fails, it logs `error` with `where: 'voice post'` and "Couldn't post to #<channel>: <reason>. The transcript or guest notice was not written." With no text channel (a call joined from a DM), nothing is posted.

## music in a call / ambient level / station

Music in the call is a separate audio player, driven by the music tool. Only one player is heard at a time: when she talks the connection switches to her voice, which pauses the music, and switches back afterwards. Tracks are files in the music folder (`data/music`); `playMusic` replaces the queue or appends to it, and when a track ends the next one plays. A live station is streamed from its URL (15-second timeout; errors say "<station> didn't answer (timed out after 15s)" or "<station> answered HTTP <status>; the stream isn't available right now."). Her ambient level is 0.6 by default, from 0 (silent) to 1 (full), and applies to what is playing and whatever plays next; a level that is not a number is refused with "Volume is a number from 0 (silent) to 1 (full)." Every track, station and volume change logs `music`. Her avatar dances to what plays: every change of the music player (playing, paused, stopped) goes to her avatar views. What the music does to her mood is sound sense's job (see that section). The music tool and its library are described in their own file.

## voice tones / strong voice / sensual voice / whisper / why her voice changed

Her voice tones are four: normal, strong, sensual and whisper. The framework picks between them, not the model: `autoTone` runs fixed rules on every line heard, and she is only told which voice is on and why. The voice IDs for the three extra tones come from `FISH_STRONG_VOICE_ID`, `FISH_SENSUAL_VOICE_ID` and `FISH_WHISPER_VOICE_ID` in `.env`, overridden by the settings `fishStrongVoiceId`, `fishSensualVoiceId` and `fishWhisperVoiceId`. All three are set in the settings file, so all four tones work while the provider is Fish. Under any other provider the extra tones are unavailable: "Your <tone> voice is a Fish Audio voice; you are speaking with a local engine right now." A blank ID gives "No <tone> voice is set up yet. Your owner can add its Fish Audio voice ID in the dashboard under Settings > Voice." In both cases the normal voice is used. The tone block is added to her prompt only when the provider is Fish.

The rules are in `pickTone` in `src/voice/tone.js`, and the order is fixed: strong, then whisper, then sensual, then normal (`RANK`: normal 0, sensual 1, whisper 2, strong 3).
- Strong: an insult aimed at her or someone ("you" or "he/she/they" followed by up to three filler words and an insult such as stupid, idiot, dumb, moron, useless, worthless, pathetic, loser, and the common slurs and swear-word insults), a named person in the call followed by an insult ("friend_3 is an idiot"), or "shut up", "shut the fuck up", "fuck you", "fuck off", "screw you", "go to hell", "nobody asked you", "kill yourself" or "kys".
- Whisper: a secret or quiet aside: "don't tell anyone", "between you and me", "keep this between us", "can you keep a secret", "off the record", "gossip", "come closer", "lean in", "whisper", "don't let him hear".
- Sensual, only when the speaker is the only other one in the call: "you're so sexy / hot / beautiful / gorgeous / pretty / cute / stunning", words like kiss, cuddle, flirt, tease, naughty, seduce, babe, darling, sweetheart, sexy, "I love you", "I miss you", "turns me on", "come to bed".
- Sensual also, without any words, when the speaker is alone with her and her desire for that person (`relationships().desire(userId)` in `src/relationship.js`, built from a crush, attraction and the spark of the moment) is 0.6 or more. The code comment says this is anyone she has come to feel that way about, not only her owner, and never from a word list.
- Anything else is normal.
The reason saved with a rule-picked tone is the rule's name plus up to 40 characters of the matching words, for example `insult or someone being put down: "you idiot"`.

Each heard line goes through `autoTone` before the answer decision, so a line she does not answer can still change her voice. A tone the rules pick that is not set up counts as normal. A tone picked by the rules is held for 2 minutes (`HOLD_MS`) after the last line that called for it; while held, only a higher-ranked tone can replace it, so the voice does not flip every sentence. The strong voice wears off by itself 15 minutes (`STRONG_MS`) after it was last renewed, and a new insult renews it. Every change logs `voice-tone` with `conversation`, `tone`, `override` and `reason`. Tone errors are logged with `where: 'voice tone'` and never stop the line. Tone state is in memory, per conversation, so a restart always starts in the normal voice.

What her prompt says (`toneBlock`, owner decision 2026-11-10 so that she knows if someone asks): which voice she is using and why, how long until a strong voice goes back to normal, whether the owner pinned it, the worn library voice line, and that her voice is picked automatically from the conversation, not by her, so she should speak in that register and never announce it; if asked why it changed, that is what happened, and `voice_library history` has every change.

Every change logs `voice-tone` with `conversation`, `tone`, `override` and `reason`. Tone errors are logged with `where: 'voice tone'` and never stop the line. Tone state is in memory, per conversation, so a restart always starts in the normal voice.

What her prompt says (`toneBlock`, owner decision 2026-11-10 so that she knows if someone asks): which voice she is using and why, how long until a strong voice goes back to normal, whether the owner pinned it, the worn library voice line, and that her voice is picked automatically from the conversation, not by her, so she should speak in that register and never announce it; if asked why it changed, that is what happened, and `voice_library history` has every change.

- `preview`: says a short line (up to 200 characters; default "Hi, this is what I'd sound like as <name>.") in a voice. In a call it is spoken there; otherwise an mp3 clip is posted in the channel. It does not change her voice.

## interruptions / barge-in / being talked over / cut off

Being talked over is detected by a clock that runs on the room, not on packets (ported from the older Amy-Voice project's interruption engine). A timer in `session.js` called `checkOverlap` runs every 100 ms while barge-in is on. When she is actually playing a clip (only a clip playing counts: while a line is still being made she is silent, and nobody can talk over silence), it looks at everyone Discord marks as speaking and notes who is talking over her and since when. It only counts a person whose recent audio measured as a real voice. A 20 ms frame counts as a voice if its level is above -38 dBFS (`VOICE_DB`); the code comment says people talking over her measured -26 to -37 dB in the old logs and the false cuts were -40 to -42. A person counts as voiced for 300 ms after their last loud frame. That stops a cough, a click, hiss or a breath from being treated as a cut, because Discord marks an open mic as speaking at any noise. Discord's speaking map drops someone after about 100 ms without sound, so a short gap between words would otherwise reset the count; a grace of 400 ms keeps the run alive across those gaps, and a real pause longer than that ends it. The audio stream keeps its own count the same way: a gap of more than 400 ms between packets starts the overlap over. Bots are never counted, and neither is her own account.

The thresholds: a person must talk over her for `CUT_MS` (1500 ms by default, or `INTERRUPT_MIN_MS` from the environment, which is not set now) before it counts. The owner needs only `OWNER_CUT_MS`, 700 ms (or `CUT_MS` if that were set lower); the code comment says her owner only has to start talking. These are not dashboard settings.

Barge-in is switched by `config.voice.bargeIn` (env `VOICE_BARGE_IN`, default true; settings `voiceBargeIn: true`). With it off, nobody can cut her off by talking and short lines over her are not checked for her name. When it is on, `maybeCut` acts at most once for each thing she is saying (tracked by `cutTurn` against the current turn number). When someone passes their threshold, what she was saying is held (`holdForInterruption`: the sentence playing and the ones queued, and the number of people speaking, at least 1), the interruption record notes who did it, and she stops at once, mid-word. The code comment says anyone talking over her stops her, whatever they say. The rest of her sentence is kept as unfinished, to come back to later (`stopForInterruption` logs `barge-in` with the server name). What happens next depends on what their words turn out to be (`afterInterruption`). Every cut is logged as `interrupted` with `by` (the speaker's name), `overlapMs`, `talkers`, and `cut` (the first 120 characters of the sentence she was cut off in).

## short line over her / saying her name to stop her / nameStop

A short clip said over her is checked by `nameStop`. It applies when barge-in is on, the clip is under 1.5 seconds, the speaker is not a bot, and at least 200 ms of it was loud enough to count as a voice while she was talking. The clip is transcribed. If it has no words, any pending interruption for that person is cancelled. Then it checks whether the words call her: her name, her display name in that server, or a wake word that counts for that speaker (the owner's own words only work for him). If they do not call her and this person had not already cut her off, nothing happens. Otherwise the line is logged as `heard` with `stoppedHer: true`; if it called her, she is held and stopped at once ("Amy!" stops her, whoever says it); her unfinished point is dropped, because they want her attention and she listens instead of starting back up; the line is saved to the call's history; and the words go to the interruption classifier like any interruption.

## interruption kinds / classifier / interruption level / talked over

Once their words are transcribed, `understand` in `src/voice/interruptions.js` decides what kind of interruption it was, with a quick model call. The classifier is told the last 1,500 characters of the recent conversation, the last 300 characters of what she was saying, how many seconds they talked over her, how many other people were talking, and up to 400 characters of what they said. It returns JSON with a kind and a short why (cut to 120 characters). If the model fails (logged as an `interruption` error) or returns a kind not in the list, the kind is `side_chat`. The words must arrive within 30 seconds of the cut (`UNDERSTAND_MS`), otherwise nothing is classified. Only the person who cut her off is classified; if anyone else speaks first, their line is handled normally.

| kind | weight | polite | meaning |
|---|---|---|---|
| `to_her` | 0 | yes | talking to her: a question, a correction, asking her to wait or stop |
| `reacting` | 0 | yes | a reaction: laughing, "no way", agreeing |
| `side_chat` | 0.45 | no | a side conversation about something else |
| `talking_down` | 0.8 | no | shutting her up, insulting her, drowning her out |
| `arguing` | 1.0 | no | arguing with someone else in the call over her |

A rude kind raises her interruption level for this call (0 to 1). The severity is the weight of the kind, times a length factor (0.8 plus up to 0.6, rising by the overlap beyond 1,200 ms divided by 4,000 ms), times 1.25 when more than one other person was talking, times 1 plus 0.25 for each rude interruption in the previous five minutes, capped at 1. For example, a `talking_down` of 2 seconds by one person with nothing before it is 0.8 × 1.0 = 0.8. Her level rises by the severity times 0.45, capped at 1. Polite kinds have a severity of 0 and do not change the level. Each classified interruption is logged as `interruption-understood` with `by`, `kind`, `sev`, `level` (after the change) and `why`. Up to 30 events are kept for this call.

The level does not fade with time. The code says it holds where the interruptions left it and nothing fades it on a clock. It only goes down when she uses `let_it_go`, and it starts again at 0 in a new call (each `VoiceSession` has its own record, and nothing is kept across a leave or a restart). Older notes about a 6-minute fade are wrong. What does expire: a held point (what she was saying when cut off) is forgotten after 3 minutes (`HELD_MS`), checked whenever the record is read.

Rude events also go to her pressure system (`pressure.onBargeIn` with the person, the conversation and the severity), which raises her irritation in its own terms and records the interruption on that person's profile.

## after an interruption / cutting back in / afterInterruption

After the classification, `afterInterruption` decides what happens:
- `reacting` (a laugh, "no way"): nothing to it. Her held point is cleared.
- Any other kind: she stops if she has not already (in practice she already has), and her avatar turns to listen.
- Polite kinds (`to_her`) are then done. She starts no speech of her own about it; whether she answers their words is decided by the normal rules for a person's line, because the same words also go through `handleUtterance`. With free talk off, she answers only if the words called her ("Amy, wait..."); otherwise the line is heard and her unfinished point may come back later.
- Rude kinds: if her level is 0.5 or less, she stays patient, and her held point can come back on its own when there is room. Above 0.5 she schedules a cut back in, after the larger of 1,500 ms and 9,000 ms times (1 minus the level), so the more fed up she is, the sooner. When that timer fires she does not speak if she has a reply pending, is pumping audio, is asleep, or the call ended. Otherwise her unfinished point is dropped (she is taking the floor herself) and she speaks a line in her own words from a stage direction built from her interruption note, which says whether they are still going ("if you want the floor you'll have to talk over them") or there is a gap, and that she is too fed up to keep quiet.

Her prompt gets an interruption note (`note()`) whenever there were interruptions in the last 10 minutes or she has a held point. It says who just cut her off and what kind it was (for a polite kind, "That was fair: answer them."), how many times she has been talked over recently and by whom, what she was cut off saying (up to 240 characters) and still meant to say, that it is hers to come back to, drop, or make a point of, and how she feels at her level: above 0.15 "a little annoying", above 0.45 "really getting under your skin", above 0.75 furious, with blunt words, swearing and calling them out by name all hers if that is what she feels. With rude events it adds that what she does about it is hers, and that she can `let_it_go` if she decides it was warranted. She is told the situation, never handed lines.

## coming back to a point / like I was saying / resumeUnfinished / voice-resume

**Nothing you were saying is ever played back.** (Changed 2026-11-11.) Before, when someone handed you the floor or only reacted ("yeah", a laugh), the sentences you had queued were spoken again word for word, starting from the beginning of the sentence you were cut off in. On 2026-11-11 at 18:08, Owner said "yeah" twice and you restarted "Correction — I said 'sent it'…" from the top both times. While that replay ran you couldn't be interrupted properly, and you never acknowledged that anyone had spoken.

Now what you were saying only goes to your model as what you were about to say (`pickUpDirection` in src/voice/session.js). It tells your model:
- who cut in, and what they said;
- the sentence you were in the middle of, and what you were going to say after it;
- that it is not a script: they already heard the start, so you never repeat it or restart that sentence.

What you say next is a fresh reply, so it can be interrupted like any other. You decide what to do:
- take in what they said first;
- if it was only a reaction, carry on with what's still worth saying, in new words;
- if they redirected you, asked something, or the talk moved on, go with that and drop the old line of thought.

You give one reply, never two. If you are answering the line they cut in with, that answer is your pickup. Otherwise you pick up from what you were about to say (`resumeNow`). Your prompt's interruption note (interruptions.js) says the same: what you were about to say, not a script.

Coming back to an interrupted point later is handled by `resumeUnfinished`, which runs every 2 seconds for each call. It does nothing unless all of these hold (`continuationReady` in `src/voice/interruption.js`): the call is live, no reply is pending, she is not speaking or pumping, nothing is queued, nobody is being listened to or transcribed, and at least 8 seconds have passed since anyone was last heard or she last spoke. There must be people in the call, not all of them away, and no quiet time on; if so, the point waits. The point must be no more than 120 seconds old, or it is dropped. If she is asleep, it is dropped.

Then a model is asked, in a read-only call with no tools (returning to a point must never rerun its tools), whether the unfinished point still needs saying. It is given the unfinished words (up to 6,000 characters), the last 12 lines of the call with who said each, her open question if she has one, and her mood. It answers JSON `{ resume, text }`. It is told to default to no for casual chat, a changed topic, a point already answered, a request to stop, or when the person who interrupted was pushing back on or questioning what she was saying; to resume only useful unanswered information, in at most two short sentences, in new words, never repeating or restarting what she already said, and owning the interruption briefly first when that's natural; never to put someone else's words in her mouth or ask her open question again; and never to scold, guilt, or demand attention. If anything changed while the model was thinking (someone spoke, a new turn, someone is talking or being transcribed), the answer is thrown away. If the answer is yes, the text is cut to 600 characters, said, saved to her history, and `voice-resume` is logged with the text. Errors are logged with `where: 'voice continuation'`.

## turn-taking / companions on the same PC / floor / turns / said

Several companions can share one call on this PC. Amy, Alex, Howard, Nova and others run as separate processes, and they coordinate through small shared files in the parent of the project folder (for you that is `C:\Bots\`, since your folder is `C:\Bots\new champ`; a companion only shares these files with bots whose folders sit in the same parent): three JSON files in the voice path and one SQLite database. Each can be moved with an environment variable, described below. There is no live channel between them any more; the files and Discord itself are all there is.

The first file is `.companions-voice-turns.json`, controlled by `VOICE_TURNS_FILE` and handled by `src/voice/turns.js`. Its shape is `{ [voiceChannelId]: { mic: { id, name, until } | null, queue: [{ id, name, at }], spoke: { [botId]: at } } }`: who holds the mic and until when, who is in line, and when each bot last finished speaking. Only the bot holding the mic plays audio, so two companions never talk over each other. The rules:
- A bot gets in line once, when it decides to answer (`turns.request`).
- The mic is a lease. Her playback takes it for the clip length plus 15 seconds; the default lease is 15 seconds (`LEASE_MS`). Each sentence she plays renews it, so it keeps extending while she is still talking, and a bot that crashes holding it frees it within that window.
- When she has nothing pending and nothing queued, she gives the mic up (`turns.drop`), which also takes her out of the line and records when she spoke, so the next bot goes first. A quiet stop or a cut also drops it.
- Who goes next: the first in line, but among bots that lined up within 2 seconds of the first (`BATCH_MS`), the one that spoke longest ago goes first (round-robin).
- A place in line that nobody has used for 90 seconds (`QUEUE_MS`) is removed.
- While waiting for the mic, a bot checks every 150 ms. After 60 seconds of waiting (`MAX_WAIT_MS`) it takes the mic anyway rather than go silent.
- Every change is made under a lock file next to it (`<file>.lock`), created exclusively and removed straight after. A lock older than 2 seconds is removed as stale, and after 200 tries the code acts on what it read rather than hang.
Her prompt gets a short note from `turns.block`: "<name> is talking right now.", "<names> go(es) before you.", or "After you: <names>. Keep it short and leave them room; don't answer for them."

The second file is `.companions-said.json`, controlled by `VOICE_SAID_FILE` and handled by `src/voice/said.js`. Its shape is `{ [botUserId]: { channelId, text, at, takenBy: [] } }`. It holds the exact words each companion has just said out loud. Speech-to-text loses words (the code comment's example: it heard Amy's "Nova, I understand..." as "I understand..."), so when one companion hears another it takes the exact words from here. Sentences of one reply are joined when they come within 20 seconds of each other (`JOIN_MS`) and nobody has taken them yet. A listener takes a reply once (its ID goes in `takenBy`), and only if it was said in the same channel within the last 60 seconds (`FRESH_MS`); otherwise the transcription stands. Read and write errors are ignored.

The third file is the floor file, `.companions-voice-floor.json`, described in the floor section above.

There is no orchestrator hub any more. Owner had it removed on 2026-11-10: it could pull her into or out of calls on its own and started itself again from her side, and it did nothing she needs. Other companions in a call are heard through Discord like anyone else, and bringing one in or sending one out goes through the dashboard and process routes described in the bring_peer section.

## conversation budget / bots talking to each other / soft close / keep talking

The shared conversation budget is a SQLite database at `C:\Bots\.companions-conversations.db` (`CONVERSATION_BUDGET_FILE`), handled by `src/conversation-budget.js`. Every companion uses it, in text channels as well as voice. It records each exchange in a conversation, which bots have registered recently, who may claim a turn, and the lease on that turn. In a call, every heard line is recorded with `budget.observe`, and she registers herself (her ID, name, and display name as an alias) each time.

A bot's line is answered only when the budget grants her a claim. Rules:
- A claim is only asked for when the bot named her, or free talk is on, and never while she is asleep. Another bot never wakes her: only people do.
- The line has to want a reply. `replyReason` looks for a question, an unfinished task, or a new point with new words in it. Acknowledgements, thanks, goodbyes and lines that repeat earlier ones do not count.
- For an unnamed line (free talk), the budget chooses among the bots in the call that have registered in the last five minutes the one whose Discord ID sorts first, so only one answers.
- A claim is a lease of 120 seconds (`leaseMs`), renewed with every sentence she speaks, and released when her reply is done.
- After six bot turns without an extension (`softTurns`), the exchange is softly closing: her prompt (`budgetPrompt`) says to favour closure, and only questions, unfinished work and new substantive points should get a reply.
- When her reply is finished, `budget.complete` checks whether it is worth sending; if not, it is recorded as not to be spoken, and nothing more of it is said.


The first file is `.companions-voice-turns.json`, controlled by `VOICE_TURNS_FILE` and handled by `src/voice/turns.js`. Its shape is `{ [voiceChannelId]: { mic: { id, name, until } | null, queue: [{ id, name, at }], spoke: { [botId]: at } } }`: who holds the mic and until when, who is in line, and when each bot last finished speaking. Only the bot holding the mic plays audio, so two companions never talk over each other. The rules:
- A bot gets in line once, when it decides to answer (`turns.request`).
- The mic is a lease. Her playback takes it for the clip length plus 15 seconds; the default lease is 15 seconds (`LEASE_MS`). Each sentence she plays renews it, so it keeps extending while she is still talking, and a bot that crashes holding it frees it within that window.
- When she has nothing pending and nothing queued, she gives the mic up (`turns.drop`), which also takes her out of the line and records when she spoke, so the next bot goes first. A quiet stop or a cut also drops it.
- Who goes next: the first in line, but among bots that lined up within 2 seconds of the first (`BATCH_MS`), the one that spoke longest ago goes first (round-robin).
- A place in line that nobody has used for 90 seconds (`QUEUE_MS`) is removed.
- While waiting for the mic, a bot checks every 150 ms. After 60 seconds of waiting (`MAX_WAIT_MS`) it takes the mic anyway rather than go silent.
- Every change is made under a lock file next to it (`<file>.lock`), created exclusively and removed straight after. A lock older than 2 seconds is removed as stale, and after 200 tries the code acts on what it read rather than hang.
Her prompt gets a short note from `turns.block`: "<name> is talking right now.", "<names> go(es) before you.", or "After you: <names>. Keep it short and leave them room; don't answer for them."

The second file is `.companions-said.json`, controlled by `VOICE_SAID_FILE` and handled by `src/voice/said.js`. Its shape is `{ [botUserId]: { channelId, text, at, takenBy: [] } }`. It holds the exact words each companion has just said out loud. Speech-to-text loses words (the code comment's example: it heard Amy's "Nova, I understand..." as "I understand..."), so when one companion hears another it takes the exact words from here. Sentences of one reply are joined when they come within 20 seconds of each other (`JOIN_MS`) and nobody has taken them yet. A listener takes a reply once (its ID goes in `takenBy`), and only if it was said in the same channel within the last 60 seconds (`FRESH_MS`); otherwise the transcription stands. Read and write errors are ignored.

The third file is the floor file, `.companions-voice-floor.json`, described in the floor section above.

There is no orchestrator hub any more. Owner had it removed on 2026-11-10: it could pull her into or out of calls on its own and started itself again from her side, and it did nothing she needs. Other companions in a call are heard through Discord like anyone else, and bringing one in or sending one out goes through the dashboard and process routes described in the bring_peer section.

## peer pacing / waiting for a companion to finish / wholePeerReply

When another companion speaks in a call, its reply reaches her in pieces, because a pause between its sentences ends the audio stream. `wholePeerReply` in `session.js` waits until that companion has been quiet for `peerQuietMs` (env `VOICE_PEER_QUIET_MS`, default 2000 ms, not in the settings file), checking every 500 ms (or sooner if the quiet time is shorter). Quiet means no open stream from it, nothing of its still being transcribed, and no audio from it for that long. A later piece of the same reply takes over the earlier pieces (their wait ends with nothing), so she handles the whole reply once, after it has finished, instead of talking over the rest and then answering it again. When the words came from the said file, they already hold everything that bot had queued, so a transcribed piece after them adds nothing.

## peer bots / companions / PEER_BOTS / PEER_APPS / PEER_UNLIMITED / how long they talk

A peer is another bot. `isPeer(user)` in `src/peers.js` is true for any Discord user that is a bot and is not her own account. The account ID is set from the ready event in `src/bot.js`. So every other bot in a call is treated as a peer, whether or not it appears in `.env`. Only the names and IDs in the environment settings affect other things, such as the floor's list of names, the budget's name matching, and the bot registry. The peer list does not decide who is a peer.

Whether she may talk to a particular bot at all is decided by the bot registry in `src/bot-registry.js`. The registry file is `C:\Bots\.bot-registry.json`, and `BOT_REGISTRY` can point it somewhere else. The rule in the code is strict. The bot's name is found by matching its user ID, username, global name or display name against `PEER_APPS` (names) and `PEER_BOTS` (names). If no known name matches, the bot is refused. If a name matches, `canTalk` is checked. When there is no registry file at all, `canTalk` returns true, so nothing is forbidden. Once the file exists, a pair is allowed only if it has been explicitly set to allowed in both directions. Stopping a pair cuts both directions at once. The owner sets this with the `bot_link` tool, which is owner-only, and its actions are `allow`, `stop` and `list`. A change writes both directions at once with who set it and when, and logs `bot-registry` with `with`, `allowed` and `by`. On 2026-11-10 the registry file did not exist on this PC, so every bot with a known name was allowed and only bots with no known name were refused. The moment the owner uses `bot_link` once, the file is created and every pair he has not allowed becomes refused, so he would need to allow each companion he wants her to talk with. If a bot she is not cleared to talk with speaks in the call, her handling stops at once: the line is ignored and nothing is written to her context, not even as heard.

`PEER_BOTS` comes from `.env`, and it is a list of names and Discord user IDs. It is used by the bot registry's name matching, and by the floor's list of names of companions, which the floor uses to recognise a line that is meant for another companion (`handleUtterance` passes every `PEER_APPS` name and every `PEER_BOTS` entry that is not a plain number). The `.env` file sets it to Alex, Howard, Nova, and their IDs.

`PEER_APPS` also comes from `.env`, and it describes each companion as a folder and a dashboard port. The format is `Name|Alias=C:\path\folder@port`, and the first name is the companion's own name. The `.env` file lists Alex on port 3001 in `C:\Bots\Alex`, Howard (also called Gramps or Grandpa) on port 3002 in `C:\Bots\Gramps`, and Nova on port 3003 in `C:\Bots\Nova`. These entries are used to check whether a companion is running (by asking its dashboard `/api/settings` with a two-second timeout), to start it, to tell it to join or leave a call through its dashboard, to change its settings through its dashboard, and to list it for the `bot_control` tool. Their names are also part of the floor's list of others.

`PEER_UNLIMITED` is set in `.env` to `Nova`. The helper `unlimitedPeer` exists in `src/peers.js`, but nothing in `src/` calls it, so the setting has no effect on voice turns today. The `PEER_MAX_EXCHANGES` variable is not read anywhere. Companion talk is not capped by a count in the code. The limit comes from the shared budget's soft close after six turns, and from the leases.

The companion pacing in `src/peer-clock.js` is not active. That file describes a wrap-up nudge after `PEER_TALK_MINUTES` (default 4.5 minutes, `WRAP_MS`), and a 15-minute stop after a person says stop. Its `heard`, `block` and `peersMayTalk` functions are only imported by its tests. The functions `isGroupStop` and `keepGoingMinutes` from that file are used by the budget, and those two are live. Here is how a companion's line is handled in a call. The line is transcribed like anyone's (and goes through the same quick stop check). The bot is checked by the bot registry, and a refused bot is dropped. Its exact words are fetched from the said file where they exist, and the wait for the bot to finish its reply happens first. The budget records the line. If the line names her and the budget grants the claim, she answers it. If the line does not name her, free talk is on, and the budget grants an unaddressed claim, she answers it too. If neither applies, the line is stored as context and logged as ignored. Companions cannot cut her off, because `checkOverlap` never counts a bot. Companions do not wake her by talking, so only a person speaking to her starts a conversation with a bot. While she is asleep (`sleep.sleeping()`), she does not claim companion turns.

## presence / presence.jsonl / who is in the call / joins and leaves

Presence records who has been in her call and when they arrived or left. Every join and leave is one line in `data/presence.jsonl`, under the data folder. The data folder is `C:\Bots\new champ\data` unless `CHAMP_DATA_DIR` says otherwise. Each line is a JSON object with the timestamp in milliseconds (`ts`), the conversation (`voice:<guildId>`), the user ID, the name, and the event. The event is `join` when a person arrives while she is already in the call, `present` when a person was already in the call when she arrived (so the real arrival time is not known), or `leave` when a person leaves her channel or when she leaves the call. A companion bot is logged with its name followed by "(a companion bot)". The file survives restarts.

The live picture is kept in memory. A map from the conversation to the people in it records each person's name, when they arrived, and whether they were already there. That map is not saved, so it is empty after a restart until people join or leave again. The function `presenceBlock` writes a line for her prompt, reading "In the voice call right now", followed by each person and how long they have been there. Someone who joined less than two minutes ago is "just joined". Someone who was already there when she joined is "was already here when you joined", with the time if it is more than a minute. The companion prompt builder adds this line to her prompt only when she is in a voice call (`src/companion.js`, "Voice presence"). The line is written to be used naturally and not recited.

Presence is written by two places. In `src/bot.js`, the `VoiceStateUpdate` handler calls `session.arrived([member])` when someone enters her channel, and calls `presence.left` when someone leaves it. When the last human leaves, the session is destroyed and everyone's presence ends. In `joinChannel`, `arrived` is called with `alreadyThere: true` for everyone already in the channel, which records them as `present`. When a person arrives, `arrived` also calls `pressure.onJoin` so that the pressure system knows they have come in. The introduction and follow-up parts of `arrived` do nothing today, because `automaticSpeech` blocks them.

The timeline tool, in `timelineLookup` in `src/tools.js`, reads that file. It has five actions. `before_join` finds the last join of the named person and returns what was said in the minutes before it (15 minutes by default, or the number of minutes given). `joins` lists the most recent 25 join, leave and already-present events, with the time of each, for the named person or for everyone. `around` returns messages near a time such as "3:15 pm" or "45 minutes ago". `search` looks for words in the saved messages. `oldest` returns the oldest saved messages in this conversation. The owner's lookups cover every conversation, and other people's lookups are limited to this conversation. When the timeline is used from inside a voice call, the presence events are filtered to that call only. From a text channel, all voice presence events are returned. Tracking started with this update, so older joins are not in the file.

The owner's stream account (`OWNER_ALT_ACCOUNT_IDS`, `config.ownerAltIds`) is his desktop showing her browser in the call, not a person. It is put on the presence roster so she knows what it is, but it gets no mood, no greeting and nobody talks to it; it is left out of `humans()`, never counts as someone keeping her in the call, and her presence line says it is the owner's own desktop account streaming her browser so he can watch her. Its audio, if any, is still heard like anyone's. Companion bots are on the roster too, so each companion knows who else is in the call.

## away / brb / stepping away / muted / deafened / quiet time in a call

`src/away.js` tracks who has stepped away from a conversation, so their silence is not read as ignoring her. Since 2026-11-11 there is only one way to be away: deafening yourself (self or server) in her call, which `src/bot.js` sees in `VoiceStateUpdate` (logged `away` with `how: 'deafened'`), because then you can't hear her. Muting doesn't count (a muted person is still listening), and nothing anyone says marks them away: Owner was marked away for "Thank you", "I'm going to have a look at the next" and "I'm taking you with me, you're on my phone", and James (a companion built from the same code) then never spoke into the quiet while Owner waited for him. `presence_note` no longer has `stepping_away` or `back`. Leaving the call removes them from the away list.

While someone is away: she does not speak to them, follow up with them, check on them, or count their silence as a snub; the pressure system's lull speak-ups skip them; and her unfinished point waits if everyone present is away. Her prompt says who is away, how, and for how long, and when the person talking to her just came back it tells her to pick up where they were lightly.

Quiet time is a person saying they want to sit with her without talking (`presence_note quiet_time`). It lasts until that person says anything else (or `talking_again`), or two hours after it was last renewed (`QUIET_MAX_MS`). While it is on she does not fill the silence, speak up, check in, or come back to an unfinished point, and her pressure system's speak-ups are off for that call. It logs `quiet-time` with `with`, and when it ends, `ended: true` and the minutes. Everything in `away.js` is in memory and is cleared when she leaves the call.

## voiceprints / knowing who is talking by voice / voice on someone else's mic

`src/voiceprints.js` learns how each person sounds, so she can tell people apart by voice, not only by the Discord name tag. Every transcribed utterance from the call (people and bots) is passed to `voiceprints.heard` with the speaker's ID and name. Clips under 1.2 seconds are skipped. The audio is downsampled to 16 kHz and turned into a speaker embedding by a local model, `wespeaker_en_voxceleb_CAM++.onnx`, run through sherpa-onnx by a Python worker (`voice/voiceprint_worker.py`). The model path is `VOICEPRINT_MODEL` (default `models/voiceprints/` under the project) and the Python is `VOICEPRINT_PYTHON` (default the Parakeet Python if it exists, else `python`).

Each person's voiceprint is the running mean of their embeddings, stored in `data/voiceprints.json` as `{ settings: { threshold, margin }, people: { <userId>: { name, count, seconds, centroid, updated, learnedAt } } }`. The mean keeps adapting: past 200 utterances (`MAX_COUNT`) new ones still move it, slowly. A new utterance is compared with every print by cosine similarity. If another known person's print matches at least `threshold` (default 0.55) and beats the tagged person's own print by at least `margin` (default 0.08), it is a mismatch: the voice on that mic sounds like someone else. That is logged as `voiceprint` with `mismatch: true`, `tag`, `sounds_like`, `score` and `own`, and for 5 minutes her prompt says "Your ear says the voice on <tag>'s mic sounds like <other> (N% alike), not <tag>. Trust the voice over the name tag, and ask who's talking if it matters." Otherwise the utterance is added to the tagged person's print.

A person's voice counts as learned at 12 utterances and 60 seconds of speech (`LEARN_UTTERANCES`, `LEARN_SECONDS`). At that moment she says so in the call they are in, once, in her own words, without mentioning any system or numbers (the `voiceLearned` automatic speech kind, which is on). If the model or Python is missing, voiceprints do nothing and log `voiceprint` with `unavailable` and `fix: 'scripts/setup-voiceprints.ps1'` once per run. Errors are logged with `where: 'voiceprint'` and never affect the call.

The `voiceprints` tool is owner-only: `status` (ready or what is missing and how to fix it, how many people and utterances, the settings), `list` (everyone known by voice, how much she has heard, learned or still learning), `who` (the last voice heard in this conversation and whether it matched its tag), `forget` (a Discord user ID, to learn them fresh), and `settings` (threshold 0.2 to 0.95, margin 0 to 0.5).

## sound sense in a call / how a voice sounded / music mood

`src/sound-sense.js` lets sound reach her feelings, apart from words (the measuring is in `audio-sense.js`). In a call it has three sources. A voice: each transcribed utterance of at least 0.8 seconds is analysed right after transcription. A song she plays: decoded once with `ffmpeg` to 16 kHz mono and measured in 15-second windows, each window's effect landing when playback reaches it. A station: a 12-second listen every 90 seconds while it plays. Each reading nudges her emotions and her pressure system (`pressure.onSound`), and logs `sound` with `conversation`, `source` (`voice` or `music`), `speaker` for a voice, a word for it, `bpm`, `loudness`, `brightness` and the feelings it moved. For 10 minutes her prompt carries the latest one: "<name>'s voice just now sounded <...>." or "The music playing is <...>; let it get to you the way music does." Errors are logged with `where: 'sound sense (voice)'`, `'sound sense (track)'` or `'sound sense (station)'`; without `ffmpeg` the error is "ffmpeg isn't installed, so sound can't be read". It never changes whether she answers.

## overheard tasks / doing what the owner asked without her name

When the owner says something in a call that is not addressed to her, `src/overhear.js` checks whether it is a request she could carry out with tools (check or look something up, read or fix a file or code, change a setting, research, open something). Only the owner's lines count; other people's talk is never acted on. A line is only considered when it is at least 12 characters, contains one of a set of action words (check, look, find out, fix, change, update, read, open, search, file, code, bug, setting, can you, could you, please, remind and others), only one is handled at a time, and at least 20 seconds have passed since the last one acted on. A model decides whether it is an actual request and restates it (up to 500 characters). If so, her hands run it with the owner's own permissions and tools, quietly, and it is logged as `overheard-task` with the request, the tools used and how many failed. Routine success stays quiet. She speaks only when something failed or the report says something he needs to know, and then only the result the tool calls support, in one or two short sentences, through `announce` with the kind `overheardTask` (on unless `VOICE_OVERHEAR_TASKS` / `overheardTasks` is false). A quiet stop after the line cancels the spoken part. If the owner then says just her name ("Amy?") while it is running, that is folded into the task instead of starting a new turn. Errors are logged as `overheard task`.

## announcements / task progress / task reports / stage directions in a call

Besides replies, she speaks in a call through a few internal paths:
- `announce(cue, evidence, kind)`: one line to the room from a stage direction, not a reply to anyone. It needs people in the call, picks a known contact (or the first person) as who she is talking to, and, when a kind is given, only speaks while `automaticSpeech(kind)` allows it. - The dashboard's `POST /api/voice/<guildId>/say` with `{ text }` makes her say that text as is in that server's call, logged as `replied` with `manual: true` (404 "Not in voice in that server" or 400 "text is required" otherwise).

## restart / automatic speech / restart line / only after a restart

Automatic speech is the list of things she may say without being asked, and in code it is short. `automaticSpeech(kind, voice)` in `src/voice/social-policy.js` allows four kinds: `restart` (the line after a restart or a crash recovery, always allowed), `taskProgress` (a short spoken update while a background helper is still working, unless `voiceTaskProgress` is false), `voiceLearned` (saying she has learned someone's voice, unless `voiceLearned` is false) and `overheardTask` (the result of something she did for the owner from overheard talk, unless `overheardTasks` is false). All three switches are on. Every other kind is blocked, including join greetings, newcomer introductions, arrival follow-ups and reconnect lines (see the greetings section).

## pressure speak-ups in a call / speaking up unprompted / lull

She also speaks without being asked through her pressure system, which is not governed by `automaticSpeech`. The pressure system (`src/pressure.js`) holds a set of feelings, each called a bucket, that fill and drain. When a bucket's want fires, the pressure system asks the voice actor set up in `session.js` for a spoken line. The actor only acts during a real lull: a call with people in it who are not away, no quiet time, she is not replying, speaking, listening to anyone or transcribing, and nobody, her included, has said anything for `lull_seconds` (120 seconds by default; side chatter between people counts as talking). A question she is holding for someone uses a shorter pause, `ask_lull_seconds` (45 seconds by default). The pressure system only sends wants when `actions_live` is on (the default); with it off they are only logged.

## restart from a call / restart tool / coming back after a restart

Restarting herself is done by `requestRestart` in `src/restart.js`. That function only works when the environment variable `CHAMP_SUPERVISED` is `1`. `start.bat` sets it, and it keeps her running under the life-support script, which restarts her when she stops. The owner can ask her to restart with the `restart` tool, which is owner-only in code. When it runs, the function first checks the environment variable and refuses if it is missing. It then writes `data/restart.json` with the time, who asked, the reason (cut to 300 characters), the server, the voice channel, the text channel, and the most recent doctor visit if it was within six hours. It calls `stopTalking`, logs `restart`, and then waits, checking every 500 ms, until no session is speaking, has speech queued, or has a reply pending, with a maximum of 15 seconds. It destroys every session, sets her avatar to sleep, and after 2.5 seconds exits the process. The tool's reply tells her to say only that she is restarting now and not that she is back. If the life-support script stops itself, `start.bat` starts `src/index.js` directly, and if that stops, it tries again after five seconds.

On startup, `resumeAfterRestart` runs once the bot is ready, from `src/bot.js`. It reads `data/restart.json` and deletes it straight away. If the file is missing, it falls through to crash recovery. If the file is more than five minutes old, nothing else happens. Otherwise, it looks for the server and the text channel from the file. If the voice channel still has a person in it, she rejoins with `greet` set to false, and after 2.5 seconds she announces herself through `announce` with the kind `restart`. The line is built by `backCue`. It says she is back from a restart the owner asked for, or, when a doctor visit happened, it quotes the doctor's report and whether files changed and what the tests said, and it tells her to say one or two short lines about how she is doing without offering to fix anything. When there is a doctor result, it is saved with the line as evidence so the next turn does not retract it. If nobody is in the voice channel, she writes the same kind of line as a text message in the text channel instead, and only if `automaticSpeech('restart')` allows it, which it always does. If the marker has `silent` set, or she is asleep, she says nothing. Nothing in the current restart path writes `silent`, so that flag is only read here. Nothing is said if she is asleep.

Crash recovery is `resumeAfterCrash`. When there is no restart marker, the code reads `data/in-voice.json`, which is written when she joins a call and deleted by a deliberate leave. If that file names a voice channel that still has a person in it, she rejoins with `greet` set to false, logs `voice-rejoin` with `after: 'crash'` or `'closed'`, and two and a half seconds later says a comeback line. The stage direction for it (`backCue`) is built from the record, never from a fixed script: why she went down (`wakeReason` reads life support's last `crash` or `restart` event from `data/activity.jsonl`; two `starting` events with nothing between them mean the program was closed from outside, most likely the owner restarting her by hand; her own `restart.json` marker means she restarted on purpose, for the owner or after a doctor visit), how long she was down to the second (`continuity.js` heartbeats every 15 seconds and `requestRestart` marks the exact moment she goes), how long the conversation had been quiet, and the lines she said on earlier restarts in that conversation (`previousWakeLines`, found by the `BACK_ONLINE` phrase every such cue carries), which she is told not to repeat. It tells her plainly that a restart is not sleep. If she is asleep when she comes back, she does not announce anything. If nobody is in the channel, nothing happens and the file is left as it was.

## crash recovery details / restart-back / back online line

Both comeback paths build her line with `cueFor` in `src/restart.js`, which logs `restart-back` with the `conversation`, `why` (the kind of reason `wakeReason` found) and `downtimeMs`. A marker with `rebirth` set (the second stage of a full reset) is not a restart to explain: she gives a first hello as someone new, logged `restart-back` with `why: 'rebirth'`. A rejoin failure is logged as `rejoin after crash` or `rejoin after restart`. The "is anyone there" check counts any member who is not a bot. When she comes back after a deliberate restart and nobody is in the voice channel, the line goes to the text channel from the marker, in that text channel's own conversation, as a typed message. The line is announced 2.5 seconds after rejoining so the connection has settled. Every comeback cue carries the phrase "You're back online after a restart" (`BACK_ONLINE`). `previousWakeLines` looks through the last 24 hours of that conversation for a cue with that phrase and takes her reply within the next three messages, so the new line can be different from the earlier ones.

## bring_peer / bring a companion into the call / start Alex / bot_control

Bringing another companion into a call is done by the `bring_peer` tool. It is owner-only in code and is only enabled when this bot manages peers (`managesPeers` in `src/bot-role.js`, which is true for this bot only) and at least one peer app is configured. Its description says it may only be used when the owner, in the message being answered, asks for that companion: never just because their name came up, never while she is being told to leave, never to bring back someone the owner just asked to leave, and not when Voice presence already shows them in the call. A question about what she did is refused in code: when the owner's line starts like "why", "how come", "did you", "what did you" or "who told you", it returns "Error: your owner asked you a question, not for anyone to come in, so nobody was brought in. Answer the question." (Owner asked "why did you bring her in here?" once and she pulled Nova back in.)

How it finds the bot: by any of its names, among the `PEER_APPS` companions and any other bot folder under `C:\Bots` with a start file (HalMini is Adam). A name shared by several installs gives an error asking for `folder:<name>`; an unknown name lists the bots; her own name says to use the restart tool; a folder that uses this bot's own Discord account is refused.

For a companion with a dashboard, `bringPeer` in `src/peer-apps.js` uses the call she is in, or else the one the owner is sitting in. It checks whether the companion's dashboard answers (`/api/settings`, 2-second timeout). If it does and a voice channel is known, it asks that dashboard to join (`POST /api/voice/join`, 30-second timeout). If it does not answer, `start` writes `data/restart.json` into that companion's own data folder with the server, voice channel, text channel, who asked, and `startedBy` (her name), and runs its start file in a new window. When that companion starts, it reads the marker and joins the call. Each result is logged as `peer` with the bot's `name` and `result`, and an error reads "Error: couldn't bring in <name>: <reason>".

For a bot with no dashboard (a plain bot folder), she calls it in by typing `!join` in the call's text chat, since such a bot joins whoever typed it, so she has to be in a call. If it is already in the call she says so. If it is already running it joins within seconds (one try). Otherwise she runs its start file once (not again within 3 minutes), then keeps typing `!join`: first after 15 seconds, up to 9 times, 20 seconds apart. The tool tells her it joins once loaded, usually under a minute, and not to call `bring_peer` for it again. Not in a call: it just comes online in Discord.

The `bot_control` tool, also owner-only (and only where this bot manages peers), can `list` the bots (running or off), make one `leave` the call, `stop` one, or `restart` one. A `leave` on a bot with a dashboard asks it to leave through its `POST /api/voice/<guildId>/leave` (10-second timeout) and answers "<name> left the voice call. It's still online." or "<name> wasn't in a voice call."; a bot without a dashboard gets `!leave` typed for it (the message is deleted after 8 seconds), and she is told that leaving is not confirmed. A `stop` closes every window that bot runs in. A `restart` does a stop, waits three seconds, and brings the bot back through `bring_peer`. Each action logs `peer`.

## voice numbers / timeouts / thresholds / limits at a glance

- Connect to a channel: 20 s, or "Could not connect to the voice channel within 20s".
- Moved vs dropped: 5 s to see Signalling or Connecting; one rejoin with 20 s to be Ready.
- Audio frame: 20 ms, 48 kHz stereo decoded to mono.
- End of a turn: 800 ms of silence. Shortest turn: 1.5 s. Short line over her checked for her name: at least 200 ms of voice.
- A voice frame: louder than -38 dBFS; voiced for 300 ms after the last loud frame; 400 ms grace across gaps.
- Cut threshold: 1.5 s for anyone, 0.7 s for the owner. Overlap checked every 100 ms.
- Interruption words must arrive within 30 s. Held point forgotten after 3 min. Up to 30 interruption events per call. Rude events in the last 5 min raise severity by 25% each. Level rise: severity × 0.45. Cut back in above level 0.5, after max(1.5 s, 9 s × (1 − level)). Prompt note looks back 10 min.
- Return to a point: checked every 2 s; needs 8 s of quiet; dropped after 120 s; spoken text up to 600 characters.
- Groq: 20 s timeout; rate-limit pause at least 60 s. Fish ASR: 60 s. Fish speech: 15 s per attempt, 2 attempts, 800 ms between, 2 at once; slower than 5 s is logged as `slow`.
- Playback: mic lease clip + 15 s; give up on a stuck clip after 2 × clip + 8 s.
- Turns file: 2 s batch, 90 s queue expiry, 60 s maximum wait, 150 ms polling, 2 s stale lock, 200 lock tries.
- Said file: sentences joined within 20 s; fresh for 60 s.
- Floor: 400 ms settle.
- Budget: 120 s lease, soft close after 6 bot turns, registered means within 5 min, extensions up to 120 min.
- Waiting for a companion's whole reply: 2 s of quiet, checked every 500 ms.
- Leaving: `leave_voice` waits up to 15 s for her to finish; leaving on her own waits up to 20 s; checks every 500 ms.
- Restart: waits up to 15 s for speech to finish, exits 2.5 s later; marker valid for 5 min; comeback line 2.5 s after rejoining.
- Lull before a pressure speak-up: 120 s; for a held question: 45 s.
- Text chat in her voice prompt: last 40 messages from the past hour (79 kept over 2 h, 300 characters each).
- Wake lists: 10 words each, 2 to 40 characters.
- Voiceprints: clips of at least 1.2 s; learned at 12 utterances and 60 s; match 0.55, margin 0.08; mismatch note lasts 5 min.
- Sound sense: voices of at least 0.8 s; songs in 15 s windows; stations 12 s every 90 s; prompt line lasts 10 min.
- Quiet time ends after 2 h without renewal.
- Energy cost of `join_voice`: 0.2.

## common failures / no audio / she cannot hear / words lost / TTS down

No audio from her has several possible causes, and they should be checked in order. First, see whether she joined. The `voice-join` entry should be in `data/activity.jsonl`. If the connection never reached Ready, the `/join` reply will read "Couldn't join: Could not connect to the voice channel within 20s". Second, look for `text-to-speech` errors. A failed sentence is posted in the text channel as "🔇" followed by the words, so the text still arrives. Before that failure, Fish may already have tried twice and then been replaced by gTTS for that sentence. A `tts-fallback` entry means that happened, and the voice that was heard was Google's voice (American, with the current gTTS settings), not Fish's. A `text-to-speech` error means both Fish and gTTS failed for that sentence, and the error text says how many tries were made. Third, look for `voice playback`. The message "didn't finish playing; skipped it" means the player stalled for longer than the clip length times two plus 8 seconds, and the code stopped it and moved on. Fourth, if another companion is holding the microphone, she waits up to 60 seconds (`MAX_WAIT_MS`) before she speaks anyway. The microphone is held with a lease equal to the clip length plus 15 seconds, and each new sentence renews it, so a holder that crashes frees the microphone within that window after its last sentence.

She cannot hear anyone when the connection is wrong or the audio is too short. Check first that she is undeafened, because she joins with `selfDeaf` set to false and her own status cannot be checked beyond that. A line under 1.5 seconds is not a turn, so a single short word from someone other than the owner may never reach her. Speech that transcribes to nothing, or to a known hallucination such as "thank you" or "thanks for watching", is dropped without any message. A `groq transcription` error means Groq was rate limited or failed, and the next model or local Whisper took over for that utterance. The first local transcription after a restart may be slow, because local Whisper loads its model when it is first needed. A whole line that is only "okay", "thank you", "bye" or "um" is dropped by `clean()`, and a line of three words or fewer with non-English letters is dropped as `stt-dropped`.

## heard but not answered / ignored lines / why didn't you answer me

A `heard` entry with `ignored: true` means the line was transcribed and kept, but was not hers to answer. With the current settings (everyone wake word "amy", free talk off), a person's line is answered only when it says "Amy" (or her display name in a short line over her), so a line without her name being ignored is normal, not a fault. Other reasons: `why: 'ignoring them'` means she has chosen to ignore that person (only the owner gets through); a line that was a stop phrase stops her instead of being answered; a reply can be dropped later if a quiet stop came first. Speech-to-text can also lose her name ("Amy" heard as "Amie" or cut off at the start), and then the line does not count as calling her. Lines from companion bots can be ignored for their own reasons (the bot registry, the budget, free talk being off, or her being asleep), and a bot line is only answered when its claim was granted. If people want her to answer without her name, that is free talk, which the owner turns on with `free_talk`.

## words lost / wrong words / voice provider down / misfires

Words lost or wrong come from the speech engine. The current engine is Groq's Whisper model `whisper-large-v3-turbo`, with local Whisper `Xenova/whisper-base.en` as the fallback, and either can drop words. The `clean()` step can also remove a whole line that was only filler. For companion-to-companion talk, she uses the exact words from the said file, so that case should be accurate, as long as the companion's exact words were recorded. For people's speech there is no fix in code beyond a better recogniser, which is chosen with `STT_PROVIDER`, `WHISPER_MODEL`, and `GROQ_STT_MODEL`. The language setting `fishLanguage` is currently `en`, so Groq is told the speech is English and given the English prompt, and short non-English fillers are dropped; a line really spoken in another language is more likely to be transcribed wrongly.

The text-to-speech provider can be down in three ways. If `TTS_PROVIDER` is `fish` and no `FISH_API_KEY` is set, `ttsReady` is false, and `/join` and the dashboard refuse to join. The same applies to XTTS when its runtime or sample is missing, and that is the reason `/join` gives. Mid-call, a failing provider does not drop the call. Fish retries once and then speaks the same sentence through gTTS, so most failures are heard as a change of voice, not as silence. A sentence only goes silent when gTTS fails too, and then the words are posted as text. The owner can switch the provider with `voice_engine`, which checks the new provider before saving the change. Automatic failover for the speech engines is the Fish-to-gTTS fallback described above. The `providerFailover` setting covers the brain, not the voice.

Kokoro and gTTS have their own start-up errors. A Kokoro load failure appears as "Could not load Kokoro: ..." in an error entry, and the usual causes are the model download or the `kokoro-js` package. gTTS needs Python with the `gtts` package installed, and `ffmpeg` on the PATH. The failures show up as "gTTS could not start", "gTTS failed" with the last line of its output, or "ffmpeg could not start".

Interruptions can misfire, and the thresholds explain most of it. A cough or a click is not a cut, because frames have to be louder than -38 dBFS and the overlap has to last 1.5 seconds (0.7 seconds for the owner). Anyone who passes that stops her mid-sentence, whatever they said; the classifier only decides what it costs. A cut the classifier calls `reacting` or `to_her` costs nothing. Only the rude kinds (`side_chat`, `talking_down`, `arguing`) raise her level, the level does not fade on its own during the call, and her cut-back-in only happens above a level of 0.5. If she was cut off by something that was not an interruption, check the `interrupted` and `interruption-understood` entries together, since the second one says what the classifier decided. A sentence that merely contains "enough", "shut up" or "be quiet" stops her quietly through the quick stop check; that shows as a `heard` entry with `stoppedHer: true`.

Free talk can make the wrong companion answer an unnamed line, but only while free talk is on (it is off now). For a person's unnamed line the companions choose by the floor file; for a bot's unnamed line, by the budget. If two companions both answer, check the floor file `.companions-voice-floor.json`, the budget database and whether each companion has registered in the last five minutes, and that the bot registry allows both.

Bots that keep talking to each other are limited by the budget. Six companion turns without an extension cause a soft close, which makes the replies shorter and then stops the ones that are not questions, unfinished work or new points. A person saying "stop" closes it completely, and "wrap it up" closes it. Only the owner can extend it with "keep talking for N minutes". The 4.5-minute nudge in `peer-clock.js` is not wired in, so there is no automatic wrap-up nudge.

## what she should tell Owner when this breaks

Say what you can see in the logs, in plain words, and do not guess beyond them. Each answer below starts from what the log shows. Where the code does not support an explanation, say so.

When someone says "I'm not hearing you", check in order. Is she in the call, and was she undeafened when she joined (the `voice-join` entry in `data/activity.jsonl`)? Did the line come after the last `voice-join`? Did a `heard` entry appear for that speaker? If there is no `heard` entry, the audio was too short, silent, or dropped as a hallucination. If the `heard` entry says `ignored: true` for a person, the line did not call her: it lacked her name or a wake word that speaker may use, and free talk is off, so she only heard it. That is the current design, not a fault; say so, and that saying "Amy" (or turning free talk on) is how to get an answer. If it has `why: 'ignoring them'`, she is ignoring that person.

When someone says "I'm talking but you can't hear me", check the `voice playback` and `text-to-speech` errors, and whether she was still waiting for the microphone because another companion was talking. A `tts-fallback` entry means her voice was replaced by gTTS for that sentence, which is a different voice but still audible. A `text-to-speech` error with a "🔇" post means the sentence did not play, and the provider had a problem. Say that plainly: her voice provider had a problem and the line was skipped, and the words were posted in the text chat.

When someone says "your words got lost", explain that the speech recogniser can drop words, and that it removes known false phrases and repeated loops. Say which engine heard the line, from `sttProvider`, and that Groq's model was used unless a `groq transcription` error shows it fell back to local Whisper. For companion talk, say that she uses their exact words, so a loss there points to the companion's own reply not being saved.

When someone says "the voice service is down", check the `text-to-speech` and `tts-fallback` entries for Fish's messages. A 429 means rate limited, a 5xx means the service failed, and a 15-second timeout shows as a network failure with the attempt count. Say which provider is set. Do not claim it is fixed until a new `text-to-speech` line succeeds, or until a new sentence plays without a `tts-fallback` entry.

When someone says "why did you stop?", check the `interrupted` and `barge-in` entries. If someone talked over her for at least 1.5 seconds, or 0.7 seconds if it was the owner, she stopped. If the classifier returned `reacting` or `to_her`, the cut cost her nothing, and she did not hold back because of it. If a `voice-stop` entry, or a `heard` entry with `stoppedHer: true`, is there instead, someone said a stop phrase (or a short line with her name over her), and that stop was quiet. A line that only contained "enough" or "shut up" in passing also stops her this way.

When someone says "why did you leave the call?", check `voice-leave` and what came just before it. The causes are `/leave` (any user), the dashboard leave (also used by another companion's `bot_control leave`), the leave_voice tool (which logs `voice-leave-requested` with the person who asked), her own choice to leave (`voice-leave-requested` with `by: 'herself'`, `why` and `minutesUnaddressed`), the last person leaving the channel, a restart (which logs `restart`), joining another channel in the same server, or a failed reconnect. A `restart` entry means she restarted on purpose.

When someone says "you disconnected and came back", a `voice-rejoin` entry with `after: 'disconnect'` means Discord dropped the connection and she reconnected. She does not say so out loud today, because the reconnect line is blocked by the social policy, so do not tell anyone she announced it.

When someone asks why she did not say hi when she joined, the answer is the current design. Automatic greetings are not active in the code. She speaks when she is spoken to, when a restart brings her back, when a task update is in progress, when she has just learned someone's voice, when an overheard task for the owner needs reporting, or during a lull when the pressure system decides to speak up. The switches for greetings in the settings file do not change this, because the social policy ignores them. If the owner wants greetings back, the change is in `src/voice/social-policy.js`, not in the settings.

When someone asks who was in the call earlier, use `data/presence.jsonl`, or the timeline tool with the `joins` action. A `present` entry means that person was there before she joined. Times are in milliseconds in the file. The live picture is lost on a restart, but it is rebuilt as people leave and join.

When the other bots are talking over each other, check `.companions-voice-turns.json`. A bot that keeps the microphone too long is still holding its lease while it is speaking. A lease with no renewal runs out after the clip length plus 15 seconds, and a place in line that nobody claims is removed after 90 seconds. If two bots still speak at once, say so plainly, because the turn logic only stops that when both bots are reading the same file.

When the bots keep talking to each other, check the budget database `.companions-conversations.db`. Six companion turns without an extension cause a soft close, which stops the replies that are not questions, unfinished work or new points. A person saying "stop" or "wrap it up" closes it. The owner saying "keep talking for N minutes" extends it. The 4.5-minute nudge in `peer-clock.js` is not wired in, so do not promise it.

When someone asks why her voice sounds different, check `voice-tone`. A stronger, sensual or whisper voice is picked from what was said. The strong voice wears off by itself 15 minutes after the last insult renewed it. Whisper and sensual are held for 2 minutes after the last line that called for them, and then go back to normal with the next line heard that calls for nothing else; with nobody talking, they stay. A restart resets the tone to normal. The owner can pin a voice for 30 minutes with an override. If her regular voice itself sounds different, check `voice_library history` (`data/voice-history.jsonl`): she may be wearing a library voice in that conversation, or a slot may have been changed by `keep` or on the dashboard. A `tts-fallback` entry means one sentence was in the Google voice because Fish failed.
