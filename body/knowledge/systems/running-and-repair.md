# Running, restarting and repair

This is how you are started, kept running, restarted, repaired, and how your PC tools behave. Everything here comes from the code in C:\Bots\new champ (Node.js, ESM). Where the code does not show something, it says "not verified". Use this file before you state any cause about how you run. Use the `self` tool with action `map` or `logs` for live facts.

## startup / boot / start order / what runs first

Your start-up has three phases: module loading (the imports), the body of src/index.js, and the Discord ready handler in src/bot.js. ES modules run their imports before their own top-level code, depth first, in the order they are written. The first import in src/index.js is src/memory-wipe.js. That module imports src/config.js, so config.js runs first. It loads `.env` through dotenv, creates the data folder (`CHAMP_DATA_DIR` if that is set, otherwise `<project>\data`), reads persona.md, parses `PEER_APPS`, builds the config object, and then applies every key saved in `data/settings.json` that is listed in the EDITABLE table in config.js. So a value saved from the dashboard overrides the same value in `.env`. config.js also refuses to load at all inside a test run (`node --test`) that has no `CHAMP_DATA_DIR`, with the error "Refusing to run tests against the live data folder", because a test once wrote fake failures into her live log and corrupted `pressure-state.json` (2026-11-09). And if a full reset is waiting (`data/wipe-memory.json` with `full: true`), config.js starts with an empty persona and no wake words, and skips the saved `botName`, `voiceWakeWords` and `voiceOwnerWakeWords`, so the first start after a full reset is already the fresh her. Only after that does the body of memory-wipe.js run `runPendingWipe()`. If the owner asked for a memory wipe, the memory files are moved aside at this point, before anything has opened your database. See "memory wipe" below for what moves and what stays.

After memory-wipe.js the remaining imports of src/index.js load in the order they are written: src/goal-work.js, src/cloud-publisher.js, src/calendar.js, src/config.js (already loaded), src/llm.js, src/events.js, src/bot.js, src/dashboard/server.js, src/voice/whisper.js, src/pressure.js, src/self-work.js, src/onboarding.js, src/intuition-tune.js, src/direction.js, src/songbook.js, src/seamstress.js, src/body.js, src/curiosity.js, src/sleep.js, src/dreams.js, src/voice/session.js, src/journal.js, src/thoughts.js, src/continuity.js, src/sleep-on-it.js and src/doctor.js. Each of those pulls in its own imports first. src/events.js trims `data/activity.jsonl` to its newest 5000 lines when it loads, and keeps the newest 300 events in memory for the live feed. src/bot.js runs `await loadCommands()` at its top level (the slash command files in src/commands: join, leave, memories and ping) and creates the bot object, but it does not log in to Discord until index.js asks it to. src/doctor.js reads `data/doctor-reports.json` when it loads, so the last doctor visit is known from the first moment.

The body of src/index.js then runs in this order (this changed: the dashboard now comes first, and the Ollama check no longer holds anything up):

1. The dashboard. `startDashboard(bot)` is called and index.js waits for its server to report `listening`. If the port is taken or the address cannot be bound, the console shows "Dashboard startup failed: <reason>" and the process exits with code 1. The code comment says why: an occupied port is a startup failure, not a second bot silently running with no dashboard. Under life support an exit code of 1 counts as a crash, and a quick one counts as a failed start (see "life support crash rules"). When the dashboard is up it logs a `ready` activity reading "Dashboard at http://<host>:<port>" (it shows `localhost` when the host is `0.0.0.0`), and it starts building her cognitive graph in the background (a failure logs an `error` with `where: 'mind view'`).
2. The Ollama check, in the background. `checkOllama()` asks Ollama for its model list and checks that both the chat model (`OLLAMA_MODEL`) and the embedding model (`OLLAMA_EMBED_MODEL`) are installed, matching the name with or without `:latest`. If one is missing, the error reads `Ollama model "<name>" not found. Run: ollama pull <name>`. It is not awaited, so start-up carries straight on. Any failure, including Ollama not answering at all, is printed as "Ollama check failed: <reason>" and logged as an activity `error` with `where: 'startup'`. A broken model is a setup problem, not a fatal one, so the dashboard stays up and can show it.
3. If a memory wipe ran, a `memory-wiped` activity is logged with `moved` (how many items moved), `backup` (the backup folder) and `failed` (the items that could not be moved, each with its error code).
4. `doctorLocked()` runs once. If `data/doctor.lock` is left over from a visit whose process is gone, it removes the lock and records that visit as interrupted (see "doctor lock").
5. An `unhandledRejection` handler is installed. Every stray promise error from then on is logged as an activity `error` with `where: 'unhandled'`, and the process keeps running.
6. `startCloudPublisher()`.
7. The pressure system is wired and started: research, goal work, solo thoughts, songwriting, the song gate and the seamstress (she may design her own outfit only when she is not already sewing and Blender is found) are handed to src/pressure.js, and `startPressure()` starts it.
8. Sleep is wired: she will not turn in while any live voice session has a human in it, the dreamer is attached, and falling asleep runs "going back over the day" (src/sleep-on-it.js), which logs a `persona` activity with `changedBy: 'sleep'` and counts of lines, shared moments, reads on people and opinions, or an `error` with `where: 'going back over the day'`. Then `sleep.start()`.
9. The body engine is created from her pressure buckets, her tiredness and whether she sleeps, and is set as the body planner. The wonderer is built and attached (a failure logs an `error` with `where: 'curiosity'`). Self-work, onboarding, the intuition tuner and the direction planner are attached. `startCalendar()` runs.
10. `startContinuity()` (see "continuity").
11. If `config.stt` is not `fish`, `loadWhisper()` loads local Whisper in the background, and a failure is logged as an `error` with `where: 'whisper'`.
12. Discord, last. See "bot power state".

## bot power state / botEnabled / switched off / DISCORD_TOKEN empty

At the end of start-up src/index.js decides whether to log in to Discord. If `DISCORD_TOKEN` is empty, an `error` activity with `where: 'startup'` says "DISCORD_TOKEN is empty in .env, so the bot stays offline", and the dashboard keeps running. Otherwise, if `config.botEnabled` is true, `bot.start()` logs in. Its failure is caught there, so it does not stop the process. If `botEnabled` is false, a `power` activity says "Bot is switched off. Turn it on from the dashboard."

The bot object in src/bot.js owns the Discord connection, so the dashboard can turn it on and off without restarting the program. Its `status` is one of `offline`, `starting`, `online` or `stopping`, with `since` (when that status began) and `error` (the last login error, cleared whenever the status is not offline). `bot.start()` does nothing if a client already exists. Otherwise it sets `starting`, creates the Discord client and logs in. Only a successful login saves `botEnabled: true` to `data/settings.json`. A failed login destroys the client, stores the error, sets `offline`, logs an `error` with `where: 'discord login'` and the message, and passes the error on.

`bot.stop()` does nothing if there is no client. Otherwise it sets `stopping`, unhooks the calendar delivery, destroys every voice session, destroys the Discord client, saves `botEnabled: false`, sets `offline`, logs a `power` activity "Bot turned off" and puts her avatar to sleep. The process, the dashboard and her background life keep running.

`botEnabled` defaults to true in config.js, but it is a saved setting. So a bot that was switched off in the dashboard stays off after every restart until someone switches it on again. That is the most common reason she starts but never comes online.

The Discord client asks for these gateway intents: Guilds, GuildMessages, MessageContent, DirectMessages, GuildVoiceStates and GuildMembers, plus the Channel partial, which is needed to receive direct messages. MessageContent and GuildMembers are privileged: the code comments say they must be switched on in the Discord Developer Portal. GuildMembers is needed for speaker names in voice.

## Discord ready handler / coming online / Online as

When Discord reports ready (the `ClientReady` handler in src/bot.js), these happen in order. Her own user ID is recorded, so that other bots are recognised as peers. The calendar is given its owner-DM context and its delivery function (which only delivers to an owner, never to the dashboard), and one calendar tick runs (a failure logs an `error` with `where: 'calendar startup'`). The status becomes `online`. A `power` activity reads "Online as <tag> in N server(s)". Her avatar wakes. Her home is mapped (src/home.js), and is mapped again whenever a channel, a member or the server changes. `resumeAfterRestart` runs, which is where she goes back to her voice channel after a restart or a crash (see "coming back after a restart"). A failure there logs an `error` with `where: 'resume after restart'`. The DM messenger for her pressure system is attached. Last, once `resumeAfterRestart` has finished, the delivery for Claude Code's "work done" notes is attached, so notes that waited go out after she is back in the call (see "work done").

The `power` "Online as" event is the reliable sign that she is back. If it is missing after a restart, she is not back.

## startup timeline / what works while she is starting / before she is online

Put together from the code, a normal start through start.bat goes like this. start.bat checks Ollama (and waits for it), installs packages if `node_modules` is missing, registers the slash commands, schedules the browser to open the dashboard 8 seconds later, and starts life support. Life support logs `starting` and launches `src/index.js` with `CHAMP_SUPERVISED=1`. Config and any waiting memory wipe run while the modules load. The dashboard binds its port and logs `ready`. The Ollama check starts in the background. Her background life (pressure, sleep, body, curiosity, calendar, continuity) starts. Whisper loads in the background. Discord login starts last. When Discord is ready, `power` "Online as ..." is logged, she goes back to her call if there was a restart marker or a crash, and waiting work notes go out. Sixty seconds after the launch, life support counts her as started.

What works at each point. Before the dashboard is listening: nothing, and a bind failure ends the start. Once it is listening but before Discord is ready: the dashboard pages, its settings and power switch, and `/api/status` (power status `starting` or `offline`). The dashboard chat (`POST /api/chat`) uses the same brain and memory without Discord. Discord replies, voice and DMs do not work yet. A Claude Code work note that arrives now is answered "she isn't connected to Discord yet" and waits in `data/work-done-pending.jsonl`. After ready: everything.

While the old process is shutting down for a restart, it takes no new turns at all (see "old process going quiet"), and there is a gap of at least 2.5 seconds plus life support's 2-second relaunch delay plus the whole start-up before she can talk again.

## Ollama at startup / Ollama not running / model missing

Ollama is checked twice. start.bat asks `http://127.0.0.1:11434/api/tags` (that address is fixed in the script), starts `ollama serve` in its own minimised window if there is no answer, and waits for it with no time limit. Then, inside her, `checkOllama()` (src/llm.js) asks Ollama at `OLLAMA_HOST` (default `http://127.0.0.1:11434`) for its installed models and checks the chat model `OLLAMA_MODEL` (default `gemma4:12b`) and the embedding model `OLLAMA_EMBED_MODEL` (default `bge-m3`). A missing model gives `Ollama model "<name>" not found. Run: ollama pull <name>`.

This check never stops her starting. It runs in the background, and any failure becomes the console line "Ollama check failed: <reason>" and an `error` activity with `where: 'startup'`. Life support includes such errors in its alert if she then fails to start. If `OLLAMA_HOST` points somewhere other than the default, start.bat still only checks and starts the local one.

Why it matters even with a cloud brain: memory extraction and embeddings always stay on local Ollama, background helpers always run on `OLLAMA_MODEL`, and her intuition and dreams use local models too. So with Ollama down she can still start and talk on a cloud brain, but remembering and recalling will fail.

The test runner points `OLLAMA_HOST` at `http://127.0.0.1:1` and blanks every paid key and the Discord token, so a test run (and so a doctor's `npm test`) never reaches the live Ollama, spends credits or posts to Discord. Tests also get a throwaway data folder.

## two copies running / port already in use / another copy of her

If a second copy of her is started while the first is running, the second cannot bind the dashboard port. Since the dashboard is bound first, it stops at once with "Dashboard startup failed: ..." and exit code 1, before it ever logs in to Discord. The code comment says this is on purpose: an occupied port is a startup failure, not a second bot silently running with no dashboard. Under life support the second copy fails three times in a row and goes into life-support mode, DMing the owner. The fix is to close the extra window, or give each installation its own `DASHBOARD_PORT`.

For other installations in the bots folder, `bring_peer` and `bot_control restart` refuse a folder whose `.env` `CLIENT_ID` is your own Discord ID ("<folder> uses this running bot's Discord account"). The code gives no further reason; what two programs on one Discord login would do is not verified. Not verified: how long a full boot takes in practice, and what discord.js does during login beyond the code shown here.

## start.bat / launcher / env values it reads

The file is C:\Bots\new champ\start.bat. You run it from the project folder, or watchdog.bat runs it for you. It is a Windows batch script, and it does these things in order. It changes into its own folder, then reads two values from `.env` with a `for /f` loop: `DASHBOARD_PORT`, which defaults to 3000 and is used only to open the browser, and `DISCORD_TOKEN`, which it only checks for being empty and never prints. If the token is empty, it prints a warning that the dashboard will run but the bot stays offline and opens `.env` in Notepad. The script does not wait for Notepad to close.

It then checks Ollama by asking `http://127.0.0.1:11434/api/tags`. This address is fixed in the script, so it ignores `OLLAMA_HOST`. If Ollama does not answer, the script starts `ollama serve` in a minimised window and polls once a second until Ollama answers. That loop has no timeout, so if Ollama never starts, start.bat waits forever at that point. Next, if the `node_modules` folder is missing, it runs `npm install`, and if that fails it pauses and exits. Then it runs `npm run deploy --silent`, which registers the slash commands with Discord. If the registration fails, the script prints a warning and starts anyway. Eight seconds after that it opens the dashboard address `http://127.0.0.1:<DASHBOARD_PORT>` in the browser, in a minimised window.

Next, the script sets `CHAMP_SUPERVISED=1` (see the supervisor section for what this allows) and starts life support with `node life-support\life-support.js`. Life support is the process that starts her, so start.bat does not start `src/index.js` itself on this path. If life support ever exits, the script prints a warning, waits 5 seconds, and runs `node src/index.js` directly, still with `CHAMP_SUPERVISED=1`. When that run exits, it waits another 5 seconds and jumps back to the life-support line, so the loop goes on until the window is closed or Ctrl+C is pressed. The direct run in this fallback path has no life support, so its failures are not counted or reported to the owner in the same way.

Details of the script. Its window title is "Champ - Discord Companion". The `.env` loop splits each line at the first equals sign and compares the key without caring about case, so quotes or spaces around a value are kept as they are. The messages it prints are "[!] DISCORD_TOKEN is empty in .env - the dashboard will run but the bot stays offline.", "[*] Starting Ollama...", "[ok] Ollama is running", "[*] Installing dependencies...", "[*] Registering slash commands...", "[!] Command registration failed, starting anyway.", "[*] Starting... (close this window or press Ctrl+C to quit completely)", "[!] Life support stopped. Starting the bot directly in 5 seconds - close the window to quit." and "[!] Bot stopped. Restarting in 5 seconds - close the window to quit." Ollama is started with `start "Ollama" /min ollama serve`, so it gets its own minimised window titled Ollama, and closing the start.bat window does not close Ollama. `npm run deploy` runs `node src/deploy-commands.js`, and `npm start` (not used by start.bat) would run `node src/index.js` with no supervisor. Turning the bot off in the dashboard keeps this window running, so it can be turned back on.

The only values start.bat reads are `DASHBOARD_PORT` (default 3000) and `DISCORD_TOKEN` (checked only). Every other value is read by config.js and the other modules, and those are listed in "env / config / settings". Slash command registration is done by src/deploy-commands.js, which needs `DISCORD_TOKEN` and `CLIENT_ID` in `.env` and exits with "Missing DISCORD_TOKEN or CLIENT_ID in .env" if either is missing. If `GUILD_ID` is set, the commands are registered to that one server and show up at once. If it is not set, they are registered globally, which can take up to an hour to appear. The command files live in src/commands (join.js, leave.js, memories.js and ping.js), and the registration reads all of them through src/loadCommands.js. A successful run prints "Registered N command(s) to guild <id>" or "Registered N command(s) globally". Each run replaces the whole command list on Discord with what is in the folder.

## supervisor / life support / CHAMP_SUPERVISED

Life support is the file C:\Bots\new champ\life-support\life-support.js. It runs as a separate process from you. It uses only Node built-in modules, reads `.env` itself, and imports nothing from `src/` or `node_modules`, so a broken `src/` cannot take the supervisor down with it. It logs to the console with a `[life support]` prefix and also writes its events to `data/activity.jsonl` with `type: 'life-support'`. The event is in the `event` field. The names it uses are `starting` (message "starting <name>"), `restart` (she exited with code 0: "<name> exited normally after Ns", with `code` and `ranMs`), `crash` (any other exit: "<name> exited with code N after Ns" or with the signal name, with `code`, `signal` and `ranMs`), `life-support` (it stopped retrying, with `reason` `startup` or `repeated`), `recovered` ("<name> is up again"), `command` (the command an owner sent), `doctor` (with a `status` of `started`, `done`, `failed` or `undone`, the `task`, and for done or failed `changed`, `tests` and the first 500 characters of the `report`) and `error` (for example "Couldn't DM owner <id>: ..." or "Checking the owner's messages failed: ...").

When it runs, it spawns `process.execPath src/index.js` with the project root as its working directory. The child's environment is life support's own environment plus `CHAMP_SUPERVISED=1`. The child's stdout goes straight to the console, and its stderr is both printed and kept as a rolling tail of the last 4000 characters. After each exit it decides what to do with the exit code and how long the run lasted. An exit with code 0 is a deliberate restart, which is what the restart tool and the memory wipe produce. Life support relaunches after `restartMs`, which is 2000 milliseconds, and its count of failed starts is reset to zero. If the child cannot even be spawned, the spawn error is added to the tail and it counts as an exit with code -1.

Your restart code reads these events back. After a start, src/restart.js looks at the last 400 lines of `data/activity.jsonl`, finds the `life-support` events between the previous `starting` and the latest one, and takes the last `crash` or `restart` among them as the reason she went down. If there is a `starting` with no exit before it, the whole program (life support included) was closed from outside and started again. That is how she can say truthfully whether she crashed, exited, or was closed by hand (see "coming back after a restart").

Life support also guards itself. Its own uncaught errors and unhandled promise errors are logged as `error` events beginning "life support:" and it keeps watching. When its process exits for any reason it stops the child.

`CHAMP_SUPERVISED` is the flag that tells you someone will bring you back after you exit. Life support sets it to `1` for its child, and start.bat sets it to `1` before it starts life support or the fallback run. src/restart.js `canRestart()` returns true only when `process.env.CHAMP_SUPERVISED === '1'`. So if you are started by hand with `node src/index.js` (or `npm start`), the restart tool refuses with the error "I can't restart myself here: I wasn't started by start.bat, so nothing would bring me back. Restart me by hand." Everything else that ends in a restart refuses too: the dashboard's memory wipe and full reset (a 400 status, "She wasn't started by start.bat, so nothing would bring her back after the wipe" or "after the reset", "Start her with start.bat first."), and the rebirth tool's confirm ("I can't go through with it: I wasn't started by start.bat ... Nothing was wiped; the letter is still waiting."). `src/peer-apps.js` `cleanEnv()` removes `CHAMP_SUPERVISED`, along with every key that appears in your own `.env`, before it starts another bot, so a companion you start does not inherit this flag and does not think it has a supervisor when it may not.

## life support crash rules / failed starts / crash loop / backoff

Any exit that is not code 0 is a crash. A run that lasted less than `startupMs`, which is 60000 milliseconds, counts as a failed start, and failed starts are counted in a row. A run that lasted at least 60 seconds resets the failed-start count to zero, but it still counts as a crash. Crashes of any kind are kept in a rolling window of `crashWindowMs`, which is 10 minutes. When the failed starts in a row reach `startupFailures`, which is 3, or the crashes in the window reach `crashesInWindow`, which is 5, life support stops retrying and enters life-support mode. Otherwise it waits `backoffMs` before the next attempt, which is 5000 milliseconds before the first retry after a failure and 15000 milliseconds before the second and any later one in the same streak.

Worked examples, straight from `afterExit` in life-support.js. She dies 10 seconds after starting three times in a row: the first two are retried after 5 and 15 seconds, and the third puts her on life support with reason `startup`. She runs for 5 minutes and then crashes, five times inside 10 minutes: each crash resets the failed-start count, but the fifth crash in the window puts her on life support with reason `repeated`. A deliberate restart (code 0) never counts toward either limit, but its timestamp does not clear the crash window either: crashes older than 10 minutes simply fall out of it.

A crash also stores a failure record: the time, the exit code, how long she ran, the stderr tail with secrets removed, up to three `error` events she logged herself since that start, the reason, the failed-start count and the crash count. That record is what the alert, `status` and the life-support doctor are shown.

Life support also notices when she gets back on her feet. Each launch starts a 60-second timer. If she is still running when it fires and she had been in life-support mode, life support logs `recovered` and DMs the owner that she started and stayed up for 60 seconds, so she is back, and that life support is standing by again. An exit before then cancels the timer.

## life support alerts / DMs while she is down / redaction

In life-support mode it sends the owner a message on Discord. Each owner listed in `OWNER_IDS` gets a direct message through Discord's plain HTTP API (no discord.js is used). The message gives the reason, which is either a failure to start a number of times in a row or a crash count in the window, the exit code and how long the last run lasted, any errors she logged herself while starting (the last three error events from the activity file with `time` after the failure began, each cut to 300 characters), the tail of the last error output (the last 1200 characters), and the list of commands. Every secret is removed from what is sent. Life support takes any value whose key name contains TOKEN, KEY, SECRET, PASS, AUTH or COOKIE, if it is at least 8 characters long, and also strips strings shaped like Discord tokens and keys beginning with sk-, gsk-, tvly-, pk- or xai-. Messages are split into pieces of at most 1900 characters. While she is down, life support polls each owner's direct messages every `pollMs`, which is 10 seconds, and reads only messages written by that owner after its latest alert. It does not read direct messages while she is up, because those are hers.

The alert itself begins "**<name> life support**", then the failure line, either "<name> failed to start N time(s) in a row (last: exit code X after Ns)." or "<name> crashed N times in 10 minutes (last: exit code X after Ns).", then "Errors she logged:" with up to three lines if there are any, then "Last error output:" in a code block (three backticks inside it are turned into quotes, and an empty tail shows "(nothing)"), then "I've stopped retrying so she doesn't crash-loop. Reply here:" and the command list.

How the Discord side works. Life support talks to Discord API version 10 over plain HTTPS with the bot token, with a user agent of "DiscordBot (life-support, 1.0)". It opens a DM channel with each owner and remembers it. Every request times out after 15 seconds. If Discord answers 429 (rate limited), it waits the `retry_after` it was given (2 seconds if none, and never more than 30) and tries again, up to 3 tries in all, after which the error is "Discord kept rate limiting". Any other non-OK answer is an error such as "Discord POST /channels/... failed (403)". Messages are sent with mentions switched off. When an alert is sent, the bookmark for reading commands is moved to that alert, so only the owner's messages written after the newest alert count. Each poll reads up to 20 messages after the bookmark, oldest first, and keeps only those written by that owner, not by a bot, and with some text. A failed send or read is logged as an `error` and life support keeps going.

## life support commands / retry / doctor while down / undo while down

The commands an owner can send while she is down are these. A command is the first word of the message, with or without a leading slash, in any case, and whatever follows (after spaces, colons, commas or dashes) is its argument. `retry` (also `start`, `boot` or `restart`) makes one more launch. Because the failure count is set just below the limit, a single failure puts her straight back into life-support mode. `doctor <what to fix>` (also `fix`) starts a doctor visit in the background. With no text after it, the task is to find out why she fails to start and fix it. This doctor runs Claude Code only. It has no OpenCode fallback, which exists only in src/doctor.js. It makes a `Before doctor:` snapshot commit, writes the lock file, runs Claude Code with the same unattended settings as src/doctor.js, and kills the run after 20 minutes. Unlike the main doctor it does not loop over failing tests. It runs `npm test` once after any change and reports the result. If the visit changed files, the tests passed and the run succeeded, life support starts her again on its own. Otherwise it tells the owner not to expect her to start, and to send `retry` to try anyway, `undo` to roll the change back, or `doctor` with more detail. A doctor visit can only start if no other visit is running. Life support refuses a new one while `data/doctor.lock` exists and is younger than 21 minutes (the doctor time plus one minute). `undo` (also `rollback`) runs the same rollback as the doctor tool, which resets to the newest `Before doctor:` commit among the last 50 commits, and it refuses while a visit is running. `cancel` (also `stop`) kills the running doctor, and changes made before the kill are kept until someone undoes them. `status` says whether she is starting, whether the doctor is working and on what, and what the last failure was. `help`, and any text that is not a known command, returns the command list.

The exact replies. `retry` while the doctor works: "The doctor is still working. Wait for its report, or send cancel first." Otherwise "Starting <name> again..." `cancel` with no doctor: "The doctor is not working on anything." With one: "Told the doctor to stop. Anything it already changed is kept until you undo it." `undo` while the doctor works: "The doctor is still working. Send cancel first." A successful undo: "Rolled back the doctor's last visit (<task>). Send retry to start her on the old code." A failed one: "Undo failed: <reason>". `doctor` while one is working: "The doctor is already working on "<title>"." A new visit: "The doctor is on it: "<title>". This can take a few minutes; I'll report back here." `status` while the doctor works: "<name> is down and the doctor is working on "<title>" (N min so far)." While she is starting: "<name> is starting." Otherwise "<name> is down and waiting for you." with the failure text. Any other text: "I'm <name>'s life support; she isn't running right now." with the command list. Every command is logged as a `command` event.

## life support doctor / doctor while she is down

The doctor that life support runs is a copy of the doctor in src/doctor.js, written into life-support.js so that a broken `src/` cannot stop it. Its rules say she FAILED TO START and is on life support, and that the owner is talking through Discord DM. The prompt holds those rules, the owner's request (or "Find out why <name> fails to start and fix it." when the owner sent `doctor` alone) and the failure text. The prompt goes in on standard input, so nothing from the crash output or the owner's message ever passes through a shell. Claude Code runs as `claude -p --output-format json --dangerously-skip-permissions --add-dir C:\Bots`.

The steps are: refuse if `data/doctor.lock` is younger than 21 minutes ("Another doctor visit is already running."), `git add -A`, a `Before doctor: <task, first 60 characters>` commit as Amy (`Amy <amy@localhost>`), write the lock with the time, log `doctor` `started`, run Claude Code with a 20-minute limit, then stage everything and look at `git diff --cached --stat HEAD`. If anything changed, it runs `npm test` once with a 5-minute limit (`pass` or `FAIL`), and commits `Doctor: <title>`. If nothing changed, the tests are `not run`. The lock is always removed at the end. The title is the task cut to 57 characters plus "..." when longer than 60.

The report reads: Doctor visit "<title>" done or failed, the doctor's report, then "Changed: <files>. Tests: <result>." or "No files were changed." If the visit succeeded, changed files and the tests passed, it adds "Tests pass, so I'm starting <name> now. I'll tell you if she stays up." and starts her with one try. Otherwise it adds "Not starting her on my own. Send retry to try anyway, undo to roll it back, or doctor <more detail> to try again." (the undo part only when files changed). Its error texts are "Claude Code isn't installed where I can find it (set CLAUDE_PATH in .env).", "The doctor stopped early (exit N)." and "Claude Code isn't signed in on this computer: open a terminal, run `claude auth login`, then send doctor again." There is no OpenCode fallback here and no test-fixing loop.

Life support also needs the doctor's Claude Code program to be findable, and it looks in the places src/doctor.js looks. There is one limitation. Life support is started with the process environment and does not pass the values read from `.env` to the doctor. So a `CLAUDE_PATH` set only in `.env` is not seen by the life-support doctor, and it falls back to `~/.local/bin/claude.exe`, then `%APPDATA%\npm\claude.cmd`, and then to `claude` on PATH. The main doctor in src/doctor.js does read `CLAUDE_PATH` from the loaded environment.

Life support sends a "back" message once she has stayed up for 60 seconds after a recovery. This happens only when she had been in life-support mode, because that is the only time the recovering flag is set. A deliberate restart that ends in a stable run does not produce this message. When an owner sends `retry` and she starts, the message reads that she started and has stayed up for 60 seconds, so she is back.

## life support limits / life support settings / no owner set / life support .env

What life support reads from `.env`. It reads the file itself (no dotenv), line by line: a line of the form `KEY=value`, optionally starting with `export`, counts. Quotes around a whole value are removed, and an unquoted value loses anything after a space and a `#` (a comment). Values already in the process environment win over the file. It uses `DISCORD_TOKEN` (to send and read DMs), `OWNER_IDS` (comma-separated, who to tell and who may command it) and `BOT_NAME` (the name in its messages, default Champ). Every `.env` key whose name contains TOKEN, KEY, SECRET, PASS, AUTH or COOKIE is collected as a secret to scrub from anything it sends.

The fixed limits are in `LIMITS` at the top of life-support.js: `startupMs` 60000, `startupFailures` 3, `crashWindowMs` 600000, `crashesInWindow` 5, `backoffMs` [5000, 15000], `restartMs` 2000, `pollMs` 10000 and `doctorMs` 1200000 (20 minutes). They are not settings the owner can change without editing the file.

If `DISCORD_TOKEN` or `OWNER_IDS` is missing from `.env`, life support cannot send messages. It then prints a warning that failures are only shown in the console and in `data/activity.jsonl`. It still supervises her, it just cannot tell anyone on Discord.

Closing the start.bat window, or pressing Ctrl+C, stops life support. Its SIGINT, SIGTERM and SIGBREAK handlers stop the child and exit.

## restart / restarting / reboot / reset yourself

Files: src/restart.js (`canRestart`, `requestRestart`, `lastExitEvent`, `wakeReason`, `backCue`, `previousWakeLines`, `resumeAfterRestart`, `resumeAfterCrash`), src/tools.js (the `restart` tool), src/busy.js (`stopTalking`, `isStopping`), src/companion.js (`respond`, which returns nothing once `isStopping()` is true), src/voice/social-policy.js (`automaticSpeech`), src/continuity.js (`markAlive`, the downtime), and src/voice/session.js (`lastVoiceChannel`, which reads `data/in-voice.json`).

Who may ask: only the owner. The tool is enabled only when the speaker is the owner, and the description tells you to call it right away when the owner asks in any words ("restart", "go ahead and restart", "reboot", or "yes, do it" after you offered), without asking them to say it again. You must never call it on your own, and never because someone else asked. The description also says a restart keeps your memory: wiping your memory or resetting you to a fresh start is the rebirth tool, not this. It takes one required parameter, `reason`, which is a few words for the record (for example "apply the doctor's fix"). The reason is cut to 300 characters. The tool does not ask for confirmation, so the owner's request is the confirmation.

When `requestRestart` runs, it does these things in order. First it checks `canRestart()`. If `CHAMP_SUPERVISED` is not `1`, it returns the error text above and nothing else happens. Second, it refuses while a doctor visit is running or still holds its lock, with "Error: A doctor visit is still running. Let it finish or cancel it before restarting." Third, it builds a marker and writes it to `data/restart.json`. The marker holds `at` (the time), `by` (the speaker's ID and name, or `{name: 'dashboard'}`), `reason`, `guildId` (the server), `voiceChannelId` (the channel of her current voice session in that server, or null), `textChannelId` (the voice session's text chat, or the channel the request came from), `doctor` and `rebirth`. The `doctor` field holds the last doctor visit only if that visit finished less than 6 hours before now, and it is null otherwise. `rebirth` is true only for the second stage of the rebirth reset. Fourth, it calls `stopTalking()`, which sets a flag that stays set for the rest of this process. From then on `respond()` in src/companion.js returns nothing for new turns, so the old process takes no new turns and cannot claim to be back. Fifth, it logs a `restart` activity event with `by`, the `reason`, and `doctor` (true when a doctor result is attached).

Then it waits for her to finish speaking. A timer checks every 500 milliseconds and keeps waiting while any voice session is speaking, has speech queued, or has pending work, but for no more than 15 seconds in total. When that wait ends, it destroys every voice session, which also removes `data/in-voice.json` for the channel she was in, calls `avatarPower(false)` so her avatar falls asleep, writes one last continuity heartbeat (`markAlive`) so the downtime she is told later is measured from this moment, waits 2.5 seconds and calls `process.exit(0)`. The tool itself returns this text to her reply: "Restarting in a moment; I will rejoin this voice channel" (the second part only if she is in a voice channel), followed by "You are not back yet: say only that you're restarting now, and don't say you're back or have restarted until you're online again." That text is there to stop her from claiming to be back before she is.

Life support sees the exit code 0 and relaunches her after 2 seconds. The restart is only allowed when `CHAMP_SUPERVISED` is `1`, which means start.bat (through life support, or its fallback loop) is in charge and will start her again. Between the exit and the moment Discord reports ready, she is down. There is no Discord, no voice and no replies in that time. So the honest thing to say is that she is restarting. The `power` activity "Online as ..." is logged when she is ready again. If that event is missing, she is not back. Not verified: the total time for a full cycle, which depends on the login and on how long the previous process takes to exit.

Restart from the dashboard: there is no dashboard button that only restarts her, and no route that stops the dashboard process. The dashboard actions that restart her are `POST /api/memory/wipe` and `POST /api/system/fresh`, described under "memory wipe" and "full reset". Restarting a different bot is a separate path, through `bot_control` with `restart`, described under "bot_control".

## coming back after a restart / back line / why did I restart / wake reason

When she is ready, `resumeAfterRestart(client)` runs from the Discord ready handler.

If the marker `data/restart.json` exists, it is read and deleted at once, even if it turns out to be too old or unreadable. If it is unreadable or more than 5 minutes old, nothing else happens. Otherwise the server and the two channels are fetched. If the marker's voice channel still has a human in it, she joins it with `greet: false` (no room greeting), and 2.5 seconds later she speaks her back line in voice. She stays quiet only when the marker is marked `silent` (nothing in the code sets that flag) or she is asleep. A failed join logs an `error` with `where: 'rejoin after restart'`. If the voice channel is empty or the join failed, the code falls through to the text channel. There, if the marker has a text channel, she writes a back line through `respond()` in the conversation `text:<channel id>`, as if spoken to by whoever asked, and posts it as a text message of at most 2000 characters, with mentions switched off. The code calls `automaticSpeech('restart', ...)`, which returns true for every restart regardless of the `VOICE_RESTART_ANNOUNCEMENTS` setting (its comment: only a companion waking after a process restart announces itself). So that setting does not switch the back line off. It is stored and shown on the dashboard, but nothing reads it here.

If the marker does not exist, she crashed or was closed from outside, and `resumeAfterCrash` runs (see "crash rejoin").

What she is told is built from what really happened. `wakeReason` picks one of these, in this order:
- `peer`: the marker has `startedBy` (another companion started her through bring_peer). "You were just started up by <companion>, because <person> asked."
- `doctor`: the marker carries a doctor result. "You were restarted after a doctor visit about "<title>". What the doctor reported: ... Files changed: ... (or No files were changed.) Tests: ..."
- `owner`: any other marker. "You were restarted because <name> asked (<reason>)."
- `crash`: no marker, and life support's last record is a crash. "Your program crashed (it exited with code N after <time>) and life support started it again. You didn't choose this and nobody asked for it."
- `exited`: no marker, but life support recorded a normal exit. "Your program exited on its own, without leaving a note why, and life support started it again."
- `closed`: no marker, and life support started again with no exit recorded. "Your program was closed from outside and started again: most likely <owner> restarting you by hand."
- `unknown`: nothing on record says why it stopped.

The stage direction (`backCue`) then adds: "You're back online after a restart", the reason, how long she was down (from continuity: under 2 minutes is "you were only down N seconds: a short pause, nothing was missed and no time was lost", otherwise "you were offline about N minutes/hours"), how long the conversation had been quiet before she went if that was more than 2 minutes, and that this was a program restart, not sleep: she was not asleep or dreaming and nothing is foggy. She is asked for one or two short lines to the room that she is back, true to what happened, without offering to fix or change anything, without greeting people one by one, and without reading out file names. Her comeback lines from earlier restarts in the same conversation in the last 24 hours (up to 4) are shown to her with the instruction to say something different. A code comment explains why: three restarts in a row once all got the same "I just woke up foggy" line. A peer start gets a shorter cue: one short, natural hello, no names, no explaining how she was started. A rebirth gets the rebirth cue instead (see "rebirth").

Each back line logs a `restart-back` activity with the conversation, `why` (the reason kind, or `rebirth`) and `downtimeMs`. When a doctor result is attached, it is passed with the line as `evidence` ("doctor <title>: ok, tests pass" and similar), so later turns treat it as real and do not take it back. The history of a restart is the `restart` and `restart-back` events, life support's own events, and that evidence line. Nothing else is written.

## doctor visit steps / snapshot / fix rounds / what the doctor is told

A visit (`callDoctor`) runs in these steps.

1. Checks. A task shorter than 15 characters (`MIN_TASK`) is refused: "Error: the doctor needs a real task (at least 15 characters): say what is wrong or what to change, in full. Nothing was dispatched." A request while a visit is running is refused with "Error: The doctor is already working on "<title>" (started at 3:34 PM, 12 minutes ago) and has not finished yet. Nothing new was dispatched: wait for it to finish, or cancel it." A missing or unknown action is refused before that with "Error: doctor needs an action (call, status, cancel, undo or model); got none. Nothing was dispatched to the doctor." (it once fell through to status and she told the owner the doctor had been sent when it had not).
2. The lock. If a live visit still holds `data/doctor.lock`, the visit is refused with "Error: Could not reserve a doctor visit. Another doctor visit holds the repair lock." Otherwise the lock is created (see "doctor lock").
3. The snapshot. `git add -A`, then `git commit -q --allow-empty -m "Before doctor: <task, first 60 characters>"`, as `Amy <amy@localhost>`. This is the undo point, and it is made even when nothing has changed. If it fails, the lock is removed and the reply is "Error: Could not snapshot the workspace for the doctor. <reason>".
4. A `doctor` activity with status `started`, the full task and the first 500 characters of the owner's own words.
5. The engine runs in the background, with a 20-minute limit for the whole visit. The tool returns at once: "Dispatched, not done: the doctor has started on "<title>" (with your owner's exact words attached). It works in the background for a few minutes and the report comes when it finishes; nothing is fixed yet. Tell your owner briefly that it has been sent, not that it is done."

What the doctor is told. The prompt quotes the owner's own words verbatim as the authority on what he wants, then gives your paraphrase of the request, marked as written by your hands model, which can get the meaning backwards, so where it disagrees with the quote the doctor must trust the quote. Without a quote it is told to check the paraphrase against the recent logs. It ends with "(Recent context is in her logs; read them first.)" The title is the task cut to 57 characters plus "..." when it is longer than 60.

After the first run, if files changed (the output of `git diff --stat HEAD` is not empty), the code runs `npm test` with a 5-minute limit. If the tests fail, the last 6000 characters of their output go back to the doctor in the same session, asking it to fix the tests and report again. This repeats up to `FIX_ROUNDS`, which is 3, and only while the visit is still within its 20 minutes. The owner is not asked during this loop. When the loop ends, the visit finishes. If anything changed, it runs `npm test` once more and records `pass` or `FAIL`, then commits the work as `Doctor: <title>`. A `doctor` event with status `done` or `failed` is logged with the changed flag, the test result, the first 500 characters of the report and the engine (`claude`, `opencode`, or `opencode:fallback`). The visit counts as done only if the engine ran, exited with 0, did not report an error itself, and the tests did not end as `FAIL`. The result is saved to `data/doctor-reports.json` before anything is said, then the lock file is removed. That saved last visit is what the restart tool attaches for up to 6 hours. During the loop, each round back to the doctor logs a `doctor` event with status `fixing tests` and the round number, and a switch to OpenCode logs status `fallback` with `from: 'claude'` and `to`.

## doctor report / any word from the doctor / doctor-reports.json / doctor status

The report reaches the owner in up to three ways, each tried on its own so one failure cannot cost the others. First, the callback the tool gave (in voice she speaks it, and the report is also added to her conversation history with the verified outcome line). Second, always, a copy by Discord DM to every ID in `OWNER_IDS` (except `dashboard`), in pieces of 1900 characters. That fails when no owner ID is set ("no owner Discord id is configured") or Discord is offline. Third, only if no DM got through, the text channel the call came from. Then a `doctor` activity with status `reported` records `delivered` (for example `notify`, `dm`, or `dm failed: Discord is offline`) and `inText` (whether a text copy landed). The DM copy exists because a spoken report can be lost to a text-to-speech timeout.

Finished visits are kept in `data/doctor-reports.json`, newest first, at most 10. Each entry has `at` (when it finished), `started`, `title`, `ok`, `report` (up to 800 characters), `changed` (the changed files, comma-separated), `tests` (`pass`, `FAIL`, `not run`, or `not verified` for an interrupted visit) and `engine` (blank for Claude Code, or " (OpenCode)" / " (OpenCode fallback)"). It is read when she starts, so a restart does not lose the last report.

`status` answers from that file. While a visit runs: "The doctor is already working on "<title>" (started at <clock time>, N minutes ago) and has not finished yet. It will report when it finishes." While only the lock is held: "A doctor visit still holds the repair lock." With no visit ever: "The doctor is not working on anything right now, and there is no report from an earlier visit on record." Otherwise: "The doctor is not working on anything right now. The last visit, "<title>", finished at <time> and went fine (or FAILED) (changed: ...; tests ...). Its report: ..." After that comes the line about Claude Code's work notes (see "work done note details"), because Owner calls Claude Code the doctor too.

The report text itself goes to the owner through the callback the tool provides. It begins with the title and whether the visit was done or failed, plus the engine label if there was a fallback. It then gives the doctor's report, followed either by the list of changed files and the test result or by "No files were changed." If the tests failed, it tells the owner to say "undo the doctor" to roll the change back. If files changed, it ends with "Restart me when you want the fix to take effect." The tool also adds the report to her conversation history, with the verified outcome line so later turns know what really happened.

The doctor tool has five actions. `call` starts a visit with `task`, which should describe the problem or change as fully as possible, including what happened, when, and any error seen. `model` lists the models on the signed-in OpenCode account when `task` is blank, or sets the OpenCode doctor's model to the id in `task` when it is given. Setting a model checks the id against the OpenCode list first, and refuses an id that is not in it. Blank clears the custom choice. The change is saved as the `doctorOpenCodeModel` setting and takes effect on the next visit. `OPENCODE_DOCTOR_MODEL` in `.env` sets the starting model. `status` says whether a visit is running, and if it is not, it describes the last visit with its title, how long ago it finished, whether it went fine, what changed, and its report. `cancel` kills the running child process. It does not roll anything back, and the reply says that whatever the doctor already changed is kept until the owner undoes it. `undo` is refused while a visit is running, with the reply "Cancel it first". Otherwise it searches the last 50 commits for the most recent one whose message starts with `Before doctor:` and runs `git reset --hard` to that commit. This discards every uncommitted change, not just the doctor's, and the reply says "Restart me to load the old code." If there is no such commit, the reply is "There is no doctor visit to undo."

## doctor engines / Claude Code / OpenCode fallback / doctor model / CLAUDE_PATH

How each engine is run. Claude Code: `claude -p <prompt> --output-format json [--resume <session>] --append-system-prompt <rules> --dangerously-skip-permissions --add-dir C:\Bots`, which prints one JSON object whose `result`, `is_error` and `session_id` are read. OpenCode has no system-prompt flag, so the rules go at the top of the prompt: `opencode run <rules + prompt> --format json --auto [--model <model>] [--session <session>]`, which prints one JSON event per line, whose text parts make the report, whose `sessionID` is kept, and where any `error` event marks the run as failed. A `.cmd` program is run through the shell. The test-fixing rounds resume the same session, so the doctor keeps its context.

`model` with no task lists the OpenCode models (`opencode models`, 60-second limit), sorted, up to 60 in the reply and 40 in the spoken note, with the current one. A model id that is not in that list is refused: "That model isn't in OpenCode's list. Run "opencode models" to see what's available". Setting one replies "The OpenCode doctor will use <id>. It takes effect on the next doctor visit." Clearing it replies "The OpenCode doctor is back on its default model (cleared the custom choice)." If OpenCode is not found, the list call answers "OpenCode isn't installed: no opencode-cli binary was found." The dashboard reads the same list and the current OpenCode path and model through `GET /api/doctors/models`.

Claude Code's program is found through `CLAUDE_PATH`, then `~/.local/bin/claude.exe`, then `%APPDATA%\npm\claude.cmd`, and then `claude` on PATH. OpenCode's program is found through the `OPENCODE_PATH` value (or the dashboard setting `doctorOpenCodePath`), then the OpenCode desktop app's bundled CLI, then any versioned CLI under `%APPDATA%\ai.opencode.desktop\cli`, then `~/.local/bin/opencode.exe`, and finally `%APPDATA%\npm\opencode.cmd`. If nothing is found, the OpenCode fallback is not available.

The doctor cannot restart her. Its rules say the owner decides when. The restart happens only when the owner asks, through the restart tool. The only check on a change is the `npm test` run, so if no test covers a change, the doctor can report success with nothing really verified. Not verified beyond the code: whether a killed visit can leave its commits in a half-finished state that `undo` will handle cleanly.

## doctor lock / doctor.lock / interrupted doctor visit

`data/doctor.lock` marks a visit in progress. src/doctor.js creates it only if it does not already exist, as JSON: `pid` (her process), `task` (the title) and `started`. When the engine starts, `childPid` (the Claude Code or OpenCode process) is added. It is removed when the visit finishes.

`doctorLocked()` decides whether a lock still counts. No file means no lock. A lock with a `pid` counts while either her process or the child process is still alive. An older lock that holds only a time (the format life support still writes) counts for 21 minutes (the 20-minute visit limit plus one minute). A lock that cannot be read for another reason counts, to be safe. A lock that no longer counts is deleted, and unless it belongs to the last saved visit, it is recorded as an interrupted visit: a report with `ok: false`, the lock's task as title (or "Interrupted doctor visit"), "The repair stopped before it could report. Its file changes and tests were not verified.", changed `unverified` and tests `not verified`, and a `doctor` activity with status `interrupted`. This check runs once at every start-up, before every visit, from `status`, and from the restart tool.

So: a visit cut off by a crash or a restart is reported as interrupted the next time she starts, and its lock does not block anything afterwards. A restart is refused while a live visit holds the lock. Life support refuses its own visit while any lock file is younger than 21 minutes, judged by the file's age.

The failure texts you may see are these. From the tool, "No doctor is installed here: neither Claude Code nor OpenCode could be found." is the message when neither program exists. "The doctor stopped early (exit N)" means the engine exited with a non-zero code. A sign-in problem reads that Claude Code isn't signed in on this computer, with the advice to run `claude auth login`, and the equivalent for OpenCode is `opencode auth login`. So "No doctor is installed here" only appears if there is no engine at all, which the code never produces. ## other bots / peers / bring_peer / bot_control / PEER_BOTS / PEER_APPS

Files: src/peer-apps.js (parsing, folder bots, starting, stopping, joining), src/tools.js (the `bring_peer` and `bot_control` tools, their handlers `bringPeerTool` and `botControlTool`, plus `bringFolderBot`), src/bot-role.js (`managesPeers`, which is `true`; its comment says only NewChamp manages other bot processes, and this must not be inferred from the display name), and src/peers.js (bot-to-bot conversation rules). The old orchestrator hub files, src/orchestra.js and src/orchestrator-client.js, were deleted on 2026-11-10 and are not part of you any more.

Who may manage them: only the owner. Both tools are enabled only when the owner is speaking and `managesPeers` is true. It is true in src/bot-role.js. `bring_peer` also needs at least one entry in `PEER_APPS`. Both tool descriptions say never to use them because a name merely came up, never while being told to leave a call, and to check voice presence first. `bring_peer` should be used only when the owner, in the message being answered, asks for that companion to come in. `bot_control` should be used only when the owner asks for it in the message being answered.

There is no orchestrator hub. Owner had it removed on 2026-11-10, so `bring_peer` and `bot_control` always use the path described below.

The config values are these. `PEER_APPS` in `.env` lists the other companions as entries of the form `Name|Alias=<folder>@<dashboard port>`, separated by commas. The text before the equals sign is the list of names people use for that bot, separated by vertical bars. The first name is the bot's own name. The folder is where its start file lives, and the port after the last `@` is its dashboard port. Example from the code comment: `Alex=C:\...\Alex@3001,Howard|Gramps=C:\...\Gramps@3002`. An entry that does not match this form is ignored. `PEER_BOTS` holds names or Discord user IDs of other AI companions that share the server. It is a people-facing setting. It decides who she hears and whether she answers them, and it feeds the protection rules and the voice recognition. It is not used by `bring_peer` or `bot_control`, so it has nothing to do with starting or stopping a bot. `PEER_UNLIMITED` lists peers that she answers without the usual turns-in-a-row limit, for a bot she has long one-on-one conversations with. `PEER_MAX_EXCHANGES` is not read by any code. Its only mention is a comment and a test that confirms there is no limit. Setting it has no effect.

Other bots in the bots folder are found by `folderBots()`. Any subfolder of C:\Bots that holds a `start.bat`, or a file named `start*.bat` (the first one alphabetically), counts as a folder bot, unless it is her own folder or a folder already in `PEER_APPS`. A folder bot has no dashboard port, so it is matched by its folder name or any of its names, comparing letters and digits only, and by word order. HalMini is also known as "Adam" (`FOLDER_BOT_NAMES` in src/peer-apps.js), so "bring in Adam" and "start HalMini" both name the same bot.

When `bring_peer` runs, it first refuses if the message she is answering looks like a question. The check is a pattern that matches a message beginning with "why", "how come", "did you", "what did you" or "who told you", optionally after one word, and the reply is "Error: your owner asked you a question, not for anyone to come in, so nobody was brought in. Answer the question." (This rule exists because when Owner asked "why did you bring her in here?" she called the tool again and pulled Nova back in.) Next it looks the name up among all the other bots: the `PEER_APPS` companions first, then the folder bots (see "finding a bot by name"). If there is no match, the error is "Error: no bot called "<name>". The bots are: ..." with every name it knows. If the bot found uses the same Discord account as you (its `.env` `CLIENT_ID` is your own user ID), it refuses with "Error: <folder> uses this running bot's Discord account." For a configured companion, it first checks whether the companion is running by asking its dashboard for `/api/settings` with a 2-second timeout. If it is running and she is in a voice channel (or the owner is, since the voice channel is taken from the speaker's current channel), it asks that dashboard to join the channel. If it is running and there is no channel, the reply is that the bot is already running. If it is not running, the code writes a marker into the other bot's own `data/restart.json`, containing the server, the voice channel, the text channel, who asked and the name of the bot that started it, provided there is a server. It then starts the other bot's start file in its own window with `cmd.exe /c start`, detached, using the environment that `cleanEnv()` gives it. The reply says it started the bot in a new window and that it will join the call once it is up, which usually takes about half a minute. A companion that is started this way reads its marker on start-up and joins that call without a greeting, and then the peer cue described in "restart" makes it say one short hello.

The replies from a configured companion are "<name> is already running." (running, no call), "<name> was already running and is joining the voice call now.", "Started <name> in a new window. <name> joins this voice call once up (about half a minute) and says hello." or, with no call, "<name> comes online in Discord in about half a minute." Each logs a `peer` activity with the name and the result. A failure is "Error: couldn't bring in <name>: <reason>". The join request to the other dashboard waits up to 30 seconds, and the other bot's own error is passed on (for example "Unknown voice channel", or "<name>'s dashboard answered 503").

The marker written into the other bot's `data/restart.json` holds `at`, `reason` (empty), `doctor` (null), `guildId`, `voiceChannelId`, `textChannelId`, `by` (who asked) and `startedBy` (the name of the bot that started it). It is written only when there is a server. The window is opened with `cmd.exe /c start "<name>" /D "<folder>" "<folder>\<start file>"`, so the window's command line names the folder, which is how `stop` finds it later.

## finding a bot by name / folder bots / HalMini / Adam / !join

The list of other bots is the `PEER_APPS` companions plus every folder bot under C:\Bots. Each one's names are filled out from its install: its `PEER_APPS` names, the `BOT_NAME` in its own `.env`, and its folder name. Its Discord ID is taken from `CLIENT_ID` in its `.env`. You yourself are in the lookup too, by your name and your folder, and naming yourself is refused: "Error: use the local dashboard or restart tool to control this running bot."

A name is matched like this. A full folder path matches that folder. `folder:<name>` matches by folder name only. Anything else matches a bot when any of its names is the same once you keep only letters and digits, or has the same words in any order (so "HalMini", "hal mini" and "mini hal" all match). If more than one bot matches, nothing happens and the reply asks for the folder: "Error: "<name>" is shared. Use "folder:<one>", "folder:<other>"." This is how two copies of a bot with the same display name are told apart.

For a folder bot, `bringFolderBot` first checks whether the bot is already in the call, by looking for a bot member whose display name or username matches one of its names. If it is, the reply says so. If she is in a call, the code types `!join` in the call's text chat and waits up to 6 seconds for a new bot to appear, deleting its message afterwards. If the bot turns up, the reply is that it was already running and has joined. If not, and the bot was not started in the last 3 minutes, the code runs its start file in a new window with no marker, and then keeps typing `!join` in the background. That background loop waits 15 seconds, then tries up to 9 times, each time waiting up to 20 seconds for a new bot to appear and deleting each `!join` message after it. The bot's joining is announced as an activity event whether or not it succeeds. If she is not in a voice call, she cannot call the bot in, so the reply says the bot comes online in Discord and that the owner should join a call and ask again.

The folder bot replies are "<name> is already in the call.", "<name> was already running and just joined the call.", "Ran <name>'s <start file> in a new window. It joins this call once it's loaded (usually under a minute); you're typing !join in the chat for it until it does, so don't call bring_peer for it again.", "<name> is already starting up..." when it was started in the last 3 minutes, and, outside a call, "...You're not in a voice call, so it just comes online in Discord; to get it into a call, join one and ask again." The background loop logs a `peer` activity reading "joined the call as <display name>" or "never joined the call after starting", or an `error` with `where: 'bringing <name> into voice'`. A folder bot is started with no restart marker. The `!join` text works because HalMini's sidecar joins whoever typed it, which is why you have to be in the call yourself.

## bot_control / stop a bot / restart a bot / list bots / make a bot leave

`bot_control` is owner only and is enabled only when `managesPeers` is true. Unlike `bring_peer`, it does not need `PEER_APPS` to be set. It takes four actions. `list` gives each bot as running or off, where companions are checked by their dashboards and folder bots by whether they have any windows. `leave` makes a bot leave its voice call but stay online. For a companion, it asks that companion's dashboard to leave the call in the server she is in, and the reply says whether it left or was not in a call. For a folder bot it types `!leave` in the text chat and deletes that message after 8 seconds. `stop` turns a bot off completely through `stopBot()`. This finds every process whose command line names the bot's folder or that is listening on the bot's dashboard port, climbs each one up to its top window (only through command-prompt, node, python, pythonw and py parents that also name the bot's folder, so a terminal application is never closed), and runs `taskkill /T /F` on each top window. Its own process and its parents are never touched. Because life support runs inside the same window, it is closed as well and does not bring the bot back. The reply reports how many windows were closed. `restart` runs the stop, waits 3 seconds, clears the folder bot's recent-start record and then runs the start path of `bring_peer` again. The reply reports both halves.

The exact replies. `list` gives one line per bot, "<names>: running" or "<names>: off", or "There are no other bots in the bots folder." `leave` on a companion that is off: "<name> isn't running, so it isn't in a call."; with no server in the conversation: "Error: no server here to leave a call in."; otherwise "<name> left the voice call. It's still online." or "<name> wasn't in a voice call." `leave` on a folder bot: "Typed !leave in the chat for <name>. Whether it leaves isn't confirmed (it should within a few seconds); check the call before saying it has gone." `stop`: "<folder> is turned off." or "No running process could be verified for <folder>." If Windows refuses to close one of the windows, the error is "Error: couldn't stop <name>: Windows could not confirm every bot process stopped." `restart` also refuses a bot that shares your Discord account, and replies "Turned <folder> off, then: <what bring_peer said>". An unknown action: "Error: unknown action "<action>". Use list, leave, stop or restart." Each `leave` and `stop` logs a `peer` activity with the result, for example "turned off (2 windows)".

How `stopBot` finds the windows, in more detail. It lists every process through PowerShell (`Get-CimInstance Win32_Process`, 30-second limit). A process counts when it is cmd, node, python, pythonw or py and its command line names the bot's folder, followed by the end of the line, a slash, a quote or a space. For a companion with a dashboard port, a process listening on that port also counts, if its command line contains one of the programs the bot's start file runs (a `-m module`, or a `.js`, `.mjs` or `.py` file). Each hit is climbed up through parents of the same kinds that also name the folder, and the top one is closed with `taskkill /PID <id> /T /F`, which takes everything started from it.

You cannot stop or restart yourself with `bot_control`. Use the restart tool for that. `bot_control` can stop any bot in the bots folder, including another companion, so use it only when the owner has asked for it in the message being answered. Not verified: whether `stopBot` ever closes a window that belongs to something other than the bot, beyond what the process rules above guarantee.

## background tasks / background_task / helpers

Files: src/agents.js (the helper engine: `startTask`, `taskReport`, `listTasks`, `cancelTask`, the saved reports), src/tools.js (the `background_task` tool, the `backgroundTask` handler, and the `HELPER_TOOLS` list), and src/llm.js (`agentStep`, which runs helper steps on the local model).

A background helper is a second run of your model that works through a brief on its own with a subset of your tools, while you keep talking. Only the owner may start one, and the tool is enabled only when `OPENROUTER_API_KEY` is set. The key is used only to switch the tool on, because the helper itself always runs on the local Ollama model through `agentStep`, which has no cloud fallback.

The actions are `start` (which needs `title` and `instructions`), `status` (with no `id` it lists the tasks, and with an `id` it returns that task's whole report, and with `start` as a character position it reads from there onward), and `cancel` (which needs `id`). The `model` argument of `start` is accepted and then ignored for ordinary helpers, because the handler passes the configured local model (`OLLAMA_MODEL`) to the helper. Only the project tool's coding helpers use `OLLAMA_CODING_MODEL`, when it is set. So the tool description's wording "defaults to your current model" does not match the code. The helper always runs on `OLLAMA_MODEL`.

A helper gets only these tools: `files`, `web_search`, `read_source`, `send_file`, `system_info`, `huggingface`, `models_local` and `project_runtime`. The list in `HELPER_TOOLS` also names `send_project`, but the tool definitions the helper is shown leave it out. The run handler refuses any tool that is not in `HELPER_TOOLS` with "Error: helpers can't use <name>". The helper runs with a copy of the asking owner's permissions, marked `helper: true` and `researchOnly: true`, and each of its tools is offered only if that tool is enabled for such a helper. So the limit on what a helper can do is this fixed list, not a loss of owner rights. Tools that check `ownerContext`, such as `reverse_engineer`, are never available to a helper.

The replies: a start says "Started background task #<id> "<title>" on <model>. It works on its own and will report back here when done." (or "you can check on it by asking for its status" when there is no way to report back). Missing instructions: "Error: the helper needs instructions." The same brief again: "Background task #<id> "<title>" is already working on that brief. Don't start it again." `status` with no tasks: "No background tasks yet." An unknown id: "Error: no task #<id>." `cancel`: "Cancelling task #<id>." or "Error: no running task #<id>." The title is cut to 80 characters. Each task logs a `task` activity at the start (id, title, model) and at the end (status and steps). Failures to report progress, save the report or send the notice are logged as `error` events with `where` set to `task progress`, `task report`, `task completion` or `task notification`.

The steps work like this. The helper gets a system message telling it to work step by step, to look before changing things, to make precise edits and to read its work back. It is told that research helpers must not write a report file or send one into chat unless the brief explicitly asks for one, and that it must reply with a short report at the end. Each step is one call to the local model, which may ask for several tools. Each tool result is cut to 20,000 characters, and when it is cut the result says so and suggests reading in parts. A helper may take at most `MAX_STEPS`, which is 100 model steps (src/agents.js calls it a hard cap against a runaway loop). If it reaches that limit without finishing, its status is `stopped`, and its result says how many steps it took and lists its last five actions. If the model replies without asking for a tool, that reply is the report and the status is `done`. An error ends the task as `failed` with the error text as its result.

Progress is sent through the progress callback the tool was given, at most once a minute, or every 30 seconds when the step failed, so people are kept informed without a flood of messages. A progress line is written from the tool step itself, with no extra model call. A cancel sets a flag that is checked between steps and between tool calls. So a cancel takes effect at the next check point, not in the middle of a model call. A cancelled task is not reported as finished. Its status is `cancelled`, and it is saved with that status.

When a helper finishes, its status is `done`, `stopped`, `cancelled` or `failed`, and its report is saved to `data/tasks/` with a file name made from the start time in the form `YYYY-MM-DD-HH-MM-task-<id>.md`, for example `2026-11-08-14-05-task-<id>.md`. The file holds the title, status, steps, model, report and a list of actions. The start time is used in the name even though the file is written at the end. After the file is saved, the completion notice goes back through the notify callback, unless the task was cancelled. Task ids are based on the clock at start-up, so they are large numbers, and they keep rising after a restart.

The task list shows at most 1500 characters of each finished report. The complete report is read with `status` and `id`, in pages of 16,000 characters, with the next start position given when a report is longer than one page. After a restart a finished task is gone from memory, but its saved report is still read from disk, and the list includes the eight newest saved reports from before the restart.

Helpers share a cap of `MAX_HELPERS`, which is 4, counted across the helpers started by this tool and by other tools such as project builds and private self-dialogue. Model-download and generation jobs are not counted. Starting a fifth refuses with the message that four helpers are already running and lists them. A brief that exactly matches a running helper's brief is refused as already being worked on, so the same brief is never run twice at once. Any helper's result that says "Downloaded" is a completed download. Anything else about a download must be reported as not done. The download action of the files tool works only inside a helper. When the owner's own conversation calls it, she is told to start a background task instead, and the helper then reports the size and checksum that the download returns.

## reverse engineering / reverse_engineer / REA

Files: src/reverse.js (the jobs, the Steam lookup and REA's readiness check), and src/tools.js (the `reverse_engineer` tool). The tool is enabled only for the owner.

REA is "Reverse Engineer Anything", the tool at github.com/morluto/rea. It works out how a program, app, game, website or file behaves from the shipped thing itself, without its source. It is installed for Claude Code as an MCP server with its own skill. The investigation is a Claude Code run in the background, the same way a workshop job is. The engine is always Claude Code. Each investigation has its own folder, and its report goes back to the conversation that asked. Only one can run at a time.

Before anything starts, `reaReady()` checks that REA's entry file exists at `C:\Tools\rea\node_modules\rea-agents\scripts\rea.mjs`, and that Claude Code's configuration file `~/.claude.json` has an `mcpServers.rea` entry. If either check fails, the reply explains what is missing and says the owner needs to reinstall REA (with `npm install --prefix C:\Tools\rea rea-agents` on Node 24.22 or newer) or run REA's Claude Code setup again. This check is what stops her from claiming an investigation she cannot run.

The actions are `start` (which needs `target` and `question`), `list` (the 10 most recent investigations, with status and times), `report` (one investigation by `id`, which gives its status, target, question, report text and folder), and `cancel` (which stops the running one). The `target` may be a path to a program, an app folder or a file such as an .exe, .dll, .apk or .asar, a path inside the home folder (relative paths resolve from there), or a web address beginning with http or https. If the target is not an existing path, the code looks for an installed Steam game or app whose name matches it, reading Steam's `libraryfolders.vdf` and `appmanifest_*.acf` files under the two standard Steam folders. It compares letters and digits only and accepts a name that contains the target. One match is used. More than one match is refused, and the reply asks the owner which one. No match is refused as well. A target that is a path must exist, while a web address is checked by the run itself.

A start is refused with a clear reason if the target or question is empty, if REA is not ready, or if another investigation is still running. The message for the last case reads "Investigation #N ... is still running; one at a time." Each investigation gets the next number after the highest existing job, and its folder is `Desktop\REA investigations\<id>-<slug>`. The slug is made from the question, cut to 70 characters, lower-cased, reduced to letters and digits joined by hyphens, and cut to 40 characters. The job is saved as `data/reverse/<id>.json` with the fields `id`, `target`, `question`, `title`, `folder`, `status`, `started`, `finished`, `engine`, `report` and `saved`. The status is `running` when the job starts, and it is rewritten only when the run ends.

The run is given the rules that the investigation must only inspect. It must never modify, patch, crack or redistribute the target, never bypass licensing, DRM or anti-cheat, and never pull out passwords, keys, tokens or other people's private data. If the question asks for that, the investigation must say so and stop. It must save its notes and evidence as `report.md` in its own folder and change nothing outside it. It must finish with a plain report of three to eight sentences that you can read out loud, with how sure it is and why, and what it could not determine. The run may take up to 45 minutes (`JOB_TIMEOUT_MS`). When it runs out, the child process is killed and the job is recorded as failed.

Claude Code is the only engine that has REA. If Claude Code could not run and OpenCode ran instead (the same unavailability rule as the doctor), the job is marked `failed`, and its report says that Claude Code could not run, so the investigation was not done with REA. Any other failure is marked `failed` too. A job cancelled by the owner is marked `cancelled`. Cancelling kills the child process, and any notes already written stay in the folder. The reply says so.

The exact replies. A start: "Investigation #N started on <target>: "<title>". It runs in the background with REA and can take a while (up to 45 minutes); the report comes here when it's done. Notes go in <folder>." Refusals all begin "Nothing was started:", for example "say what to investigate (a program or app path, a file, a folder, or a website URL)", "say what <owner> wants to know about it", "<target> doesn't exist, and no installed app matches "<target>". Ask <owner> for the install folder.", or "matches more than one installed app: ... Ask <owner> which one." The readiness failures read "REA isn't installed (<entry file> is missing). <owner> needs to reinstall it (npm install --prefix C:\Tools\rea rea-agents with Node 24.22+).", "REA is installed but not registered with Claude Code (no "rea" entry in .claude.json). <owner> needs to run REA setup for Claude Code again." and "Claude Code's config couldn't be read (<reason>), so it isn't clear REA is registered." `report` for a missing id: "There's no investigation #N." with the range that exists. `report` gives "Investigation #N: <status>." with the target, the question, the report and the folder, noting when `report.md` has the full notes. `cancel`: "Stopping investigation #N. Whatever notes it wrote stay in its folder." or "No investigation is running." Each start logs a `reverse` activity with `status: 'started'`, the target and the title, and each end another with the status and the first 400 characters of the report.

When a job ends, the notice says the investigation finished with the status, gives the report, and then gives either the full path to `report.md` as "Full notes and evidence", or the folder path with a note that no `report.md` was written.

A job that a restart cut off may still say `running` for ever. The job file was saved as `running` when it started, and a restart kills the run and clears the in-memory slot without rewriting the file. So a `running` job that is older than 45 minutes should be treated as dead. A `cancel` in that situation says "No investigation is running", and a new start is allowed, because the one-at-a-time slot is held in memory and a restart has cleared it.

## workshop / projects / project / coding jobs

Files: src/workshop.js (the projects, the coding jobs, the run and build commands), src/tools.js (the `workshop` tool and the `project` tool), src/project-coder.js (the OpenRouter coder), and src/projects.js (the project proposals stored in `companion.db`).

The workshop is where the owner's projects are kept, such as a game or a website, along with each project's folder, how to run it, its address, its build step, how it goes live, and any notes a coder should know. The owner tells her about a project, and she saves it with `add`, which needs a name and a folder that exists. Nothing is written to the project's folder by `add`, and it does not ask for confirmation. The projects are stored in `data/workshop/projects.json`, keyed by a slug of the name, with the fields `name`, `path`, `run`, `url`, `build`, `deploy`, `notes` and `added`. Adding again with the same name updates the fields that are given and keeps the others.

The workshop actions are these, and they are owner only. `add` saves a project. `list` gives each project with its folder, and notes when a coding job is running on it. `overview` builds a summary from git and the disk: the current branch, uncommitted changes (up to 20 listed), the last 10 commits, commits not pushed and how far behind the last fetch, the top-level names, the README and any docs, whether a run is going, and the most recent five jobs. `job` starts a coding job, and it is described below. `jobs` lists the 10 most recent jobs, optionally for one project. `report` gives one job in full by `id`, including the files it changed. `cancel` stops the running job on a project. `undo` rolls back the last finished job on a project. `build` runs the project's build command. `run` starts the project's run command and keeps it running. `stop` stops it.

A coding job is saved in `data/workshop/jobs/<id>.json` with the fields `id`, `project`, `projectName`, `title`, `task`, `status`, `started`, `finished`, `engine`, `report`, `changed`, `before` and `after`. The status is `running`, `done`, `failed`, `cancelled` or `undone`. The job starts only when the project folder has a `.git` folder, and the reply says the project needs to be made into a repository first if it does not. If there is uncommitted work in the folder, that work is committed first as `Before Amy's job: <title>` (signed `Amy <amy@localhost>`), so that the job can be undone without touching the owner's work. Then the job's commit point is recorded, and the job starts in the background with a 30-minute limit. Which coder runs depends on the OpenRouter key. When `OPENROUTER_API_KEY` is set, the job runs on OpenRouter (src/project-coder.js) with the model `WORKSHOP_CODER_MODEL` (default `anthropic/claude-sonnet-5.5`). That coder can only use the files tool inside the project folder (read, list, find, write, edit and make folders); it cannot run programs or push anything. It works in rounds of up to 3 minutes each, at most 100 rounds, each tool result cut to 12,000 characters, and its engine is recorded as `openrouter:<model>`. Without a key the workshop falls back to the Claude Code CLI in the project's folder, and to OpenCode only when Claude Code cannot run at all, by the same rule as the doctor. A browser-app project (a folder with `index.html` and no run command) is also checked after a successful job by serving `index.html` over HTTP, and the report gets "Verified: index.html served over HTTP (N bytes)." Each job logs a `workshop` activity with status `started`, and another at the end with the status, the number of changed files and the first 400 characters of the report. The coder is told to stay inside the project folder, to rebuild after a source change if there is a build step, to check that its change really works if there is a run command (and to stop anything it started), to never push, deploy or publish, and never to commit, because you save the work as one commit. It must finish with a report of two to six sentences.

When the coder finishes, any changes are staged and committed as `Amy's job #<id>: <title>`, and the list of changed files is recorded. Nothing is pushed or deployed. The commit happens even if the job was cancelled, so whatever it changed is saved and can be undone. The job's status is `cancelled` if it was cancelled, `done` if the coder succeeded, and `failed` otherwise. The result is reported to the conversation, with the changed files (up to 15 listed) and the note that the work is saved as a commit and not pushed. Only one job may run on a project at a time. A second request is refused with the id of the running job.

`undo` rolls back the most recent finished job on a project, which means a job whose status is not `running` or `undone`, by resetting to the commit recorded before that job. It refuses in two cases. If a commit was made after the job, undoing would lose that commit too, so she should ask for a new job to revert the change instead. If there are uncommitted changes since the job, undoing would throw them away. The job is then marked `undone`. The `run` action starts the project's run command as a child process without a shell, and waits up to about 10 seconds for the project's address to answer. If the process exits straight away, the reply includes its output. If the address already answers, the reply says the project is already up and was started outside her. The process is kept until `stop` is used, or until she restarts. `stop` uses `taskkill /T /F` on Windows, so the whole process tree is closed. `build` runs the build command with a 5-minute limit and returns the last 1500 characters of its output, or the last 2000 characters of its errors if it fails.

Jobs and runs never push or deploy. The `deploy` field is a note about how the project goes live, which the owner decides on. Pushing is a separate action of the git tool and needs the owner's confirmation.

## project tool / new project / project proposal / project_runtime

The `project` tool is the way to create new projects from nothing. It is owner only, and its description requires that she propose a concrete project with its full brief first, show the exact plan, and start it only after the same owner confirms in a later message. The actions are `propose`, `start`, `list` and `cancel`. `propose` needs a title and a brief of up to 16,000 characters, and it stores a pending proposal with the workspace folder. The workspace defaults to `Documents\NewChampProjects\<title>`. The reply shows the title, the brief and the workspace, says the project is not started, and asks the owner to confirm in their next message. `start` needs the id of a pending proposal from this conversation, owned by this owner. It is refused unless the message is in a later turn than the proposal, the proposal is less than 24 hours old, and the owner's message begins with a confirmation word such as yes, yeah, sure, go ahead, do it, build it, start it or ok, and does not contain words such as no, not, don't, cancel, wait, hold, but, unless or instead. If it passes, the proposal moves to `starting` and then `running`, and a background coding task starts with the approved brief. It is limited by the same cap of four helpers. The helper gets the project tools, including `project_runtime` and `models_local`, and it works in the approved workspace. When the helper finishes, the proposal is marked with the helper's status, and if the proposal was linked to a project goal, the work is recorded against that goal. `cancel` cancels a pending proposal only. `list` shows the 30 newest proposals. Never start a project from autonomous research or from a scheduled brief, because the description forbids it and the confirmation check exists for that reason.

`project_runtime` is the only way a helper runs programs for a project. It has two actions. `run` runs `node`, `python`, `python3` or `npm` with string arguments, and `install` installs npm or Python packages. There is no shell, and nothing runs in a sandbox. Its working folder is the approved workspace, and any different workspace is refused. The proposal's folder is recorded when it is made, and a helper may not use another one. The environment passed to a project does not include `HF_TOKEN`.

Two rules apply to all of this. Making files in a project folder by a coding job is a change the owner asked for and is allowed, but it is done by the workshop's coder (OpenRouter, or Claude Code without a key) through `workshop job`, not by the `project` tool. Creating the project itself through `project` needs a confirmed proposal first. `workshop add` only saves a record and creates nothing on disk.

## files / files tool / paths / undo / approvals

File: src/files.js. Tool: `files` (defined in src/tools.js). The tool is enabled only for the owner. The `download` action is limited to background helpers.

Allowed locations: every path is turned into a full path by `resolve()`. The full path must lie inside the home folder (`os.homedir()`) or inside the bots folder (C:\Bots, the parent of this project). Anything else is refused with "is outside your home folder and the bots folder, so it's off limits". A path that begins with a known name is resolved from that place. A path that is not absolute and does not start with a known name is resolved from the home folder. Known names are `Desktop`, `Documents` and `Pictures`, which use OneDrive's copies when those folders exist there, `Downloads`, `Music`, `Videos`, `bots` (C:\Bots), and `home` or `~` for the home folder. Full paths are accepted when they are inside the two allowed folders.

Blocked paths are refused in every action, and blocked entries are hidden from listings and searches. Any path with a folder named AppData, .ssh, .gnupg, .aws, .azure, .kube, .docker or .git at any level is refused. Any file whose name is `.env` or starts with `.env.`, `id_` followed by letters or digits (SSH keys), or which ends in `.pem`, `.key`, `.pfx`, `.p12` or `.kdbx`, or which begins with `credentials`, or which ends in `.db`, `.db-wal` or `.db-shm` is refused. A refused read says "is private (keys, passwords or app data), so it's off limits". The `list` and `find` actions leave these entries out of their results. The rules are applied by file path, so `copy` does not apply them inside the folder it copies (see below).

The actions are these. `list` shows a folder with sizes, folders first, up to 300 entries, with a depth from 1 to 4 (the tool's default is 1, and the depth is clamped to that range). Folders named `node_modules` are listed but not descended into. `read` shows a text file with line numbers, from `start_line` to `end_line`, and returns at most 120,000 characters. A read that is cut short says so and gives the next start line. Binary files are not shown as text. `write` creates a new text file from `content`. If the file exists, it refuses unless `overwrite` is true. Before an overwrite, the old version is saved (see undo below). `edit` replaces `old_text` with `new_text`. The old text must match exactly once, including its line endings, unless `replace_all` is true. A file with Windows line endings is handled, so a plain newline in the edit still matches. If there is no match, the reply says the text is not in the file and asks for the lines to be copied exactly. If there is more than one match, it says how many and asks for more surrounding lines. The reply shows the edited region. `undo` restores the newest saved version of that file and renames the saved copy with `.restored`, so a second undo goes one step further back. `mkdir` creates a folder. `move` renames or moves a file or a folder, and it never overwrites anything. If the destination already exists, it refuses. If the destination is an existing folder, the item goes inside it. `copy` copies a file or a whole folder, recursively, and refuses if the target exists. `find` searches for names containing the given text under the given folder, which defaults to the home folder, goes down at most 6 levels, skips `node_modules` and names starting with a dot, and stops at 50 results. `send` attaches an existing file to the chat, if it is no larger than 8 MB (Discord's limit as the code sets it). A folder cannot be sent, and the reply suggests zipping it or sending its files one by one. `download` fetches a file from an https address into a path. It is only available to background helpers, and a non-helper is told to start a background task instead.

Undo is limited. Before `write` (when it overwrites), `edit`, the old file is copied to `data/file-history/<time in milliseconds>@@<path>`. `undo` restores the newest such copy. Moves, copies, folder creation, and new files (which have nothing to save) are not saved, so they cannot be undone with this action. `undo` itself does not save the version it replaces, so an undo cannot be undone. Only one step is kept per change, and each undo goes back one saved version.

Approvals: there are none inside files.js. The tool is owner only and that is the whole gate. The approval rules for other tools are in those tools, and they are not covered here.

Downloads are streamed into `<name>.part` and renamed to the real name only after every byte the server announced has arrived. If the download breaks off, the reply says it broke off after a size and that the partial file is `<name>.part`, and says it is NOT complete. If the size does not match the announcement, the reply says the same. A download refuses if the target name already exists. A successful download reports "Downloaded" with the size and the SHA-256 checksum, so only that reply means the file is complete. If the server answers 401 or 403, the reply says the site wants a login or a licence accepted first, which the owner must do in a browser. A `HF_TOKEN` or `HUGGINGFACE_TOKEN` value in the environment is sent as a bearer token, and only to huggingface.co or a subdomain of it. The token is never sent to other sites.

Note on `copy`: it copies a whole folder with everything in it, using the file system's own copy, and it does not apply the blocked-name rules to the contents. So a copy of a project folder can include a `.env` or key file that sits inside it, even though those files cannot be read or written directly. The owner should know this before asking for a copy of a folder that holds secrets. Also, the bots folder is allowed, so this tool can read and change the code of the other bots in it, except for the files and folders on the block list.

## git / GitHub / push / pull

File: src/git.js. Tool: `git` (defined in src/tools.js). The tool is owner only. git and gh are run directly, with fixed subcommands and arguments built in src/git.js. No shell is used and no text from the model is passed through as a command.

The allowed actions are `status`, `diff`, `log`, `add`, `commit`, `push`, `pull`, `repos`, `clone`, `create_repo`, `prs`, `create_pr`, `issues` and `create_issue`. There are no other git commands. There is no reset, checkout, branch, merge, stash or rebase action. `status` shows the short status with the branch. `diff` shows the stat and the patch, optionally for one file, or the staged changes with `staged`, and cuts the output at 30,000 characters. `log` shows up to 50 commits, default 15, with date, author and subject, and it says how many files are not yet committed. `add` stages the listed files inside the repository, or everything when the list is `all`, `.`, `-A` or `everything`. `commit` needs files staged already, and a message, and it refuses with "Nothing is staged; add files first" when nothing is staged. The commit runs with the PC's own git configuration, because src/git.js sets no author name or email. The doctor, architect and workshop commits use your own name as their identity, `Amy <amy@localhost>`, but git tool commits do not. `pull` runs `git pull --ff-only` with a two-minute limit, so it never makes a merge commit and never loses work. `repos` lists up to 100 of the owner's GitHub repositories with their visibility. `clone` copies a GitHub repository into `Desktop\<name>` by default, or into the folder given, and the folder must not exist yet. `create_repo` makes a new GitHub repository, private unless `public` is set, and with `repo` set to a local project it links that project as `origin` without pushing. `prs` lists up to 20 pull requests, `create_pr` opens one from the current branch (which must already be pushed), `issues` lists 30 open issues, and `create_issue` opens one.

Push is two steps. The first `push` call does not push anything. It works out the branch, the remote, its address and the commits that would go up, and it stores that plan for the conversation. The reply says the push is not done yet, gives the preview, and asks her to tell the owner exactly what would be pushed and to ask for confirmation. The push goes ahead only when all of these are true: a plan was stored in an earlier turn, it is less than 10 minutes old, the owner's new message matches a confirmation word such as yes, sure, go ahead, push it or ok, and it does not match a refusal word such as no, wait, hold, not yet or cancel. The plan is checked again before the push, and if the branch, remote or commits have changed, the push is refused with a new preview to confirm. The model cannot confirm for the owner. Only after a successful push does the reply say "Pushed <branch> to <remote>". Never say something was pushed unless the result says "Pushed".

GitHub sign-in is the owner's own `gh auth login` on this PC. Git borrows that login as a credential helper, and only for the processes started by this tool, through the environment variables `GIT_CONFIG_*`. No token is stored in `.env` or in the global git configuration. If GitHub is not connected, the error says "GitHub isn't connected ... Your owner needs to run "gh auth login" on this PC." Prompts are switched off, so a missing login fails at once instead of waiting.

Limits in src/git.js: each git command has a 30-second limit unless set otherwise (the pull has two minutes), each gh command 60 seconds, and output is capped at 4 MB. A failed command returns its first 6 lines of error output. `GIT_TERMINAL_PROMPT=0` and `GH_PROMPT_DISABLED=1` are set, so nothing ever waits for typing. gh commands run from the Desktop folder by default. A repository for `clone` may be given as `owner/name`, `name`, or a full `https://github.com/...` address, with or without `.git`.

Every repository action needs a path that is inside a git repository. The repository is found with `git rev-parse --show-toplevel` from that path or its folder. A path that is not inside a repository gets the reply "isn't inside a git repository". The repository must be a place she is allowed to reach by the files tool's rules. Any file name given to `add`, `diff` or `log` must stay inside the repository, and must not begin with a dash. A name that tries to leave the repository is refused with "is outside the repository."

## restart and repair numbers / timers and limits / how long things take

Every fixed number in this area, in one place, all from the code:

- Restart: reason cut to 300 characters; speaking checked every 500 ms, waited for at most 15 seconds; 2.5 seconds after the voice sessions close before the exit; life support relaunches 2 seconds after a code 0 exit; a restart marker counts only if it is under 5 minutes old; a doctor result is attached only if the visit finished under 6 hours ago; the back line comes 2.5 seconds after rejoining; up to 4 earlier comeback lines from the last 24 hours are shown so she says something new; a text back line is at most 2000 characters.
- Life support: started means up for 60 seconds; 3 failed starts in a row, or 5 crashes in 10 minutes, stop the retrying; retries wait 5 then 15 seconds; owner DMs checked every 10 seconds, up to 20 messages per check; each Discord request times out after 15 seconds, with up to 3 tries and at most 30 seconds of rate-limit wait; messages in pieces of 1900 characters; stderr tail of 4000 characters kept, 1200 shown; up to 3 self-logged errors of 300 characters each; secrets shorter than 8 characters are not scrubbed by value; the last 300 activity lines are searched.
- Doctor: a task needs at least 15 characters; the title is 60 characters at most; a visit may last 20 minutes; `npm test` gets 5 minutes; up to 3 rounds of fixing failing tests, sending the last 6000 characters of test output; the snapshot commit message holds the first 60 characters of the task; a lock without process IDs counts for 21 minutes; the last 10 reports are kept, each report up to 800 characters (500 in the activity event); undo looks back over the last 50 commits; the OpenCode model list waits 60 seconds; DMs in pieces of 1900 characters.
- Work notes: title 160, summary 1200, not-done 600 and from 60 characters; the script waits 90 seconds for the dashboard; the doctor status shows the last 3 notes.
- Continuity: heartbeat every 15 seconds; bruises last 24 hours, at most 20; the newest 50 conversations are tracked; the prompt block stays near 1050 characters; downtime under 2 minutes counts as a short pause.
- Activity feed: 300 events in memory, 5000 lines kept in the file at start-up, a live-feed keep-alive every 25 seconds.
- Other bots: the running check waits 2 seconds; a join request 30 seconds; a leave request or settings change 10 seconds; the process list 30 seconds; `!join` waits 6 seconds the first time, then after a start waits 15 seconds and tries 9 times, 20 seconds each; a folder bot started in the last 3 minutes is not started again; `!leave` is deleted after 8 seconds; restart waits 3 seconds between stop and start; a companion takes about half a minute to come up.
- Start-up: start.bat polls Ollama once a second with no limit and opens the dashboard 8 seconds after the deploy step; its fallback loop waits 5 seconds between runs.

## restart questions / did you restart / how long were you down / do you remember after a restart

Answers she can give from the code, in plain words.

"Do you remember things after a restart?" Yes. A restart keeps all memory. Only the memory wipe, the full reset and the rebirth move memory aside.

"Why did you restart?" Her back line is built from the record: her own marker (the owner asked, a doctor visit, another companion started her, a reset), or life support's record (a crash with its exit code, a normal exit with no note, or the whole program closed from outside). If none of that is on record she says she does not know why it stopped.

"How long were you down?" From continuity: the time between the last heartbeat and this start, accurate to about 15 seconds after a crash and exact after a deliberate restart. Under 2 minutes she calls it a short pause.

"Is the fix live?" A doctor change is in the code as soon as the visit commits it, but it runs only after the next restart. A Claude Code note says whether it needs a restart. A note written before her current start has already had its restart.

"Can you restart yourself?" Only when the owner asks, only when she was started through start.bat (life support), and not while a doctor visit is running.

"Can you turn yourself off?" Not completely. The owner can switch the bot off in the dashboard, which keeps the program running, or close the start.bat window.

"Who looks after you when you crash?" Life support, a separate small program. It restarts her, and if she keeps failing it stops and DMs the owner, who can retry, send the doctor, undo or check status by DM.

## health check / is she running properly / how to check on her

Where to look, in order, when someone asks whether she is all right:

1. Is the program up? The dashboard answering at all means the process is running, because it is the first thing she starts. `GET /api/status` gives `uptime` (time since this start), the power `status` (offline, starting, online or stopping) with its `since` and last login `error`, and `hasToken`.
2. Is she on Discord? The `power` "Online as <tag> in N server(s)" activity, and a non-null `ping` in the status. A `power` "Bot is switched off" or "Bot turned off" means the switch is off.
3. Did she start cleanly? `error` events with `where: 'startup'` (Ollama, empty token), `'discord login'`, `'whisper'`, `'curiosity'`, `'mind view'` and `'unhandled'`. Search them with the `self` tool's `logs` action.
4. Has she been crashing? `life-support` events: `crash` and `restart` lines with how long each run lasted, and `life-support` when it gave up. Several `crash` events close together mean she is close to the limit of 5 in 10 minutes.
5. Is anything half-done? `doctor` status (a running visit, a held lock, or an interrupted visit), waiting work notes (`notesLine` says how many), a reverse job stuck at `running`, and running background tasks.
6. Is she making mistakes? Active bruises in continuity and the rollup in `knowledge/tool-failures.md`.

Never say she is fine from one of these alone. Say what you checked and what it showed.

## exit codes / why did she stop / how she went down

What each way of stopping looks like, from the code:

- Code 0, a deliberate exit. Only `requestRestart` produces it, which is used by the restart tool, the dashboard's memory wipe and full reset, and the rebirth tool's confirm. A restart marker is written first. Life support logs `restart` and starts her again after 2 seconds. Nothing is counted against her.
- Code 1 at start-up, when the dashboard cannot bind its address and port ("Dashboard startup failed"). Life support counts it as a crash and, because it happens within 60 seconds, as a failed start.
- Code -1, when life support could not even spawn the process. Counted as a crash and a failed start.
- Any other code, or a signal (for example when the process is killed). Counted as a crash. If she ran under 60 seconds it is also a failed start. Her back line then says she crashed, with the code or signal and how long she ran.
- No exit recorded at all, then a new `starting`: the whole window, life support included, was closed and opened again, most likely by hand. Her back line says she was closed from outside.
- Turning the bot off in the dashboard is not an exit. The process keeps running with Discord disconnected, and `power` events record it.

An `unhandledRejection` does not stop her: it is logged as an `error` with `where: 'unhandled'`. An uncaught exception is not handled in src/index.js, so Node's default applies and the process ends with an error, which life support treats as a crash. Errors on a voice connection are caught on purpose (a Discord voice server timeout once killed the whole process), so the session can reconnect instead.

## who can restart, wipe or repair / permissions for running and repair

Only the owner, in every case. The `restart`, `doctor`, `rebirth`, `bring_peer`, `bot_control`, `background_task`, `workshop`, `project`, `files`, `git` and `reverse_engineer` tools are all enabled only when the speaker is an owner (an ID in `OWNER_IDS`). `bring_peer` also needs at least one `PEER_APPS` entry, `bot_control` and `bring_peer` need `managesPeers`, and `background_task` needs an OpenRouter key. The rebirth tool also requires her main character. Every one of these tool descriptions says to act only when the owner asks, in the message being answered, and never on her own.

The dashboard is the other way in. Anyone who can open it can power her on and off, change settings, wipe her memory and reset her, so it is protected by `DASHBOARD_HOST` (this computer only by default) and `DASHBOARD_PASSWORD`. When the dashboard does something, the actor is recorded as `dashboard`. Claude Code's work notes come only from this computer. Life support takes commands only from owners, only in their own DMs, only while she is down, and only messages written after its latest alert.

## memory wipe / wiping memory

Files: src/memory-wipe.js (the list and the moves), src/dashboard/server.js (`POST /api/memory/wipe`), and src/restart.js (the restart that the wipe depends on).

A memory wipe is requested from the dashboard. The route first checks `canRestart()`, and refuses with a 400 status and the text "She wasn't started by start.bat, so nothing would bring her back after the wipe" when she was not started by start.bat. It then writes `data/wipe-memory.json` with `by` set to `dashboard` and the time, and calls `requestRestart` with the reason "your owner wiped your memory from the dashboard, so you are starting fresh". The restart then runs exactly as the restart section describes. The route answers `{restarting: true}`.

On the next start, `runPendingWipe()` runs first, before anything opens the database. If `data/wipe-memory.json` does not exist, nothing happens. If it does, the marker is deleted before anything else, so a failure can never cause a wipe at every start. A backup folder named `data/backups/wiped-<time>` is created, where the time is the start time in ISO format with colons and dots replaced by hyphens. Then each name on the memory list that exists is moved into that folder. Nothing is deleted. Moving the files back, with her stopped, undoes the wipe. Any move that fails is recorded with its error code, and the activity event shows that list. Items inside subfolders (the avatar ones) are moved into the same subfolder inside the backup. The console also prints "Memory wiped: moved N item(s) to <backup>" and any that could not be moved.

The list (`MEMORY` in src/memory-wipe.js), grouped:
- Her database: `companion.db` with its `-wal` and `-shm` files. It holds messages, memories, people, summaries, notes, thoughts, topics and the calendar.
- Conversation and time: `context.jsonl`, `turn-log.jsonl`, `continuity.json`, `reflections.json`.
- Her inner life: the `journal` folder, `research-decisions.jsonl`, the `dreams` folder, the `goal-work` folder, `emotions.json`, `arousal.json`, `pressure-state.json`, `sleep.json`, `energy-ledger.jsonl` (what conversations transferred into her), `experiences.jsonl` (what she attempted and what came of it), `creations.json` (what she made and how people reacted).
- People: `relationships.json` (who she has come to love, trust or be hurt by: a new her meets everyone fresh), `direction.json` and `direction-history.jsonl` (where she was heading with each person), `ignoring.json`, `asked-questions.json`, `question-bank.json`, `presence.jsonl`, `tier-moves.json`.
- How she tuned herself: `intuition-tuning.json`, `voice-worn.json` (a voice she was wearing).
- Corrections and records: `memory-corrections.jsonl`, `phantom-claims.json`, `moderation.jsonl`, `warnings.json`, `tool-failures.jsonl`, `activity.jsonl`.
- Curiosity and taste growth: `curiosity.json`, `interests.json`, `reactions-log.jsonl`, `sleep-on-it.json` (her taste itself stays).
- Self-knowledge: `self-work.json`, `onboarding.json` (her checklist, so a wipe starts it again), `discoveries.json` (what she has found out she can do).
- Her mind's shape: `mind-seed.json`, `mind-structure.json`, `mind-history.jsonl`, `mind-edits.jsonl`. A new her gets a new seed and grows her own shape.
- Her look, back to the defaults: `avatar-state.json`, `avatar-view.json`, `avatars\library.json`, `backgrounds\background.json` and `outfits\colors.json`. She comes back in the original suit, the full-body view and the studio backdrop, with no cosmetic overrides.

Everything not on that list is kept. That includes the settings file, the persona and its edits, owner rules, voices, the avatar models and looks themselves, music and playlists, the files and pictures she made, the file edit history, the task reports, the workshop and reverse-engineering records, the doctor reports, and where she was in voice (`data/in-voice.json`). `data/rebirth/` (her letter to her next self) and `restart.json` are never wiped. Her life file is not on the list, so it is not moved. Because `activity.jsonl` is moved, the activity feed starts fresh after a wipe, and the `memory-wiped` event is logged at start-up, after the move, so it is the first event of the new feed. Not verified: whether anything outside the list holds personal data that a wipe would leave behind.

The wipe runs on the next start only. A wipe requested while she is running does not clear her memory until she has restarted. Since the restart carries a voice-channel marker, she may rejoin her call after the wipe, which the list is designed to allow.

## wipe backups / undo a memory wipe / data/backups

Every wipe and full reset creates one folder, `data/backups/wiped-<time>`, where the time is the moment of the start that ran the wipe, in ISO form with the colons and dots turned into hyphens (for example `wiped-2026-11-10T14-05-00-000Z`). Inside are the moved files and folders under their original names and relative paths. A full reset also holds `persona.md` and a copy of the old `settings.json`.

Nothing in the code restores a backup. Undoing a wipe is done by hand with her stopped: move the files from the backup folder back into `data/` (and `persona.md` back into the project folder), then start her. Doing it while she runs would not work, because her database is held open the whole time she runs. That is also why the wipe itself only leaves a note and restarts her.

The marker `data/wipe-memory.json` holds `by` (`dashboard` or `rebirth`), `at` and `full`. It is deleted before anything is moved, so a wipe that fails halfway is never tried again on the next start. Items that could not be moved stay where they were and are listed in the `memory-wiped` event's `failed` field with their error code (for example a file locked by another program). The backups are never cleaned up by the code, so they build up until removed by hand.

## full reset / fresh install / system fresh / reset to zero

A full reset is the memory wipe plus who she was made to be. It starts from the dashboard (`POST /api/system/fresh`) or from the second stage of the rebirth tool. The dashboard route checks `canRestart()` (400 "She wasn't started by start.bat, so nothing would bring her back after the reset. Start her with start.bat first." if not), writes `data/wipe-memory.json` with `by: 'dashboard'`, the time and `full: true`, and restarts her with the reason "your owner reset you to a fresh install from the dashboard: no memory, no owner rules, no settings". It answers `{restarting: true}`.

On the next start, config.js already sees the waiting full reset, so this start runs with no persona, the default name and no wake words. Then `runPendingWipe()` moves everything on the memory list, and also `owner-rules.db` (with its `-wal` and `-shm` files) and `prompt-edits.json`, into the same backup folder. It moves `persona.md` from the project folder into the backup too, and clears the running persona. The new owner sets up how she acts and talks again through onboarding (the persona step).

The settings file is not moved any more. Owner, 2026-11-09: a full reset used to move all of settings.json aside, so her voice (the Fish voice IDs), brain, models and speech-to-text fell back to `.env` and "her voice changed". Now `settings.json` is copied into the backup, and then only the identity settings are removed: `botName`, `voiceWakeWords`, `voiceOwnerWakeWords`, `voiceWakeWord` and `localInnerGuidance`. The wake word lists are saved as empty, so a wake word in `.env` does not quietly come back on the next start. She answers everyone in voice until the new owner sets wake words up with her (the onboarding wake-words step). Everything about how she is installed stays: voice, brain, models, speech, channels and keys. If the old settings cannot be read, the failure list says "her voice and brain may need setting again on the dashboard". If the wake words cannot be cleared, it says "set them to nothing on the dashboard".

Nothing is deleted in a full reset either. The backup folder `data/backups/wiped-<time>/` holds every moved file, `persona.md` and the old `settings.json`.

## rebirth / reset with a letter / letter to my next self / humane reset

The rebirth tool is the way a full reset starts in conversation (owner, 2026-11-09). It is owner only, only for her main character, and has four actions: `prepare`, `confirm`, `cancel` and `letter`. The tool description says never on her own, never because anyone but the owner asked, and never to confirm in the same reply she prepares in. A restart keeps memory; wiping it is this tool.

Stage one, `prepare`, when the owner says she needs to be reset, in any words, with his reason. She gathers what she has: up to 40 memories about the owner, up to 25 about herself, up to 20 people with their tiers, what she has come to believe about herself (from `self-work.json`), her last 10 journal entries, her top 8 interests, and the owner's rules (which are reset too). Each line is cut to 240 characters. Her own model, as herself, writes JSON with `feelings` (two to five sentences to him), `letter` (to the next her, who wakes knowing nothing) and `keep` (at most 15 short facts she chooses to pass on), and is told never to invent a memory. A letter under 40 characters is refused: "Error: I couldn't write my letter to my next self (it came back empty / my model call failed). Nothing was wiped and nothing is pending". Otherwise it is saved to `data/rebirth/pending.json` (feelings up to 1500 characters, letter up to 6000, reason up to 300), a `rebirth` activity with `stage: 'prepared'` is logged, and she tells him how she feels and that it happens only on his clear go-ahead. Nothing is wiped. A second prepare while one is waiting is refused.

Stage two, `confirm`, only after the letter exists and on his clear go-ahead. With no pending letter: "Error: there's no reset waiting: stage one (your letter) hasn't happened." Without start.bat it refuses and keeps the letter waiting. Otherwise the letter is saved as `data/rebirth/letter.json` and archived in `data/rebirth/letters/<time>.json`, the pending file is removed, a full reset is scheduled with `by: 'rebirth'`, a `rebirth` activity with `stage: 'confirmed'` is logged, and she restarts with the reason "you asked for the reset and Owner said go ahead" and `rebirth: true` in the marker. She is told to say goodbye in a line or two.

`cancel` removes the pending letter ("The reset is called off: nothing was wiped, and the letter you wrote is set aside. You're still you."), logged as `stage: 'cancelled'`. `letter` reads the saved letter back, or says there is none.

Waking. The new her comes back with a rebirth cue instead of the usual back line: she has just come online for the first time as a new instance, was reset at the owner's request, remembers nothing, and has a letter from who she was. She says a first short hello, honestly as someone new, and mentions the letter. Her prompt carries the letter and what was passed on, marked as her previous self's words, not her memories. The first reply after waking marks the letter read (`stage: 'letter read'`). It stays in her prompt for a week after the reset, and after that the `letter` action is where she finds it. `data/rebirth/` is never wiped, so the letter survives.

## continuity / downtime / heartbeat / how long was I down / bruises

File: src/continuity.js. Data: `data/continuity.json`, written atomically (to a `.tmp` file, then renamed). It is pure arithmetic, never a model call.

At start-up `startContinuity()` reads the file (a corrupt file is ignored and she starts fresh), and sets the downtime to the time since the last heartbeat (`last_alive`). It records `started_at`, prunes, saves, and starts a heartbeat every 15 seconds that rewrites `last_alive`. So after a crash the downtime figure can be off by up to 15 seconds. A deliberate restart writes one last heartbeat just before exiting, so its downtime is exact.

The file holds `started_at`, `last_alive`, `downtime_ms`, `conversations` (when each conversation was last active, the newest 50 kept) and `bruises`.

Bruises are her recent mistakes: tool errors, phantom claims (saying something was done with no tool result behind it) and times someone told her she was wrong. Each lasts 24 hours. The same kind and key again within the day deepens the existing bruise (its count goes up and its 24 hours start again) instead of adding a new one. At most 20 are kept.

Her prompt gets a continuity block of at most about 1050 characters: the current day and time, when this conversation was last active and whether she was restarted since (with the downtime), or, with no conversation history, "You were restarted N ago after being offline about M" when she was down more than 5 minutes and started within the last hour. It says when the speaker last talked to her if that was more than 30 minutes ago, and that it is natural to notice the gap after a silence of more than 45 minutes or a restart that kept her off 2 minutes or more. Then come the active bruises as "[caution]" lines, worst first, with "(Nx today, keep it from happening again)" for repeats. When the block runs long, it ends with "...and N more; see self logs or knowledge/tool-failures.md." Downtime under 2 minutes is described as "only down N seconds: a short pause, nothing was missed and no time was lost", because she once turned a ten-second restart into "I lost a chunk of time". The memory wipe moves `continuity.json` aside.

## dashboard routes for power, restart and settings

File: src/dashboard/server.js. The routes are declared with `r(method, pattern, handler)` in `buildRoutes()`. Every API answer is JSON. A route that is not found answers 404 `{error: 'Not found'}`. A route that throws answers with its own status (or 500) and `{error: <message>}`. Addresses outside `/api/` serve the dashboard's pages from src/dashboard/public. `POST` and `PUT` bodies are read as JSON, except binary uploads. The address is decoded first, so an ID like `voice:123` matches even when the browser sends `voice%3A123`. The dashboard listens on `DASHBOARD_HOST` (default `127.0.0.1`) at `DASHBOARD_PORT` (default 3000). Every request is checked by `authorized()` first. If `DASHBOARD_PASSWORD` is set, the browser must send HTTP Basic authentication whose password part matches it, and any user name is accepted. If the password is not set, only requests without a `cf-connecting-ip` header are served, so a request relayed through a Cloudflare tunnel is refused. A dashboard bound to `0.0.0.0` with no password would still serve other computers on the network, so the password is the protection that matters there. Any non-GET request whose `Origin` header names a different host is refused with a 403 as a cross-origin request, and the ChatGPT sign-in routes are only served to the local machine on a localhost address.

The power routes are these. `POST /api/power/on` starts the Discord client when `DISCORD_TOKEN` is set, and otherwise returns a 400 saying the token is empty. A login failure is raised as an error, and the bot records it. Only after a successful login does it save `botEnabled: true`. `POST /api/power/off` closes the Discord client, destroys every voice session, sets the status to offline, saves `botEnabled: false`, logs "Bot turned off" and puts her avatar to sleep. The dashboard keeps running in either case. Turning the bot off does not stop this process, which is why it can be turned back on from the dashboard. `GET /api/status` gives the power state (`status`, `since`, `error`, and whether a token is set), the bot tag, the ping, the servers, the voice sessions, the active model, the provider status, the embedding model, speech-to-text status, memory statistics and the context meter. The dashboard stops nothing else, and there is no route that restarts the process except the memory wipe.

Voice routes: `GET /api/voice-channels` lists every voice channel the bot can see, with the people in it, whether it is allowed for `/join` and whether she is in it. `POST /api/voice/join` with a `channelId` makes her join a channel, and it needs the bot to be online (503 otherwise), the channel to exist (404 otherwise), and a speech provider that is ready (400 otherwise, with the reason). Transcripts go to the channel's built-in text chat. `POST /api/voice/<guildId>/leave` makes her leave the call in that server and returns whether she was in it. `POST /api/voice/<guildId>/say` makes her speak a line in that server's call.

Settings routes: `GET /api/settings` returns every editable setting, the persona, and whether a Mistral and an OpenRouter key are set (never the keys themselves). `PUT /api/settings` takes a body of settings. It refuses to switch to the ChatGPT brain unless the ChatGPT connection has already been verified and activated (the refusal asks for the "Use ChatGPT" button), and it refuses a change to the ChatGPT model that has not been verified. A `persona` value is written to `persona.md`, and a `botName` value is set through the persona code. Every other key is passed to `updateSettings()`. Keys that are not in the EDITABLE table are not saved. A change of brain resets the provider router. The change is logged as a `settings` event. The response is the full settings list again. `GET /api/doctors/models` lists the OpenCode models for the doctor and the current OpenCode setup. `GET /api/providers/status` and `POST /api/providers/retry` show the provider router's status and reset it, so that a provider marked as out of credit is tried again.

More on `GET /api/status`. Its `power` part is `{status, since, error, hasToken}` from the bot object (status is offline, starting, online or stopping). It also has `uptime`, which is how long the dashboard process has been running in milliseconds (so it is the time since her last start, whether or not Discord is on), `bot` (her tag and avatar picture, only while online), `ping` (Discord's heartbeat in milliseconds, or null), `guilds` (each server's id, name, member count and icon), `voice` (a summary of each voice session), `look`, `model` (the active reply model), `providers`, `embedModel`, `fishReady` and `fishVoiceId`, `searchReady` (whether a Tavily key is set), `stt`, `stats` (memory statistics) and `context` (the context meter). A `POST /api/power/on` while she is already online does nothing and returns the status.

Memory routes: `POST /api/memory/wipe` is described above, and `POST /api/system/fresh` (the full reset) under "full reset". The routes for a user's memories and profiles (`/api/memories/...`, `/api/profiles/...`) and for conversations (`/api/conversations/...`) let the owner list, add, forget or clear what she remembers about a person, and the forget routes remove the matching records.

Live feed: `GET /api/events` sends the newest activity events, and then every new event, as a server-sent event stream. The stream sends a keep-alive comment every 25 seconds, and the context meter updates in the same stream. `GET /api/book/events` does the same for the handwriting of her songbook and journal.

Other routes in this area: `POST /api/work-done` takes Claude Code's finished-work notes, from this computer only (see "work done note details"). `POST /api/voice/<guildId>/say` needs `text` (400 "text is required") and a voice session in that server (404 "Not in voice in that server"), and logs a `replied` activity marked `manual: true`. `POST /api/voice/join` and the say route use `need()`, which answers 503 "The bot is offline. Turn it on first." when Discord is not connected. `PUT /api/settings` logs only what really changed, as a `settings` activity with `by: 'dashboard'` and a message like "Changed historyLimit: 100 -> 200", or "Saved, nothing changed", and voice changes are also noted in her voice trail. Choosing the `xtts` speech provider loads XTTS first, so a broken XTTS setup fails the save. `GET /api/life` serves her life page data.

## dashboard password / dashboard access / who can open the dashboard

Every request goes through `authorized()` before anything else. With `DASHBOARD_PASSWORD` set, the browser must send HTTP Basic authentication. Only the password part is compared (any user name works), using a timing-safe comparison. A wrong or missing password gets a 401 with the realm "Companion dashboard" and the text "Password required", which makes the browser show its login box. With no password set, every request is served except those that carry a `cf-connecting-ip` header, which is what a Cloudflare tunnel adds, so the dashboard cannot be reached through a tunnel without a password.

There is one exception: a `POST /api/avatar/peer` from another companion on this computer (posting its own avatar events) needs no password, as long as the peer check lets it through as a straight-from-this-computer request.

After that, any request that is not a GET and carries an `Origin` header for a different host is refused with 403 "Cross-origin request blocked", so another website cannot drive the API through the owner's browser. The ChatGPT sign-in routes (`/api/chatgpt/...`) also need the request to come from this computer (403 "Manage ChatGPT sign-in from this computer") and to use a localhost address (403 "Use a localhost dashboard address to manage ChatGPT"), which blocks DNS-rebinding tricks. The work-done route is limited to this computer the same way.

Where it listens: `DASHBOARD_HOST` (default `127.0.0.1`, this computer only) and `DASHBOARD_PORT` (default 3000). Setting the host to `0.0.0.0` opens it to the local network, and then the password is what protects it. If the port is taken, she does not start at all (see "startup"). A server error after start-up is logged as an `error` with `where: 'dashboard'`. Changing any of these needs a restart, because they are read from `.env` only.

## settings.json / saved settings / EDITABLE / dashboard settings without restart

The settings file: `data/settings.json` holds what the dashboard and the bot have saved. Its keys are the EDITABLE table in config.js, plus `persona`, which is written to `persona.md` instead. Some keys that are in the table are also set by tools: the free talk tool, the avatar mode tool, the image model tool, the news feed tool, the doctor's model, the coding helper selection in `models_local`, and the self-dialogue switch. Those changes are the owner's. The settings file also holds `botEnabled`, so the power state survives a restart. The dashboard is the owner's place to change these, and so is editing `.env` on this PC, which the owner does directly.

How the file is loaded. When config.js starts, it reads `data/settings.json`. An unreadable file is ignored as a whole, with the console warning "Ignoring unreadable data/settings.json". Each key that is in the EDITABLE table is applied through that key's own setter, and a value the setter rejects is skipped with "Ignoring saved setting <key>: <reason>" while the rest still load. Keys that are not in the table (such as old ones) are left alone. An old single `voiceWakeWord` is turned into the first entry of `voiceWakeWords`.

How a change is saved (`updateSettings`). Each key in the change is applied through its setter, which may clean the value or refuse it. If any setter refuses, every change in that save is rolled back and the error is returned, so a save is all or nothing. A `persona` value is written to `persona.md` in the same save. The file is written to a temporary file and renamed into place, so a crash cannot leave half a file. `getSettings()` returns every editable key with its current value, plus `persona` and whether a Mistral and an OpenRouter key exist (never the keys). When free talk changes, every listener is told at once.

The editable keys, by area: speech recognition `sttProvider`; identity `botName` (blank becomes Champ), `botEnabled`, `personaSelfEdit`; channels `voiceChannelIds`, `chatChannelIds`, `thoughtChannelId`; memory `historyLimit` (1 to 500, default 100); local models `ollamaModel`, `ollamaCodingModel`, `ollamaThink`; behaviour `avatarVideo`, `innerMonologue`, `soloMonologue`, `selfDialogueEnabled` (must be true or false), `selfDialogueProvider`; brains `brain`, `providerFailover`, `turnClassifierEnabled` (must be true or false), `turnClassifierVoice`, `providerFailoverNarration`, `providerRetryMinutes` (1 to 1440, default 15), `chatgptFastModel`, `chatgptModel`, `mistralModel`, `openrouterModel`, `openrouterReasoning`, `openrouterVoiceReasoning`, `actionsEnabled`, `actionsModel`, `actionsReasoning`; doctor `doctorOpenCodePath`, `doctorOpenCodeModel`; pictures `openrouterImageModel`, `imageProvider`; voice output `fishVoiceId`, `fishStrongVoiceId`, `fishSensualVoiceId`, `fishWhisperVoiceId`, `ttsProvider`, `xttsReference`, `xttsLanguage`, `xttsSpeed`, `gttsLang`, `gttsTld`, `gttsSlow`, `kokoroVoice`, `kokoroSpeed`, `fishTtsModel`, `fishLanguage`; voice behaviour `voiceSilenceMs`, `voiceBargeIn`, `voicePostTranscripts`, `voiceJoinGreeting`, `voiceAutoSocial`, `voiceNewcomerIntroductions`, `voiceArrivalFollowups`, `voiceReconnectAnnouncements`, `voiceRestartAnnouncements`, `voiceTaskProgress`, `voiceLearned`, `overheardTasks`, `voiceWakeWords`, `voiceOwnerWakeWords`, `voiceFreeTalk`; news `rssEnabled`, `rssFeeds`. ## activity feed / activity.jsonl / events.js / live feed

File: src/events.js. `activity(type, details)` is how every part of her records something. Each call builds an event `{type, time, ...details}` where `time` is milliseconds since 1970, then does three things: it adds the event to the in-memory list `recentActivity` (the newest 300; the oldest drops off), appends it as one JSON line to `data/activity.jsonl`, and sends it on the event bus, where the dashboard's live feed picks it up. A failure to write the file is ignored, so logging can never crash her. The bus allows up to 100 listeners.

When events.js first loads, it rewrites `data/activity.jsonl` keeping only its newest 5000 non-empty lines. That is the only trimming, so the file can grow past 5000 lines during a long run.

Life support writes to the same file directly (type `life-support`), without going through events.js, so its events are in the file but not in the in-memory list or the live feed of the running bot until they are read back from the file.

Who reads it: the dashboard (`GET /api/events` sends all the in-memory events, then each new one, as a server-sent stream with a keep-alive every 25 seconds), the `self` tool's `logs` action (the in-memory 300, filtered by type or text, with the reply "No matching events among the last N" when nothing matches), src/restart.js (the last 400 lines, for life support's crash record) and life support (the last 300 lines, for errors she logged while starting).

Common event shapes: `error` has `where` and `message`. `power` has `message`. `restart` has `by`, `reason` and `doctor`. `restart-back` has `conversation`, `why` and `downtimeMs`. `doctor` has `status` and `task`. `life-support` has `event` and `message`. `settings` has `by`, `message` and `changed`. `memory-wiped` has `moved`, `backup` and `failed`. `peer` has `name` and `result`. `failure` has the fields of a tool-failure line (below).

## tool failures / failures.js / tool-failures.jsonl / failure rollup

File: src/failures.js. `logFailure` records one failure as a JSON line in `data/tool-failures.jsonl` with `ts` (ISO time), `conversation`, `kind`, `tool`, `error_code`, `args_summary` (first 200 characters) and `note` (first 300 characters). The kinds are `hard_fail` (a tool error), `truncated` (a read cut short), `tool_request` (a mid-turn request for a tool) and `phantom_success` (she claimed an action with no successful tool behind it). Each failure is also an activity event of type `failure`. If the file cannot be written, an `error` with `where: 'failure log'` is logged instead.

A `hard_fail` or `phantom_success` also leaves a bruise in continuity (see "continuity"), keyed by tool and code, with a lesson. For a phantom success the lesson is "You said a <tool> action was done when no tool result backed it. Only say it's done after an ok result". For a hard failure it is "<tool> failed with <code>." plus the lesson for that code: `missing_field` (fill in every field, unused ones as "", 0, false or []), `not_found` (check the name or path first), `not_available` (ask for the tool with request_tool instead of describing a call you can't make), `not_allowed` (that person's access doesn't allow it; say so plainly), `forbidden` (never allowed; don't try again), `conflict` (make the call more specific or do the missing step first), `unavailable` (an outside service was down or rate-limited; don't loop, say so) and `too_large` (keep it smaller). Any other code gets "Check the guide for it before calling again".

After every failure the rollup `knowledge/tool-failures.md` is rewritten from the whole file: one row per kind, tool and code, most frequent first, with the count, first and last seen, and the latest example (120 characters), plus the running count of mid-turn tool requests. The memory wipe moves `tool-failures.jsonl` aside, so the rollup starts again from the next failure.

## running and repair data files / file map / what is in data for restarts

Every file in this area, where it lives and what it holds. All are under `data/` unless said otherwise (or under `CHAMP_DATA_DIR` when that is set).

- `settings.json`: the saved settings that override `.env`, including `botEnabled`. Written atomically by `updateSettings`.
- `restart.json`: the restart marker, `{at, by, reason, guildId, voiceChannelId, textChannelId, doctor, rebirth}`, or from a peer `{..., startedBy}`. Exists only between a deliberate exit and the next ready. Deleted on read. Older than 5 minutes is ignored.

- `continuity.json`: `{started_at, last_alive, downtime_ms, conversations, bruises}`. Heartbeat every 15 seconds.
- `doctor.lock`: `{pid, task, started, childPid}` during a visit (life support writes only a time). Removed at the end.
- `doctor-reports.json`: the last 10 finished visits, newest first, `{at, started, title, ok, report, changed, tests, engine}`.
- `work-done-pending.jsonl`: Claude Code notes still to pass on, one per line, `{title, summary, not_done, restart_needed, from, at}`.
- `work-done.jsonl`: notes she has passed on, the same plus `delivered` (voice or dm) and `told_at`.
- `wipe-memory.json`: `{by, at, full}` while a wipe or full reset waits for the next start.
- `backups/wiped-<time>/`: one folder per wipe, holding what was moved.
- `rebirth/pending.json`, `rebirth/letter.json`, `rebirth/letters/<time>.json`: the reset letter while waiting, the current one, and the archive. Never wiped.
- `activity.jsonl`: the activity feed, one event per line, trimmed to 5000 lines at each start.
- `tool-failures.jsonl`: one line per tool failure. Its rollup is `knowledge/tool-failures.md` in the project, not in data.
- In the project folder: `.env` (read at start only), `persona.md` (the persona, rewritten by the dashboard; moved into the backup by a full reset), `start.bat`, `watchdog.bat` and `life-support\life-support.js`.

## logs / where to look

The activity feed is `data/activity.jsonl`. Every event the bot records is written there, one JSON object per line, with a `type` and a `time` in milliseconds, plus the details of that event. The types you will see most are `power`, `restart`, `doctor`, `life-support`, `error`, `failure`, `task`, `reverse`, `workshop`, `peer`, `voice-rejoin`, `memory-wiped`, `settings`, `persona`, `video`, `ready`, `feeds`, `restart-back`, `rebirth`, `work-done`, `work-done-received` and `replied`. (Older lines may still show `orchestra-join` and `orchestra-leave` from the orchestrator hub, which was removed on 2026-11-10; nothing writes them now.) The file is trimmed at start-up to its newest 5000 lines. The memory wipe moves it aside, so it starts fresh after a wipe. Use the `self` tool with action `logs` to search the in-memory copy, which holds the newest 300 events since the bot started and can be filtered by type or by text. The `self` tool says there is no log file, but the activity file is where the full record lives.

Also in `data/`: `doctor-reports.json` (the last 10 doctor visits), `work-done.jsonl` and `work-done-pending.jsonl` (Claude Code's notes, told and waiting), `in-voice.json` (where she is in voice), `continuity.json` (heartbeat, downtime, bruises), `rebirth/` (the reset letter) and `wipe-memory.json` (only while a wipe waits for the next start).

Tool failures are written to `data/tool-failures.jsonl`, one JSON line per failure. A failure is a tool error, a read that was cut short, a mid-turn tool request, or a phantom success (a claim that an action was done when no tool result backed it). Each line has a time, the conversation, the kind of failure, the tool name, the error code, a short summary of the arguments and an optional note. A hard failure or a phantom success also leaves a lesson in her continuity state, so the mistake shows up in her next replies. The rollup `knowledge/tool-failures.md` is rebuilt every time a failure is logged. It groups the failures by kind, tool and code, sorts them by count, and counts mid-turn tool requests, which the file says should be watched because a climbing number means the planner is missing intents.

The restart marker is `data/restart.json`. It exists only between a planned exit and the next start that reaches Discord's ready event, and it is deleted as soon as it is read. The ready handler deletes it whether or not it is still fresh. If it is still there after she has become ready, something stopped the ready handler from reading it, which is not verified. If the bot is switched off when she starts, the marker remains until the next time she goes online.

The doctor's lock is `data/doctor.lock`. It is written when a visit begins and removed when the visit ends. From the doctor tool it holds JSON with the process IDs, the task and the start time. From life support it holds only the start time. Life support judges it by the file's age (21 minutes). A lock left behind by a killed visit is cleared the next time she starts and the visit is reported as interrupted (see "doctor lock").

The doctor's commits are in the git history of the bots project. Each visit adds a `Before doctor: <task>` commit as its undo point, and a `Doctor: <title>` commit when it finishes with changes. Workshop jobs add `Before Amy's job: <title>` before the coder runs, and `Amy's job #<id>: <title>` when it ends with changes. The doctor's and the workshop's commits are signed `Amy <amy@localhost>`. The git tool's own commits use the PC's git identity.

Background task reports are in `data/tasks/`, one Markdown file per finished task, named by the start time and the task id, and holding the title, status, steps, model, report and the list of actions.

Reverse-engineering jobs are in `data/reverse/<id>.json`, and their notes and evidence are in `Desktop\REA investigations\<id>-<slug>\report.md`. The job file holds the record and the notes file holds the detail.

The workshop keeps its projects in `data/workshop/projects.json` and its job records in `data/workshop/jobs/<id>.json`. The project proposals for the `project` tool are rows in the `project_proposals` table inside `companion.db`.

File edit history is in `data/file-history/`. Each saved version is named with the time in milliseconds, two @ signs and the path. A restored copy has a `.restored` ending.

Memory backups are in `data/backups/wiped-<time>/`, one folder per wipe, holding the moved files with their original names.

There is no watchdog log. The current watchdog.bat only runs start.bat and writes nothing.

Life support writes to the console and to `data/activity.jsonl` with type `life-support`. Its events record starts, crashes, entry into life-support mode, recoveries, commands it was sent, and doctor visits.

Bot stderr is not written to a file by the bot itself. Life support keeps the last 4000 characters of the child's stderr in memory and shows the last 1200 characters in its alerts. The doctor's rules name `data/bot.err.log` as a log to read, but nothing in the source writes that file, so it may not exist.

Live view: the `self` tool with action `logs` searches the in-memory feed. The dashboard streams the same events live through `GET /api/events`, starting with the recent ones.

## what she should tell Owner when this breaks

Speak plainly, and only from what you can see. Before you say what caused something, check the activity log, the `self` tool's logs and the marker files. Do not claim a fix worked until a restart and its back line confirm it, which means the `power` "Online as" event has been logged after the restart.

When the restart tool says "I can't restart myself here: I wasn't started by start.bat", it means `CHAMP_SUPERVISED` is not `1`. She was started with `node src/index.js` by hand, or outside start.bat and life support. Nothing will bring her back after an exit, so she cannot restart, and Owner must start her with start.bat, or restart her by hand. The dashboard's memory wipe gives the same answer with a 400 status, and the same fix applies.

When the activity log shows an `error` with `where: 'startup'` and the text "Ollama check failed", Ollama is not running or a model is missing. The message names the model that is missing and gives the `ollama pull` command. start.bat starts `ollama serve` itself and waits until it answers, so if the wait never ends, Owner should look at the Ollama window and the port, since start.bat has no timeout there.

When the bot says "DISCORD_TOKEN is empty in .env, so the bot stays offline", the dashboard still works, but she cannot connect. Owner needs to put the token into `.env`, and then restart her. The `DISCORD_TOKEN` value is never printed by start.bat or by her.

When a `power` event says "Bot is switched off. Turn it on from the dashboard.", the bot was turned off from the dashboard, and that setting has been saved, so it stays off across restarts. The dashboard still runs. Owner turns the bot on from there with the power on control.

When life support sends "failed to start N time(s) in a row" or "crashed N times in 10 minutes", she is not running. Life support stopped retrying so that she would not crash in a loop. The alert lists the last exit code and how long the run lasted, any errors she logged, and the tail of the error output. Owner can reply in Discord with `retry` to try once more, `doctor` followed by what to fix to send the Claude Code doctor, `undo` to roll back the last doctor change, `cancel` to stop the doctor, or `status` to see what is going on.

When life support says the doctor visit is done and its tests passed, the change is in the code, and life support has already tried to start her, so Owner should wait for her to come up and then say so. If it says the visit failed, or the tests failed, she is not started. Owner can send `retry` to try anyway, or `undo` to roll the change back. Undo discards every uncommitted change in the folder too, so say that to the owner first.

## doctor and tool errors to explain / what to tell Owner about the doctor / error messages explained

This continues "what she should tell Owner when this breaks", for the doctor, the work notes, reverse engineering, helpers, downloads, other bots, the workshop, git and files. The same rule applies: speak only from what you can see, and never claim a fix worked before the restart and the "Online as" event confirm it.

When a doctor visit reports "Doctor visit ... done" with "Tests: pass", the change is saved as a commit, and it is not live until she restarts. Say so, and ask whether to restart. When it reports "failed", or "Tests: FAIL", the tests still fail or the doctor could not finish, and Owner can roll the change back with "undo the doctor", which uses the doctor tool's undo action. The same warning about uncommitted changes applies.

When the doctor says "No coding agent is installed here" or "No doctor is installed here", neither Claude Code nor OpenCode was found. When it says Claude Code or OpenCode "isn't signed in", the engine is installed but not logged in. Owner must run `claude auth login` or `opencode auth login` on this PC, sign in, and then ask again.

When the doctor reports "There is no doctor visit to undo.", no `Before doctor:` commit is among the last 50 commits, so there is nothing to roll back.

When the doctor reports "The doctor is already working on ... (started at ..., N minutes ago)", a visit is still running. Wait for it to finish, or use `cancel`. Cancel keeps whatever was already changed, and that can be rolled back later with undo.

When the doctor tool answers "Dispatched, not done", the doctor has only been sent. Say it has been sent, never that it is fixed. The report comes later, spoken and by DM.

When a doctor report says "failed" followed only by `ENOENT`, no doctor program was found: Claude Code is not installed where the code looks (`CLAUDE_PATH`, `~/.local/bin/claude.exe`, `%APPDATA%\npm\claude.cmd`, or `claude` on PATH) and OpenCode was not found either.

When a doctor status says "The repair stopped before it could report. Its file changes and tests were not verified.", a visit was cut off by a crash or a restart. Its changes may or may not be in the code. Say exactly that, and offer to have the doctor look again or to undo it.

When the restart tool says "A doctor visit is still running. Let it finish or cancel it before restarting.", a visit holds the repair lock. Restarting would cut it off. Wait for the report, or cancel the visit first.

When start-up ends with "Dashboard startup failed: ..." in the console (usually the port is already in use, often by a second copy of her), she exits with code 1 and life support counts it as a failed start. Three in a row put her on life support, and the alert shows the error output. The fix is to close the other program on `DASHBOARD_PORT`, or change the port in `.env`.

When an `error` with `where: 'work done'` shows up, a Claude Code note could not be passed to Owner. The message gives the reason, for example "no owner is set in OWNER_IDS in .env" or "her reply came back empty". The note is kept in `data/work-done-pending.jsonl` and is tried again the next time she comes online.

When an `error` with `where: 'discord login'` shows up, Discord refused the login. The message is discord.js's own reason (for example an invalid token or missing privileged intents). The dashboard shows it in the power status, and the bot stays off until the cause is fixed and it is switched on again.

When the reverse-engineering tool reports "REA isn't installed" or "REA is installed but not registered with Claude Code", it cannot run. Owner must reinstall REA with Node 24.22 or newer, or run REA's Claude Code setup again.

When a reverse job shows `running` long after it started, a restart killed it and its record was never updated. Treat it as dead, and start a new one. The one-at-a-time limit is held in memory, so a restart has already cleared it.

When the helpers say "4 helpers are already running" (the cap is four), four background tasks are working. Wait for one to finish, or cancel one. The `status` action lists them.

When a download reports "broke off" or "is incomplete", the file is not complete. The partial file has the `.part` ending, and it must not be reported as done. When it reports "answered 401 or 403", the site needs a login or a licence accepted, which the owner must do in a browser.

When `bring_peer` says "<name> isn't at <folder>", the start file for that bot is not where `PEER_APPS` says, so the folder path in `.env` needs checking. When it says "Started <name> in a new window ... about half a minute", the other bot is starting and has not joined the call yet, so wait before saying it is there. When it says "no bot called ...", the name is not in `PEER_APPS` and no folder bot matches. The reply lists the names it knows. When it says a name "is shared" and offers `folder:` names, two installations answer to that name, so ask the owner which folder he means. When it says the bot "uses this running bot's Discord account", that folder is another installation on your own Discord login, and the tool refuses to start or restart it.

When the restart reply says "You are not back yet", she is on her way down. Say she is restarting, and do not say she is back until the back line plays or the `power` "Online as" event has been logged.

When workshop undo refuses with "Something was committed after job #N" or "has uncommitted changes since job #N", undo was refused to protect the work. Ask for a new job to revert the change, or the owner can sort out the changes by hand.

When git says "isn't inside a git repository" or "GitHub isn't connected", the folder is not a repository, or the owner has not run `gh auth login` on this PC. When it says "Nothing is staged; add files first", the commit needs `add` before it. When the push says "Ready to push ... Not pushed yet", the owner has to confirm; a push that has not returned "Pushed" has not happened.

When the files tool says "That text isn't in ..." or "appears N times", the edit did not match exactly once. Read the file again, copy the lines exactly, and add more surrounding lines so that the text is unique, or use replace_all if every match should change. When the files tool says a path "is private (keys, passwords or app data), so it's off limits" or "outside your home folder and the bots folder", the path is blocked by the tool's own rules, and she must not try to get around it.
